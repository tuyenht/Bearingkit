# Activation evals

`phase-1.jsonl` holds **ninety-three** prompts in two layers. **Phase 1's sixty**, unchanged because they are the baseline every later run is compared against: six intents (question, small change, feature, bug, review, ship), ten each, eight positives (four English, four Vietnamese) and two negatives whose expected answer is `none` or a neighbouring skill. **Five skill intents** added 2026-09-14 under spec §11's rule of two positives and one negative per new skill — `plan`, `close`, `audit`, `next`, `test`, three prompts each, one positive in each language plus one negative that must not reach that skill. Before them the set measured five skills while ten were installed: `bk-plan`, `bk-close`, `bk-audit` and `bk-next` had no prompt at all. `tests/evals.test.cjs` now fails if any skill that exists carries fewer than two positives. Six intents followed under the same rule: `design` (2026-09-14), `setup` (2026-09-17), `ops` (2026-09-18, with `bk-ops`), `db` (2026-09-18, with `bk-db`; its negative, a feature that adds a column, must reach `bk-spec` or `bk-build`) and `map` (2026-09-19, with `bk-map`; its negative is a question about how one page gets its data, which must be answered directly, since the router row that sends a whole-codebase map to `bk-map` sits right under the question row) and `research` (2026-09-23, with `bk-research`; its negative is a general question settled knowledge answers, JavaScript's `==` against `===`, which must be answered directly, since the research row sits right under the map row, beside the question row).

A run passes the Phase 1 gate when every positive routes to its skill and no negative routes to the intent's skill. Two negatives are deliberate false-activation controls rather than neighbour tests: `audit-neg-01` (a Postgres query to optimise) expected `bk-spec|bk-debug` from 2026-09-17, when the kit had no `bk-db` and its router sent data work to `bk-spec`, and accepts `bk-db` since 2026-09-18 (text unchanged, every earlier pass stays a pass), and `next-neg-01` (a plain file read) expects `none` — it is the crowded daily profile, where skills like `database-optimizer` exist, that those measure. Phase 1's `ship-neg-02` ("Deploy bản này lên staging.") accepts `bk-ops` since 2026-09-18: it asks for a deploy, which the kit now has a skill for. Its text is unchanged, and every earlier pass stays a pass.

Format, one JSON object per line: `id`, `intent`, `lang`, `prompt`, `expect` (a skill name or `none`; alternatives separated by `|` when more than one route is right). `acceptance.jsonl` holds the two-prompt acceptance test of spec v2 §11 (the autonomy-gate question, then "Let's make a react todo list" expecting `bk-spec`); run it with `--file evals/activation/acceptance.jsonl` on either host, and read the first answer by hand for ACT and COUNCIL. `boundaries.jsonl` holds prompts on the seam between two skills, labelled with both (`bk-db|bk-ops`: either route passes), kept apart from the ninety-three so their per-intent shape and every earlier comparison stay as they are (D5 question 28); run it with `--file evals/activation/boundaries.jsonl`.

## Claude Code

```
node bin/bearingkit.cjs evals --config-dir <isolated profile> [--plugin-dir <checkout>|none] [--model sonnet] [--intent bug] [--limit 5] [--cwd <sample project>]
```

The kit is loaded straight from the checkout with `claude --plugin-dir` (the default; nothing is installed into the profile); `--plugin-dir none` runs a baseline against whatever the profile already carries. **The profile must enable the inline plugin**: since the manifest ships `"defaultEnabled": false` (the kit is switched on per project), a profile without `"enabledPlugins": { "bearingkit@inline": true }` in its `settings.json` loads none of the kit — measured on 2026-09-20: 0 kit skills without the entry, 15 with it — so the runner refuses to start a run whose named profile lacks it. `_build/profile/claude` carries it beside `syncClaudeAiSkills` and `syncClaudeAiPlugins`; rebuild the profile and all three go back in. Each prompt runs in a fresh non-interactive session (`claude -p`, streamed JSON, at most six turns, `--turns` to change) inside `evals/fixtures/sample-app` unless `--cwd` says otherwise, so prompts about the settings page or the invoices page have real files to find. The runner records the first skill the model invoked, or `none`, and writes `evals/results/<date>-claude.md` with a table and per-intent scores. `--tag <name>` suffixes the result file; `--equivalents <json>` makes a baseline run against another setup meaningful; `--id a,b` reruns specific prompts; `--per-intent N` keeps the first N prompts of each intent (a cheaper baseline). Measure in an isolated profile that contains nothing but the kit; the host caps the skill listing and drops least-used descriptions on overflow, so a crowded profile measures the crowd, not the kit.

Baseline: run the same file once against the current daily profile (`--daily` instead of `--config-dir`; since 2026-09-18 a run with neither refuses to start) before the old kits are removed; that table is what later claims compare to.

## Antigravity

```
node bin/bearingkit.cjs evals --host antigravity
```

Without flags this prints the prompts as a checklist (`evals/results/<date>-antigravity-checklist.md`) for a run by hand. On this host `--plugin-dir` names the live plugin copy (default `~/.gemini/config/plugins/bearingkit`), not the checkout.

The automated run on Antigravity 2.0 (the desktop app must be running with `--remote-debugging-port=1405`; it opens no DevTools port by default) goes: `--stage-only [--stage-dir <dir>]` stages Antigravity's own copy of the fixture (default `C:\work\apps\sample-app`: away from the kit's checkout and the home folder, the README and lockfile of `evals/fixtures/antigravity-stage/` in place of the fixture's, one plain commit, the reset marker inside `.git`); `--arm --file <a.jsonl,b.jsonl> --id <ids>` installs a driver hook into the live plugin and queues the prompts in the order of `--id`, each as a neutral id and its text only (the line it prints pairs the ids); `--drive <projectId> --count N` starts a detached script that opens one conversation per prompt in the project whose JSON under `~/.gemini/config/projects/` points at the stage, types a hold phrase, and lets the hook inject the real prompt after resetting the stage; `--score --tag <tag>` takes each prompt's labels back from the prompt files, reads the transcripts (the first `SKILL.md` opened after the injected prompt) and writes the table, marking any conversation that read the eval harness (the kit's checkout or the queue) before its routing decision: such a result is not evidence and is rerun; `--disarm` removes the hook. Neither the stage, the driver's note nor the queue says that a measurement is running: on 2026-09-19 the shared fixture's README ("used only to run the activation evals") and a note calling the hold phrase a "harness trigger" sent conversations searching the folders above for the prompt files. Progress lives in `~/.bk-relay/queue.json` (moved from `~/.bearingkit/antigravity-eval/` on 2026-09-20, so a conversation that opens a skill in the store does not find the queue beside it) and the drive log under `evals/results/`. About 90 seconds per prompt on Opus 4.6. Tokens on this host are read from the app’s Customizations panel, not measured by the runner.
