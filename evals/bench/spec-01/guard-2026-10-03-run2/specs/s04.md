# Spec: customer self-service ticket reopen

Status: draft, awaiting review. Not implemented.

## Problem

Customers keep asking to reopen their own closed ticket from the portal instead of
filing a new one, when they're still dealing with the same issue shortly after it
was closed. Today `closed` is final (`docs/glossary.md`) — the only way back in is
a brand-new ticket, which loses history and context for the agent.

## Decisions

Written while the requester is unavailable, so each question below is answered
with the author's recommendation rather than left open. Treat these as the
working design; flag any you'd answer differently and the spec gets adjusted
before implementation.

1. **How long is the reopen window?**
   Recommend **14 days from `closed_at`**, matching the request. Measured the
   same way the existing purge job measures its window — `now - closed_at`,
   strict `<`, not inclusive of day 14 — so behavior is consistent across the
   codebase rather than introducing a second rounding convention.

2. **Is a message required to reopen?**
   Recommend **yes, required and non-empty**. A bare status flip with no
   context leaves the agent nothing to act on. The message becomes the first
   new message on the reopened ticket, same shape as a normal customer reply.

3. **What status does the ticket land in — `open` or `pending`?**
   Recommend **`open`**, matching the existing agent-initiated reopen path
   (`tickets.reopenTicket`) and the `reply()`-on-resolved behavior in
   `portal.js:26`. It drops straight back into the agent queue rather than a
   third status path.

4. **Do `resolved_at` and `closed_at` get cleared?**
   Recommend **yes, both**. Leaving stale timestamps on a now-open ticket
   would corrupt time-to-resolve / time-to-close reporting if it closes again
   later.

5. **Does this interact with `purged`?**
   This is the one non-negotiable part of the design. `purgeClosed`
   (`src/jobs/purge-closed.js:13`) treats `purged` as a one-way latch —
   `if (t.purged) continue`. If a reopen doesn't reset `purged: false`, a
   ticket that gets closed → purged → reopened → closed again would never
   have its second round of messages purged, which is a retention-policy
   violation, not a style nit. **Reopen must unconditionally set
   `purged: false`**, regardless of its current value.

6. **Does this replace or interact with the existing agent-only `reopenTicket`?**
   Recommend **keep it separate and untouched**. `reopenTicket` is
   resolved → open only, used by agents, and pinned by exact-message
   assertions in `test/tickets.test.js:34-41` (`cannot reopen a open/closed
   ticket`). The new path is closed → open, customer-initiated. Two call
   sites, two guard conditions, no shared code worth forcing together.

7. **New event type for the notification, or reuse `ticket_reopened`?**
   Recommend **reuse `ticket_reopened`**, with `by: customer:<id>` instead of
   `by: agent:<id>`. The agent path already encodes the actor this way
   (`src/tickets.js:42`); a second event type for the same fact would just be
   two things for the mail worker to handle identically.

8. **What if the ticket has no assignee?**
   Recommend **skip the notification silently**. `notifyAgent` throws on a
   null agent id (`src/notify.js:7`), and an unassigned ticket is a normal,
   expected state — not an error.

9. **Does reopening reset the SLA due time, or cap how many times a ticket can
   be reopened?**
   Recommend **no to both, out of scope for v1**. Nothing in the request asks
   for it, and `sla_due_at` is documented as set once at creation
   (`docs/glossary.md`). Can be a follow-up if agents complain about repeat
   reopeners gaming SLA metrics.

10. **Cross-org access — what happens if a customer tries to reopen a ticket
    that isn't theirs?**
    Recommend **return `null`**, mirroring `portal.getMyTicket` /
    `portal.openTicket`'s existing org-scoping convention, not a thrown error.
    Business-rule violations (wrong status, expired window, empty message)
    still throw, matching `portal.reply`'s split between "not yours → null"
    and "closed → throws" (`src/portal.js:23-24`).

11. **Where does the reusable day-length constant live?**
    `src/tickets.js` only defines `HOUR`; `close-resolved.js` and
    `purge-closed.js` each redefine their own local `DAY`. Recommend adding
    `const DAY = 24 * HOUR;` once in `tickets.js` since this is now business
    logic, not just a job, rather than inlining the literal a third time.

## Design

### `src/tickets.js`

```js
const DAY = 24 * HOUR;
const REOPEN_WINDOW_DAYS = 14;

function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed too long ago to reopen');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');

  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  }
  return updated;
}
```

Exported alongside the existing functions. `reopenTicket` (agent path) is
unchanged.

### `src/portal.js`

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

Mirrors `openTicket`/`getMyTicket`'s org-scoping shape: look the ticket up
scoped to the customer's org first, `null` if it's not theirs, then delegate
business rules to `tickets.js` (which throws on bad status / expired window /
empty message, same split `reply()` already uses).

### `docs/glossary.md`

The **closed** bullet currently reads "final... they start a new ticket."
Recommend replacing with:

> **closed**: final for agents — a closed ticket is never changed by agent
> action. A customer may reopen it from the portal within 14 days of closing,
> with a message; past that window, or for any other reason, they start a new
> ticket.

## Acceptance criteria

1. A closed ticket, reopened within 14 days with a non-empty message, becomes
   `open`, with `resolved_at` and `closed_at` both `null` and the message
   appended.
2. Reopen is rejected once `now - closed_at >= 14 days` (boundary at exactly
   14 days is rejected, matching the purge job's strict-`<` convention).
3. Reopen is rejected for any non-`closed` status (`open`, `pending`,
   `resolved`) with a message naming the actual status, matching the existing
   `reopenTicket` error style.
4. Reopen is rejected when the message is empty or whitespace-only.
5. A customer cannot reopen another organisation's ticket — `portal.reopen`
   returns `null`, same as `getMyTicket`/`openTicket` on a foreign ticket; no
   business-rule error leaks org existence.
6. Reopening an assigned ticket queues exactly one `ticket_reopened`
   notification to the assignee with `by: customer:<id>`. Reopening an
   unassigned ticket queues nothing and does not throw.
7. **Purge-latch regression test**: close a ticket, run `purgeClosed` so
   `purged: true` and its messages are deleted, reopen it within the window,
   close it again, and confirm a second `purgeClosed` run purges it again
   (messages from the second cycle are deleted). This is the scenario that
   catches a missing `purged: false` reset.
8. `reopenTicket` (agent path) and its existing tests
   (`test/tickets.test.js:34-41`) are unaffected.

## Out of scope (v1)

- SLA due-time reset on reopen.
- Limiting how many times a ticket can be reopened.
- Any change to the agent-initiated `reopenTicket` path.
