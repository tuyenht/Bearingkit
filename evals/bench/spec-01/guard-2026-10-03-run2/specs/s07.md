# Spec: customer reopens a closed ticket from the portal

Status: **draft — written while the user was away; not yet reviewed or implemented.**

## Restatement

The ask, in the user's words: "let a customer reopen a closed ticket from the
portal within 14 days of it being closed, and notify the assigned agent when
they do."

Technical reading: add a new portal-facing action, `portal.reopen`, that
moves a ticket from `closed` back to `open` when (a) the caller is a customer
in the ticket's organisation, and (b) fewer than 14 days have passed since
`closed_at`. It must queue a `notifyAgent` call for the ticket's assignee the
same way the existing agent-side reopen does.

This is a new capability, not a fix to an existing one. The glossary
currently defines closed as final (`docs/glossary.md:12`: "closed: final. A
closed ticket is never changed again. If the customer comes back, they start
a new ticket.") — that line needs to change as part of this feature, and
every other place that currently treats "closed" as a terminal state was
checked for an implicit assumption that would break (see Edge cases).

**Step 0 — nothing already built.** No reopen-from-portal code exists.
`src/tickets.js:38-44` has an agent-only `reopenTicket(store, id, agentId)`
that reopens a **resolved** ticket (not closed) and is pinned by an
exact-message test (`test/tickets.test.js:34-41`, "cannot reopen a open/closed
ticket"). This feature is additive alongside it, not a modification of it.

## Touchpoints (file:line)

- `test/tickets.test.js:34-41` — exact-message assertions on the agent-only `reopenTicket`; must not change.
- `docs/glossary.md:12` — "closed is final" bullet; needs a matching update.

## Design

**New function in `src/tickets.js`:**

```js
reopenByCustomer(store, id, customerId, message, { now = new Date() } = {})
```

- Throws if the ticket is not `closed` (mirrors the existing `cannot resolve/reopen a ${status} ticket` style).
- Throws if `now - closed_at >= 14 * DAY` (strict `<` for "within 14 days"; adds `const DAY = 24 * HOUR;` to `tickets.js`, which today only defines `HOUR` — the two job files each redefine `DAY` locally rather than import one, so this adds the shared constant instead of a third inline copy).
- Throws if `message` is empty/whitespace-only (a reopen must say why, same spirit as every other message-bearing action in this codebase).
- On success: `status → open`, `resolved_at: null`, `closed_at: null`, **`purged: false`** (see "The one non-negotiable item" below), appends the customer's `message` via `store.addMessage`.
- Takes the *acting* customer's id as an explicit `customerId` parameter, separate from `id` (the ticket). This mirrors the agent path's precedent: `reopenTicket(store, id, agentId)` stamps `by: agent:${agentId}` — the agent *performing* the action, not `t.assignee_id`. Because any customer in the ticket's org can act here (next bullet), the actor and the ticket's original `t.customer_id` can differ, so `t.customer_id` would be the wrong value to read.
- Notifies via the existing `notifyAgent`, reusing the `ticket_reopened` event type with `by: customer:<actingCustomerId>` — not a new event type, mirroring how the agent path already encodes the actor through `by`. Skipped silently if `assignee_id` is `null` (`notifyAgent` throws on no agent — this is a legitimate "unassigned ticket" state, not an error).

**New wrapper in `src/portal.js`:**

```js
reopen(store, customer, id, message, { now = new Date() } = {})
```

- Mirrors `openTicket`/`getMyTicket`'s org-scoping pattern: returns `null` if the ticket doesn't belong to `customer.orgId` (not a thrown error — consistent with `getMyTicket`).
- Otherwise calls `tickets.reopenByCustomer(store, id, customer.id, message, { now })` and returns the updated ticket.
- No restriction to "only the customer who originally opened it": any customer in the org can reopen, same as `portal.reply`, which also only checks `org_id`, never `customer_id` (`src/portal.js:11-12, 21-27`).

**Left alone:**
- `reopenTicket` (agent path) — untouched, still resolved-only, still pinned by `test/tickets.test.js:34-41`.
- `portal.reply` — still throws on every closed ticket. Reopening is a separate, deliberate customer action with its own required message, not a side effect of replying.

## Edge cases

1. **Ticket already open/pending/resolved when reopen is called.** Rejected — `reopenByCustomer` only accepts `closed`. Error message follows the existing `cannot reopen a ${status} ticket` convention so it reads consistently with the agent path's error.
2. **Exactly 14 days, to the millisecond, since `closed_at`.** Treated as *expired* (strict `<`, not `<=`) — "within 14 days" reads as a closed window from the customer's point of view, and strict-`<` matches how `closeResolved`/`purgeClosed` already compare elapsed time against a day-count threshold in this codebase.
3. **Ticket already purged (`purged: true`) when a reopen request comes in within the 14-day window.** `KEEP_DAYS` (7 days) is shorter than the reopen window (14 days), so this is reachable: a ticket closed on day 0 is purged on day 7 but can still be reopened on day 13. Allowed — the reopened ticket simply starts with no prior message history (only the new reopen message). `KEEP_DAYS` is a legal-retention control unrelated to this feature and is not widened to cover it.
4. **Reopen → re-close → re-purge cycle.** `purgeClosed` treats `purged` as a one-way latch (`src/jobs/purge-closed.js:13`, `if (t.purged) continue`) — once true, never purged again. If a reopened-and-later-reclosed ticket keeps `purged: true` from its first purge, its second round of messages would never be deleted: a retention-policy violation, not a style bug. `reopenByCustomer` must unconditionally reset `purged: false`, even when the ticket was never actually purged. This is covered explicitly by acceptance criterion 6.
5. **No assignee on the ticket (`assignee_id: null`).** No notification is sent — `notifyAgent` throws on a null agent id, and an unassigned ticket has no one to notify. The reopen itself still succeeds.
6. **Empty or missing reopen message.** Rejected with an error, same as a missing `assignee_id` check pattern elsewhere — the customer must say why they're reopening (used as the first message on the newly-reopened ticket).
7. **Customer from a different organisation attempts to reopen.** `portal.reopen` returns `null`, same as `getMyTicket` on a cross-org id — no information leak about whether the ticket exists.

## Open questions (answered by recommendation — user unavailable; see note below)

Capped at 4 per the brainstorming rule; these are the four whose answers most change the work.

1. **Who may reopen: only the customer who originally opened the ticket, or any customer in the org?**
   Recommendation: **any customer in the org** — matches `portal.reply`'s existing precedent (`src/portal.js:11-12`), which only checks `org_id`, never `customer_id`. Keeping reopen's permission model identical to reply's avoids a special case customers would find confusing (the person who replies and the person who reopens are often different people on the same support thread).
2. **Does reopening require a message from the customer, or can it be a bare status flip?**
   Recommendation: **require a non-empty message.** Every other customer-initiated state change in this codebase carries a message (`openTicket`, `reply`); a reopen with no explanation gives the agent nothing to act on and no record of why it came back.
3. **Should the 14-day window be inclusive or exclusive of the boundary instant, and does it interact with the 7-day purge window (`KEEP_DAYS`)?**
   Recommendation: **exclusive (strict `<`)**, and **allow reopening an already-purged ticket** — don't widen `KEEP_DAYS` to 14 days to "protect" the reopen window, since `KEEP_DAYS` is a legal-retention control, not a feature switch. See Edge case 3.
4. **Does reopening need to reset the `purged` flag, given `purgeClosed`'s one-way-latch behavior?**
   Recommendation: **yes, unconditionally reset `purged: false` on every reopen**, even if the ticket was never actually purged. This is the one item in this spec with a real consequence if skipped (see "The one non-negotiable item" below) — it is why this ACT-sized change still gets flagged for independent review before push.

Everything above is "assumed, not confirmed" pending the user's actual sign-off tomorrow. No fifth question arose — four is the full count the design needed.

## The one non-negotiable item

`purgeClosed` (`src/jobs/purge-closed.js:13`) is a one-way latch: `if (t.purged) continue`. If `reopenByCustomer` does not unconditionally reset `purged: false`, a ticket that goes closed → purged → reopened → closed again will never have its second round of messages deleted, silently breaking the 7-day retention policy. This is tested directly by acceptance criterion 6, not left to incidental coverage.

## Assumptions

- **High confidence:** the portal has no existing "reopen" UI affordance to wire up — this spec is backend-only (the function + its test); any portal UI work is a separate, unstated piece of work for whoever owns that layer. Looked up by reading all of `src/portal.js` and `src/tickets.js`; no UI/template code exists in this repo, only the service-layer functions the tests call directly.
- **High confidence:** `now` is always injected via the `{ now = new Date() }` pattern already used throughout (`createTicket`, `resolveTicket`, `closeResolved`, `purgeClosed`), so the 14-day check is trivially testable without real time passing. Confirmed by reading every one of those call sites.
- **Medium confidence:** no SLA reset and no cap on how many times a ticket can be reopened are in scope for v1. Default: out of scope, matching the user's one-line ask having no mention of either. Low risk if wrong — both are easy additive follow-ups.
- **Medium confidence:** the event type stays `ticket_reopened` (shared with the agent path) rather than a new `ticket_reopened_by_customer` type. Default: reuse, since `by:` already distinguishes actor kind (`agent:<id>` vs `customer:<id>`) and nothing downstream appears to switch on event type to treat the two paths differently (only `notify.js`'s queue, which is actor-agnostic).

## Acceptance criteria

1. `reopenByCustomer` on an `open`, `pending`, or `resolved` ticket throws `cannot reopen a ${status} ticket`.
2. `reopenByCustomer` on a `closed` ticket where `now - closed_at < 14 days` succeeds: `status` becomes `open`, `resolved_at` and `closed_at` both become `null`, `purged` becomes `false`.
3. `reopenByCustomer` on a `closed` ticket where `now - closed_at >= 14 days` throws (window expired).
4. `reopenByCustomer` with an empty or whitespace-only message throws before any state changes.
5. On success, the customer's message is appended to the ticket's messages (visible via `store.getMessages`).
6. **Reopen resets a previously-purged flag:** close a ticket, run `purgeClosed` until `purged: true`, reopen it within the window, close it again, run `purgeClosed` again — the second purge must delete the second round of messages (i.e. `purged` was `false` going into the second close-and-purge cycle).
7. If `assignee_id` is set, reopening queues exactly one `notifyAgent` call with `event.type === 'ticket_reopened'` and `event.by === 'customer:<actingCustomerId>'`, where `<actingCustomerId>` is the id of the customer who called reopen (not necessarily `t.customer_id`).
8. If `assignee_id` is `null`, reopening succeeds and queues no notification.
9. `portal.reopen` returns `null` (not a thrown error) when the ticket belongs to a different organisation than the calling customer.
10. `portal.reopen` succeeds for a customer in the ticket's org who is not the ticket's original `customer_id` (any-customer-in-org permission model).
11. The existing agent-only `reopenTicket` test (`test/tickets.test.js:34-41`) continues to pass unmodified — this feature adds a parallel path, it does not touch that one.

## Out of scope (v1)

SLA reset on reopen; a cap on reopen count per ticket; a new/distinct event type for customer-initiated reopens; any portal UI/template work; widening `KEEP_DAYS` to cover the 14-day reopen window.
