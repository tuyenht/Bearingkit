# Spec: customer reopens a closed ticket from the portal

## 1. Restatement

**In the user's words:** "Let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do."

**Technical reading:** add a portal-facing action that moves a ticket from `closed` back to `open`, gated on `now - closed_at < 14 days`, callable only by the customer whose organisation owns the ticket, and that queues a notification to the ticket's assignee (if any) when it succeeds. This is a new, separate action — not a change to the existing agent-side `reopenTicket` (resolved→open) or to `portal.reply` (which currently refuses on any closed ticket, `src/portal.js:24`).

No gap between the two readings.

## 3. Edge cases

1. **Ticket closed more than 14 days ago.** Rejected. Error, not a silent no-op, so the portal can show a reason.
2. **Ticket not closed (open/pending/resolved).** Rejected — reopen-by-customer only applies to `closed`. (Resolved tickets already reopen via `portal.reply`, `src/portal.js:26`.)
3. **Ticket belongs to a different organisation.** Returns `null`, mirroring `getMyTicket`'s existing org-scoping (`src/portal.js:12`) — never leaks existence of another org's ticket.
4. **Ticket has no assignee (`assignee_id` is `null`).** Reopen still succeeds; notification is skipped silently. Calling `notifyAgent` with a null agent throws (`src/notify.js:7`), so this must be an explicit guard, not an oversight.
5. **Ticket was already purged (`purged: true`, messages deleted).** Still reopenable within the 14-day window (purge runs at day 7, reopen window is 14 days, so this is a real case, not theoretical). The ticket comes back with no message history — see Q4 below for why a message is required here.
6. **Ticket reopened, then closed again, then its new purge-eligibility.** `purged` must reset to `false` on reopen, or `purgeClosed` (`src/jobs/purge-closed.js:13`) skips it forever via the `if (t.purged) continue` latch — the new round of messages would never be deleted. This is a data-retention correctness issue, not a style choice.
7. **Empty or missing reopen message.** Rejected with an error — see Q4.
8. **Concurrent reopen calls on the same ticket** (e.g., double-click). The store's `updateTicket` is a synchronous in-memory map (`src/store.js:19`); in production this is one row-level update. No special locking needed — rely on the existing status check to make a second concurrent call fail (ticket is no longer `closed` once the first call completes), same as every other status transition in this codebase.

## 4. Questions and recommendations

**Q1: Does reopening clear `resolved_at` and `closed_at`, or only `closed_at`?**
Recommendation: clear both to `null`, same as the agent-side `reopenTicket` clears `resolved_at` (`src/tickets.js:41`). A reopened ticket is fully back in `open`, and leaving a stale `resolved_at`/`closed_at` around would make duration/SLA reporting on the ticket wrong if it closes again later. *(Confidence: medium — flagging for explicit sign-off since it changes historical-looking fields.)*

**Q2: What event type does the notification use — reuse `ticket_reopened` or add a new one?**
Recommendation: a new type, `ticket_reopened_by_customer`, distinct from the agent-side `ticket_reopened` (`src/tickets.js:42`). Downstream notification rendering ("Agent X reopened..." vs "Customer reopened...") needs to tell these apart without inspecting the `by` field, and keeping the agent-side event untouched avoids any risk to the pinned test at `test/tickets.test.js:30-31`.

**Q3: Does the reopened ticket keep its old assignee, or go back to the unassigned queue?**
Recommendation: keep the existing `assignee_id` unchanged. The customer is continuing a conversation with (what was) their agent; losing the assignment would mean someone else picks it up cold. This also matches why the agent should be notified at all — they're still the owner.

**Q4: Is a message required to reopen, or can the customer just flip the status?**
Recommendation: require a non-empty message (added as the ticket's first new entry on reopen). Reason: the message-purge window (7 days, `src/jobs/purge-closed.js:7`) is shorter than the proposed reopen window (14 days). Without a required message, a customer reopening on day 10 would hand the agent a ticket with zero conversation history and no way to know why it's back. Requiring a message guarantees the agent always has something to act on.

**Q5: Should there be a limit on how many times a ticket can be reopened, or an SLA reset?**
Recommendation: no limit, no SLA reset, for this iteration. Nothing in the request asks for either, and adding them now would be scope creep (YAGNI). Revisit only if abuse or SLA-gaming is observed in practice.

**Q6: Where does the 14-day window measure from if the ticket has been reopened and closed again before?**
Recommendation: always from the current `closed_at`, whatever its most recent value is. There's no concept of an "original" close date tracked anywhere in the schema, and introducing one is unneeded for the stated requirement.

## 5. Design

Add to `src/tickets.js`:
- `const DAY = 24 * HOUR;` next to the existing `HOUR` (line 6) — avoids a third ad-hoc inline literal; the two job files already each define their own local `DAY`, but this constant belongs with the other duration constants on the ticket module since the reopen window is a ticket-level business rule, not a job-level one.
- `const REOPEN_WINDOW_DAYS = 14;`
- `reopenByCustomer(store, id, message, { now = new Date() } = {})`:
  - `mustGet` the ticket (reuses the existing helper, `src/tickets.js:46`).
  - Throw if `t.status !== STATUS.CLOSED`.
  - Throw if `now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY`.
  - Throw if `message` is empty/whitespace-only.
  - `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null, purged: false })`.
  - `store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() })`.
  - If `t.assignee_id`, call `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id, by: `customer:${t.customer_id}` })`.
  - Return the updated ticket.

Add to `src/portal.js`:
- `reopen(store, customer, id, message, { now = new Date() } = {})`:
  - `getMyTicket(store, customer, id)` first; return `null` if it's not the customer's org (mirrors `openTicket`/`getMyTicket`'s existing pattern, `src/portal.js:10-18`).
  - Otherwise delegate to `tickets.reopenByCustomer(store, id, message, { now })` and return the result.

`docs/glossary.md:12` — update the **closed** bullet to note the 14-day customer reopen window instead of stating closed is unconditionally final.

## 8. Acceptance criteria

1. A closed ticket less than 14 days past `closed_at` can be reopened by a customer in its own organisation, with a non-empty message, and ends up with `status: 'open'`.
2. A closed ticket 14 days or more past `closed_at` is rejected with an error when reopen is attempted.
3. A non-closed ticket (open, pending, resolved) is rejected with an error when `reopenByCustomer`/`portal.reopen` is called on it.
4. A customer from a different organisation gets `null` from `portal.reopen`, not an error and not the ticket data.
5. An empty or whitespace-only message is rejected with an error; the ticket is not changed.
6. On success, `resolved_at` and `closed_at` are both `null`, and `purged` is `false` — including when the ticket had `purged: true` beforehand.
7. On success, if `assignee_id` is set, exactly one notification of type `ticket_reopened_by_customer` is queued to that agent; if `assignee_id` is `null`, no notification is queued and no error is thrown.
8. The existing agent-side `reopenTicket` (`src/tickets.js:38`) and its pinned test (`test/tickets.test.js:34-41`) are unchanged and still pass.
9. `portal.reply` on a closed ticket still throws (`src/portal.js:24`) — reopen does not change that behavior.
10. A ticket reopened and then closed and purged again has its new messages deleted by `purgeClosed` on the next eligible run (verifies the `purged: false` reset actually un-sticks the latch, not just that the field reads `false` once).

## 9. Out of scope

- Any limit on number of reopens per ticket.
- SLA due-time reset or recalculation on reopen.
- Reassigning or clearing the assignee on reopen.
- Changing the agent-side `reopenTicket` or the resolved-ticket reopen path in `portal.reply`.
- A UI/portal-page change — this spec covers the `tickets.js`/`portal.js` business logic only.
