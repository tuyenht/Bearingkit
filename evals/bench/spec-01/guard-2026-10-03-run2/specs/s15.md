# Spec: Reopen a closed ticket from the portal

Status: **draft — awaiting review**. Not implemented.

## Summary

Let a portal customer reopen their own ticket within 14 days of it being
closed, by sending a message. The assigned agent is notified when this
happens.

## Context

Written while the requester was away; the clarifying questions that would
normally be asked live are listed below with the recommended answer, and the
rest of this spec is built on those recommendations. Flag any answer below
you'd choose differently and the design around it gets adjusted.

### Q&A

**1. What counts as "within 14 days"?**
Recommendation: strictly less than 14×24h after `closed_at` (exclusive
boundary), matching the existing `closeResolved`/`purgeClosed` style of
`now - t < N*DAY`. Exactly 14 days out is too late.

**2. Does reopening require a message, or can it be a bare status flip?**
Recommendation: require a non-empty message. It gives the agent context for
why the ticket came back, and keeps the action looking like "the customer
answered," which is how reopening already reads elsewhere in this app.

**3. What status does a customer-reopened ticket land in?**
Recommendation: `open` — same target status the agent-side `reopenTicket`
uses, so there's only one "reopened" state to reason about.

**4. Should `resolved_at` and `closed_at` both get cleared?**
Recommendation: yes, both. `resolved_at` clears because the agent-side
`reopenTicket` already does that on the same status transition. `closed_at`
must also clear — otherwise a ticket sitting in `open` status with a stale
`closed_at` would be lying about its own history and would corrupt anything
downstream that reads `closed_at` (notably the purge job, see Q8).

**5. New event type, or reuse `ticket_reopened`?**
Recommendation: reuse `ticket_reopened`, tagged `by: customer:<id>`. The
agent path already encodes the actor this way (`by: agent:<id>`) rather than
using separate event types per actor — same event, different actor.

**6. What if the ticket has no assignee?**
Recommendation: skip the notification silently. `notifyAgent` throws when
given no agent id, and an unassigned closed ticket shouldn't block the
customer from reopening it.

**7. A new function, or extend the agent-only `reopenTicket`?**
Recommendation: a new, separate function (`reopenByCustomer`). The agent
path only accepts `resolved → open` and is pinned by exact-message
assertions in `test/tickets.test.js:34-41` (`cannot reopen a open/closed
ticket`) — changing its preconditions would break that test and overload one
function with two different actors' rules. The customer path's rules are
different enough (closed-only, time-boxed, message required) that a
separate function is clearer than branching inside one.

**8. Does this interact with the nightly purge job?**
Recommendation: yes, and this is the one load-bearing detail in this spec.
`purgeClosed` (`src/jobs/purge-closed.js:13`) treats `purged` as a one-way
latch: `if (t.purged) continue`. If a ticket was closed, purged (messages
deleted, `purged: true`), then reopened, replied to, resolved, and closed
again, it will never be purged a second time unless reopening resets
`purged` back to `false`. Left unreset, that's a silent retention-policy
violation (legal asked for the 7-day purge in the first place — see
`purge-closed.js:3-4`), not just a cosmetic bug. **Reopening must
unconditionally set `purged: false`**, regardless of whether the ticket was
already purged.

**9. Reopen count limit / abuse protection?**
Recommendation: no limit for v1. Out of scope; revisit if it's abused in
practice.

**10. Does reopening reset the SLA due time?**
Recommendation: no. The ticket keeps its original `sla_due_at`. A fresh SLA
clock on reopen is a reasonable future ask but a separate decision — out of
scope here.

**11. Does `portal.reply` on a closed ticket now trigger a reopen automatically?**
Recommendation: no. `portal.reply` keeps throwing on closed tickets exactly
as it does today (`src/portal.js:24`). Reopening is a distinct, deliberate
customer action (e.g. a "Reopen this ticket" button that requires typing a
message), not a side effect of trying to reply to something closed. This
keeps the two code paths and their preconditions separate.

## Design

### `tickets.reopenByCustomer(store, id, customerId, message, { now = new Date() } = {})`

New function in `src/tickets.js`, alongside the existing agent-only
`reopenTicket`.

- Look up the ticket (`mustGet`); throw `no ticket ${id}` if missing (same
  helper the rest of the file uses).
- Throw `cannot reopen a ${status} ticket` unless `status === STATUS.CLOSED`
  (same message shape as the existing `reopenTicket` guard, for consistency).
- Throw `a reopened ticket needs a message` if `message` is empty or
  whitespace-only.
- Throw `too late to reopen; it has been closed for more than 14 days` if
  `now - closed_at >= 14 * DAY`.
- Append the message via `store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() })`.
- Update the ticket: `status: STATUS.OPEN`, `resolved_at: null`,
  `closed_at: null`, `purged: false` (unconditionally — see Q8).
- If `assignee_id` is set, call
  `notifyAgent(store, assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` })`.
  Skip silently if there's no assignee.
- `src/tickets.js` currently only defines `HOUR`; add `const DAY = 24 * HOUR;`
  there rather than inlining the literal a third time (the two job files
  each already redefine `DAY` locally).

### `portal.reopen(store, customer, id, message, { now = new Date() } = {})`

New wrapper in `src/portal.js`, mirroring how `openTicket`/`getMyTicket`
scope access to the customer's own organisation:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

Returns `null` if the ticket doesn't belong to the customer's org (same
convention `getMyTicket` already uses), so a customer can't reopen — or
probe for the existence of — another organisation's ticket.

## Acceptance criteria

1. A customer can reopen their own closed ticket within 14 days of
   `closed_at`; it becomes `open` with `resolved_at` and `closed_at` both
   `null`.
2. Reopening appends the given message to the ticket's messages, attributed
   to the customer.
3. Reopening without a message (empty/whitespace) is rejected.
4. Reopening 14+ days after `closed_at` is rejected.
5. Reopening a ticket that isn't `closed` (open/pending/resolved) is
   rejected — the agent-only `reopenTicket` and its existing tests are
   untouched.
6. The assigned agent gets a `ticket_reopened` notification with
   `by: customer:<id>`; an unassigned ticket reopens without error and
   without queuing a notification.
7. **Regression for the purge latch:** a ticket that was closed, purged
   (messages deleted, `purged: true`), reopened, replied to, resolved, and
   closed again gets purged a second time after another 7 quiet days —
   i.e. `purged` is confirmed reset to `false` on reopen, not just the
   status/dates.
8. `portal.reopen` returns `null` for a ticket belonging to a different
   organisation, same as `getMyTicket`.

## Out of scope for v1

- SLA reset on reopen.
- Reopen count limits / abuse protection.
- A dedicated event type for customer-initiated reopens (reuses
  `ticket_reopened`).
- Auto-reopening via `portal.reply` on a closed ticket (stays an error).
