# Reopen a closed ticket from the portal

## Restatement

Customers have been asking to reopen a ticket themselves instead of filing a
new one when a closed issue turns out not to be fixed. The request: let a
portal customer reopen their own organisation's closed ticket within 14 days
of it being closed, and notify the assigned agent when they do.

Technical reading: add a customer-facing counterpart to the existing
agent-only `reopenTicket` (`src/tickets.js:38-44`), which only accepts
`resolved → open` and is not reachable from the portal. The new path must
accept `closed → open`, be callable only through the customer's own
organisation, enforce a 14-day window measured from `closed_at`, and reuse
the existing agent-notification mechanism (`src/notify.js:6-9`).

The user is away until tomorrow. Per their instruction, every question below
is answered inline with a recommendation rather than left open, and the
design below is built on those recommendations.

## Touchpoints

- `src/tickets.js:4` — `STATUS` enum (target status is `STATUS.OPEN`).
- `src/tickets.js:6` — only `HOUR` is defined here; no `DAY` constant exists
  yet (`src/jobs/*.js` each redefine `DAY` locally).
- `src/tickets.js:38-44` — `reopenTicket(store, id, agentId)`, the existing
  agent-only reopen. Resolved-only; stays untouched (see Edge case 3).
- `src/tickets.js:46-50` — `mustGet`, reused for the new function.
- `src/portal.js:10-14` — `getMyTicket`, the org-scoping pattern every portal
  function follows (checks `t.org_id !== customer.orgId` only, never
  `customer_id`).
- `src/portal.js:21-28` — `reply`, the closest existing precedent: throws on
  a closed ticket, flips `resolved`/`pending` back to `open`.
- `src/notify.js:6-9` — `notifyAgent` throws if called with no `agentId`, so
  every call site must guard on `assignee_id` first.
- `src/jobs/purge-closed.js:7,13` — `KEEP_DAYS = 7`; `if (t.purged) continue`
  is a one-way latch consumed by the nightly purge job.
- `src/jobs/close-resolved.js:5` — `QUIET_DAYS = 3`, unrelated but shows the
  job's `DAY` constant convention.
- `test/tickets.test.js:34-41` — pins the agent-only `reopenTicket`'s exact
  error messages (`cannot reopen a open ticket`, `cannot reopen a closed
  ticket`); the new function must not change that behavior.
- `docs/glossary.md:12` — "closed: final... If the customer comes back, they
  start a new ticket." This sentence becomes wrong and needs an update.

## Design

Add two functions, following the existing split between ticket rules and
portal scoping:

**`tickets.reopenByCustomer(store, id, actingCustomerId, message, { now = new Date() } = {})`**
in `src/tickets.js`:

1. `mustGet` the ticket; if `status !== STATUS.CLOSED`, throw
   `` cannot reopen a ${t.status} ticket `` (same message shape as the
   agent path, different function — no collision with the pinned test).
2. If `now - closed_at >= 14 * DAY` (strict), throw `too late to reopen;
   this ticket closed more than 14 days ago`. Add `const DAY = 24 * HOUR;`
   next to `HOUR` (`src/tickets.js:6`) rather than inlining the literal a
   third time.
3. If `message` is empty/whitespace, throw `a message is required to
   reopen a ticket`.
4. `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null,
   closed_at: null, purged: false })` — `purged` is reset unconditionally,
   not only when previously `true` (see Edge case 2, the non-negotiable
   part of this spec).
5. `store.addMessage(id, { from: 'customer', body: message, at:
   now.toISOString() })`.
6. If `t.assignee_id` is set, `notifyAgent(store, t.assignee_id, { type:
   'ticket_reopened', ticketId: id, by: \`customer:${actingCustomerId}\` })`.
   Skip silently if `assignee_id` is null — `notifyAgent` throws on a null
   id (`src/notify.js:7`).
7. Return the updated ticket.

No new event type: `ticket_reopened` already exists for the agent path and
differs only by its `by:` value, matching how that path already encodes the
actor.

**`portal.reopen(store, customer, id, message, { now = new Date() } = {})`**
in `src/portal.js`, mirroring `reply`'s shape:

1. `const t = getMyTicket(store, customer, id); if (!t) return null;` — same
   org-scoping as every other portal function, no extra `customer_id`
   check (matches `reply`, which never restricts to the ticket's original
   author either).
2. `tickets.reopenByCustomer(store, id, customer.id, message, { now })` —
   the acting customer's id is passed explicitly, not `t.customer_id`,
   because any customer in the ticket's organisation may act and that can
   differ from who originally opened it.
3. Return `getMyTicket(store, customer, id)` to include the fresh message
   list, same as `reply`'s return shape.

`docs/glossary.md`'s "closed" bullet is updated to: "closed: final. A
closed ticket is never changed again, except that the customer may reopen
it within 14 days of closing; after that, or once reopened and closed
again, they start a new ticket." (The 7-day purge window is unrelated to
this and is not mentioned here — see Q4.)

## Edge cases

1. **Reopening right at the 14-day boundary.** Strict `<` on
   `now - closed_at`, matching the strict `<` style already used by
   `purgeClosed` (`src/jobs/purge-closed.js:14`) and `closeResolved`
   (`src/jobs/close-resolved.js:11`). A ticket closed exactly 14 days ago
   (to the millisecond) is no longer reopenable.
2. **A ticket that was already purged, then reopened, then closed and
   purged again.** `purgeClosed`'s `if (t.purged) continue` latch
   (`src/jobs/purge-closed.js:13`) is one-way. If reopen only cleared
   `purged` when it was previously `true`, this is a no-op either way — but
   the unconditional reset in step 4 above is what actually matters: it
   guarantees the *next* close-and-purge cycle isn't skipped because the
   flag was never cleared. Acceptance criterion 6 below exercises exactly
   this reopen → re-close → re-purge cycle.
3. **No assignee on the ticket.** `notifyAgent` throws if given a null
   `agentId` (`src/notify.js:7`); the new function checks `assignee_id`
   before calling it and reopens successfully with no notification sent.
4. **A different customer in the same organisation reopens it** (not the
   one who originally filed it). Allowed — see Q1. `actingCustomerId` is
   recorded in the notification `by:` field, not `t.customer_id`.
5. **Empty or whitespace-only message.** Rejected before any state change,
   mirroring how `createTicket`/`reply` always require a body.
6. **A ticket from another organisation, or a non-existent ticket id.**
   `portal.reopen` returns `null` via `getMyTicket`'s existing org check,
   same as every other portal function — no new error type introduced.
7. **Reopening a ticket whose messages were already purged** (closed more
   than 7 but fewer than 14 days ago). See Q4 — allowed; the reopened
   ticket simply has no prior message history, only the new one added in
   step 5.
8. **The agent-only path (`resolved → open`).** Left completely untouched;
   it has its own function and its own pinned test assertions
   (`test/tickets.test.js:34-41`). Customer reopen is a new, separate
   action, not a widening of the existing one.

## Questions and recommendations

**Q1. Can any customer in the ticket's organisation reopen it, or only the
one who originally filed it?**
Recommendation: any customer in the organisation. Every existing portal
function (`getMyTicket`, `reply`) scopes by `org_id` only and never checks
`customer_id` — adding an author-only restriction here would be a new rule
inconsistent with how the rest of the portal already treats shared,
per-organisation ticket visibility.

**Q2. What identifies the "actor" recorded in the notification, given the
acting customer may differ from the ticket's original customer?**
Recommendation: pass the acting customer's id as an explicit parameter
(`actingCustomerId`), separate from the ticket's stored `customer_id`. This
mirrors the agent path, where `reopenTicket(store, id, agentId)` records the
agent *performing* the reopen, not `t.assignee_id`.

**Q3. Should reopening always clear the `purged` flag, or only when it was
previously `true`?**
Recommendation: always clear it (set unconditionally to `false`), regardless
of its prior value. This is the one correctness-critical decision in this
spec: `purgeClosed`'s `if (t.purged) continue` is a one-way latch, so any
path that leaves `purged: true` in place (or merely preserves whatever it
already was) risks a ticket that silently never gets purged again after a
second close — a retention-policy violation, not a style choice.

**Q4. The purge window (`KEEP_DAYS = 7`) is shorter than the proposed
14-day reopen window — a ticket can legally be reopened after its messages
are already gone. Widen `KEEP_DAYS`, or accept the gap?**
Recommendation: accept it. A reopened ticket with no prior message history
is a reasonable, visible outcome (the customer's new message is still
added). `KEEP_DAYS` is a legal-retention control answering a different
question ("how long do we keep conversation text") and widening it to serve
this feature would weaken that policy for an unrelated reason.

## Assumptions

- The 14-day window is measured from `closed_at`, not from ticket creation
  or last message. **Confidence: high** — `closed_at` is the only closing
  timestamp the schema already has (`src/tickets.js:18`), and it's the
  natural reading of "within 14 days of it being closed."
- A message is required to reopen (reusing the existing `addMessage` call,
  not a bodiless status flip). **Confidence: high** — matches every other
  state-changing portal action (`openTicket`, `reply`), which all require a
  body.
- No limit on how many times a ticket can be reopened, and no SLA
  (`sla_due_at`) reset on reopen. **Confidence: medium** — nothing in the
  request mentions either, and the existing agent-side `reopenTicket` does
  not reset SLA either; scoping this out keeps the change minimal, but the
  user may want a reopen-count cap once this reaches real customers.
- `notifyAgent`'s queue (`src/notify.js:4-9`) is a sufficient notification
  mechanism (no new channel needed). **Confidence: high** — it's exactly
  the mechanism the agent-side reopen already uses for the same event type.

- The change touches 4 files (`src/tickets.js`, `src/portal.js`,
  `docs/glossary.md`, `test/tickets.test.js`), above this project's
  informal 3-file ACT/bk-build threshold — routes to **bk-plan**, not
  straight to bk-build.
- Flagging for **independent review before push anyway**, despite the

  flag that gates the nightly data-deletion job
  (`src/jobs/purge-closed.js:13`), and bk-protocol's hot-path list includes
  data deletion. The change itself isn't a deletion operation, but it
  controls one, which is the kind of adjacency worth a second pair of eyes.

## Acceptance criteria

1. A closed ticket, reopened by a customer in its organisation within 14
   days of `closed_at`, ends up with `status: 'open'`, `resolved_at: null`,
   `closed_at: null`, and the new message appended.
2. Reopening at exactly 14 days (or later) throws and leaves the ticket
   unchanged.
3. Reopening with an empty or whitespace-only message throws and leaves the
   ticket unchanged.
4. Reopening a ticket in a different organisation returns `null` (no
   throw), matching `getMyTicket`'s existing behavior.
5. Reopening a ticket with an assignee queues exactly one notification to
   that agent, of type `ticket_reopened`, with `by: customer:<actingCustomerId>`.
   Reopening an unassigned ticket queues no notification and does not throw.
6. A ticket that is reopened, then closed again, then purged again (past
   `KEEP_DAYS`) has its messages deleted the second time — i.e. `purged` is
   not stuck `true` from an earlier purge cycle.
7. The existing agent-only `reopenTicket` behavior and its pinned error
   messages (`test/tickets.test.js:34-41`) are unchanged.
8. A ticket closed more than `KEEP_DAYS` (7) but fewer than 14 days ago can
   still be reopened, ending up with no prior messages but the new one
   present.

## Out of scope

- Any reopen-count limit.
- Any SLA (`sla_due_at`) reset or recalculation on reopen.
- Widening `KEEP_DAYS` to cover the full 14-day reopen window (Q4).
- Any change to the agent-only `reopenTicket` path.
