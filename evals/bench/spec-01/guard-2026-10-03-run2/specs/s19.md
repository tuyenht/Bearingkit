# Spec: customer self-service ticket reopen

Status: draft, awaiting review. Written while the requester was away; open
questions below are answered with a recommendation rather than left blocking,
per their request. Not implemented.

## Restatement

Customers keep asking to reopen their own closed tickets instead of opening a
new one. We'll let a portal customer reopen a ticket that is currently
`closed`, as long as it closed within the last 14 days, and notify the
assigned agent when they do.

## Touchpoints

- `src/tickets.js` — new `reopenByCustomer` business-rule function, alongside
  the existing agent-only `reopenTicket`.
- `src/portal.js` — new `reopen` wrapper, mirroring `openTicket`/`reply`'s
  org-scoping.
- `docs/glossary.md` — the "closed: final" bullet is no longer quite true.
- `test/tickets.test.js` — new tests.

No changes to `src/notify.js`, `src/store.js`, or the nightly jobs
(`close-resolved.js`, `purge-closed.js`) — see the `purged`-flag note below
for why `purge-closed.js`'s *behavior* still matters even though its code
doesn't change.

## Design

**New function — `tickets.reopenByCustomer(store, id, customerId, message, { now })`**

```js
const REOPEN_DAYS = 14;

function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_DAYS * DAY) {
    throw new Error('too late to reopen this ticket');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');

  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  }
  return updated;
}
```

`tickets.js` currently only defines `HOUR`; this adds `const DAY = 24 * HOUR;`
next to it rather than inlining the literal a third time (the two job files
each already redefine `DAY` locally).

**New wrapper — `portal.reopen(store, customer, id, message, { now })`**

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = store.getTicket(id);
  if (!t || t.org_id !== customer.orgId) return null;
  reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

Mirrors `openTicket`/`getMyTicket`: scoped by `org_id` only, returns `null`
for a ticket outside the customer's org (same shape as `getMyTicket`, not a
thrown error).

**Why a new function instead of extending `reopenTicket` or `reply`:**

- `tickets.reopenTicket(store, id, agentId)` is agent-only and
  resolved-only, and is pinned by exact-message assertions in
  `test/tickets.test.js` ("cannot reopen a open/closed ticket"). Reusing it
  for a different actor and a different source status would break those
  tests and conflate two different permission models. Left untouched.
- `portal.reply` already throws on any closed ticket ("this ticket is
  closed; please open a new one") — that's existing, deliberate behavior for
  the normal case. Reopening is a separate, explicit action a customer
  opts into, not a side effect of answering.

**Notification:** reuses the existing `ticket_reopened` event type and the
existing `notifyAgent` queue — no new event type. The `by` field follows the
precedent set by the agent path (`by: agent:${agentId}`, the *actor*, not
`t.assignee_id`): here it's `by: customer:${actingCustomerId}`. Skipped
silently if `assignee_id` is null, since `notifyAgent` throws if called
without an agent and an unassigned ticket has no one to notify.

## Edge cases

- **Wrong status.** Only `closed` tickets qualify. A `resolved` ticket
  already has its own reopen paths (customer reply, agent `reopenTicket`);
  `open`/`pending` tickets aren't closed at all. `reopenByCustomer` rejects
  all of these with `cannot reopen a <status> ticket`, matching
  `reopenTicket`'s existing error shape.
- **Window boundary.** Window check is `now - closed_at < 14 days` (strict),
  matching the strict-`<` pattern already used by `closeResolved`'s
  quiet-period check and `purgeClosed`'s retention check. A ticket closed
  exactly 14 days ago (to the millisecond) is just outside the window.
- **Empty/missing message.** Rejected. A reopen should carry *why* the
  customer is coming back, especially since the prior message history may
  already be gone (next bullet).
- **Ticket already purged.** `purge-closed.js`'s `KEEP_DAYS` is 7 days —
  shorter than the 14-day reopen window — so a ticket can legally be
  reopened after its message history was already deleted. Recommendation:
  allow it; the reopened ticket just starts with no prior history plus the
  new message. We should not widen `KEEP_DAYS` to cover the reopen window —
  that's a legal/retention control unrelated to this feature.
- **Reopening a previously-purged ticket.** `purgeClosed` treats `purged` as
  a one-way latch (`if (t.purged) continue`). If reopening doesn't reset it
  back to `false`, a second close→purge cycle would never delete the new
  round of messages — a retention-policy violation, not just a style
  nit. `reopenByCustomer` resets `purged: false` unconditionally, whether or
  not it was already `true`.

## Open questions (answered by recommendation — see note above)

**Q1: Can any customer at the org reopen, or only the one who originally opened the ticket?**
Recommendation: any customer in the org. This mirrors existing behavior —
`portal.reply` and `getMyTicket` already check only `org_id`, never
`customer_id` — so reopen follows the same access model as every other
portal action instead of introducing a new, narrower one.

**Q2: Whose id goes in the notification's `by: customer:<id>` field?**
Recommendation: the *acting* customer's id, passed explicitly as
`reopenByCustomer`'s `customerId` parameter — not the ticket's original
`t.customer_id`. Because any org customer can act (Q1), the two can differ;
using `t.customer_id` would misattribute the action if someone else at the
org reopens it. This mirrors the agent path, which stamps `by:
agent:${agentId}` for whoever performed the action, not a stored owner
field.

**Q3: Should reopening reset the `purged` flag?**
Recommendation: yes, unconditionally (see "Reopening a previously-purged
ticket" above). This is the one non-negotiable item in this spec — getting
it wrong is a silent data-retention bug, not a style choice.

**Q4: `KEEP_DAYS` (7) is shorter than the reopen window (14) — widen `KEEP_DAYS`, or accept the gap?**
Recommendation: accept it. Allow reopening a ticket whose messages were
already purged; don't change `KEEP_DAYS`, since that constant is a
legal-retention control with its own rationale ("we do not keep
conversation text of finished tickets longer than a week"), not something
to tune for this feature's convenience.

## Assumptions

- No SLA reset on reopen — the original `sla_due_at` is left as-is. Out of
  scope for v1; no customer ask for it.
- No limit on how many times a ticket can be reopened within its window.
  Out of scope for v1.
- Reopen always lands the ticket in `open` (unassigned agents still see it;
  assigned ones get notified), never back in `pending`.

## Classification

Gate-pattern matching alone says **ACT** (no auth/tenant/migration path or
keyword hit). Flagging for independent review anyway: this change touches
the `purged` flag that gates `purge-closed.js`'s data-deletion job. The
change itself isn't a deletion operation, but getting the flag reset wrong
has the same blast radius as one.

This spec touches 4 files (`tickets.js`, `portal.js`, `glossary.md`, test
file), above the informal 3-file threshold for going straight to
implementation — next step is a short implementation plan, not a direct
build.

## Acceptance criteria

1. A customer can reopen their own org's `closed` ticket within 14 days of
   `closed_at`; the ticket becomes `open`, `resolved_at` and `closed_at` are
   cleared, and the customer's message is appended.
2. Reopening more than 14 days after `closed_at` throws and leaves the
   ticket untouched.
3. Reopening a non-closed ticket (`open`, `pending`, `resolved`) throws and
   leaves the ticket untouched.
4. Reopening with an empty or missing message throws before any state
   changes.
5. If the ticket has an assignee, reopening queues a `ticket_reopened`
   notification to that agent with `by: customer:<actingCustomerId>`; if
   unassigned, no notification is queued (and nothing throws).
6. Reopen → close again → `purgeClosed` after `KEEP_DAYS` correctly deletes
   the *second* round of messages (regression test for the `purged`-latch
   reset).
7. `portal.reopen` returns `null` for a ticket outside the calling
   customer's organisation, without leaking its existence.
8. A customer from a different org in the same `closed`+within-window state
   cannot reopen another org's ticket (covered by #7's org check, asserted
   explicitly).

## Out of scope

- SLA re-evaluation on reopen.
- Reopen-count limits or rate limiting.
- Changing `purge-closed.js`'s `KEEP_DAYS` retention window.
- Any UI/portal-frontend work — this spec covers the `tickets`/`portal`
  module layer only.
