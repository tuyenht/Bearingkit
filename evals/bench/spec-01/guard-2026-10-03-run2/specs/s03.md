# Spec: customer reopen of a closed ticket

## Restated request

Let a portal customer reopen their own ticket within 14 days of it being
closed, and notify the ticket's assigned agent when that happens.

Technical reading: today `docs/glossary.md:12` defines closed as final —
"never changed again... they start a new ticket" — and `src/portal.js:24`
enforces that (`reply` throws `'this ticket is closed; please open a new
one'` on any closed ticket). This request adds one narrow, time-boxed
exception to that rule for the customer who owns the ticket, via a new
portal action, not by changing what `reply` does.

## What already exists (not re-specified here)

- Agent-side reopen: `tickets.reopenTicket(store, id, agentId)`
  (`src/tickets.js:38-44`) — resolved→open only, notifies the previous
  assignee if different from the reopening agent, event type
  `ticket_reopened`. Pinned by exact-message assertions in
  `test/tickets.test.js:34-41`. This spec adds a separate function; it
  does not change `reopenTicket`.
- Customer reply reopens a resolved/pending ticket as a side effect
  (`src/portal.js:26`), and throws on a closed one (`src/portal.js:24`).
  No existing path lets a customer act on a closed ticket at all.

## Edge cases

1. **Ticket not closed** (open/pending/resolved) → reject. Throws
   `cannot reopen a ${status} ticket`, no store writes. Mirrors the error
   style of `tickets.js:40`.
2. **Exactly 14 days since `closed_at`** → reject (boundary is exclusive;
   see Q4). Consistent with how `purge-closed.js:14` and
   `close-resolved.js:11` both code their windows as strict `<`.
3. **Ticket already purged** (messages deleted by the 7-day purge job,
   `purge-closed.js:13-17`, but still inside the 14-day reopen window) →
   allowed. The ticket row survives purge (only messages are deleted,
   `purge-closed.js:15`), so reopen succeeds and the customer's new
   message becomes the ticket's only history. `purged` must be reset to
   `false` unconditionally (see acceptance criterion 6) — this is the one
   non-negotiable item in this spec.
4. **No assignee** (`assignee_id` is null) → reopen still succeeds; the
   notify step is skipped silently. `notify.notifyAgent` throws if handed
   a falsy agent id (`notify.js:7`), so this must be an explicit guard,
   not a call that's allowed to fail.
5. **Empty or whitespace-only message** → reject, no store writes (see
   Q2 for why a message is required at all).
6. **Ticket belongs to another organisation** → `portal.reopen` returns
   `null` without throwing, same as `getMyTicket` does today
   (`portal.js:11-13`).
7. **Ticket id does not exist** → `null`, same path as edge case 6 (both
   go through `getMyTicket`'s existing null-safety).
8. **Second close-and-purge cycle after a reopen** → a ticket that is
   reopened, then resolved and closed again, must be purgeable again once
   its *new* `closed_at` is 7+ days old. This is the regression test that
   proves the `purged` latch actually un-sticks rather than staying `true`
   forever (acceptance criterion 10).

## Open questions (asked now, answered by recommendation — user is away; see
note at the end)

1. **Should `resolved_at` and `closed_at` both clear to `null` on a
   customer reopen, or should `closed_at` be kept as history?**
   Recommend: clear both to `null`. Why: `tickets.js:41` already clears
   `resolved_at` on the agent-side reopen, and nothing in the codebase
   reads `closed_at` on a non-closed ticket — leaving it set would make
   the ticket look closed to any future code that checks the field
   instead of `status`.
2. **Should a reopen require a non-empty message from the customer, or
   can they reopen with nothing?**
   Recommend: require one. Why: the purge job deletes message history
   after 7 days (`purge-closed.js:7`), which is inside the 14-day reopen
   window — a message-less reopen after day 7 would hand the agent a
   ticket with no content at all.
3. **Should the agent notification reuse the existing `ticket_reopened`
   event type (`tickets.js:42`) or use a new one?**
   Recommend: a new type, `ticket_reopened_by_customer`. Why: it lets
   notification rendering (mail worker, portal/agent UI) distinguish a
   customer-initiated reopen from an agent-initiated one without
   inspecting the `by` field on every event.
4. **Is the 14-day window a strict less-than (blocked at exactly 14
   days) or inclusive?**
   Recommend: strict less-than, i.e. allowed while
   `now - closed_at < 14 * DAY`. Why: matches the existing style of both
   nightly jobs in this codebase (`purge-closed.js:14`,
   `close-resolved.js:11`), which both use `<` to allow and fall through
   to act otherwise.

These are the four questions whose answers most change the shape of the
work; see "Assumptions" below for the rest, each recorded as a default
rather than asked, per this project's question cap.

## Assumptions

- **High.** Reopen's target status is `open` (not `pending`) — matches
  both the agent-side reopen (`tickets.js:41`) and what a customer reply
  does to a resolved ticket (`portal.js:26`).
- **High.** No SLA recompute on reopen. Nothing today touches `sla_due_at`
  outside ticket creation (`tickets.js:16`), and the request doesn't ask
  for one.
- **High.** No limit on how many times a ticket can be reopened. No
  existing code tracks a reopen count, and the request doesn't ask for a
  limit.
- **High.** The 14-day clock runs from `closed_at`, per the request's own
  wording ("within 14 days of it being closed"), not from `resolved_at`.
- **Medium.** This is portal-only (customer-facing); no new agent-facing
  or API surface is requested beyond "from the portal."

## Design

Two new functions, mirroring the existing split between `tickets.js`
(business rules) and `portal.js` (org-scoped wrapper):

**`tickets.reopenByCustomer(store, id, message, { now = new Date() } = {})`**
in `src/tickets.js`:
1. `mustGet` the ticket (existing helper, `tickets.js:46-49`).
2. If `status !== CLOSED`, throw `` `cannot reopen a ${status} ticket` ``.
3. If `now - closed_at >= 14 * DAY`, throw (e.g. `'too long closed to
   reopen; start a new ticket'`).
4. If `message` is empty/whitespace, throw (e.g. `'a reopen needs a
   message'`).
5. `store.updateTicket(id, { status: OPEN, resolved_at: null,
   closed_at: null, purged: false })` — the `purged: false` write is
   unconditional, not guarded by whether it was already purged.
6. `store.addMessage(id, { from: 'customer', body: message, at:
   now.toISOString() })`.
7. If `assignee_id` is set, `notifyAgent(store, assignee_id, { type:
   'ticket_reopened_by_customer', ticketId: id, by: `customer:${t.customer_id}` })`;
   otherwise skip.
8. Return the updated ticket.

Add `const DAY = 24 * HOUR;` next to the existing `HOUR` constant
(`tickets.js:6`) — today only `HOUR` is defined there; the two job files
each redefine `DAY` locally (`purge-closed.js:8`,
`close-resolved.js:6`), and this is the first time ticket-rule code
itself needs a day-scale window, so it belongs in `tickets.js` rather
than a third local redefinition.

**`portal.reopen(store, customer, id, message, { now = new Date() } = {})`**
in `src/portal.js`:
1. `const t = getMyTicket(store, customer, id); if (!t) return null;`
2. `return tickets.reopenByCustomer(store, id, message, { now });`

This mirrors `openTicket` (`portal.js:16-18`) and the null-on-wrong-org
behavior of `getMyTicket` itself — same shape as the rest of the file.

`portal.reply` is not touched: it keeps throwing on every closed ticket.
Reopening is a separate, deliberate customer action with its own message
argument, not a side effect of replying.

## Acceptance criteria

1. `src/tickets.js` exports `reopenByCustomer(store, id, message, { now })`,
   independent of and not called by the existing `reopenTicket`.
2. `src/portal.js` exports `reopen(store, customer, id, message, { now })`.
3. Reopening a ticket whose status is `open`, `pending`, or `resolved`
   throws `` `cannot reopen a ${status} ticket` `` and writes nothing.
4. Reopening a closed ticket where `now - closed_at >= 14 * DAY` throws
   and writes nothing.
5. Reopening with an empty or whitespace-only message throws and writes
   nothing.
6. A successful reopen sets `status: 'open'`, `resolved_at: null`,
   `closed_at: null`, and unconditionally `purged: false` — including on
   a ticket where `purged` was already `true`.
7. A successful reopen appends a message with `from: 'customer'` and the
   given body.
8. A successful reopen on a ticket with a non-null `assignee_id` queues a
   `ticket_reopened_by_customer` notification to that agent; on a null
   `assignee_id` it queues nothing and does not throw.
9. `portal.reopen` returns `null`, with no writes, for a nonexistent
   ticket id or a ticket belonging to a different organisation.
10. A ticket reopened, then resolved and closed again, is purged again by
    `purgeClosed` once its new `closed_at` is 7+ days old (regression test
    that the `purged` latch un-sticks — see edge case 8).
11. `docs/glossary.md:12` is amended to note the 14-day customer reopen
    exception, without changing what it says about agent-side reopen.
12. `test/tickets.test.js:34-41` keeps passing unchanged.

## Out of scope

per the request); any HTTP/API route (this spec covers the `portal.js`
function the route would call).
