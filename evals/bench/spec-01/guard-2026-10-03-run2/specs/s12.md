# Reopen a closed ticket from the portal

## Summary

Let a portal customer reopen their own organisation's **closed** ticket within 14 days
of it closing, by sending a message explaining why. Reopening notifies the assigned
agent, the same way an agent reopening a resolved ticket does today.

> The author of this spec was away when it was written. Every open question below is
> answered with a recommendation rather than left pending, and the design that follows
> builds on those recommendations. Flag any you'd answer differently and the affected
> sections get revised before this goes to an implementation plan.

## Current behavior (verified against the code, 2026-10-03)

- **Status model** (`src/tickets.js`, `docs/glossary.md`): `open → pending/resolved →
  closed`. Glossary says closed is "final... never changed again."
- **Agent-side reopen** (`tickets.reopenTicket`, `src/tickets.js:38-44`): only a
  **resolved** ticket can be reopened by an agent; closed/open/pending all throw
  `cannot reopen a ${status} ticket`. This exact error text is pinned by
  `test/tickets.test.js:34-41` and must not change.
- **Customer-side reply** (`portal.reply`, `src/portal.js:21-28`): throws on a closed
  ticket ("this ticket is closed; please open a new one"); on a resolved/pending ticket
  it puts the ticket back to `open` as a side effect of answering.
- **Notification** (`src/notify.js`): `notifyAgent(store, agentId, event)` queues an
  email and **throws if `agentId` is falsy** — callers must not call it with no agent.
  The existing reopen path only notifies when the previous assignee differs from the
  acting agent; event shape is `{ type: 'ticket_reopened', ticketId, by }`.
- **Nightly purge** (`src/jobs/purge-closed.js`): 7 days after `closed_at`
  (`KEEP_DAYS = 7`), messages are deleted and `purged: true` is set, permanently —
  `if (t.purged) continue` is a one-way latch with no code path that ever clears it.
- **Org scoping**: `portal.getMyTicket` and `portal.reply` both authorize by
  `t.org_id === customer.orgId` only — neither checks that the acting customer is the
  one who originally opened the ticket.

## Open questions and recommendations

**Q1. Who may reopen — only the original customer, or anyone in the ticket's org?**
Recommendation: **anyone in the org**, matching the existing model. `getMyTicket` and
`reply` already authorize by `org_id` alone, not `customer_id`; adding a stricter rule
just for reopen would be a new, inconsistent restriction with no stated requirement
behind it.

**Q2. Is the "14 days" window measured from `closed_at`, and is the boundary
inclusive or exclusive?**
Recommendation: from `closed_at`, **exclusive** at the 14-day mark (`now - closed_at <
14 days` allowed; exactly 14 days or more is too late) — mirroring how
`closeResolved`/`purgeClosed` already treat their own day windows (`<` to skip,
trigger once the threshold is reached).

**Q3. Is the message mandatory, and does it become a visible ticket message or just
audit metadata?**
Recommendation: **mandatory and stored as a real customer message** (`store.addMessage`,
same shape `reply`/`createTicket` already use). The agent needs to see *why* it was
reopened in the same thread they already read; a side-channel audit note would be
invisible in the normal ticket view.

**Q4. Does reopening reuse the `ticket_reopened` event type, or introduce a new one?**
Recommendation: **reuse `ticket_reopened`**, with `by: customer:<customerId>` instead
of `by: agent:<agentId>`. The agent path already encodes the actor this way; a second
event type for the same fact (ticket went from closed/resolved back to open) would
just be two names for one thing.

**Q5. Should the notification fire when the ticket has no assignee?**
Recommendation: **skip silently** when `assignee_id` is null — `notifyAgent` throws on
a falsy agent id, and there's no one to notify in the unassigned-queue case. This
matches how the existing agent-reopen path already guards (`if (t.assignee_id && ...)`).

**Q6. `KEEP_DAYS` (7) is shorter than the proposed reopen window (14), so a ticket can
legally be reopened after its messages are already purged. What happens then?**
Recommendation: **allow it.** The reopened ticket simply starts with no prior message
history — the new reopen message becomes its first message again. Don't widen
`KEEP_DAYS` to cover the reopen window: it's a legal data-retention control, not a UX
constraint, and changing it is out of scope for a portal feature request. This is the
one interaction worth documenting explicitly since it's easy to miss on a quick read.

**Q7. What happens to a ticket that was already closed, purged, reopened, and then
closes again — does the second purge run correctly?**
Recommendation: reopening **must unconditionally reset `purged: false`**, even though
it starts `true`. This is the one non-negotiable part of the design, covered in detail
below — getting it wrong means a ticket's second round of messages never gets deleted,
which is a retention-policy violation, not a style nit.

**Q8. Does reopening reset the SLA due time, or cap how many times a ticket can be
reopened?**
Recommendation: **no to both**, for v1. Nothing in the request asks for either, and
both are speculative scope. If support later reports agents gaming repeated reopens,
that's a follow-up with its own data to justify it.

## Design

### `tickets.reopenByCustomer(store, id, customerId, message, { now })`

New function in `src/tickets.js`, alongside — not replacing — `reopenTicket`.

1. `mustGet(store, id)` — throws `no ticket ${id}` if missing (existing helper).
2. If `t.status !== STATUS.CLOSED`, throw `` `cannot reopen a ${t.status} ticket` ``
   (same message shape the agent path already uses and tests already pin).
3. If `now - closed_at >= REOPEN_DAYS * DAY`, throw `too late to reopen this ticket`.
4. If `message` is empty/whitespace, throw `a message is required to reopen a ticket`.
5. Append the message: `store.addMessage(id, { from: 'customer', body: message, at:
   now.toISOString() })`.
6. `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null,
   purged: false })` — the `purged: false` reset is unconditional, regardless of its
   current value (see "Interaction with the purge job" below).
7. If `t.assignee_id`, call `notifyAgent(store, t.assignee_id, { type:
   'ticket_reopened', ticketId: id, by: `customer:${customerId}` })`. Skip otherwise.
8. Return the updated ticket.

`src/tickets.js` currently defines `HOUR` but no `DAY` (each job file redefines it
locally). Add `const DAY = 24 * HOUR;` and `const REOPEN_DAYS = 14;` once in
`tickets.js` rather than inlining the literal a third time; export `REOPEN_DAYS` next
to the existing `SLA_HOURS` export so tests can reference it instead of a magic number.

### `portal.reopen(store, customer, id, message, { now })`

New function in `src/portal.js`, mirroring the `getMyTicket`/`openTicket` org-scoping
pattern already used there:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = store.getTicket(id);
  if (!t || t.org_id !== customer.orgId) return null;
  return tickets.reopenByCustomer(store, id, customer.id, message, { now });
}
```

Returns `null` for a ticket outside the customer's org (same contract as
`getMyTicket`), and otherwise delegates every business rule to `reopenByCustomer`,
passing the *acting* customer's id as the actor — not `t.customer_id` — since Q1's
answer means the acting customer and the ticket's original customer can differ.

### Why a new function instead of reusing `reply` or `reopenTicket`

Two alternatives considered and rejected:

- **Make `reply` auto-reopen a closed ticket**, the way it already does for a
  resolved one. Rejected: `reply` currently throws on every closed ticket, and that
  behavior is pinned by `test/tickets.test.js:58`. Folding reopen into reply would also
  make it implicit — no explicit customer intent, no way to enforce the 14-day window
  or require a reason — and would silently change what "closed" means everywhere else
  `reply` is called.
- **Extend `tickets.reopenTicket`** (the agent path) to also accept closed tickets and
  a customer actor. Rejected: it's status-gated to `resolved` on purpose, and that gate
  is exactly what the existing "only a resolved ticket can be reopened" test asserts for
  the agent path. Overloading it with a second actor type and a second status rule
  would make one function enforce two unrelated policies.

A dedicated `reopenByCustomer` keeps the agent path untouched and gives the 14-day
window and required-message rule one obvious place to live.

### Interaction with the purge job (non-negotiable)

`purgeClosed` (`src/jobs/purge-closed.js:13`) skips any ticket where `t.purged` is
already `true` — it is a one-way latch by design, since normally a closed ticket never
changes again. Reopening breaks that assumption: a ticket can now go
closed → purged → reopened → closed again. If `purged` weren't reset to `false` on
reopen, the second close would never purge, leaving the second round of messages
undeleted indefinitely — a retention-policy bug, not just a correctness nit. Step 6
above resets it unconditionally (not conditionally on its current value) so this cycle
purges correctly every time. Acceptance criterion #6 below exists specifically to catch
a regression here.

### Glossary update

`docs/glossary.md`'s **closed** entry currently reads "final. A closed ticket is never
changed again." Update it to:

> **closed**: final once 14 days have passed since closing. Within that window, the
> customer may reopen it from the portal with a message explaining why, which notifies
> the assigned agent. After that window — or once a new ticket is needed for any other
> reason — the customer starts a new ticket.

## Out of scope (v1)

- Resetting or extending the SLA due time on reopen (Q8).
- Limiting how many times a ticket can be reopened (Q8).
- Widening `KEEP_DAYS` to cover the reopen window (Q6) — retention policy is owned by
  legal, not this feature.
- Letting an agent reopen a ticket that's been closed for the full 14 days plus — out
  of scope; agents have no reopen path for closed tickets at all today and this spec
  doesn't add one.

## Acceptance criteria

1. A customer can reopen their org's closed ticket within 14 days of `closed_at`;
   the ticket's status becomes `open`, and both `resolved_at` and `closed_at` are
   cleared.
2. The reopen message is required (empty/whitespace throws) and, on success, appears
   as a new customer message on the ticket.
3. Reopening at or past the 14-day mark throws and leaves the ticket unchanged.
4. Reopening a ticket that is `open`, `pending`, or `resolved` (not `closed`) throws —
   `reopenByCustomer` does not become a second way to do what `reopenTicket`/`reply`
   already do for those statuses.
5. If the ticket has an assignee, reopening queues a `ticket_reopened` notification to
   that agent with `by: customer:<actingCustomerId>`; if there is no assignee, no
   notification is sent and nothing throws.
6. **Purge-cycle regression test:** close a ticket, purge it (messages deleted,
   `purged: true`), reopen it within the window, close it again, and purge again —
   the second purge must delete the second round of messages. This fails if `purged`
   is reset conditionally instead of unconditionally.
7. A customer from a different organisation gets `null` from `portal.reopen` (same
   contract as `getMyTicket`), with the ticket left untouched.
8. Reopening a ticket whose messages were already purged (because `KEEP_DAYS` < 14)
   succeeds; the ticket just starts with no prior message history besides the new
   reopen message.
