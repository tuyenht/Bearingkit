# Spec: customer self-service ticket reopen

Status: **draft — written while the user was away; awaiting review.** Not implemented.

## 1. Restated request

> Let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do.

Technical reading: add a customer-facing counterpart to the existing agent-only `reopenTicket` (`src/tickets.js:38-44`, resolved→open only). The new path must work from `closed`, be time-boxed to 14 days from `closed_at`, and reuse the existing notification channel (`src/notify.js`) to tell the assignee, the same way the agent path already does.

## 2. Clarifying questions, answered by recommendation

The user is away until tomorrow and asked for recommendations embedded inline rather than a live Q&A. Each item below is a decision a reviewer would otherwise be asked to make.

**Q1: Does reopening require a message from the customer, or can they reopen with one click?**
**Recommendation: require a non-empty message.** A reopen with no explanation gives the agent nothing to act on, and every other customer-facing mutation that touches a ticket (`portal.reply`, `portal.openTicket`) already carries a body. Treat reopen as "reply that also flips the status," not a bare state change.

**Q2: Is the 14-day window measured from `closed_at`, and is it inclusive or exclusive at the boundary?**
**Recommendation: strict `now - closed_at < 14 days`, i.e. exclusive at the boundary.** This matches the existing style in `close-resolved.js:11` and `purge-closed.js:14`, both of which use `< N * DAY` to gate the action. Day 14 at or past the exact instant of closing is "too late"; day 13-point-anything is fine.

**Q3: What happens to a ticket that was already purged (its messages deleted by the nightly job) when it's reopened inside the 14-day window?**
**Recommendation: allow it.** `purgeClosed` runs 7 days after close (`purge-closed.js:7`), which is inside the 14-day reopen window, so a ticket can legitimately be both purged and still reopenable (day 8–13). Reopening such a ticket just means it resumes with no prior message history — that's a true statement about the ticket, not a bug. The one thing that must happen: **`purged` must be reset to `false`** (see Q4/gotcha below), or the next close+purge cycle silently keeps deleted messages' ticket in a state where the job thinks it already purged it and skips cleanup forever.

**Q4: Should the SLA due time (`sla_due_at`) be recalculated on reopen?**
**Recommendation: no, out of scope for v1.** Nothing in the request asks for it, and `createTicket` is the only place `sla_due_at` is set today (`tickets.js:16`). Recomputing it would need a product decision about what SLA a reopened ticket deserves (same SLA? fresh clock? none?) that isn't implied by the request. Flag it as a known follow-up, don't guess at an answer.

**Q5: Should there be a limit on how many times a ticket can be reopened, or who can do it (any customer in the org, vs. only the one who opened it)?**
**Recommendation: no reopen-count limit, and any customer in the ticket's organisation** — this mirrors how every other portal function scopes by `org_id` only, never by `customer_id` (`portal.js:11-12`, `getMyTicket`; `portal.js:21-27`, `reply` — neither checks that the acting customer is the one who opened the ticket). Reopen should not invent a stricter rule than reply already has.

**Q6: What should the `by` field on the notification event say — the ticket's original `customer_id`, or the customer who performed the reopen?**
**Recommendation: the acting customer**, i.e. whoever is calling the function, not `t.customer_id`. This is a correction to an earlier draft of this same design, which had recorded `by: customer:<id>` ambiguously. The agent-side precedent settles it: `reopenTicket(store, id, agentId)` stamps `by: agent:${agentId}` — the *agent performing the action* — not `t.assignee_id`. Since Q5 allows any customer in the org to act, the actor and the ticket's original opener can differ, so the function must take the acting customer's id as an explicit parameter and use that.

**Q7: Does this change belong in a hot-path review even though it doesn't touch an auth/payments/migrations path?**
**Recommendation: yes, flag it for review attention anyway.** No path or content pattern in this change matches the kit's COUNCIL-area globs (no `auth/`, `migrations/`, `tenant*/`, etc.), so by the letter of the gate it classifies as ACT (see §5). But the change resets `purged: false` on a row the nightly data-deletion job (`purge-closed.js`) uses as a one-way latch (§5, Q3) — get a second pair of eyes on that one interaction specifically before it ships, even though the overall change doesn't need a council.

## 3. Edge cases

| Case | Handling |
|---|---|
| Empty or whitespace-only message | Reject before any mutation: `throw new Error('a message is required to reopen a ticket')`. Ticket and store are left untouched. |
| Ticket not in `closed` status (open, pending, or resolved) | Reject: `throw new Error(\`cannot reopen a ${t.status} ticket\`)` — same phrasing the agent-only path already uses for its own rejections (`tickets.js:40`), kept as a distinct function so the pinned test strings for the agent path (`test/tickets.test.js:37,40`) are untouched. |
| Window expired (`now - closed_at >= 14 days`) | Reject: `throw new Error('this ticket closed too long ago to reopen')`. Ticket stays closed. |
| Ticket belongs to a different organisation than the acting customer | Return `null`, same convention as `getMyTicket` (`portal.js:11-12`) and `openTicket`'s implicit scoping — no exception, no information leak about the ticket's existence. |
| Ticket has no assignee (`assignee_id === null`) | Skip the notification call entirely. `notifyAgent` throws if handed a falsy agent id (`notify.js:7`), so the caller must guard it — same guard the existing agent-side `reopenTicket` already has at `tickets.js:42` (`if (t.assignee_id && ...)`, simplified here to `if (t.assignee_id)` since there's no "don't notify yourself" case for a customer actor). |
| Ticket was already purged (`purged: true`, messages deleted) but is still inside the 14-day window | Allowed. Reopen resets `purged: false` in the same update that reopens it, so a subsequent close + 7-day purge cycle deletes the new message history instead of silently no-op'ing forever (the latch at `purge-closed.js:13`). This is the one correctness-critical edge case in this spec — see acceptance criterion #7. |
| Two reopen attempts on the same ticket in quick succession (no real concurrency in the in-memory store, but worth stating) | The second call sees the first call's result: status is already `open`, so it hits the "not closed" rejection (`cannot reopen a open ticket`) rather than double-notifying or double-appending messages. No explicit locking needed given the store's synchronous, single-threaded semantics; production (Postgres) should use the same optimistic check — the status-guard read-then-write is the concurrency control, not a separate mechanism. |

## 6. Design

### `src/tickets.js`

Add a `DAY` constant (the file currently only defines `HOUR` — `tickets.js:6`; the two job files each redefine `DAY` locally rather than import one, so this is the first shared use):

```js
const DAY = 24 * HOUR;
const REOPEN_WINDOW_DAYS = 14;
```

Add a new exported function, kept separate from the agent-only `reopenTicket` so its pinned test assertions (`test/tickets.test.js:37,40`) stay untouched:

```js
function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed too long ago to reopen');
  }
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  }
  return updated;
}
```

Export it alongside the existing functions.

### `src/portal.js`

Add a thin org-scoping wrapper, mirroring the existing `openTicket`/`getMyTicket`/`reply` pattern:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  tickets.reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

(Requires importing `reopenByCustomer` from `./tickets` alongside the existing `STATUS, createTicket` import, and returning the full ticket-plus-messages shape, same as `reply` does on its last line.)

### `docs/glossary.md`

The **closed** bullet (`glossary.md:12`) currently reads:

> **closed**: final. A closed ticket is never changed again. If the customer comes back, they start a new ticket.

Replace with:

> **closed**: final after 14 days. A closed ticket is never changed by an agent, and a customer cannot reply to it — but the customer can reopen it themselves within 14 days of closing, which puts it back to open. Past that window, if the customer comes back, they start a new ticket.

### `test/tickets.test.js`

New cases to add (acceptance criteria below double as the test list):
- Reopen within window succeeds, clears `resolved_at`/`closed_at`, sets status `open`, stores the message.
- Reopen at/after 14 days throws.
- Reopen a non-closed ticket (open, pending, resolved) throws with the status-specific message.
- Reopen with an empty message throws, ticket unchanged.
- Reopen from a different org returns `null`.
- Reopen notifies the assignee with `by: customer:<actingId>`; no assignee → no notification, no throw.
- Reopen a purged ticket resets `purged`, and a subsequent close + 7-day purge cycle deletes the new messages (the regression test for the latch bug).

## 7. Acceptance criteria

1. `portal.reopen(store, customer, id, message)` on a closed ticket inside the 14-day window sets status to `open`, clears `resolved_at` and `closed_at`, and appends the message.
2. The same call at or past 14 days from `closed_at` throws and leaves the ticket closed.
3. The same call on an open, pending, or resolved ticket throws `cannot reopen a <status> ticket` and leaves the ticket unchanged.
4. The same call with an empty or whitespace-only message throws and leaves the ticket unchanged.
5. The same call against a ticket outside the customer's organisation returns `null`.
6. On success, if the ticket has an assignee, `notify.drain()` contains one `ticket_reopened` event addressed to that agent with `by: customer:<actingCustomerId>`. If there is no assignee, no event is queued and no error is thrown.
7. Reopening a ticket whose `purged` flag was already `true` resets it to `false`; closing and purging it again afterward deletes its (new) messages rather than being skipped by the latch.
8. The agent-only `reopenTicket` (`tickets.js:38`) and its pinned test assertions (`test/tickets.test.js:34-41`) are unchanged.
9. `docs/glossary.md`'s **closed** entry reflects the reopen exception.

## 8. Out of scope (v1)

- SLA recalculation on reopen (Q4).
- A limit on how many times a ticket can be reopened (Q5).
- Restricting reopen to the specific customer who originally opened the ticket, as opposed to any customer in the org (Q5).
- Any portal UI work — this spec covers `tickets.js`/`portal.js` only, no view layer exists in this codebase to extend.
