# Spec: customer self-service ticket reopen

Status: draft, awaiting review. Written 2026-10-03 while the user was away;
per their instruction, clarifying questions are answered inline with a
recommendation rather than left open for live Q&A. Nothing in this spec has
been built yet.

## Restatement

Request, in the user's words: "let a customer reopen a closed ticket from the
portal within 14 days of it being closed, and notify the assigned agent when
they do."

Technical reading: today `docs/glossary.md:12` defines **closed** as final —
"a closed ticket is never changed again. If the customer comes back, they
start a new ticket" — and the only reopen path is agent-side,
`resolved`-only (`src/tickets.js:38-44`, guarded by exact-message assertions
in `test/tickets.test.js:34-41`). This request adds a *second*, customer-
facing reopen path for `closed` tickets specifically, bounded by a 14-day
window off `closed_at`, and changes the glossary's "closed is final" rule.
The two reopen paths (agent: resolved→open, customer: closed→open) are kept
separate rather than merged, since they have different source statuses,
different actors, and different guard rails.

## Design

Two new functions, mirroring the existing agent-side shape:

```js
// src/tickets.js
function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed too long ago to reopen');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  }
  return updated;
}
```

```js
// src/portal.js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

Notes on the design:

- `reopenByCustomer` takes the *acting* customer's id as an explicit
  parameter, separate from the ticket's own `customer_id`. This mirrors the
  agent path, where `by: agent:${agentId}` names the agent who performed the
  action, not `t.assignee_id`. See Q1/Q2.
- `purged: false` is set unconditionally on every reopen, whether or not the
  ticket was actually purged — see Q3, the non-negotiable part of this spec.
- The notify guard (`if (t.assignee_id)`) mirrors how `reopenTicket` already
  avoids calling `notifyAgent` with no agent (`src/notify.js:7` throws on a
  falsy id).
- `portal.reply` is left untouched — it still throws on any closed ticket.
  Reopening is a deliberate, separate action, not a side effect of replying.

## Open questions (answered inline, per the user's instruction)

**Q1 — Can any customer in the ticket's organisation reopen it, or only the
one who originally opened it?**
Recommendation: any customer in the org. `t.customer_id` is never checked
anywhere else in `portal.js` — `getMyTicket` and `reply` only check
`org_id` (`src/portal.js:11-12`, `21-27`). Restricting reopen to the
original opener would be a new, inconsistent rule for this one action.

**Q2 — Whose id goes in the notification's `by:` field — the ticket's
original `customer_id`, or the id of whoever clicks "reopen"?**
Recommendation: the acting customer's id, passed explicitly as
`customerId`. Since Q1 allows any org customer to act, and the actor may
differ from the ticket's original `customer_id`, using `t.customer_id`
would misattribute the action. This exactly mirrors the agent path, where
`by: agent:${agentId}` is the performer, not `t.assignee_id`.

**Q3 — The purge job (`src/jobs/purge-closed.js:13`) treats `purged` as a
one-way latch (`if (t.purged) continue`). What happens to that flag on
reopen?**
Recommendation: reset `purged: false` unconditionally, every time, even if
it was never `true`. This is not a style choice — if a ticket is reopened,
closed again, and purged again, a stale `purged: true` left over from the
first cycle would make the job skip it forever, silently keeping
conversation text past the 7-day retention policy
(`src/jobs/purge-closed.js:2-4`'s stated legal reason). Acceptance
criterion #7 below exists specifically to catch a regression here.

**Q4 — The purge window (`KEEP_DAYS = 7`) is shorter than the proposed
14-day reopen window. A ticket can legally be reopened after its messages
are already purged — is that acceptable, or should one of the two windows
change?**
Recommendation: acceptable as-is; don't widen `KEEP_DAYS` to cover reopens.
`KEEP_DAYS` is an unrelated legal-retention control, not a feature of this
change. A ticket reopened after purge simply starts its new conversation
with no prior message history — the ticket row itself (subject, dates, org)
is never deleted, so nothing about the reopen fails.

## Assumptions

- The reopen window is 14 days, strictly less-than, measured from
  `closed_at` to `now` — matching the "within 14 days" wording literally.
  Confidence: high (this is what was asked; no project convention to look
  up).
- A non-empty message is required to reopen, same as opening a new ticket
  requires a body (`src/tickets.js:21`). Confidence: high — mirrors
  existing create-ticket shape, and "reopen" implies telling the agent why.
- Reopening sets status to `open` (not `pending`), matching what both
  existing reopen paths already do (`reopenTicket`, `portal.reply` on a
  resolved ticket). Confidence: high.
- No SLA reset and no cap on how many times a ticket can be reopened.
  Confidence: medium — reasonable default for v1, but worth a product
  decision if reopen abuse becomes a real pattern. Not asked as one of the
  four questions above since it doesn't block building this.

## Acceptance criteria

1. `reopenByCustomer` throws `cannot reopen a ${status} ticket` for any
   status other than `closed` (mirrors the existing error wording style).
2. `reopenByCustomer` throws when `now - closed_at >= 14 days`; succeeds at
   exactly `now - closed_at < 14 days`.
3. `reopenByCustomer` throws when `message` is empty or whitespace-only.
4. On success: `status` → `open`, `resolved_at` → `null`, `closed_at` →
   `null`, `purged` → `false`, and the message is appended as a customer
   message.
5. On success, if `assignee_id` is set, `notifyAgent` is called once with
   `{ type: 'ticket_reopened', ticketId, by: 'customer:<customerId>' }`; if
   `assignee_id` is null, no notification is attempted (and no error).
6. `portal.reopen` returns `null` when the ticket belongs to a different
   organisation than `customer.orgId`, without revealing whether the ticket
   exists.
7. Regression for the purge latch: a ticket that is reopened, closed again,
   and left 7+ days past its *new* `closed_at` has its messages deleted by
   `purgeClosed` on the next run — i.e. a ticket purged once can be purged
   again after a second close. This is the test that would fail if `purged`
   were reset conditionally instead of unconditionally.
8. The existing agent-only `reopenTicket` behavior and
   `test/tickets.test.js:34-41`'s exact error-message assertions are
   unchanged.

## Out of scope

- SLA recalculation on reopen.
- Limiting how many times a ticket can be reopened.
- Changing `KEEP_DAYS` or the purge job's own logic (only the `purged` flag
  reset on the ticket touches that job).
- Any portal UI work — this spec covers the `tickets.js`/`portal.js`
  business logic only.
