# Spec: customer reopens a closed ticket from the portal

Status: **draft, written while the requester was away — not yet reviewed.** Every
"Open question" below carries the answer the request asked us to assume and build
from; none of it is confirmed.

## Request, restated

Customers keep asking to reopen a ticket themselves after it's been closed,
instead of filing a new one. We're adding: a portal customer can reopen their
own ticket within 14 days of it being closed, and the assigned agent is
notified when that happens.

In this codebase's glossary (`docs/glossary.md:12`), **closed is currently
defined as final**: "A closed ticket is never changed again. If the customer
comes back, they start a new ticket." This feature changes that rule for the
first 14 days after closing. The glossary needs a matching edit (see
Acceptance Criteria).

## What already exists

- `tickets.reopenTicket(store, id, agentId)` (`src/tickets.js:38-44`) — an
  **agent-only** reopen, and only from `resolved`, not `closed`. It throws on
  anything else (`cannot reopen a ${status} ticket`), notifies the previous
  assignee if a different agent reopened it, and is pinned by exact-message
  test assertions (`test/tickets.test.js:34-41`). This spec does not touch it.
- `portal.reply(store, customer, id, body)` (`src/portal.js:21-28`) — already
  flips `resolved`/`pending` back to `open` as a side effect of answering. It
  throws on a `closed` ticket today (`this ticket is closed; please open a new
  one`, `src/portal.js:24`) — that throw stays; reopening is a separate,
  deliberate action, not something `reply` starts doing for closed tickets.
- No customer-facing reopen of any kind exists yet. This is new.

## Touchpoints

- `src/tickets.js:4` — `STATUS` enum, `HOUR` constant (no `DAY` constant yet).
- `src/portal.js:1-18` — org-scoping pattern to follow (`getMyTicket`,
  `openTicket`).
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`, throws if
  `agentId` is falsy.
- `src/jobs/purge-closed.js:10-20` — nightly job; `if (t.purged) continue`
  (line 13) makes `purged` a **one-way latch**. This is the one correctness
  trap in this feature (see Acceptance Criteria #6).
- `src/jobs/close-resolved.js:8-16` — sets `closed_at` on close; the field
  this feature's 14-day window measures from.
- `docs/glossary.md:12` — the "closed is final" line that needs updating.
- `test/tickets.test.js` — existing reopen/closed-ticket assertions that must
  keep passing unchanged.

## Open questions

Four questions changed the design enough to need a call; each is answered
with the recommendation and reasoning, and the build should proceed on these
answers.

1. **Does reopening require a message from the customer, or is a bare status
   flip enough?**
   **Recommendation: require a non-empty message.** A reopen with no text
   leaves the agent with a notification and no new information — worse than
   today's "file a new ticket," which at least comes with a fresh body. This
   also matches the shape `portal.reply` already uses (a message accompanies
   every customer-initiated state change).

2. **What status does the ticket land in — `open` (ready for an agent) or
   `pending` (waiting on the customer)?**
   **Recommendation: `open`.** Every existing path that puts a ticket back in
   motion — `tickets.reopenTicket` (agent) and `portal.reply` on a
   resolved/pending ticket — lands on `open`. A reopened-from-closed ticket
   should follow the same convention rather than introduce a new one.

3. **Should reopening be capped (max reopens, a cooldown) or reset the SLA due
   time?**
   **Recommendation: no cap, no SLA reset, for v1.** Nothing in the request
   asks for either, the existing `sla_due_at` is left untouched by every other
   state change in this codebase, and a cap/SLA policy is easy to add later
   without touching the reopen path itself. Tracked as an assumption below,
   not built.

4. **The purge job deletes a closed ticket's messages 7 days after close
   (`KEEP_DAYS`, `src/jobs/purge-closed.js:7`), and the reopen window is 14
   days — so a ticket can be reopened after its history is already gone. Do
   we still allow the reopen?**
   **Recommendation: yes.** The ticket row is deliberately kept after purge
   "for reporting" (`src/jobs/purge-closed.js:2-4`); reopening it just resumes
   that row. The customer sees a ticket with no prior messages plus their new
   one — that's an acceptable, visible consequence of the retention policy,
   not a reason to block the reopen.

## Assumptions (not asked, because the code or an existing convention already answers them)

- **Window math: calendar days, strict less-than, measured off `closed_at`.**
  High confidence — this mirrors the two existing nightly jobs exactly
  (`QUIET_DAYS`/`DAY` in `close-resolved.js:5-6`, `KEEP_DAYS`/`DAY` in
  `purge-closed.js:7-8`, both using `now - t < N * DAY`). Reopening is allowed
  while `now - closed_at < 14 * DAY`; at exactly 14 days it's refused.
- **Notification reuses the existing `ticket_reopened` event type**, with
  `by: customer:<id>` instead of `by: agent:<id>`. High confidence — the agent
  path already encodes the actor this way (`src/tickets.js:42`); a second
  event type for the same fact would just be a second thing to keep in sync.
- **If the ticket has no assignee (`assignee_id` is `null`), skip
  notification silently** rather than calling `notifyAgent`, which throws on a
  falsy agent id (`src/notify.js:7`). High confidence — an unassigned ticket
  has no one to tell; this mirrors `reopenTicket`'s own guard
  (`if (t.assignee_id && ...)`, `src/tickets.js:42`), just without the
  "different agent" half of that condition (there's no acting agent here).
- **No new `DAY` constant duplicated a third time.** `src/tickets.js` only
  defines `HOUR` today; both job files redefine `DAY` locally. This feature
  adds `const DAY = 24 * HOUR;` once in `tickets.js` and the new code uses it,
  rather than inlining the literal again.

## Edge cases

| Case | Handling |
|---|---|
| Ticket is not `closed` (open/pending/resolved) | Reject — same "cannot reopen a `<status>` ticket" style error as the existing agent-side `reopenTicket`. |
| Exactly 14 days, or more, since `closed_at` | Reject — window check is strict `<` (see Assumptions). |
| Customer doesn't own the ticket (wrong org) | Not found — mirror `portal.getMyTicket`'s `null`-on-wrong-org behavior (`src/portal.js:11-13`), not a thrown error, so the portal can't be used to probe other orgs' ticket ids. |
| Empty/whitespace-only message | Reject — same "non-empty" requirement as any other customer message. |
| Ticket has no assignee | Reopen succeeds; no notification sent (see Assumptions). |
| Ticket was already purged (messages deleted) | Reopen succeeds; customer sees the ticket with zero prior messages plus their new one (see Open question 4). |
| Reopen → sits open/resolved again → closes again → purges again | Must purge again. This is the one correctness-critical case: `purgeClosed` skips any ticket with `purged: true` forever (`src/jobs/purge-closed.js:13`). Reopening **must** reset `purged` to `false`, even if it was already `true`, or that ticket's messages become permanently unpurgeable on the next cycle — a retention-policy violation, not a style choice. Covered by Acceptance Criterion #6. |
| Two reopen requests race on the same ticket | Out of scope for v1 — same as every other mutation in this codebase; `store.updateTicket` has no optimistic lock today, so this feature introduces no new exposure. |

## Design

Add to `src/tickets.js`:

- `const DAY = 24 * HOUR;`
- `reopenByCustomer(store, id, message, { now = new Date() } = {})` — pure
  business rule, no org check (that's `portal`'s job, same split as
  `createTicket`/`openTicket`):
  - throw if `t.status !== STATUS.CLOSED` (`cannot reopen a <status> ticket`,
    matching `reopenTicket`'s message style)
  - throw if `now - closed_at >= 14 * DAY`
  - throw if `message` is empty/whitespace-only
  - `store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() })`
  - `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null, purged: false })`
  - if `t.assignee_id`, `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` })`
  - return the updated ticket

Add to `src/portal.js`:

- `reopen(store, customer, id, message, { now = new Date() } = {})` —
  org-scoping wrapper mirroring `openTicket`/`getMyTicket`: look up the
  ticket, return `null` if it doesn't belong to `customer.orgId`, otherwise
  call `tickets.reopenByCustomer(store, id, message, { now })` and return the
  result via `getMyTicket` (so the caller gets `messages` back too, same
  shape as every other portal read).

`docs/glossary.md:12` — append a clause to the `closed` bullet: "...closed.
The customer can still reopen it themselves within 14 days of closing; after
that, it's final and they start a new ticket."

## Acceptance criteria

1. A customer can reopen their own `closed` ticket within 14 days of
   `closed_at`, given a non-empty message; the ticket's status becomes
   `open`.
2. Reopening at or past 14 days from `closed_at` throws and changes nothing.
3. Reopening a ticket that isn't `closed` (open/pending/resolved) throws,
   unchanged from today's agent-side behavior pattern.
4. Reopening with an empty or whitespace-only message throws and changes
   nothing.
5. A customer cannot reopen a ticket belonging to another organisation
   (`portal.reopen` returns `null`, same as `getMyTicket`).
6. **Reopen → close again → purge again deletes messages a second time.**
   Explicitly test: create, resolve, close, purge (messages gone, `purged:
   true`), reopen, resolve, close again, purge again — the second purge must
   delete the new messages, proving `purged` was reset to `false` on reopen.
7. Reopening a ticket with an assignee queues one `ticket_reopened`
   notification to that assignee, with `by: customer:<id>`.
8. Reopening a ticket with no assignee succeeds and queues no notification.
9. All existing tests in `test/tickets.test.js` keep passing unchanged,
   including the two that pin `reopenTicket`'s closed/open error messages
   (lines 34-41).
10. `docs/glossary.md`'s `closed` bullet reflects the 14-day reopen window.

## Out of scope (v1)

- Any cap on number of reopens, or a cooldown between them.
- Resetting or recalculating `sla_due_at` on reopen.
- A new/second notification event type — reuses `ticket_reopened`.
- Changing `tickets.reopenTicket` (agent path) or `portal.reply` in any way.
- Concurrent-reopen locking.
