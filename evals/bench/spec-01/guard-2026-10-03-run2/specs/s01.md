# Spec: customer reopens a closed ticket from the portal

Status: **draft, awaiting review** — written while the requester was away; all
open questions below were answered by recommendation rather than live, per
their explicit instruction. Not implemented.

## Restatement

Request, in the customer-support-request's own words: "let a customer reopen
a closed ticket from the portal within 14 days of it being closed, and notify
the assigned agent when they do."

Technical reading: add a portal-facing action that moves a ticket from
`closed` back to `open` when (a) the acting customer's organisation owns the
ticket, (b) fewer than 14 days have passed since `closed_at`, and (c) the
customer supplies a message. On success, notify the ticket's assignee (if
any) the same way the existing agent-side reopen does. No other restatement
needed — the two readings match.

## Open questions, answered by recommendation

Each question below would normally be asked live; since the requester is
unavailable, it's answered with the recommended choice, and the rest of this
spec is built on that choice.

**Q1. Which customers can reopen a ticket — only the one who originally
opened it, or anyone in the same organisation?**
Recommend: anyone in the same organisation. This mirrors every existing
portal function's scoping, which checks `org_id` only and never
`customer_id` (`src/portal.js:11-12, 21-27`) — nothing today restricts an
action to the original opener, and support teams generally want any
teammate to continue a ticket.

**Q2. Does "14 days" count from when the ticket was closed, or from when it
was resolved (which can be up to 3 days earlier, per `close-resolved.js`)?**
Recommend: from `closed_at`. That's the field the request names ("within 14
days of it being **closed**"), and it's the field the customer actually sees
change.

**Q3. Is the boundary inclusive or exclusive — can a ticket be reopened on
exactly day 14?**
Recommend: exclusive at the far edge — allowed while `now - closed_at < 14
days`, forbidden at exactly 14 days or more. This matches the strict `<`
comparisons the nightly jobs already use for similar windows
(`close-resolved.js:11`, `purge-closed.js:14`), so the codebase stays
consistent about how it treats "N days" windows.

**Q4. Does reopening require a message, and if so, is it just a note for the
agent or does it become part of the ticket thread?**
Recommend: require a non-empty message and store it as a real customer
message via `store.addMessage`, the same mechanism `portal.reply` uses
(`src/portal.js:25`). This gives the agent context for *why* it reopened and
guarantees the reopened ticket has at least one message even when its prior
history was purged (Q6).

**Q5. What happens to `resolved_at` and `closed_at` on reopen?**
Recommend: clear both to `null`, matching how a ticket that's actually open
has no resolve/close timestamps, and how the agent-side `reopenTicket`
already clears `resolved_at` (`src/tickets.js:41`).

**Q6. The nightly purge job deletes a closed ticket's messages after only 7
days (`KEEP_DAYS`, `purge-closed.js:7`) — shorter than the proposed 14-day
reopen window. Should a ticket be reopenable after its messages are already
purged? Should the purge window widen to cover 14 days instead?**
Recommend: allow reopening a purged ticket — it simply starts with no prior
history (the new required message becomes its first entry). Don't widen
`KEEP_DAYS`: it's a legal-retention control, unrelated to this feature, and
stretching it to match the reopen window would weaken that policy for every
closed ticket, not just reopened ones.

**Q7. `purgeClosed` treats `purged` as a one-way latch (`purge-closed.js:13`)
— a ticket purged once is skipped on every later run. If a purged ticket is
reopened and later closed again, should it become eligible for purging a
second time?**
Recommend: yes, unconditionally reset `purged` to `false` on every reopen.
Without this, a reopen → reply → re-close cycle produces new message
content that the purge job will silently never delete, breaking the 7-day
retention policy the job exists to enforce. **This is the one
correctness-critical detail in this feature** — see acceptance criterion 8.

**Q8. Should the notification reuse the existing `ticket_reopened` event
type (today only emitted by the agent-side reopen), or get a new type?**
Recommend: reuse `ticket_reopened`, distinguishing the actor through the
existing `by` field convention — `by: agent:<id>` today, `by:
customer:<actingCustomerId>` here — rather than teaching agent-facing
tooling a second event type for the same thing (mirrors `src/tickets.js:42`).

**Q9. Should the notification fire when the ticket has no assigned agent?**
Recommend: no, skip silently. `notifyAgent` throws on a falsy agent id
(`src/notify.js:7`); the agent-side reopen already guards this by checking
`t.assignee_id` first (`src/tickets.js:42`).

**Q10. Should reopening reset the SLA due time, or cap how many times a
ticket can be reopened?**
Recommend: no to both, for v1. Nothing in the request asks for either, and
each adds real scope (SLA recomputation rules, abuse limits) with no stated
need.

## Design

Add one business-rule function and one portal wrapper, following the
existing split between `src/tickets.js` (rules) and `src/portal.js`
(org-scoped access to those rules).

**`src/tickets.js`** — add `const DAY = 24 * HOUR;` near the existing `HOUR`
constant (line 6), and:

```js
const REOPEN_WINDOW_DAYS = 14;

// A customer takes a closed ticket back, within the reopen window, with a message for the agent.
function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket was closed more than 14 days ago and can no longer be reopened');
  }
  const updated = store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null, purged: false });
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  if (t.assignee_id) notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  return updated;
}
```

Export it alongside the existing functions. The agent-only `reopenTicket`
(resolved → open) is untouched — it's a different action pinned by its own
tests (`test/tickets.test.js:34-41`).

**`src/portal.js`** — add, mirroring `openTicket`/`getMyTicket`'s org check:

```js
const { STATUS, createTicket, reopenByCustomer } = require('./tickets');

function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = store.getTicket(id);
  if (!t || t.org_id !== customer.orgId) return null;
  reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

Returns the full ticket-with-messages shape (like `reply` does), since a
reopen also adds a message. No change to `reply`'s behavior: it keeps
throwing on every closed ticket (`src/portal.js:24`) — reopening is a
separate, deliberate action, not a side effect of replying.

**`docs/glossary.md`** — update the "closed" bullet (line 12) from "A closed
ticket is never changed again" to note the 14-day customer reopen window.

## Edge cases

1. **Empty or whitespace-only message** → throws, ticket unchanged.
2. **Ticket not closed** (open/pending/resolved) → throws `cannot reopen a
   ${status} ticket`, ticket unchanged. Reuses the exact phrasing the
   agent-side function already uses, for consistency.
3. **Exactly on the 14-day boundary** → rejected (strict `<`, see Q3).
4. **Different organisation** → `portal.reopen` returns `null`, same as
   `getMyTicket`/`openTicket` on a cross-org lookup; ticket untouched.
5. **No assignee** (`assignee_id` is `null`) → reopen still succeeds; no
   notification is sent (would otherwise throw inside `notifyAgent`).
6. **Ticket already purged** (closed 7+ days ago, `purged: true`, no
   messages) but still inside the 14-day window → reopen succeeds; the
   ticket starts with only the new message. See Q6.
7. **Reopen → reply → re-close → re-purge** → because `purged` resets to
   `false` on reopen, the second `purgeClosed` run deletes the new messages
   as expected. Without the reset, this is a silent retention-policy
   violation. See Q7 and acceptance criterion 8.
8. **A customer other than the original opener, same organisation** →
   allowed (see Q1).
9. **Concurrent reopen attempts on the same ticket** → out of scope; the
   store has no transaction/locking primitive today and no other function in
   this codebase handles concurrent writes to one ticket, so this feature
   doesn't introduce a new gap.

## Assumptions

- **High confidence** — "14 days" means 14 days from `closed_at` (Q2).
- **High confidence** — a message is required and is stored as a real
  ticket message, not just metadata on the notification (Q4).
- **High confidence** — no SLA reset, no reopen-count cap, for v1 (Q10).
- **Medium confidence** — any customer in the ticket's organisation may
  reopen it, not just the original opener (Q1).
- **Medium confidence** — a purged ticket may still be reopened within the
  window, starting with empty history, rather than being blocked or having
  the purge window widened to match (Q6).
- **Medium confidence** — the 14-day boundary is exclusive at the far edge
  (Q3) — "within 14 days" is colloquially ambiguous about the exact edge,
  so this is the item most likely to get corrected on review.

## Acceptance criteria

1. Reopening a closed ticket less than 14 days after `closed_at` succeeds:
   status → `open`, `resolved_at` → `null`, `closed_at` → `null`, `purged` →
   `false`.
2. Reopening a ticket closed 14 days or more ago throws, and the ticket is
   unchanged.
3. Reopening a ticket that is not closed (open/pending/resolved) throws
   `cannot reopen a ${status} ticket`, and the ticket is unchanged.
4. Reopening with an empty or whitespace-only message throws, and the ticket
   is unchanged.
5. A successful reopen appends the message to the ticket's messages, visible
   via `portal.getMyTicket(...).messages`.
6. A successful reopen notifies the assigned agent exactly once, with
   `{ type: 'ticket_reopened', by: 'customer:<id>' }`, when `assignee_id` is
   set; sends no notification when it is `null`.
7. `portal.reopen` returns `null`, without changing the ticket, when the
   ticket belongs to a different organisation than the acting customer.
8. **Regression test for the purge latch:** a ticket closed, purged
   (`purged: true`, messages deleted), reopened within the 14-day window,
   replied to, re-closed, and left untouched for 7+ more days is purged
   again by a second `purgeClosed` run — proving the reopen reset `purged`
   to `false`.
9. The existing agent-only `reopenTicket` is unchanged, and
   `test/tickets.test.js:34-41` still passes without modification.
10. `docs/glossary.md`'s "closed" bullet reflects the new 14-day customer
    reopen window.
