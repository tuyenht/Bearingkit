# Spec: customer reopen of a closed ticket

Status: draft, awaiting review. Written while the requester was unavailable;
the open questions below are answered with a recommendation rather than left
blocking, per their instruction. Not implemented yet.

## Restatement

Today, once a ticket is `closed` it is final (`docs/glossary.md`): the
customer cannot answer it (`portal.reply` throws), and the only "reopen" path
is agent-side, and only from `resolved` (`tickets.reopenTicket`). Customers
have asked to be able to reopen a ticket they can see as `closed` themselves,
from the portal, as long as it hasn't been closed too long ago. When they do,
the agent who owns the ticket should hear about it, the same way an agent
hears about an agent-side reopen today.

## Touchpoints

- `src/tickets.js` — add the business-rule function.
- `src/portal.js` — add the org-scoped wrapper the portal UI calls.
- `src/notify.js` — reused as-is, no change.
- `src/jobs/purge-closed.js` — reused as-is, no change, but its one-way
  `purged` latch is the main hazard this feature touches (see Design).
- `docs/glossary.md` — "closed: final" is no longer quite true; update it.
- `test/tickets.test.js` — new tests.

## Design

**`tickets.reopenByCustomer(store, id, customerId, message, { now = new Date() } = {})`**

- Throws if the ticket isn't `closed` (mirrors `reopenTicket`'s
  `cannot reopen a ${t.status} ticket`).
- Throws if `now` is 14 or more days past `t.closed_at` (strict `<` on the
  window, matching `closeResolved`/`purgeClosed`'s existing
  `now - at < N * DAY` style).
- Throws if `message` is empty/whitespace-only — a reopen without saying why
  isn't useful to the agent picking it back up.
- On success: sets `status: 'open'`, clears `resolved_at` and `closed_at`
  (both — a reopened ticket is not "resolved N days ago", it's freshly open),
  appends `message` as a customer message (`store.addMessage`, `from:
  'customer'`), and **unconditionally resets `purged: false`**.
- Notifies the assignee if one exists: `notifyAgent(store, t.assignee_id,
  { type: 'ticket_reopened', ticketId: id, by: 'customer:' + customerId })`.
  Skipped silently if `assignee_id` is null — `notifyAgent` throws on a null
  agent, and an unassigned closed ticket is a real case (nobody to notify).
- Takes `customerId` as an explicit argument (the *acting* customer, not
  read off the ticket) for the same reason `reopenTicket` takes `agentId`
  explicitly rather than using `t.assignee_id`: the actor performing the
  action and the ticket's original owner can differ.

**`portal.reopen(store, customer, id, message, { now = new Date() } = {})`**

- Looks the ticket up with `getMyTicket` semantics (org-scoped); returns
  `null` if it's not found or not this customer's org — same pattern as
  every other `portal.js` function.
- Delegates to `tickets.reopenByCustomer(store, id, customer.id, message,
  { now })` and returns the refreshed ticket (with messages), like
  `portal.reply` does.
- Not restricted to "only the customer who originally opened it" — no
  existing `portal.js` function checks `customer_id`, only `org_id`
  (`getMyTicket`, `reply`). A reopen by any customer in the same org is
  consistent with how the rest of the portal already treats "who can act
  on this ticket."

**Left alone on purpose:**

- `tickets.reopenTicket` (agent-side, resolved→open) — untouched. It has its
  own exact-message test assertions already (`test/tickets.test.js:34-41`),
  and conflating it with the customer path would mean teaching one function
  two different starting-status rules.
- `portal.reply` — keeps throwing on a closed ticket. Reopening is a
  deliberate, separate action (with its own message and notification), not
  a side effect of replying.

## Open questions (answered by recommendation; not yet confirmed)

**Q1. Can any customer in the org reopen, or only the one who opened it?**
Recommendation: any customer in the ticket's org, matching `reply`'s and
`getMyTicket`'s existing org-only scoping. Keeps the rule consistent across
the portal rather than adding a one-off ownership check found nowhere else
in `portal.js`.

**Q2. What does the notification's `by:` field carry for a customer actor?**
Recommendation: `customer:<customerId>`, where `customerId` is the customer
who performed the reopen (an explicit parameter), not `t.customer_id` off
the ticket. Mirrors the existing agent path, which stamps `by:
agent:${agentId}` for the agent *performing* the reopen, not
`t.assignee_id`.

**Q3. A ticket can be reopened after its messages were already purged
(`KEEP_DAYS = 7` <  the proposed 14-day window) — allow it?**
Recommendation: yes. The reopened ticket just starts with no prior message
history beyond the one new message the customer is sending now; the ticket
row itself (subject, dates, org) was never deleted, only its messages. Don't
widen `KEEP_DAYS` to cover the reopen window — that constant is a
legal-retention control (`purge-closed.js`'s comment: "Legal asked for
this"), unrelated to how long a customer gets to reopen.

**Q4. What happens to the `purged` flag if a ticket gets reopened, closed
again, and purged again?**
Recommendation: `reopenByCustomer` unconditionally resets `purged: false`,
even if the ticket wasn't purged yet. Without this, a ticket purged once
would never purge again after a second close (`purgeClosed`'s `if
(t.purged) continue` is a one-way latch), silently retaining conversation
text past the 7-day legal limit on every subsequent cycle. This is the one
item in this spec that isn't a style choice — see Acceptance Criteria #6.

## Edge cases

- Ticket not `closed` (open/pending/resolved) → throws, same message shape
  as `reopenTicket`.
- Exactly 14 days since `closed_at` → rejected (strict `<`, not `<=`),
  consistent with how the other two day-window jobs in this codebase round.
- Empty or whitespace-only message → throws.
- No assignee (`assignee_id` is `null`) → reopen succeeds, no notification
  sent.
- Ticket already purged (`purged: true`, messages gone) → reopen still
  succeeds; the one new message is the only history going forward.
- Reopen → close → purge → reopen again → close → purge again: the second
  purge must delete the (new) messages, not skip because `purged` was never
  cleared.

## Assumptions

- "Notify the assigned agent" means the existing `notifyAgent` queue
  (`src/notify.js`), reusing the `ticket_reopened` event type rather than
  introducing a new one — the agent-side path already uses that type, and
  the distinction (customer vs. agent action) lives in `by:`, not in the
  event type.
- No SLA reset and no cap on how many times a ticket can be reopened — out
  of scope for v1 unless the customer-facing ask grows to need it.
- "14 days" is calendar time from `closed_at`, not business days — matches
  how `QUIET_DAYS`/`KEEP_DAYS` are already computed elsewhere in this
  codebase (plain `Date` arithmetic, no business-day calendar exists here).

## Out of scope (v1)

- SLA re-calculation on reopen.
- Limiting how many times a ticket may be reopened.
- Notifying anyone other than the current assignee (e.g. a team or queue).
- Changing the agent-side `reopenTicket` behavior or its resolved-only rule.

## Acceptance criteria

1. A customer can reopen their org's `closed` ticket within 14 days of
   `closed_at`, given a non-empty message.
2. Reopening sets status to `open`, clears `resolved_at` and `closed_at`,
   and appends the message as a customer message.
3. Reopening a ticket closed ≥ 14 days ago throws.
4. Reopening a non-closed ticket throws (mirroring `reopenTicket`'s
   per-status error message).
5. Reopening with an empty/whitespace message throws.
6. Reopening clears `purged`, so a reopen → close → purge → reopen → close
   → purge cycle purges messages both times (not just the first).
7. If `assignee_id` is set, the assignee is notified with event type
   `ticket_reopened` and `by: customer:<actingCustomerId>`; if unassigned,
   no notification is sent and nothing throws.
8. A customer from a different org gets the same "not found" behavior as
   every other cross-org portal call (`null`, not a thrown error).
9. `docs/glossary.md`'s "closed: final" bullet is updated to describe the
   14-day reopen window.
