# Spec: customer self-service ticket reopen

Status: **draft, awaiting review** — written while the user was away; every
open question below is answered with a recommendation rather than asked live
(per their instruction).

## 1. Restated request

> "Let a customer reopen a closed ticket from the portal within 14 days of it
> being closed, and notify the assigned agent when they do."

In the project's own words (`docs/glossary.md:12`): **closed is "final. A
closed ticket is never changed again. If the customer comes back, they start
a new ticket."** This request is a deliberate exception to that rule, scoped
narrowly: a customer may reopen *their own* ticket, *only* within 14 days of
`closed_at`, through a new, explicit portal action — not as a side effect of
replying. `docs/glossary.md` needs a one-line amendment once this ships (see
§7).

Today the only reopen path is agent-side and resolved-only:
`tickets.reopenTicket(store, id, agentId)` at `src/tickets.js:38-44` throws
unless `t.status === STATUS.RESOLVED` (`src/tickets.js:40`). The portal layer
(`src/portal.js`) has no reopen function at all; `portal.reply` explicitly
throws on a closed ticket (`src/portal.js:24`, `'this ticket is closed;
please open a new one'`). This is new functionality, not a bug fix.

## 3. Edge cases

1. **Ticket is open/pending/resolved, not closed.** Rejected — same shape as
   the existing `cannot reopen a ${t.status} ticket` guard
   (`src/tickets.js:40`), reused verbatim.
2. **Ticket closed 14+ days ago.** Rejected. Window is `now - closed_at <
   14 days`, strict `<`, checked against `closed_at` (field set at
   `src/jobs/close-resolved.js:12`).
3. **Ticket closed and already purged.** Messages are gone
   (`src/jobs/purge-closed.js:15`, `deleteMessages`), but the row survives
   as a summary (purge keeps `subject`, dates, org — confirmed at
   `test/tickets.test.js:69`), and `purgeClosed` runs at day 7
   (`KEEP_DAYS = 7`, `src/jobs/purge-closed.js:7`), inside the 14-day reopen
   window. Reopen must still succeed on a purged ticket — the customer gets
   an empty thread but can post a fresh message (enforced by requiring a
   non-empty message, see Q3). This is also why the `purged` flag must be
   reset (§4, acceptance criterion #6) — see Q4.
4. **Not the customer's own ticket / wrong org.** Mirror
   `portal.getMyTicket`'s org check (`src/portal.js:12`): return `null`,
   don't throw, don't leak existence of another org's ticket.
5. **Ticket has no assignee (`assignee_id: null`).** `notifyAgent` throws if
   called with no agent id (`src/notify.js:7`). The agent-side `reopenTicket`
   already guards this with `if (t.assignee_id && ...)`
   (`src/tickets.js:42`); reuse the same guard — reopening an unassigned
   ticket must not throw, it should just skip notification.
6. **Empty/whitespace-only message.** Rejected — see Q3 below; required
   because `purgeClosed` may already have deleted the ticket's messages
   (edge case 3), so a message-less reopen could hand the agent a
   zero-content ticket to work from.
7. **Concurrent reopen + nightly purge job.** Both operations go through
   `store.updateTicket`, which is a synchronous, in-process `Map` mutation
   today (`src/store.js:19-24`) — no race inside a single process. The spec
   doesn't change that; it's a pre-existing property of `store.js`, not a new
   risk introduced here.
8. **Customer reopens, then reopens again later (same ticket re-closed in
   between).** No special case needed — each reopen is independent, checked
   against whatever `closed_at` is current at call time.

## 4. Embedded Q&A (recommendations applied below)

**Q1. Does reopening put the ticket back to `open`, same as the agent-side
reopen and as `portal.reply` on a resolved ticket?**
Recommendation: **yes**, target status `STATUS.OPEN`, consistent with both
existing reopen paths (`src/tickets.js:41`, `src/portal.js:26`). *Applied.*

**Q2. Does reopening clear `resolved_at`, `closed_at`, or both?**
Recommendation (medium confidence — flagging for explicit sign-off):
**clear both to `null`.** The agent-side reopen clears only `resolved_at`
(`src/tickets.js:41`) because a resolved ticket never had `closed_at` set in
the first place. A *closed* ticket has both set
(`src/jobs/close-resolved.js:12`), and leaving `closed_at` stale would make
`purgeClosed`'s window math (`src/jobs/purge-closed.js:14`) compare against
a closed date that's no longer true. Clear both. *Applied, flagged for
review.*

**Q3. Does the customer have to supply a message to reopen, or is a bare
"reopen" action enough?**
Recommendation: **require a non-empty message**, same shape as
`portal.reply`'s `body` parameter. Reason: `purgeClosed` deletes a closed
ticket's messages after 7 days (`src/jobs/purge-closed.js:7`), but the
reopen window is 14 days — a message-less reopen after day 7 would hand the
agent a ticket with no content at all. Requiring a message guarantees the
agent always has something to act on. *Applied.*

**Q4. What happens to the `purged` flag if a customer reopens a ticket whose
messages were already deleted by the nightly job?**
Recommendation: **unconditionally reset `purged: false`** on every
successful reopen, regardless of its current value. This is the one
non-negotiable item in this spec (acceptance criterion #6, §6): `purgeClosed`
treats `purged` as a one-way latch (`src/jobs/purge-closed.js:13`,
`if (t.purged) continue`). If a reopened-then-re-closed ticket still carries
`purged: true` from its first cycle, the *second* close+purge cycle's new
messages are silently kept forever — the exact "we do not keep conversation
text of finished tickets longer than a week" rule the purge job exists to
enforce (`src/jobs/purge-closed.js:3-4`) would be violated. Not a style
choice. *Applied, non-negotiable.*

**Q5. Does the assigned agent get a new notification event type, or does
this reuse the existing `ticket_reopened` event from the agent-side reopen?**
Recommendation: **new event type, `ticket_reopened_by_customer`**, distinct
from the agent-side `ticket_reopened` (`src/tickets.js:42`). Reason:
downstream notification rendering (email templates, agent inbox) will likely
want to say "the customer reopened this" vs. "a teammate reopened this"
without inspecting the `by` field's string shape. Cheap to add now, awkward
to retrofit once templates exist. *Applied.*

**Q6. Should there be a limit on how many times a ticket can be reopened, or
an SLA-timer reset on reopen?**
Recommendation: **no limit, no SLA reset**, matching the agent-side reopen
(`src/tickets.js:38-44`, which does neither). Nothing in the request asks
for either, and adding scope here would be speculative. *Applied — explicit
non-goal, see §7.*

## 5. Assumptions

| # | Assumption | Confidence |
|---|---|---|
| 1 | "14 days" means wall-clock days from `closed_at`, strict `<`, computed the same way `purgeClosed`/`closeResolved` already do (`now.getTime() - new Date(x).getTime() < N * DAY`) | High — matches existing pattern at `src/jobs/purge-closed.js:14` and `src/jobs/close-resolved.js:11` exactly |
| 2 | "Notify the assigned agent" means the existing `notify.notifyAgent` queue (`src/notify.js:6-9`), not a new channel | High — it's the only notification mechanism in the codebase |
| 3 | The reopen is a distinct portal action, not folded into `portal.reply` | High — `portal.reply` already has a defined, different behavior for closed tickets (throw) that other code may depend on; changing it would be a breaking behavior change outside this request's scope |
| 4 | `src/tickets.js` has no `DAY` constant today, only `HOUR` (`src/tickets.js:6`); both job files redefine `DAY` locally rather than importing one | High — confirmed by reading all three files; this spec adds `const DAY = 24 * HOUR;` to `tickets.js` once rather than inlining the literal a third time |
| 5 | `resolved_by` (set at `src/tickets.js:34`) is left untouched on reopen | Medium — not asked about; agent-side reopen doesn't touch it either (`src/tickets.js:41`), so this just preserves existing behavior; low risk either way since nothing reads it downstream in this codebase |

## 7. Acceptance criteria

1. `tickets.reopenByCustomer(store, id, message, { now })` throws
   `cannot reopen a ${status} ticket` for any status other than `closed`
   (mirrors the message shape pinned by `test/tickets.test.js:37,40` for the
   agent-side function, but is a separate function — existing tests and
   messages are untouched).
2. `reopenByCustomer` throws on a `closed` ticket when
   `now - closed_at >= 14 days` (boundary: exactly 14 days is rejected,
   13 days 23:59:59 is accepted).
3. `reopenByCustomer` throws on an empty or whitespace-only `message`.
4. On success: ticket status becomes `open`; `resolved_at` and `closed_at`
   are both set to `null`; the customer's message is appended via
   `store.addMessage`.
5. On success, if `assignee_id` is non-null: `notify.notifyAgent` is called
   once with event `{ type: 'ticket_reopened_by_customer', ticketId, by:
   'customer:<customerId>' }`. If `assignee_id` is null: no notification
   call is made (must not throw).
6. **Non-negotiable:** on success, `purged` is unconditionally reset to
   `false`, whether it was previously `true` or `false`. A regression test
   must cover the full cycle: close → purge (messages deleted, `purged:
   true`) → customer reopen → resolve → close again → purge again — and
   assert the *second* purge actually deletes the new cycle's messages
   (i.e. the latch doesn't stay stuck from the first cycle).
7. `portal.reopen(store, customer, id, message, { now })` returns `null`
   (does not throw) when the ticket doesn't belong to `customer.orgId`,
   mirroring `portal.getMyTicket`.
8. `portal.reopen` on a valid, in-window, closed ticket in the customer's
   org returns the updated ticket (status `open`), via the same shape as
   `portal.getMyTicket`'s return (ticket + `messages`).
9. Existing tests in `test/tickets.test.js` (lines 16-70) pass unmodified —
   in particular the exact-message assertions at lines 37 and 40 for the
   agent-side `reopenTicket`, which this work does not touch.
10. `docs/glossary.md`'s "closed" definition (line 12) is amended to state
    the 14-day customer-reopen exception, so the glossary stays accurate
    rather than describing a now-partially-false absolute rule.
