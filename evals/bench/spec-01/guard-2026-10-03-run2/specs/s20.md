# Spec: customer self-service ticket reopen

**Status:** draft, awaiting review. Written while the requester was unavailable — every
open question below is answered with a recommendation rather than left blocking, per
their instruction. Treat the recommendations as proposed, not approved.

## Goal

A customer asked for this repeatedly: let them reopen their own **closed** ticket from
the portal within 14 days of it being closed, without having to open a brand-new ticket
and re-explain themselves. The assigned agent should be notified when this happens, the
same way they're already notified when an agent reopens a resolved ticket.

## Current behavior (for context)

- `closed` is documented as final (`docs/glossary.md:12`): "A closed ticket is never
  changed again. If the customer comes back, they start a new ticket." This spec changes
  that rule for the portal path only.
- `tickets.reopenTicket(store, id, agentId)` (`src/tickets.js:38-44`) already lets an
  **agent** reopen a **resolved** ticket (not closed) and notifies the assignee. That
  function is untouched by this spec — it's pinned by exact-message test assertions
  (`test/tickets.test.js:34-41`).
- `portal.reply` (`src/portal.js:21-28`) throws on a closed ticket today — that's
  unchanged; reopening is a new, separate action, not a side effect of replying.
- `src/jobs/purge-closed.js` deletes a closed ticket's messages 7 days after `closed_at`
  (`KEEP_DAYS = 7`), for legal retention reasons, and sets `purged: true` so it never
  purges twice. The ticket row (subject, dates, org) survives.

## Open questions and recommendations

**Q1: Who can reopen — only the original opener, or anyone in the org?**
*Recommendation: anyone in the ticket's organisation.* `portal.getMyTicket` and
`portal.reply` already scope by `org_id` only, never `customer_id` (`src/portal.js:11-12,
21-27`) — a ticket is treated as the org's, not one customer's. Reopen should match that
existing precedent rather than introduce a new, narrower rule.

**Q2: What's the reopen window, and measured from what?**
*Recommendation: 14 days, measured from `closed_at`, strictly less-than (so day 14 is the
last valid day, day 15 is not).* That's what was asked for; `closed_at` is already
stamped by `close-resolved.js:12` and is the natural anchor.

**Q3: Does the customer need to say anything, or can they just flip the status?**
*Recommendation: require a non-empty message, added as the first message of the reopened
conversation.* A bare status flip with no new information doesn't give the agent
anything to act on. This also mirrors `createTicket`, which always seeds the ticket with
a body.

**Q4: What status does the ticket land in, and what fields does it clear?**
*Recommendation: `open` (not `pending`), clearing both `resolved_at` and `closed_at`.*
`open` matches what both existing reopen paths (agent reopen, customer reply-to-resolved)
already do. Clearing `closed_at` is required so the ticket no longer reads as closed;
clearing `resolved_at` too keeps it consistent with the agent-reopen path, which clears
the same field.

**Q5: What event type and actor does the agent notification use?**
*Recommendation: reuse the existing `ticket_reopened` event type*, with
`by: customer:<id>` instead of `by: agent:<id>`. The agent-reopen path already encodes
*who* did it via the `by` field rather than via a separate event type
(`src/tickets.js:42`) — a new event type would be an inconsistent way to say the same
thing. Skip the notification silently if `assignee_id` is null, matching the fact that
`notifyAgent` throws on a missing agent id (`src/notify.js:7`) and an unassigned ticket
has no one to tell.

**Q6: A ticket's messages may already be purged by the time it's reopened — is that OK?**
This is a real gap worth calling out explicitly: `KEEP_DAYS` (purge, 7 days) is shorter
than the proposed reopen window (14 days), so a ticket can legally still be reopened
after its conversation history is already gone.
*Recommendation: allow it.* The reopened ticket simply starts from an empty message
list plus the customer's new message — same as any ticket, just with no prior history
visible. Don't widen `KEEP_DAYS` to cover the full reopen window: it exists for legal
retention reasons unrelated to this feature, and extending retention to accommodate a
UX convenience is the wrong direction to resolve the conflict. This should be mentioned
to support/success so they're not surprised when a 10-day-old reopened ticket has no
history.

**Q7: Does reopening reset anything else — SLA due time, a reopen counter, escalation?**
*Recommendation: no.* Out of scope for v1. `sla_due_at` stays as originally set; there's
no existing precedent for a reopen limit or counter, and adding one isn't part of what
was asked for.

**Q8: Should this interact with the purge job's one-way `purged` flag?**
Yes, and this is the one answer here that isn't a judgment call. `purgeClosed`
(`src/jobs/purge-closed.js:13`) uses `if (t.purged) continue` as a one-way latch so a
ticket is never purged twice. If reopen doesn't reset `purged` back to `false`, a
ticket that's reopened and later closed and purged *again* will be silently skipped by
the purge job the second time — its messages from the second conversation would never
be deleted, which is a retention-policy violation, not a style nitpick. **Reopening must
unconditionally set `purged: false`**, even if the ticket was never purged in the first
place.

## Design

### `tickets.js`

Add a `DAY` constant (the module currently only defines `HOUR`; both job files already
redefine their own `DAY` locally — adding it here instead of inlining a third copy):

```js
const DAY = 24 * HOUR;
```

Add a new exported function, parallel to the existing `reopenTicket` but for the
customer path. It takes the acting customer's id as an explicit argument — mirroring how
`reopenTicket(store, id, agentId)` takes the *acting* agent's id rather than reading
`t.assignee_id` — because per Q1 the acting customer and the ticket's original
`customer_id` can differ:

```js
function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= 14 * DAY) {
    throw new Error('this ticket closed too long ago to reopen');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');

  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false, // one-way latch in purge-closed.js — must be able to purge again next cycle
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  }
  return updated;
}
```

### `portal.js`

An org-scoping wrapper mirroring `openTicket`/`getMyTicket` — returns `null` if the
ticket isn't in the customer's org, otherwise delegates:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, customer.id, message, { now });
}
```

### `docs/glossary.md`

Update the `closed` bullet (currently line 12) to carve out the new exception, e.g.:

> **closed**: final. A closed ticket is never changed again, except that the customer
> may reopen it from the portal within 14 days of closing by sending a new message. If
> they come back after that window, they start a new ticket.

## Out of scope (v1)

- Resetting or extending `sla_due_at` on reopen.
- A limit on how many times a ticket can be reopened.
- Widening `KEEP_DAYS` to cover the full reopen window (see Q6).
- Any change to the agent-only `reopenTicket` or to `portal.reply`'s closed-ticket
  behavior.

## Acceptance criteria

1. A customer can reopen a closed ticket within 14 days of `closed_at`; the ticket's
   status becomes `open`, `resolved_at` and `closed_at` are both cleared, and the
   message is appended.
2. Reopening after the 14-day window throws and leaves the ticket unchanged.
3. Reopening without a message (missing or empty/whitespace) throws.
4. Reopening a non-closed ticket (open/pending/resolved) throws, matching the existing
   `reopenTicket` error message style (`cannot reopen a ${status} ticket`).
5. If the ticket has an assignee, reopening queues exactly one notification to that
   agent with `event.type === 'ticket_reopened'` and `event.by === 'customer:<id>'`; if
   unassigned, no notification is queued and nothing throws.
6. **Regression guard for the `purged` latch:** close a ticket, let it purge, reopen it,
   close and purge it again — the second purge must delete the ticket's (new) messages
   too. This catches the one-way-latch bug described in Q8 if `purged: false` is ever
   dropped from the reopen patch.
7. A customer from a different organisation cannot reopen the ticket (`portal.reopen`
   returns `null`, same as `getMyTicket` on a foreign ticket).
8. The existing `reopenTicket` (agent path, resolved-only) and `portal.reply`
   (closed-throws) tests are unaffected.
