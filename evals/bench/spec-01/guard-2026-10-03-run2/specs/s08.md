# Spec: customer reopens a closed ticket from the portal

Status: **draft — awaiting review**. Written while the user was away; every
question below is answered with a recommendation rather than asked live, per
the user's instruction. Nothing in this spec has been implemented.

## 1. Restatement

**Request, in the user's words:** "let a customer reopen a closed ticket from
the portal within 14 days of it being closed, and notify the assigned agent
when they do."

**Technical reading:** add a new customer-facing portal action,
`portal.reopen`, that moves a ticket with `status: 'closed'` back to
`status: 'open'`, but only when called within 14 days of that ticket's
`closed_at`, and that queues a notification to the ticket's `assignee_id` via
the existing `notify.notifyAgent`.

**Where the request's wording and the project's glossary differ:**
`docs/glossary.md:12` currently defines closed as "final. A closed ticket is
never changed again. If the customer comes back, they start a new ticket."
This feature is a deliberate, scoped exception to that rule, not a
contradiction of it — the glossary needs a one-line amendment (see §3,
touchpoint 4) so "closed is final" and "reopenable for 14 days" don't read as
contradictory to the next person who touches this code.

There is already a *reopen* concept in the codebase, but it is a different
feature: `tickets.reopenTicket(store, id, agentId)` (`src/tickets.js:38-44`)
lets an **agent** take a **resolved** ticket back to open. It does not touch
`closed` tickets and is not reachable from the portal. This spec adds a
second, separate reopen path for customers acting on `closed` tickets; it
does not change the agent path.

## 2. Touchpoints

- `src/tickets.js:38-44` — existing agent-only `reopenTicket`, resolved→open
  only. Left untouched. New function added alongside it.
- `src/portal.js:21-28` — existing `reply`, which already throws on a closed
  ticket (`'this ticket is closed; please open a new one'`) and already
  re-opens a `resolved`/`pending` ticket as a side effect of answering. New
  function added alongside it, not folded into `reply` (see §4, design note).
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)` queues a
  notification; throws if `agentId` is falsy, so callers must guard.
- `src/jobs/purge-closed.js:7,13` — `KEEP_DAYS = 7` and the `if (t.purged)
  continue` one-way latch. Directly relevant: see §5 edge cases and the open
  question in §6.4.
- `test/tickets.test.js:34-41` — pins the agent-path `reopenTicket`'s exact
  error strings (`/cannot reopen a open ticket/`, `/cannot reopen a closed
  ticket/`). The new customer path must not change these.
- `docs/glossary.md:12` — the "closed: final" bullet needs a one-line
  amendment.

No existing reopen-from-portal code or prior attempt was found; this is new.

## 3. Design

**New function in `src/tickets.js`:**

```js
reopenByCustomer(store, id, customerId, message, { now = new Date() } = {})
```

Business rules:
- Throws if the ticket is not `closed` (any other status is rejected —
  mirrors the agent path's status guard).
- Throws if `now` is 14 or more days past `closed_at` (strict `<`, so a
  ticket closed at `T` is reopenable up to but not including `T + 14d`).
- Throws if `message` is empty or whitespace-only (see §6 assumptions — this
  is a product default, not something the user asked for explicitly).
- On success: sets `status: 'open'`, clears **both** `resolved_at` and
  `closed_at` (a reopened ticket is not "resolved as of some past time" or
  "closed" any more — leaving either stale would corrupt `closeResolved`'s
  and `purgeClosed`'s date math if the ticket is resolved and closed again
  later), and resets `purged: false` unconditionally (see §6.3 — this is the
  one non-negotiable part of the design).
- Appends the customer's message as a normal message
  (`store.addMessage(id, { from: 'customer', body: message, at:
  now.toISOString() })`), the same way `reply` does, so the agent sees why it
  was reopened.
- Notifies the assignee: `if (t.assignee_id) notifyAgent(store, t.assignee_id,
  { type: 'ticket_reopened', ticketId: id, by: \`customer:${customerId}\` })`
  — skipped silently when unassigned, because `notifyAgent` throws on a null
  agent (`src/notify.js:7`). Reuses the existing `ticket_reopened` event type
  rather than inventing a new one; the `by` field is how the agent path
  already distinguishes actors (`by: agent:${agentId}`), so `by:
  customer:<id>` extends the same convention instead of adding a new field.

`customerId` is the **acting** customer's id, passed explicitly by the
caller — not read off `t.customer_id`. This matters because, per §3's org
wrapper below, any customer in the ticket's organisation may act, so the
acting customer and the ticket's original opener can differ.

Adds `const DAY = 24 * HOUR;` next to the existing `HOUR` constant
(`src/tickets.js:6`) rather than inlining the 14-day literal or copying the
pattern the two job files already use of each redefining `DAY` locally.

**New function in `src/portal.js`:**

```js
reopen(store, customer, id, message, { now = new Date() } = {})
```

A thin org-scoping wrapper, following the exact shape of `openTicket` /
`getMyTicket`: looks up the ticket, returns `null` if it doesn't exist or
`t.org_id !== customer.orgId`, otherwise calls
`tickets.reopenByCustomer(store, id, customer.id, message, { now })` and
returns the refreshed ticket (with `messages`, like `getMyTicket` does).

No check against `t.customer_id` — mirrors `reply` and `getMyTicket`, which
scope by organisation only, never by "only the customer who opened it"
(`src/portal.js:11-12`, `21-27`). Scoping any tighter would be new, unrequested
behavior inconsistent with how every other portal action already works.

**Not changed:**
- `tickets.reopenTicket` (agent path) — untouched, still resolved-only.
- `portal.reply` — still throws on every closed ticket. Reopening is a
  separate, deliberate action a customer takes on purpose, not a side effect
  of trying to send a message to a closed ticket.
- `jobs/purge-closed.js`, `jobs/close-resolved.js` — untouched; `purged` is
  reset *by the reopen function*, not by the purge job.

## 4. Edge cases

1. **Empty or missing reopen message.** Rejected: `reopenByCustomer` throws
   (`'a reopen message is required'`). See §6 assumptions — existing
   `reply`/`addMessage` don't validate emptiness anywhere else, so this is a
   new rule introduced specifically here, not a precedent extension.
2. **Wrong organisation.** A customer from another org calling
   `portal.reopen` on a ticket that isn't theirs gets `null`, exactly like
   `getMyTicket`/`reply` today (`src/portal.js:11-12`). No error, no leak of
   whether the ticket exists.
3. **Ticket not closed.** `open`/`pending`/`resolved` tickets are rejected by
   `reopenByCustomer`'s status guard (distinct error message from the
   agent-path one, so the two pinned test assertions in
   `test/tickets.test.js:37,40` are unaffected).
4. **Exactly at the 14-day boundary.** `now - closed_at == 14 * DAY` is
   rejected (strict `<`), so "within 14 days" reads as a 14×24h window that
   does not include the 14-day mark itself. Needs its own boundary test
   (`at(14)` closed → reject, `at(13.999...)` → accept), mirroring how
   `test/tickets.test.js:52-59` already tests `closeResolved`'s own boundary.
5. **Ticket already purged before the 14-day window closes.** `KEEP_DAYS = 7`
   (`src/jobs/purge-closed.js:7`) is shorter than 14 days, so a ticket's
   messages can legally be purged before its reopen window expires. Decided
   in §6.4: allowed — the reopened ticket just starts with no prior message
   history, consistent with the row otherwise staying as a summary after
   purge (`src/jobs/purge-closed.js:2-4`).
6. **Reopen → re-close → re-purge cycle.** Without resetting `purged: false`
   on reopen, a ticket purged once would have `purged: true` forever
   (`src/jobs/purge-closed.js:13`'s one-way latch), so a *second*
   close-and-purge cycle would silently never delete the new round of
   messages — a retention-policy violation. §6.3 makes the reset
   unconditional; acceptance criterion #6 below exists specifically to catch
   a regression here.
7. **Unassigned ticket.** `notifyAgent` throws on a null agent
   (`src/notify.js:7`), so the notify call is guarded with `if
   (t.assignee_id)`, matching how the agent path already guards
   (`src/tickets.js:42`, though for a different reason — skipping
   self-notification).

## 5. Open questions (answered by recommendation — user unavailable)

1. **Can any customer in the ticket's organisation reopen it, or only the
   one who originally opened it?**
   **Recommendation: any customer in the org**, same as every other portal
   action (`reply`, `getMyTicket`). Adding a tighter "only the original
   opener" rule would be new, unrequested scoping inconsistent with the rest
   of the portal, and the org is already the codebase's unit of access
   control (`docs/glossary.md:18`).
2. **When notifying the agent, whose id goes in the `by:` field — the acting
   customer, or the ticket's original `customer_id`?**
   **Recommendation: the acting customer's id**, passed as an explicit
   parameter (mirrors the agent path, which stamps the *performing* agent's
   id via its own `agentId` parameter, not `t.assignee_id`). Since question 1
   allows any org customer to act, these two ids can differ, so
   `t.customer_id` would sometimes be the wrong value.
3. **Must reopening reset the ticket's `purged` flag?**
   **Recommendation: yes, unconditionally**, even if it was never purged.
   This is the one place in this feature with real consequences if gotten
   wrong (see edge case 6) — it is a retention-policy correctness issue, not
   a style preference.
4. **`purge-closed`'s `KEEP_DAYS` (7 days) is shorter than the proposed
   reopen window (14 days) — should they be reconciled?**
   **Recommendation: no — leave `KEEP_DAYS` at 7.** It is a legal-retention
   control unrelated to this feature's purpose; widening it to cover 14 days
   would extend how long conversation text is kept, which needs its own
   sign-off, not a side effect of this spec. Instead, accept that a reopened
   ticket may have already lost its prior messages (edge case 5).

## 6. Assumptions

- **A non-empty message is required to reopen.** *(medium confidence)*
  Not stated in the request. Recommended because it gives the notified agent
  a reason the ticket came back, and because the portal UI will need
  something to submit anyway; if the user disagrees this is a one-line
  removal of the check.
- **The window is computed against `closed_at`, not `resolved_at` or
  `created_at`.** *(high confidence)* — "within 14 days of it being closed"
  in the request maps directly to the `closed_at` field that already exists
  (`src/tickets.js:18`, set by `src/jobs/close-resolved.js:12`).
- **"Notify the assigned agent" means the existing `notify.notifyAgent`
  queue, reusing the `ticket_reopened` event type.** *(high confidence)* —
  the agent-side reopen path already establishes this exact mechanism and
  event type for the same real-world action (an agent or customer bringing a
  closed/resolved ticket back); inventing a second event type for the same
  meaning would fragment anything that consumes these events later.
- **No SLA reset and no limit on how many times a ticket can be reopened.**
  *(medium confidence)* — out of scope per the request as stated; flagged
  explicitly in §8 in case that's wrong.

  `bk-protocol/references/gate-patterns.md`), and no COUNCIL content pattern

  (`src/jobs/purge-closed.js:13`). bk-protocol's hot-path list includes "data
  deletion"; this change doesn't delete data itself, but it directly controls
  whether a *later* deletion job runs on a given ticket again. Getting the
  reset wrong is silent (no test fails today) and has a real retention-policy
  consequence, so it should get a second set of eyes even though no gate
  pattern forces that.
- **Touches 4 files** (`src/tickets.js`, `src/portal.js`,
  `docs/glossary.md`, `test/tickets.test.js`) — one past this project's
  informal 3-file ACT/bk-build threshold, so the next step is a plan, not a

## 8. Acceptance criteria

1. `tickets.reopenByCustomer` rejects a ticket whose status is `open`,
   `pending`, or `resolved` (distinct error message from the agent-path
   `reopenTicket`'s, so neither of `test/tickets.test.js:37,40` changes).
2. Calling it on a `closed` ticket less than 14 days past `closed_at` sets
   `status: 'open'`, `resolved_at: null`, `closed_at: null`.
3. Calling it exactly 14 days (or more) past `closed_at` throws and makes no
   change to the ticket.
4. Calling it with an empty or whitespace-only message throws and makes no
   change to the ticket.
5. On success, the customer's message is appended
   (`store.getMessages(id)` grows by one, `from: 'customer'`).
6. On success, if `assignee_id` is set, exactly one notification is queued
   with `type: 'ticket_reopened'` and `by: customer:<actingCustomerId>`; if
   `assignee_id` is null, no notification is queued and nothing throws.
7. On success, `purged` is reset to `false` — including when it was already
   `true`. Regression test: close → purge (messages gone, `purged: true`) →
   reopen within the window → close again → purge again (`now` ≥
   `closed_at + KEEP_DAYS`) → messages added after reopen are deleted and
   `purged` is `true` again. This is the test that would have caught the
   one-way-latch bug if the reset were missing or conditional.
8. `portal.reopen` returns `null` (and makes no change) when the ticket
   belongs to a different organisation, same as `getMyTicket`.
9. `portal.reopen` on a ticket in the caller's own organisation succeeds
   even when the caller is not the ticket's original `customer_id`
   (confirms question 1's recommendation).
10. `docs/glossary.md`'s "closed" bullet reflects the 14-day reopen
    exception and no longer reads as "never changed again" without
    qualification.

## 9. Out of scope (v1)

- Resetting or extending the SLA due time on reopen.
- Limiting how many times a ticket can be reopened.
- Letting a customer reopen from anywhere other than the portal (e.g. by
  replying to a closed-ticket notification email).
- Reconciling `KEEP_DAYS` with the 14-day reopen window (§5, question 4).
- Any UI/portal-frontend work — this spec covers the `tickets.js`/`portal.js`
  functions and their contract only.
