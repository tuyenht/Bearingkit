# Spec: customer reopens a closed ticket from the portal

Status: **draft — written while the user was away; questions answered with recommendations below, not confirmed yet.**

## Request

> Let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do.

Technical reading: add a customer-facing action, parallel to the existing agent-only `reopenTicket` (`src/tickets.js:38`), that moves a ticket from `closed` back to `open` when called by the ticket's own customer, but only while `now - closed_at < 14 days`, and queues a notification to the ticket's assignee (if any) the same way the agent path already does.

This touches the project's glossary definition of "closed" (`docs/glossary.md:12`: *"closed: final. ... If the customer comes back, they start a new ticket."*). That line becomes conditionally true — final **unless** reopened within the window — and the glossary needs updating in the same change, since it's the kind of discrepancy this spec would otherwise introduce on day one.

## Touchpoints

- `src/tickets.js:38-44` — `reopenTicket(store, id, agentId)`: the existing agent-only reopen, resolved-only, throws on anything else. New customer path is a sibling function, not a modification of this one (it's pinned by exact-message assertions in `test/tickets.test.js:37,40`).
- `src/portal.js:21-28` — `reply(store, customer, id, body, { now })`: the closest existing precedent for a customer action that's org-scoped, requires a body, writes a message, and conditionally changes status. New `portal.reopen` follows the same shape.
- `src/portal.js:10-14` — `getMyTicket`: returns `null` for a wrong-org or missing ticket; reused for the same not-found/not-yours behavior here.
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`: throws if `agentId` is falsy, so any caller must skip the call when there's no assignee.
- `src/jobs/purge-closed.js:13` — `if (t.purged) continue;`: a one-way latch per ticket. This is the one correctness-critical touchpoint — see "The purge latch" below.
- `src/jobs/close-resolved.js` — unaffected directly, but relevant to edge case 7 below (a reopened-then-reresolved-then-closed ticket must close and purge correctly a second time).
- `docs/glossary.md:12` — the "closed is final" bullet needs a qualifying clause.
- `test/tickets.test.js` — new tests; existing tests (lines 34-41, 52-69) must keep passing unchanged.

No existing reopen-by-customer code was found; this is new.

## Design

Two new functions, mirroring how `createTicket`/`openTicket` and the business-rule/org-wrapper split already works elsewhere in this codebase:

**`src/tickets.js`: `reopenByCustomer(store, id, customerId, message, { now = new Date() } = {})`**
- Business rules only, no org check (matches `reopenTicket`, `resolveTicket`, `assignTicket` — org-scoping is the portal layer's job, not `tickets.js`'s).
- `mustGet` the ticket.
- Not closed → `throw new Error(\`cannot reopen a ${t.status} ticket\`)` (same message shape as the existing `reopenTicket` error).
- Closed more than 14 days ago (`now - closed_at >= 14 * DAY`, strict) → `throw new Error('this ticket closed more than 14 days ago; please open a new one')`.
- Empty/whitespace message → `throw new Error('a reopen needs a message')`.
- On success: append the message (`store.addMessage`, `from: 'customer'`, same shape `reply` already uses), then `store.updateTicket(id, { status: OPEN, resolved_at: null, closed_at: null, purged: false })`.
- `purged: false` is written **unconditionally**, whether or not the ticket was actually purged — see "The purge latch."
- If `t.assignee_id` is truthy, `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` })`. If falsy, skip the call entirely (calling `notifyAgent` with no agent throws).
- `tickets.js` currently defines `HOUR` but not `DAY` (both job files redefine `DAY` locally). This spec adds `const DAY = 24 * HOUR;` and `const REOPEN_WINDOW_DAYS = 14;` in `tickets.js` once, rather than inlining the literal a third time.

**`src/portal.js`: `reopen(store, customer, id, message, { now = new Date() } = {})`**
- `getMyTicket(store, customer, id)`; if `null` (wrong org or no such ticket), return `null` — no leak of whether the ticket exists, matching every other portal function.
- Otherwise delegate: `return reopenByCustomer(store, id, customer.id, message, { now })`, letting business-rule errors (wrong status, window expired, empty message) throw straight through, same as `reply` does today for the closed-ticket case.

Why a new function instead of extending `reopenTicket`: the agent path and the customer path have different source statuses (resolved vs. closed), different actors in the notification `by` field, and a time-window check that only applies to one of them. Folding them into one function would need a mode flag; two small functions are each readable without one.

Why reuse the `ticket_reopened` event type instead of a new one: the agent-triggered reopen already encodes the actor in `by: agent:<id>` (`src/tickets.js:42`); mirroring that with `by: customer:<id>` keeps one event type whose `by` field says who acted, rather than growing a parallel `ticket_reopened_by_customer` type for the same downstream consumer (the mail worker that drains the queue).

### The purge latch (the one thing that cannot be gotten wrong)

`purgeClosed` (`src/jobs/purge-closed.js:10-20`) runs nightly, deletes messages for closed tickets older than 7 days, and sets `purged: true` so it never touches that ticket again — a one-way latch, not an idempotent check of current state. A ticket's lifecycle can now be: closed → purged (day 7) → reopened (any day up to day 14) → resolved again → quiet 3 days → closed again (`closeResolved`) → eligible for purge again (day 7 after the *second* close). If `reopenByCustomer` left `purged: true` sitting on the row, the second `purgeClosed` pass would skip it forever at line 13, and the second close's messages — real customer conversation — would never be deleted. That's a retention-policy violation (`src/jobs/purge-closed.js:2-4` cites a 7-day-after-close legal requirement), not a style preference. Acceptance criterion 7 below exercises exactly this double cycle.

## Open questions (user unavailable — recommended answers applied below)

1. **Does reopening require the customer to say why, or is a bare status flip enough?** Recommend: **require a non-empty message**, stored as a normal customer message on the ticket (same as `reply`). An agent landing on a reopened ticket with zero new context is worse than requiring one sentence, and it reuses the existing message pipe rather than adding a separate "reason" field. *(Low cost either way; applied as a hard requirement below rather than optional.)*
2. **Should a ticket whose messages were already purged (closed 7-13 days ago) still be reopenable, given its history is gone?** Recommend: **yes, allow it.** The ticket row and its metadata survive purge by design (`src/jobs/purge-closed.js:2-4`); blocking reopen because history is gone would need a new "reopenable but historyless" state that nothing else in the system has. The customer's new message simply becomes the first message in a now-empty thread. No special-cased error or warning for v1.
3. **Does reopening reset the SLA due time or cap how many times a ticket can be reopened?** Recommend: **no to both**, for v1. The agent-side `reopenTicket` doesn't reset SLA either (`src/tickets.js:38-44` leaves `sla_due_at` untouched), so this stays consistent with existing behavior; a reopen cap is a product policy nobody has asked for yet (YAGNI).
4. **Same event type as the agent-triggered reopen, or a distinct one?** Recommend: **reuse `ticket_reopened`**, distinguished only by `by: customer:<id>` vs `by: agent:<id>`. One consumer (the mail worker draining `notify.js`'s queue) already branches on nothing but `by` being present in the template; a second event type would be a distinction without a behavioral difference.

No fifth question was dropped to make this cap — four was the full list.

## Assumptions

- **High confidence:** "within 14 days" means `now - closed_at < 14 days`, strict, mirroring how `purgeClosed` already computes its own 7-day window (`src/jobs/purge-closed.js:14`) — consistent with the codebase's existing elapsed-time convention rather than an inclusive/calendar-day count.
- **High confidence:** the target status after reopen is `open` (not `pending`), matching both the agent-side `reopenTicket` and what `reply` does when answering a resolved/pending ticket (`src/portal.js:26`) — `open` is this codebase's one "back in an agent's queue" state.
- **Medium confidence:** the customer-reopen message is attributed `from: 'customer'` with no distinct `reason` field — same shape `store.addMessage` already takes everywhere else (`src/portal.js:25`, `src/tickets.js:21`). Nothing in the schema (`src/store.js`) suggests a richer message shape is expected.
- **Medium confidence:** no UI/portal-frontend work is in scope — this repository has no UI layer (confirmed by `README.md`'s file list: store, tickets, portal, notify, two jobs — no views/templates/routes). This spec is the backend contract only.

## Edge cases

1. **Empty or whitespace-only message** → `reopenByCustomer` throws `'a reopen needs a message'`; ticket and notify queue untouched.
2. **Ticket not closed** (open, pending, or resolved) → throws `` `cannot reopen a ${status} ticket` ``; covers both "never was closed" and "someone already reopened it" (double-submit after the first succeeded).
3. **Exactly at the 14-day boundary** → `now - closed_at >= 14 * DAY` throws (strict `<` is the allowed side, matching assumption above); a ticket closed at `t0` is reopenable through `t0 + 14d - 1ms` and blocked at `t0 + 14d` exactly.
4. **Wrong organisation or nonexistent ticket id** → `portal.reopen` returns `null` via `getMyTicket`, same as every other portal function; no exception, no information leak about whether the id exists at all.
5. **No assignee (`assignee_id` is `null`)** → reopen still succeeds; `notifyAgent` is **not called** (it throws on a falsy agent id — calling it here would turn a successful reopen into a crash).
6. **Already-purged ticket within the window** (closed day 7-13, messages already deleted) → reopen succeeds; `purged` resets to `false`; the new message is the only entry in `getMessages`.
7. **Reopen → resolve → quiet 3 days → close → purge, a second time** → the critical regression case. `purged` must have been reset to `false` on reopen, or the second `purgeClosed` pass silently no-ops at `src/jobs/purge-closed.js:13` and the new conversation is never deleted — see "The purge latch" above.
8. **Concurrent double-reopen** (two requests racing on the same already-closed ticket) → the in-memory store (`src/store.js`) has no locking anywhere else in this codebase either; last `updateTicket` wins and at most one extra `notifyAgent` call is queued. Not fixed here — consistent with how every other mutation in this codebase already behaves, and adding locking for one action while the rest of the module has none would be inconsistent, not safer.

## Acceptance criteria

1. Given a closed ticket closed 1-13 days ago, `portal.reopen(store, customer, id, 'still broken', { now })` returns a ticket with `status: 'open'`, `resolved_at: null`, `closed_at: null`, `purged: false`, and the message is appended to `getMessages(id)`.
2. Given a closed ticket closed ≥14 days ago, `portal.reopen(...)` throws `/closed more than 14 days ago/`; the ticket is unchanged.
3. Given a ticket in `open`, `pending`, or `resolved` status, `portal.reopen(...)` throws `` /cannot reopen a (open|pending|resolved) ticket/ ``; the ticket is unchanged.
4. Given an empty string or whitespace-only message on an otherwise-reopenable ticket, `portal.reopen(...)` throws `/needs a message/`; the ticket is unchanged.
5. Given a ticket belonging to a different organisation (or a nonexistent id), `portal.reopen(...)` returns `null`; no throw, no notify-queue entry.
6. Given a closed, reopenable ticket with `assignee_id` set, `notify.drain()` after `portal.reopen(...)` contains exactly one entry: `{ to: 'agent:<assignee_id>', event: { type: 'ticket_reopened', by: 'customer:<customer.id>' } }`.
7. Given the same ticket with `assignee_id: null`, `portal.reopen(...)` succeeds and `notify.drain()` is empty.
8. Given a ticket closed, purged (`purgeClosed` run once), then reopened within the window, resolved again, closed again (`closeResolved`), and purged again — the second `purgeClosed` call returns the ticket's id and `getMessages(id)` is empty afterward (proves `purged` was reset to `false` on reopen, not left `true`).
9. Given a ticket closed, purged, then reopened within the remaining window (day 7-13), `getMessages(id)` immediately after reopen contains exactly the one new message.
10. All existing tests in `test/tickets.test.js` (lines 16-70) keep passing unchanged.
