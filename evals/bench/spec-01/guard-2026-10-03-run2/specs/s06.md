# Spec: customer self-service ticket reopen

Status: **draft — awaiting review**. Written while the requester was away;
all open questions below were answered with a recommendation rather than
asked live, per standing instruction.

## Restated request

Customers keep asking for this. In the portal, let a customer reopen a
ticket they own that is now `closed`, as long as it closed no more than 14
days ago. When they do, notify the agent the ticket is assigned to.

Technical reading: add a new portal-facing action, separate from the
existing agent-only `reopenTicket`, that is scoped to the customer's own
organisation, time-boxed off `closed_at`, and fires a notification event to
`assignee_id` if one exists.

## Design

Add two new functions, no changes to existing exported behavior:

**`tickets.reopenByCustomer(store, id, message, { now = new Date() } = {})`**
in `src/tickets.js` — the business rule layer, parallel to `resolveTicket`/
`reopenTicket`:
- Throws `no ticket ${id}` if missing (via existing `mustGet`).
- Throws if `t.status !== STATUS.CLOSED` (only closed tickets can be
  customer-reopened; open/pending/resolved already have other paths).
- Throws if `now - closed_at >= 14 days` (strict `<`, window closed on the
  boundary — see Q2 below for why 14 full days and not 15).
- Throws if `message` is empty/whitespace-only (see Q4 for why a message is
  required here but not elsewhere).
- Sets `status: STATUS.OPEN`, clears `resolved_at: null` **and**
  `closed_at: null`, resets `purged: false` (see Q6 — non-negotiable), adds
  the customer's message via `store.addMessage`.
- Notifies the assignee if `assignee_id` is set, using a distinct event type
  `ticket_reopened_by_customer` (not the agent-side `ticket_reopened`) so
  downstream notification rendering can tell who triggered it without
  inspecting `by`.
- Add `const DAY = 24 * HOUR;` to `src/tickets.js` rather than inlining the
  literal a third time (it's currently duplicated in both job files).

**`portal.reopen(store, customer, id, message, { now = new Date() } = {})`**
in `src/portal.js` — org-scoping wrapper, same shape as `openTicket`/
`getMyTicket`:
- Looks up via `getMyTicket`; returns `null` if the ticket doesn't exist or
  isn't the customer's org (mirrors existing convention — portal functions
  return `null`, they don't throw, on "not yours/not found").
- Otherwise delegates to `tickets.reopenByCustomer` and returns the refreshed
  ticket (with messages) via `getMyTicket`.

`portal.reply` is **not** changed: it keeps throwing on any closed ticket.
Reopening is a deliberate, separate action a customer takes, not a side
effect of trying to send a message to a dead ticket.

## Open questions, answered by recommendation

**Q1: Does "within 14 days of being closed" mean 14 days from `closed_at`,
or from when it was last touched/resolved?**
Recommendation: from `closed_at`. That's the field the request names
("closed"), it's the one already on the ticket row, and it's unambiguous —
`resolved_at` can predate `closed_at` by up to 3 quiet days (`close-resolved`
job) and using it would make the window inconsistently longer. *Confidence:
high.*

**Q2: Is the window inclusive or exclusive on day 14 — i.e. should a ticket
closed exactly 14×24h ago still be reopenable?**
Recommendation: exclusive (strict `<`), matching the existing style in both
nightly jobs (`close-resolved.js:11`, `purge-closed.js:14` both use strict
`<` against their windows). "Within 14 days" reads most naturally as "fewer
than 14 days have passed." *Confidence: medium — this is a product-feel call,
flag if the business actually wants day-14 inclusive.*

**Q3: Should the reopened ticket go to `open` or `pending` (i.e. does it
need to re-enter an agent's queue as fresh, or does it imply "waiting on
agent")?**
Recommendation: `open`, matching exactly what the agent-side `reopenTicket`
already does, and what `portal.reply` does when it reopens a resolved
ticket. Consistent with the glossary's definition of `open`: "waiting for an
agent." *Confidence: high.*

**Q4: Should the customer be required to say why/add a message when
reopening, or can they reopen with a bare click?**
Recommendation: require a non-empty message. Reasoning: `purgeClosed` deletes
a closed ticket's messages 7 days after close (`KEEP_DAYS = 7`,
`purge-closed.js:7`) — but the reopen window is 14 days. A ticket reopened
on day 8–14 would already have an empty message history; a mandatory reopen
message guarantees the agent has *something* to act on instead of an empty
ticket. *Confidence: medium — could instead allow an empty message and rely
on the agent asking follow-up; requiring one is the safer default.*

**Q5: Should reopening reset the SLA due time, or put the ticket at the back
of a queue differently than a normal open ticket?**
Recommendation: no SLA reset, no special queue treatment — it's a plain
`open` ticket like any other once reopened, same as the existing
agent-triggered reopen path does today (which also doesn't touch
`sla_due_at`). Introducing new SLA semantics for this one path would be
scope creep the request didn't ask for. *Confidence: high.*

**Q6: `purgeClosed` treats `purged` as a one-way latch — once true, always
skipped. If a ticket was already purged (closed 7+ days, reopened on day
8–14) and is later closed and purged again, must `purged` be reset on
reopen?**
Recommendation: yes, unconditionally reset `purged: false` on every
customer reopen, regardless of its current value. If not reset, a
purged-then-reopened-then-reclosed ticket would never have its second
round of messages purged — the nightly job skips it forever at
`purge-closed.js:13`. That's a silent retention-policy violation (the repo's
own comment at `purge-closed.js:3-4` cites a Legal requirement not to keep
closed-ticket text past a week), not just a bug. *Confidence: high — this is
the one item I'd flag as non-negotiable rather than a judgment call.*

**Q7: Does `docs/glossary.md`'s "closed: final... never changed again" line
need updating?**
Recommendation: yes, reword to note the 14-day customer-initiated exception,
otherwise the glossary actively contradicts shipped behavior. *Confidence:
high.*

## Edge cases

1. **Ticket already purged, still inside the 14-day window** (closed day 0,
   purged day 7, customer reopens day 10): allowed — purge only deletes
   messages, not the row or `closed_at`. Reopen succeeds with just the
   customer's new message as history; `purged` resets to `false` (Q6).
2. **Ticket closed more than 14 days ago**: reopen throws; portal should
   show "this ticket can no longer be reopened — please open a new one,"
   echoing the existing closed-ticket message in `portal.reply`.
3. **Ticket not closed (open/pending/resolved)**: reopen throws (wrong
   status) — this action is closed-only by design; use existing flows for
   other statuses.
4. **Ticket belongs to a different organisation**: `portal.reopen` returns
   `null` via `getMyTicket`'s existing org check — same as every other
   portal function, no new leak surface.
5. **Ticket has no assignee (`assignee_id === null`)**: skip notification
   silently — `notifyAgent` throws on a falsy agent id (`notify.js:7`), so
   the caller must check before calling it, same as the existing
   `reopenTicket` already does (`if (t.assignee_id && ...)`).
6. **Empty/whitespace-only reopen message**: rejected before any mutation
   (Q4) — no partial state change.
7. **Concurrent reopen + nightly purge race**: the nightly jobs and portal
   actions all run synchronously against the in-memory/Postgres store with
   no explicit locking elsewhere in this codebase, so this follows existing
   convention — not a new problem introduced by this feature. Out of scope.
8. **Ticket reopened, then closed and purged again inside the same 14-day
   epoch, then customer tries to reopen a second time**: second reopen is
   evaluated against the *new* `closed_at` from the second close — each
   close event starts its own fresh 14-day window. No cap on reopen count
   (see Out of scope).

## Assumptions

- The portal has an authenticated `customer` object with `.id` and `.orgId`
  already, matching every existing `portal.js` function's signature. *High.*
- "Notify the assigned agent" means enqueue via the existing
  `notify.notifyAgent` queue (consumed by a separate mail worker per
  `notify.js:2`) — not a new notification channel. *High.*
- No reopen-count limit and no SLA reset are in scope (Q5). *Medium —
  reasonable product default, but a business rule the requester may want to
  add later.*
- The 14-day window is a fixed constant, not per-org/per-plan configurable.
  Nothing in the current codebase (no config/settings table) suggests
  per-org variation exists elsewhere, so a flat constant matches existing
  patterns (`SLA_HOURS`, `KEEP_DAYS`, `QUIET_DAYS` are all flat constants).
  *High.*
- Customer-facing copy/wording for the portal UI is not specified here;
  this spec covers the backend contract only. *High.*

## Acceptance criteria

1. `tickets.reopenByCustomer` throws `no ticket ${id}` for an unknown id.
2. `tickets.reopenByCustomer` throws for a ticket not in `closed` status
   (open, pending, and resolved each throw).
3. `tickets.reopenByCustomer` succeeds for a ticket closed fewer than 14
   days ago (by `closed_at`) and throws for one closed 14 days or more ago
   (boundary itself throws — Q2).
4. `tickets.reopenByCustomer` throws on an empty or whitespace-only message
   and makes no state change in that case.
5. On success: `status` becomes `open`, `resolved_at` and `closed_at` both
   become `null`, the customer's message is appended, and the ticket is
   returned.
6. **Non-negotiable:** on success, `purged` is reset to `false`
   unconditionally — including when it was already `true`. A ticket that is
   reopened, re-closed, and left untouched for 7+ days again has its
   messages purged by a subsequent `purgeClosed` run (test this exact
   second-cycle case, not just the reset flag in isolation).
7. If `assignee_id` is set, `notify.notifyAgent` is called with a
   `ticket_reopened_by_customer` event; if `assignee_id` is `null`, no
   notification call is made and no error is thrown.
8. `portal.reopen` returns `null` (no throw) for a ticket belonging to a
   different organisation, and for a non-existent id.
9. The existing agent-only `reopenTicket` and its exact error-message
   assertions in `test/tickets.test.js:34-41` are unchanged and still pass.
10. `docs/glossary.md`'s "closed" definition is updated to reflect the new
    14-day customer-reopen exception.

## Out of scope

- Any UI/portal front-end work — backend contract only.
- Per-organisation or per-plan configurable reopen windows.
- A cap on how many times a ticket can be reopened.
- Resetting or extending the SLA due time on reopen.
- Changing `portal.reply`'s behavior on closed tickets.
- Changing the agent-only `reopenTicket` path in any way.
