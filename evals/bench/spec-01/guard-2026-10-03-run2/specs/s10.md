# Spec: customer self-service ticket reopen

## Request

Let a customer reopen their own **closed** ticket from the portal within 14
days of it being closed, and notify the assigned agent when they do.

Written while the requester was unavailable; the open questions below are
answered with a recommendation rather than asked live, per their request.
Review before implementation starts.

## Current behavior (verified against the live code)

- Statuses: `open`, `pending`, `resolved`, `closed` (`src/tickets.js:4`).
  Per `docs/glossary.md`, **closed is final** — "if the customer comes
  back, they start a new ticket." This spec changes that rule.
- `tickets.reopenTicket(store, id, agentId)` (`src/tickets.js:38-44`) is the
  only existing reopen path. It's **agent-only** and only accepts a
  `resolved` ticket (`cannot reopen a ${status} ticket` otherwise). It's
  pinned by exact-message assertions in `test/tickets.test.js:37,40` — not
  to be touched by this work.
- `portal.reply` (`src/portal.js:21-28`) throws `'this ticket is closed;
  please open a new one'` on a closed ticket, and reopens (to `open`) a
  `resolved`/`pending` ticket as a side effect of answering. Closed-ticket
  behavior here is unchanged by this spec — reopening stays a deliberate,
  separate action, not a reply side effect.
- `jobs/close-resolved.js` closes a `resolved` ticket 3 quiet days after
  `resolved_at`, setting `closed_at`.
- `jobs/purge-closed.js` deletes a closed ticket's messages 7 days after
  `closed_at` and sets `purged: true` — and that flag is a **one-way
  latch**: `if (t.purged) continue` (`src/jobs/purge-closed.js:13`). This
  matters directly for this feature (see Acceptance Criteria #6).
- `notify.notifyAgent(store, agentId, event)` throws if `agentId` is falsy
  (`src/notify.js:7`) — callers must not invoke it with no assignee.
- `src/tickets.js` defines `HOUR` but not `DAY`; `DAY` is currently
  redefined locally in each job file.

## Open questions, answered by recommendation

**1. What counts as "within 14 days of closed"?**
Recommendation: strictly less than 14×24h after `closed_at` (`now - closed_at < 14 days`), consistent with how the existing jobs compare elapsed time. On exactly day 14 the window has closed.

**2. What status does a reopened ticket land in?**
Recommendation: `open` — the same target status the existing agent-side and reply-side reopen paths use. No new status; the glossary's four statuses are unchanged.

**3. Which timestamps get cleared?**
Recommendation: both `resolved_at` and `closed_at` → `null`. `resolved_at` already gets cleared by every existing reopen path; `closed_at` must also clear since the ticket is no longer closed, and leaving a stale `closed_at` around would be a latent trap for any future code that keys off it. (Medium confidence — flag for explicit sign-off since it's not forced by any existing code path.)

**4. Is a message required to reopen?**
Recommendation: yes, require a non-empty message, and record it on the ticket as the customer's reopen message. The purge window (7 days) is shorter than the reopen window (14 days), so a ticket reopened on day 8–14 may have **no prior messages left** — an empty reopen would hand the agent a ticket with zero context.

**5. What happens to the `purged` flag?**
Recommendation: reopening unconditionally resets `purged` to `false`, regardless of its current value. This is the one non-negotiable part of the design: `purgeClosed`'s `if (t.purged) continue` is a one-way latch, so if reopen leaves `purged: true` untouched, a second close→purge cycle on the same ticket will silently skip deleting its new messages — a retention/legal violation per the rationale documented in `jobs/purge-closed.js:3-4`, not just a style nit.

**6. New notification event, or reuse the existing one?**
Recommendation: reuse the existing `ticket_reopened` event type, with `by: `customer:${customerId}`` as the discriminator — mirroring how the agent path already encodes the actor in `by` (`by: `agent:${agentId}``, `src/tickets.js:42`). Adding a second event type for the same underlying fact (ticket reopened) would duplicate what `by` already exists to express; a consumer that needs agent-vs-customer rendering parses the `by` prefix either way.

**7. What if the ticket has no assignee?**
Recommendation: skip notification silently. `notifyAgent` throws on a falsy `agentId` (`src/notify.js:7`), and there's no one to notify, so the reopen itself must still succeed.

**8. Does reopening reset the SLA due time?**
Recommendation: no. `sla_due_at` is about first response on the ticket's original lifecycle; nothing in the request asks for an SLA reset, and reopening isn't a new ticket. Out of scope unless asked for explicitly.

**9. Is there a limit on how many times a ticket can be reopened?**
Recommendation: no limit for v1. Add one later only if abuse is actually observed.

## Design

Add to **`src/tickets.js`**:
- `const DAY = 24 * HOUR;` and `const REOPEN_WINDOW_DAYS = 14;`
- `reopenByCustomer(store, id, message, { now = new Date() } = {})`:
  1. `mustGet` the ticket (throws `no ticket ${id}` if missing, matching every other function here).
  2. If `t.status !== STATUS.CLOSED`, throw (e.g. `'only a closed ticket can be reopened'` — deliberately a different message from the agent path's `cannot reopen a ${status} ticket`, since this is a different function with different rules, not a drop-in replacement).
  3. If `now - closed_at >= REOPEN_WINDOW_DAYS * DAY`, throw (e.g. `'too long since this ticket was closed to reopen it'`).
  4. If `message` is missing or blank after trim, throw (e.g. `'a message is required to reopen a ticket'`).
  5. `store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() })`.
  6. `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null, purged: false })`.
  7. If `t.assignee_id`, call `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${t.customer_id}` })`.
  8. Return the updated ticket.

Add to **`src/portal.js`**:
- `reopen(store, customer, id, message, { now = new Date() } = {})`: look up the ticket, return `null` if missing or `t.org_id !== customer.orgId` (mirrors `getMyTicket`'s org check exactly); otherwise call `tickets.reopenByCustomer` and return `getMyTicket(store, customer, id)`.

Update **`docs/glossary.md`**: the `closed` bullet changes from "final... they start a new ticket" to note the 14-day customer reopen window, so the glossary stays accurate.

Add to **`test/tickets.test.js`** (not written yet — listed for the implementation plan): happy path within window; rejection past 14 days; rejection on a non-closed ticket; rejection on empty message; cross-org reopen returns `null`; no-assignee reopen succeeds without notifying; **a reopen → re-close → re-purge cycle actually deletes the new messages the second time** (the direct test of acceptance criterion #6, since that's the one failure mode that's silent and easy to ship broken).

## Acceptance criteria

1. A customer can reopen their own closed ticket within 14 days of `closed_at` via `portal.reopen`.
2. Reopening sets `status` to `open`.
3. Reopening clears `resolved_at` and `closed_at` to `null`.
4. Reopening requires a non-empty message; the message is recorded as a new customer message on the ticket.
5. Reopening a ticket that isn't closed throws.
6. **Reopening unconditionally resets `purged` to `false`, even if the ticket was already purged** — verified by a test that purges, reopens, closes, and purges again, confirming the messages from the *second* cycle are actually deleted.
7. Reopening more than 14 days after `closed_at` throws.
8. Reopening a ticket belonging to a different organization returns `null` (no error), matching `getMyTicket`'s existing cross-org behavior.
9. If the ticket has an assignee, reopening queues a `ticket_reopened` notification to them with `by: customer:<id>`; if there's no assignee, no notification is queued and reopening still succeeds.
10. `portal.reply` and `tickets.reopenTicket` (the agent-only path) are unchanged — existing tests, including the pinned-message assertions at `test/tickets.test.js:37,40`, keep passing untouched.

## Out of scope

- Resetting or extending the SLA due time on reopen.
- A limit on how many times a ticket can be reopened.
- Any new ticket status (reopened tickets reuse `open`).
- Changing the 7-day purge window or the 3-day close-quiet window.
- Email/notification template copy — this spec only adds the queued event; rendering is unchanged.
