# Spec: customer-initiated ticket reopen (portal)

Status: **draft — awaiting review**. Written while the requester was unavailable; every open
question below was answered with a recommendation rather than asked live, per their instruction.
Nothing in this spec has been built yet.

## 1. Request, restated

**In the requester's words:** "Let a customer reopen a closed ticket from the portal within 14
days of it being closed, and notify the assigned agent when they do."

**Technical reading:** add a new portal-facing action, `portal.reopen`, that transitions a ticket
from `closed` back to `open` when called by a customer in that ticket's organisation, only if the
ticket's `closed_at` is less than 14 days in the past, and that triggers the existing agent
notification path (`notify.notifyAgent`) for the ticket's assignee. This is a new, separate action
— it is not a side effect of `portal.reply` (which keeps rejecting replies to closed tickets;
`portal.js:24`), and it is not the same code path as the agent-only `tickets.reopenTicket`
(`tickets.js:38`, resolved → open only).

The two readings agree; nothing in the request is ambiguous about the end-user behavior itself.
The open questions below are about implementation details the request doesn't specify.

## 2. Touchpoints (current code)

- `src/tickets.js:37-44` — `reopenTicket(store, id, agentId)`: the existing agent-side reopen,
  resolved-only, stays untouched.
- `src/tickets.js:4-6` — `STATUS`, `SLA_HOURS`, `HOUR`; only `HOUR` is defined here, not `DAY`
  (each job file redefines `DAY` locally: `src/jobs/close-resolved.js:6`,
  `src/jobs/purge-closed.js:8`).
- `src/portal.js:10-14` — `getMyTicket`: org-scoping pattern to mirror (`t.org_id !== customer.orgId
  → null`), not `t.customer_id` — a ticket's org, not its original opener, is the access boundary.
- `src/portal.js:21-28` — `reply`: closed tickets throw `'this ticket is closed; please open a new
  one'`; this must keep throwing — reopen is a deliberate separate action.
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`: throws if `agentId` is falsy, so any
  caller must guard against `assignee_id === null`.
- `src/jobs/purge-closed.js:7,13-14` — `KEEP_DAYS = 7`; `if (t.purged) continue` is a one-way latch
  that must be reset on reopen or a second purge cycle silently never runs.
- `src/jobs/close-resolved.js` — unaffected; included for the close→reopen→close round-trip this
  feature creates.
- `docs/glossary.md:12` — "closed: final... If the customer comes back, they start a new ticket."
  This sentence becomes false and needs an update.
- `test/tickets.test.js:34-41` — pins the agent-only `reopenTicket`'s exact error messages
  (`cannot reopen a open/closed ticket`); do not change those strings.

## 3. Edge cases

1. **Closed ticket older than 14 days.** Reject. Error, not a silent no-op, so the portal can show
   a clear message ("too old to reopen").
2. **Ticket not closed (open/pending/resolved).** Reject with a status-specific error, mirroring
   `reopenTicket`'s `cannot reopen a ${status} ticket` pattern for consistency.
3. **Ticket belongs to a different organisation.** Return `null`, exactly like `getMyTicket` and
   `reply` already do for cross-org access — no existence leak.
4. **No assignee (`assignee_id === null`).** Reopen succeeds; skip the notification call entirely.
   Calling `notifyAgent` with a null id throws (`notify.js:7`), so this must be an explicit guard,
   not left to fail.
5. **Ticket already purged (`purged: true`), reopened, then closed and left idle again.** The
   `purged` flag must be reset to `false` on reopen, or `purgeClosed`'s `if (t.purged) continue`
   latch means the messages from the *second* closed period are never deleted — a retention-policy
   violation, not just a bug. Acceptance criterion #6 below exists specifically to catch a
   regression here.
6. **Reopen requested with an empty/missing message.** Reject. The agent-side `reopenTicket` takes
   no message at all, but a customer-initiated reopen needs one so the agent knows why it came
   back — see Q2.
7. **Ticket closed 13 days ago, 7-day `KEEP_DAYS` purge already ran, customer reopens on day 13.**
   Legal to reopen (within the 14-day window) even though the conversation history is already
   gone. See Q6 — this is accepted as correct behavior, not a bug.
8. **Concurrent reopen + nightly purge job.** Not a real race in this codebase — `purgeClosed` and
   `reopenByCustomer` both run as synchronous, single-process calls against an in-memory/DB store
   with no interleaving within a call; out of scope to add locking beyond what already exists for
   every other ticket mutation here.

## 4. Open questions, answered by recommendation

**Q1. Exact boundary of "within 14 days" — calendar days, or milliseconds from `closed_at`?**
Recommendation: strict `<` on elapsed milliseconds since `closed_at`, matching the existing
`QUIET_DAYS`/`KEEP_DAYS` style (`now.getTime() - new Date(t.closed_at).getTime() < 14 * DAY`).
Confidence: high — this is the one pattern already used twice in this codebase for "N days since
timestamp X," so matching it is lower-risk than inventing calendar-day semantics.

**Q2. Does reopening require a message from the customer, or is it a bare status flip?**
Recommendation: require a non-empty message, stored as a normal customer message on the ticket
(reusing `store.addMessage`), the same way `createTicket` requires a `body` for the first message.
A bare reopen with no context gives the agent nothing to act on. Confidence: medium — the request
doesn't say either way; this is a product judgment call, not something the code implies.

**Q3. What should the notification's `by` field say, given a customer (not an agent) triggered
it?** Recommendation: reuse the existing `ticket_reopened` event type (don't invent a new one —
mirrors how the agent path already encodes the actor via `by`), with
`by: customer:<actingCustomerId>`. The *acting* customer's id, not the ticket's original
`customer_id` — see Q4, they can differ. Confidence: high — directly mirrors the precedent at
`tickets.js:42` (`by: agent:${agentId}`, the agent *performing* the action, not some other stored
field).

**Q4. Can any customer in the ticket's organisation reopen it, or only the one who opened it?**
Recommendation: any customer in the organisation — mirror `getMyTicket`/`reply`'s existing
boundary, which checks only `org_id`, never `customer_id` (`portal.js:11-12`, `21`). Introducing a
narrower rule for reopen alone would be a new, inconsistent access model with no stated reason.
Confidence: high — matches the one access-control precedent already in this file.

**Q5. Does reopening reset the SLA due time or any reopen counter?** Recommendation: no. Out of
scope for v1 — the request only asks for the reopen action and the notification, not SLA policy
changes. If the business wants a reopen-triggered SLA reset later, that's a separate decision with
its own tradeoffs (e.g., could be gamed by repeated reopen/close cycles). Confidence: medium — this
is a scope call, flagging it so it isn't assumed later.

**Q6. The purge job runs after 7 days (`KEEP_DAYS`), shorter than the 14-day reopen window — should
`KEEP_DAYS` be extended to cover it?** Recommendation: no, leave `KEEP_DAYS` at 7. It's a
legal/retention control (`purge-closed.js:3-4`, "Legal asked for this") unrelated to this feature;
widening it would be a retention-policy change disguised as a side effect of an unrelated feature.
A ticket reopened after purge just starts its new open period with no prior message history, which
is legal and acceptable. Confidence: medium — a retention-policy change needs its own
sign-off, not one bundled into this spec.

**Q7. Should the portal's `getMyTicket`/ticket list expose anything new (e.g., "can be reopened
until <date>") so the UI can show/hide a Reopen button?** Recommendation: out of scope for this
spec — it only covers the backend action. The portal UI layer can compute "closed_at + 14 days >
now" itself from the existing ticket record; no new field is strictly required. Confidence: low —
depends on how the portal frontend is actually built, which isn't in the files reviewed here; flag
for whoever picks up the UI side.

## 5. Design

Two new functions, mirroring the existing agent-side/portal-wrapper split:

**`tickets.reopenByCustomer(store, id, actingCustomerId, message, { now = new Date() } = {})`**
(`src/tickets.js`)
- Business rules only, no org-scoping (same division of labor as `reopenTicket` vs.
  `portal.reopen`).
- Throws `no ticket ${id}` via the existing `mustGet` if missing.
- Throws `cannot reopen a ${status} ticket` unless `t.status === STATUS.CLOSED`.
- Throws `this ticket is too old to reopen` if `now.getTime() - new Date(t.closed_at).getTime() >=
  14 * DAY`.
- Throws `a reopen needs a message` if `message` is empty/whitespace-only.
- Adds the message via `store.addMessage(id, { from: 'customer', body: message, at:
  now.toISOString() })`.
- Updates the ticket: `status: STATUS.OPEN`, `resolved_at: null`, `closed_at: null`, `purged:
  false` (unconditionally — see edge case #5).
- If `t.assignee_id` is set, calls `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened',
  ticketId: id, by: `customer:${actingCustomerId}` })`. If `assignee_id` is null, skips the call.
- Adds `const DAY = 24 * HOUR;` to `tickets.js` (currently only `HOUR` is defined there; every job
  file redefines `DAY` locally — this is the first place in `tickets.js` itself that needs it).

**`portal.reopen(store, customer, id, message, { now = new Date() } = {})`** (`src/portal.js`)
- Mirrors `openTicket`/`getMyTicket`'s org-scoping wrapper style.
- Looks up the ticket; returns `null` if missing or `t.org_id !== customer.orgId` (no existence
  leak across orgs, consistent with every other portal function).
- Otherwise calls `tickets.reopenByCustomer(store, id, customer.id, message, { now })` and returns
  the refreshed ticket (same shape as `getMyTicket`'s return, i.e. including `messages`).

**Not changed:**
- `tickets.reopenTicket` (agent-only, resolved→open) — stays exactly as is; pinned by
  `test/tickets.test.js:34-41`.
- `portal.reply` — keeps throwing on closed tickets; reopen is a separate action, never an implicit
  side effect of replying.
- `purgeClosed`, `closeResolved` — unchanged; their existing behavior is what makes the
  reopen→reclose→purge round-trip in acceptance criterion #6 meaningful to test.

**Docs:** `docs/glossary.md`'s closed-ticket bullet (line 12) needs a replacement sentence, e.g.:
> **closed**: final for replies — a closed ticket is never changed by an agent or by the customer
> replying. The customer may reopen it themselves from the portal within 14 days of closing; after
> that, or after 14 days, they start a new ticket.

## 6. Acceptance criteria

1. A customer can reopen a ticket closed 13 days, 23 hours ago; the ticket's status becomes
   `open`, `resolved_at` and `closed_at` are both `null`.
2. A customer cannot reopen a ticket closed exactly 14 days ago or longer; the call throws and the
   ticket is unchanged.
3. A customer cannot reopen a ticket that is `open`, `pending`, or `resolved`; the call throws a
   status-specific error and the ticket is unchanged.
4. A customer in a different organisation gets `null` from `portal.reopen`, not an error and not
   the ticket's data.
5. Reopening with an empty message throws and the ticket is unchanged; reopening with a message
   adds it to the ticket's message list from `from: 'customer'`.
6. Reopening notifies the assignee with a `ticket_reopened` event and `by: customer:<id>` when one
   is assigned; reopening an unassigned ticket does not throw and queues no notification.
7. Round-trip regression: close a ticket, purge it (`purged` becomes `true`, messages deleted),
   reopen it, reply to put it back through `resolveTicket`/`closeResolved` a second time, purge
   again — the second purge must delete the second period's messages (i.e. `purged` was correctly
   reset to `false` on reopen, not left `true` from the first purge).
8. The pre-existing agent-only `reopenTicket` behavior and its exact error strings
   (`test/tickets.test.js:34-41`) are unchanged.
