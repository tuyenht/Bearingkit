# Spec: customer reopens a closed ticket from the portal

Status: **draft — not implemented, awaiting review**

## Problem

Customers keep asking for a way to reopen a ticket that's already been
closed, instead of having to open a brand-new one and re-explain
themselves. We want to let them do this from the portal, within a limited
window, and make sure the agent who owned the ticket knows it came back.

## Open questions, answered by recommendation

I'm away-user-unavailable for this pass, so rather than block on these,
here's each question I'd normally ask, with the answer I'm recommending.
Flag any of these to change on review — nothing below is implemented yet.

1. **Who can reopen a ticket?**
   Recommend: only a customer in the ticket's own organisation — the same
   org-scoping `portal.getMyTicket` / `portal.reply` already enforce. No new
   permission concept.

2. **How long is the reopen window, and measured from what?**
   Recommend: 14 days from `closed_at` (not `resolved_at` — a ticket can sit
   resolved for a while before the nightly job closes it; the customer's
   clock should start when it actually closed). Strict `<` 14 days, matching
   the strict-`<` style already used in `close-resolved.js` and
   `purge-closed.js`.

3. **Does reopening require a message?**
   Recommend: yes, a non-empty message is required. The customer is
   re-raising something after the agent considered it done; the agent
   needs context, not just a bare status flip. The message is recorded the
   same way `portal.reply` records one (`store.addMessage`, `from:
   'customer'`).

4. **What status does the ticket return to?**
   Recommend: `open`, same target status the agent-initiated reopen uses.
   Not `pending` — the ball is back in the agent's court.

5. **Does reopening reset the SLA due time?**
   Recommend: no. `sla_due_at` stays as originally set. Resetting SLA
   clocks on reopen is a bigger policy question (does a returning ticket
   get a fresh SLA, a shortened one, none at all?) that deserves its own
   discussion. Out of scope for v1.

6. **Is there a limit on how many times a ticket can be reopened this way?**
   Recommend: no limit for v1. Nothing in the current model tracks a reopen
   count, and there's no stated abuse problem to design against yet.

7. **Should this reuse the existing `reopenTicket` function (agent path)?**
   Recommend: no — add a separate function. `reopenTicket` is agent-only,
   requires `status === RESOLVED`, and its exact error messages
   (`cannot reopen a open ticket`, `cannot reopen a closed ticket`) are
   pinned by `test/tickets.test.js:34-41`. The customer path has a
   different precondition (`status === CLOSED` plus the 14-day window) and
   a different actor; forcing them into one function would mean branching
   on "who's calling" inside the ticket model, which is worse than two
   small functions.

8. **Should `portal.reply` just reopen a closed ticket itself, instead of a
   separate action?**
   Recommend: no. `reply` on a closed ticket stays an error
   (`'this ticket is closed; please open a new one'`), unchanged. Reopening
   is a deliberate, named action the customer takes on purpose, not a side
   effect of answering — that keeps the audit trail (and the notification)
   honest about what actually happened.

9. **What happens to the "closed is final" line in the glossary?**
   Recommend: update it to mention the 14-day reopen window, since "never
   changed again" will no longer be strictly true. See below.

10. **What event does the assigned agent get notified with?**
    Recommend: reuse the existing `ticket_reopened` event type (same one
    the agent-initiated reopen already sends via `notify.notifyAgent`),
    with `by: customer:<id>` instead of `by: agent:<id>`. Mirrors how the
    event already distinguishes the actor without needing a new event
    type. If there's no assignee (`assignee_id === null`), skip the
    notification silently — `notifyAgent` throws if called with no agent,
    and there's no one to tell.

## Design

### `src/tickets.js`: `reopenByCustomer(store, id, customerId, message, { now } = {})`

Business rule only — no org check here, same division of labor as
`createTicket` vs. `portal.openTicket`.

- Throws if the ticket isn't `closed` (any other status): the customer
  path doesn't apply to a ticket that's still live.
- Throws if `now - closed_at >= 14 days`.
- Throws if `message` is empty/whitespace-only.
- On success: sets `status: 'open'`, clears `resolved_at: null` and
  `closed_at: null`, and — this is the part that matters even though it's
  easy to miss — sets `purged: false` **unconditionally**, regardless of
  whether the ticket had already been purged. See "Why `purged` must
  reset" below.
- Adds the customer's message via `store.addMessage` (`from: 'customer'`).
- Notifies the assignee per recommendation #10 above, skipping silently if
  `assignee_id` is null.

Add `const DAY = 24 * HOUR;` in `tickets.js` for this function to use,
rather than inlining the literal a third time (`close-resolved.js` and
`purge-closed.js` each already define their own local `DAY`). Not
proposing to refactor those two jobs to import it — that's a separate,
unrelated cleanup and would widen this change's diff for no behavioral
reason.

### `src/portal.js`: `reopen(store, customer, id, message, { now } = {})`

Thin org-scoping wrapper, same shape as `openTicket` / `getMyTicket`:

- Looks up the ticket; returns `null` if it doesn't exist or isn't the
  customer's org (same contract as `getMyTicket`).
- Otherwise calls `tickets.reopenByCustomer(store, id, customer.id,
  message, { now })` and returns the refreshed ticket (with messages, like
  `getMyTicket` does).

### Why `purged` must reset

`purgeClosed` (`src/jobs/purge-closed.js:13`) treats `purged` as a one-way
latch — once true, it skips the ticket forever (`if (t.purged) continue`).
If a ticket was closed, sat for 7+ days, got purged, and the customer then
reopens it within the (still-open) 14-day window, the ticket now has new
messages again. If `purged` stayed `true`, a second close → wait 7 days →
purge cycle would skip it, and those new messages would never get
deleted. That's not a style nit — it'd quietly violate the retention
policy `purge-closed.js`'s own comment cites ("Legal asked for this").
`reopenByCustomer` must set `purged: false` on every reopen, purged or not.

### `docs/glossary.md`

Update the **closed** bullet from:

> closed: final. A closed ticket is never changed again. If the customer
> comes back, they start a new ticket.

to something like:

> closed: the agent considers this done. A customer can reopen it from the
> portal within 14 days of closing; after that, or once they've let it
> sit, they start a new ticket instead.

## Acceptance criteria

1. A customer can reopen their own closed ticket within 14 days of
   `closed_at`; the ticket's status becomes `open`, `resolved_at` and
   `closed_at` are both cleared, and the message is recorded.
2. Reopening at exactly 14 days (or later) fails; the ticket stays closed.
3. Reopening with an empty message fails.
4. Reopening a ticket that isn't closed (`open`/`pending`/`resolved`)
   fails — use `tickets.reopenTicket` (agent path) or `portal.reply`
   instead, as appropriate.
5. `portal.reopen` returns `null` for a ticket that doesn't exist or
   belongs to a different organisation, same as `getMyTicket`; it never
   leaks whether the ticket exists to the wrong org.
6. **Reopen → re-close → re-purge round trip:** close a ticket, purge it
   (messages deleted, `purged: true`), reopen it as the customer within
   the 14-day window, close it again, and purge again after 7 more days —
   the second purge must delete the new messages too (i.e. `purged` was
   reset to `false` on reopen, not left `true`).
7. If the ticket has an assignee, reopening queues a `ticket_reopened`
   notification to that agent with `by: customer:<id>`. If the ticket has
   no assignee, reopening succeeds with no notification queued.
8. `tickets.reopenTicket` (agent path) and its existing tests/error
   messages are untouched.

## Out of scope for v1

- Resetting or adjusting the SLA due time on reopen.
- Limiting how many times a given ticket can be reopened.
- Any change to `portal.reply`'s behavior on closed tickets.
- Reopening by an agent on the customer's behalf through this path (the
  agent already has `tickets.reopenTicket`, for resolved tickets, and
  nothing requests agent-initiated reopen-after-close here).
