# Spec: customer reopens a closed ticket from the portal

Status: **draft, awaiting review** — written while the user was away; every
open question below was answered by recommendation rather than live, per
their instruction. Nothing in this spec is implemented yet.

## Restatement

Customers asked for a way to reopen their own closed ticket from the
portal, instead of opening a new one, as long as it's been closed no more
than 14 days. When they do, the agent assigned to the ticket should be
notified.

Technical reading: today `docs/glossary.md:12` defines **closed** as
final — "A closed ticket is never changed again. If the customer comes
back, they start a new ticket" — and `src/portal.js:24` enforces that by
throwing on `reply` to a closed ticket. This feature is a deliberate,
time-boxed exception to that rule, added as its own portal action
(`portal.reopen`), not a side effect of replying. The glossary's "closed is
final" line needs to change to reflect the exception.

The only existing reopen path is agent-side and different in kind:
`tickets.reopenTicket` (`src/tickets.js:38-44`) takes a **resolved**
ticket back to open, and is a different action from what's being asked for
here (a **closed** ticket, from the **customer**). It stays untouched.

## Touchpoints

- `src/tickets.js:38-44` — existing agent-side `reopenTicket`, resolved→open
  only. Pinned by exact-message assertions in `test/tickets.test.js:34-41`.
  New function added alongside it, not a modification to it.
- `src/portal.js:21-28` — `reply`, the only other place a closed ticket's
  status is checked from the portal side. New `portal.reopen` mirrors its
  org-scoping pattern (`src/portal.js:11-12`).
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`, reused as-is;
  throws if `agentId` is falsy, so callers must guard.
- `src/jobs/purge-closed.js:13-17` — `if (t.purged) continue` is a one-way
  latch read by the nightly purge job. This is the one piece of existing
  behavior a reopen can silently break if not handled (see Q3).
- `src/jobs/purge-closed.js:7` (`KEEP_DAYS = 7`) and the new 14-day reopen
  window overlap in an awkward way (see Q4).
- `docs/glossary.md:12` — the "closed is final" line needs a matching
  caveat.
- `src/tickets.js:6` — only `HOUR` is defined today; `DAY` is currently
  redefined locally in each job file (`src/jobs/close-resolved.js:6`,
  `src/jobs/purge-closed.js:8`). The 14-day window needs a `DAY` constant;
  adding it once in `tickets.js` avoids a third copy of the literal.

## Design

**New function**, `src/tickets.js`:

```js
function reopenByCustomer(store, id, customerId, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket was closed more than 14 days ago; please open a new one');
  }
  if (!message || !message.trim()) throw new Error('reopening a ticket needs a message');
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened', ticketId: id, by: `customer:${customerId}` });
  }
  return updated;
}
```

Takes `customerId` as an explicit parameter rather than reading
`t.customer_id` off the ticket — see Q1 and Q2 below for why.

**New wrapper**, `src/portal.js`, mirroring `openTicket`/`reply`'s
org-scoping and closed-ticket pattern:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  reopenByCustomer(store, id, customer.id, message, { now });
  return getMyTicket(store, customer, id);
}
```

`portal.reply` is unchanged — it still throws on every closed ticket.
Reopening is a separate, deliberate action the customer takes, not a side
effect of answering.

`docs/glossary.md:12` changes from:

> **closed**: final. A closed ticket is never changed again. If the
> customer comes back, they start a new ticket.

to something like:

> **closed**: final, with one exception: the customer may reopen it
> themselves within 14 days of closing, from the portal. After that
> window, they start a new ticket.

## Edge cases

1. **Ticket closed more than 14 days ago.** Rejected with a clear error;
   the portal UI falls back to "start a new ticket" (existing `openTicket`
   flow, unchanged).
2. **Empty or whitespace-only reopen message.** Rejected — a message is
   required. Not treated as an open question: a reopen with no explanation
   gives the notified agent nothing to act on, so requiring one follows
   directly from the request's own "reopen ... and notify" framing.
3. **Ticket has no assignee (`assignee_id` is null).** Reopen succeeds;
   notification is skipped. `notifyAgent` throws on a falsy `agentId`
   (`src/notify.js:7`), so the call is guarded exactly like the existing
   agent-side `reopenTicket` already guards it (`src/tickets.js:42`).
4. **A different customer in the same org reopens it than the one who
   originally opened it.** Allowed — see Q1.
5. **Ticket was already closed, reopened, and closed again** (reopen →
   back to resolved → closed again by the nightly job, or reopened a
   second time). Each reopen re-checks `status === CLOSED` and the 14-day
   window off the *current* `closed_at`; there's no reopen-count limit (see
   Q5/out-of-scope).
6. **Ticket was already purged** (nightly `purgeClosed` ran, `purged: true`,
   messages deleted) **and is then reopened within the 14-day window.**
   `KEEP_DAYS` (7 days) is shorter than the reopen window (14 days), so
   this is reachable. See Q3 and Q4 — `purged` resets to `false`
   unconditionally, and the reopened ticket simply has no prior message
   history.
7. **Concurrent reopen and nightly purge job.** Both jobs operate per-ticket
   with no cross-ticket locking today (the existing `closeResolved`/
   `purgeClosed` pair has the same property), so this isn't a new class of
   race; out of scope to fix generally.

## Open questions (answered by recommendation — user unavailable)

1. **Can any customer in the ticket's organisation reopen it, or only the
   one who originally opened it?**
   **Recommended: any customer in the org.** `portal.reply` already only
   checks `org_id`, never `customer_id` (`src/portal.js:11-12, 21-27`) —
   the portal's existing convention is org-level access, not
   customer-level. Restricting reopen to the original opener would be a
   new, narrower access rule invented for this one feature, inconsistent
   with how replying already works.

2. **When notifying the agent, whose id goes in the `by:` field —
   `customerId`, or do we read it off the ticket?**
   **Recommended: the id of the customer actually performing the reopen,
   passed in explicitly** (`reopenByCustomer(store, id, customerId, ...)`),
   not `t.customer_id` read off the ticket. The agent-side precedent,
   `reopenTicket(store, id, agentId)`, stamps `by: agent:${agentId}` for
   the agent *doing* the reopening, not some other stored field — and
   per Q1, the acting customer and the ticket's original `customer_id` can
   now legitimately differ.

3. **The nightly purge job treats `purged` as a one-way latch
   (`src/jobs/purge-closed.js:13`: `if (t.purged) continue`). Does
   reopening need to reset it?**
   **Recommended: yes, unconditionally, as part of the same reopen call.**
   If a purged ticket is reopened, re-answered, and closed again without
   resetting `purged`, the second close-and-purge cycle would silently skip
   it forever — its new messages would never get deleted. Legal's
   retention policy (`src/jobs/purge-closed.js:2-4`: no conversation text
   kept past a week on a finished ticket) would then be violated with no
   visible symptom. This is the one item in this spec I'd flag as
   non-negotiable rather than a style preference — acceptance criterion
   #6 below exists specifically to pin it down with a test.

4. **`KEEP_DAYS` (7 days, `src/jobs/purge-closed.js:7`) is shorter than the
   proposed 14-day reopen window, so a ticket can legally be reopened after
   its messages are already gone. Allow that, or extend `KEEP_DAYS` to 14
   to match?**
   **Recommended: allow it; don't touch `KEEP_DAYS`.** A reopened ticket
   with no prior history just starts fresh from the reopen message —
   that's a reasonable, visible outcome, not a bug. `KEEP_DAYS` is a
   legal-retention control unrelated to this feature's purpose; widening it
   would weaken that policy to serve a UX edge case, which isn't this
   spec's call to make.

(A fifth candidate question — "should there be a limit on how many times a
ticket can be reopened?" — is answered below as an out-of-scope assumption
instead, since its answer doesn't change this feature's shape, only
whether a future one gets added.)

## Assumptions

- **No SLA reset on reopen.** (High confidence.) The request only asks for
  reopen + notify; `sla_due_at` is set once at creation (`src/tickets.js:16`)
  and nothing else in the codebase ever recomputes it, including the
  existing agent-side reopen. Recomputing it here would be new scope the
  request didn't ask for.
- **No limit on reopen count.** (High confidence.) Nothing in the request
  or the existing code suggests one; adding one would be speculative.
- **14-day window is measured off `closed_at`, strictly less-than (a ticket
  closed exactly 14 days ago is past the window), mirroring how
  `closeResolved`/`purgeClosed` both use strict `<` against their own
  windows** (`src/jobs/close-resolved.js:11`, `src/jobs/purge-closed.js:14`).
  (High confidence — this is the existing codebase convention, not a new
  choice.)
- **The reopen message is appended as a normal customer message** (same
  shape as `reply`'s `store.addMessage` call, `src/portal.js:25`), not a
  separate "reopen reason" field with its own storage. (High confidence —
  no such field exists anywhere in `store.js`, and inventing one is out of
  proportion to the request.)

## Requirements (acceptance criteria)

1. A customer can reopen a ticket that belongs to their organisation and
   is currently `closed`, by calling `portal.reopen(store, customer, id,
   message)`, provided `now - closed_at < 14 days`.
2. Reopening sets `status: 'open'`, clears `resolved_at` and `closed_at`
   (both to `null`), and appends `message` as a customer message.
3. Reopening a ticket closed 14 or more days ago throws and changes
   nothing.
4. Reopening with an empty or whitespace-only message throws and changes
   nothing.
5. If the ticket has an assignee, reopening queues a notification to that
   agent (`notifyAgent`, event `{ type: 'ticket_reopened', ticketId,
   by: 'customer:<actingCustomerId>' }`). If it has no assignee, no
   notification call is made (and none is attempted that would throw).
6. **Reopening a `purged` ticket resets `purged` to `false`.** A
   reopen → re-close → re-purge cycle (via `closeResolved` then
   `purgeClosed`) deletes the new cycle's messages again — i.e. purge
   isn't permanently skipped just because the ticket was purged once
   before.
7. `portal.reopen` on a ticket outside the customer's organisation returns
   `null` and changes nothing, matching `getMyTicket`'s existing behavior.
8. The existing agent-side `tickets.reopenTicket` (resolved→open) and its
   pinned tests in `test/tickets.test.js:34-41` are unchanged.
9. `portal.reply` still throws on every closed ticket, reopened or not —
   reopening is a separate action, not folded into `reply`.

## Out of scope (v1)

- SLA recalculation on reopen.
- A limit on how many times a ticket can be reopened.
- Changing `KEEP_DAYS` or any other purge-timing behavior.
- A portal-side UI; this spec covers `src/tickets.js` and `src/portal.js`
  only.
- Notifying anyone other than the current assignee (e.g. a team or queue
  notification when unassigned).
