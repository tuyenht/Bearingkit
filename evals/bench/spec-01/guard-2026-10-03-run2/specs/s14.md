# Spec: customer reopen of a closed ticket

Status: draft, awaiting review. Written while the requester was unavailable;
every open question below is answered with a recommendation rather than
left blocking, per their instruction to work from recommendations.

## Restatement

Customers ask to be able to reopen their own closed ticket from the portal
instead of opening a new one, as long as it has not been closed for too
long. Technical reading: add a portal-facing action that takes a closed
ticket back to `open` when the caller is a customer in the ticket's
organisation and the ticket's `closed_at` is within a 14-day window, records
the customer's message as part of the reopen, and notifies the ticket's
assignee the same way the existing agent-side reopen does. The glossary's
"closed is final" rule changes to "final, unless a customer reopens it
within 14 days."

## Touchpoints

  else. Stays untouched.
- `src/tickets.js:4-6` — `STATUS`, `SLA_HOURS`, `HOUR`; no `DAY` constant
  exists yet (job files each define their own `DAY` locally).

- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`; throws if

- `src/jobs/close-resolved.js:5-16` — pattern for a nightly job reading

- `docs/glossary.md:12` — "closed: final... never changed again" needs a

## Design

Add `tickets.reopenByCustomer(store, id, customerId, message, { now })`,
parallel to the existing agent-side `reopenTicket` but with its own rules:

- Ticket must be `closed`; anything else throws (mirrors `reopenTicket`'s
  own status check).
- `now - closed_at` must be strictly less than 14 days; at or past 14 days
  throws.
- `message` must be non-empty; it's recorded as a customer message on the
  ticket before reopening.
- On success: status → `open`, `resolved_at` → `null`, `closed_at` → `null`,
  `purged` → `false` (see the purge interaction below), notify the assignee
  via `notifyAgent` with a `ticket_reopened` event and `by: customer:<customerId>`
  — if `assignee_id` is null, skip the notify call silently rather than
  calling `notifyAgent` with no agent (it throws, `notify.js:7`).
- `customerId` is the *acting* customer's id, passed in explicitly, not read
  off `t.customer_id`. Reason: the agent-side precedent stamps `by:
  agent:${agentId}`, the agent performing the action, not the ticket's
  original assignee — the actor is who did it, not who the ticket belongs
  to. Since reopen access is org-scoped, not customer-scoped (see edge
  cases), the acting customer and the ticket's original customer can differ.

Add `portal.reopen(store, customer, id, message, { now })` as the
org-scoping wrapper, mirroring `openTicket`/`getMyTicket`: looks up the
ticket, returns `null` if it's not the customer's org, otherwise calls
`tickets.reopenByCustomer(store, id, customer.id, message, { now })` and
returns the refreshed ticket with messages.

Add `const DAY = 24 * HOUR;` to `src/tickets.js` (it already has `HOUR` but
not `DAY`; job files redefine `DAY` locally — `tickets.js` gets its own
rather than a third inlined literal).

## Edge cases

1. **Ticket already purged when the reopen window is still open.**
   `KEEP_DAYS` (7 days) is shorter than the 14-day reopen window, so a
   ticket can legally be reopened after its messages were already deleted
   by `purgeClosed`. Recommendation: allow the reopen anyway — the reopened
   ticket just starts with no prior message history, same as any ticket
   whose history was purged. Don't widen `KEEP_DAYS` to cover 14 days; it's
   an unrelated legal-retention control, and widening it to accommodate
   this feature would keep conversation text longer than legal asked for.
2. **A different customer in the same org reopens a ticket they didn't
   open.** `portal.reply` already allows this (only checks `org_id`, never
   `customer_id`, `portal.js:11-12`) — reopen follows the same precedent for
   consistency, not a new restriction. Anyone in the organisation can act on
   the organisation's ticket, same as replying.
3. **Reopen, then close, then purge again.** `purgeClosed`'s `purged` flag
   is a one-way latch (`purge-closed.js:13`) — once set it's never
   unset by that job. If reopen doesn't reset `purged: false`, a
   second close-and-purge cycle's messages would never be deleted, since
   `purgeClosed` would keep skipping the ticket. `reopenByCustomer` must
   unconditionally reset `purged: false` on every reopen, whether or not it
   was already `true`. This is the one correctness point in this spec that
   isn't a style choice — it's a retention-policy violation if missed, and
   acceptance criterion 6 below exists specifically to catch it.
4. **No assignee on the ticket.** `notifyAgent` throws if called with a
   falsy agent id (`notify.js:7`). `reopenByCustomer` must check
   `assignee_id` before calling it and skip notification silently when
   there is none, matching how a newly-created, unassigned ticket behaves
   elsewhere.
5. **Empty or missing reopen message.** Rejected with an error before any
   state changes — reopening without saying why defeats the point of
   requiring a message, and the agent has nothing to act on.
6. **Exactly at the 14-day boundary.** Window is `now - closed_at < 14 *
   DAY`, strict less-than, matching `purgeClosed`'s own strict `<` pattern
   (`purge-closed.js:14`) for consistency. A ticket closed exactly 14 days
   ago can no longer be reopened.
7. **Reopening a `resolved` or `open` ticket via this path.** Rejected —
   `reopenByCustomer` requires `status === 'closed'`. A resolved ticket
   already has its own reopen path for customers: answering it via
   `portal.reply` puts it back to open (`portal.js:26`). This new function
   is for closed tickets specifically.

## Open questions, answered by recommendation

**Q1. Can any customer in the ticket's organisation reopen it, or only the
customer who originally opened it?**
Recommendation: any customer in the organisation, matching the existing
`portal.reply` precedent, which checks only `org_id` (`portal.js:11-12`).
Introducing a stricter rule just for reopen would be inconsistent with
every other portal action and isn't something the request asked for.

**Q2. Whose id goes in the notification's `by:` field — the acting customer,
or the ticket's original customer?**
Recommendation: the acting customer, passed as an explicit parameter.
The agent-side reopen already establishes this pattern (`by:
agent:${agentId}`, the agent who performed the action, not
`t.assignee_id`) and Q1 means the acting and original customer can differ.

**Q3. What happens to the `purged` flag on reopen?**
Recommendation: unconditionally reset to `false`. See edge case 3 — this is
a correctness requirement, not a judgment call, because of the one-way
latch in `purgeClosed`.

**Q4. The reopen window (14 days) is longer than the message-retention
window (`KEEP_DAYS = 7`) — should either change?**
Recommendation: leave both as they are and allow edge case 1 (reopen after
purge, with no prior history). `KEEP_DAYS` is a legal-retention control,
unrelated to this feature; widening it to paper over the overlap would be
scope creep with a compliance cost.

## Assumptions

- The 14-day window and "notify the assigned agent" are satisfied by
  reusing the existing `notifyAgent` queue and a `ticket_reopened` event
  type (same type the agent path already uses), rather than a new event
  type or notification channel. Confidence: medium — reasonable default,
  not stated explicitly by the requester.
- No SLA reset and no limit on how many times a ticket can be reopened.
  Confidence: medium — not asked for, and adding either would be unrequested
  scope.
- The reopen message is stored the same way an ordinary customer reply is
  stored (`store.addMessage` with `from: 'customer'`). Confidence: high —
  matches `portal.reply`'s own pattern exactly (`portal.js:25`).

## Acceptance criteria

1. `tickets.reopenByCustomer` on a `closed` ticket within 14 days of
   `closed_at`, given a non-empty message, sets status to `open`,
   `resolved_at` to `null`, `closed_at` to `null`, and appends the message
   as a customer message.
2. The same call on a ticket closed 14 or more days ago throws, and leaves
   the ticket's status, `resolved_at`, and `closed_at` unchanged.
3. The same call on a ticket that is `open`, `pending`, or `resolved`
   (never closed) throws, and changes nothing.
4. The same call with an empty or missing message throws before any field
   on the ticket changes.
5. If the ticket has an assignee, reopening queues exactly one notification
   to that assignee with event type `ticket_reopened` and `by:
   customer:<actingCustomerId>`. If the ticket has no assignee, reopening
   queues no notification and does not throw.
6. A ticket that is closed, reopened by a customer, closed again, and left
   past `KEEP_DAYS` is purged by `purgeClosed` on its second cycle exactly
   as it would be the first time — i.e. `purged` is `false` immediately
   after reopen, confirming the latch was reset.
7. `portal.reopen` returns `null` (and changes nothing) when the ticket
   does not belong to the calling customer's organisation, mirroring
   `portal.getMyTicket`.
8. `portal.reopen` succeeds for a customer in the right organisation who is
   not the ticket's original customer (edge case 2 / Q1).
9. The existing tests in `test/tickets.test.js:34-41` for the agent-only
   `reopenTicket` keep passing unmodified, including their exact error
   message assertions.

## Out of scope

- SLA due-time changes on reopen.
- A limit on how many times a ticket can be reopened.
- Changing `KEEP_DAYS` or any other purge/retention timing.
- Any change to the agent-side `reopenTicket`.
