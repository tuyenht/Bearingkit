# Spec: customer self-service ticket reopen

Status: draft, awaiting review. Written while the requester was unavailable;
every open question below is answered with a recommendation rather than left
blank, per their instruction. Treat the recommendations as proposed, not
approved.

## Problem

Customers keep asking to reopen a ticket themselves after it's closed,
instead of filing a new one and losing the history. Today `docs/glossary.md`
says closed is final, and `portal.reply` (`src/portal.js:21-28`) throws on
any closed ticket. The only existing reopen path is `tickets.reopenTicket`
(`src/tickets.js:38-44`), and it's agent-only: it requires status
`resolved`, not `closed`.

## Goal

A customer can reopen their own closed ticket from the portal, within 14
days of it closing, and the assigned agent is notified.

## Open questions and recommendations

**1. New function, or extend `reopenTicket`?**
Recommend a new `tickets.reopenByCustomer`, leaving `reopenTicket` untouched.
`reopenTicket` requires status `resolved` and its exact error message is
pinned by `test/tickets.test.js:34-41`; bending it to also accept `closed`
for a different actor type would complicate one function into two concerns.

**2. What status does a reopened ticket land in?**
Recommend `open`. Matches the existing convention: a customer answering a
resolved/pending ticket (`portal.reply`) and an agent reopening a resolved
ticket (`reopenTicket`) both land on `open`.

**3. How is the 14-day window measured, and which boundary wins at the edge?**
Recommend measuring from `closed_at`, using the same `<` comparison style as
`closeResolved`/`purgeClosed`: allowed while
`now - closed_at < 14 * DAY`, rejected at exactly 14 days and beyond. So "14
days" means the window closes at the start of day 14, consistent with how
the existing jobs treat their own day thresholds.

**4. Does this interact with the purge job's `purged` flag?**
Yes, and this is the one point in the spec that isn't a style choice.
`purgeClosed` (`src/jobs/purge-closed.js:13`) skips any ticket where
`t.purged` is already `true`. If a customer reopens a ticket that was
already purged (purge runs at day 7, reopen window is open through day 13),
and `reopenByCustomer` doesn't clear `purged`, then every message added
after reopen would never be purged on a future close — they'd sit past
Legal's 7-day retention limit forever. **`reopenByCustomer` must
unconditionally reset `purged: false`.** This is acceptance criterion #6
below and the one thing not to drop if the rest of the spec changes.

**5. Does `portal.reply`'s "closed tickets take no answers" rule change?**
Recommend no. Reopening stays a distinct, deliberate action the customer
chooses from the ticket view, not an automatic side effect of replying to a
closed ticket. `portal.reply` keeps throwing on closed tickets exactly as it
does today.

**6. Does reopening require a message from the customer?**
Recommend yes, non-empty, same as opening a new ticket. A reopen with no
stated reason is hard for the agent to act on, and it costs nothing to
require one line of text.

**7. Does reopening reset or extend the SLA?**
Recommend no SLA change. `sla_due_at` is "when the first answer is due";
that already happened. No requirement has come in for a reopen SLA, so
don't invent one.

**8. Is there a limit on how many times a ticket can be reopened this way?**
Recommend no limit for now. Add one later if it's abused in practice;
nothing about repeat reopens has been reported as a problem.

**9. Who gets notified, and under what event name?**
Recommend a new event type `ticket_reopened_by_customer` (distinct from the
agent-driven `ticket_reopened`, so agents and any downstream filtering can
tell the two apart), sent to `assignee_id` via the existing `notifyAgent`
queue (`src/notify.js`). Unlike the agent path, there's no "actor" to
compare the assignee against — the actor here is always the customer — so
notify whenever an assignee exists. If the ticket is unassigned, skip
notification; it's already visible in the unassigned queue.

**10. Who is allowed to call this — any customer at the org, or only the
ticket's original author?**
Recommend any customer at the ticket's organisation, matching every other
portal permission check (`portal.getMyTicket` keys on `org_id`, not
`customer_id`).

**11. Does the glossary need updating?**
Yes. `docs/glossary.md`'s closed definition currently reads "closed: final
... If the customer comes back, they start a new ticket," which becomes
wrong. See acceptance criterion #7.

## Design

New function in `src/tickets.js`:

```js
function reopenByCustomer(store, id, { message, now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed more than 14 days ago; please open a new one');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, { status: STATUS.OPEN, closed_at: null, purged: false });
  if (t.assignee_id) notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id });
  return updated;
}
```

(`REOPEN_WINDOW_DAYS = 14`, `DAY = 24 * 60 * 60 * 1000`, alongside the
existing `SLA_HOURS`/`HOUR` constants.)

Portal entry point in `src/portal.js`, next to `reply`:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, { message, now });
}
```

`getMyTicket` already scopes by `customer.orgId`, so this covers permission
question #10 for free — same pattern `reply` uses.

## Acceptance criteria

1. A `closed` ticket less than 14 days past `closed_at` can be reopened by a
   customer in its organisation; it moves to `open`.
2. A closed ticket 14 or more days past `closed_at` is rejected with a clear
   error; status is unchanged.
3. A non-closed ticket (open/pending/resolved) is rejected with an error
   naming its current status, same style as `reopenTicket`'s existing error.
4. A customer outside the ticket's organisation gets the same "not found"
   behavior as every other portal lookup (`getMyTicket` returns `null`).
5. Reopening without a message (missing or blank) is rejected; reopening
   with one appends it to the message history as a `customer` message.
6. **Reopening always sets `purged: false`, including when the ticket had
   already been purged.** A subsequent close-and-wait-7-days cycle must purge
   the new messages exactly as it would for a never-purged ticket.
7. If the ticket has an assignee, they receive a queued
   `ticket_reopened_by_customer` notification naming the ticket. If
   unassigned, no notification is sent and nothing throws.
8. `tickets.reopenTicket` (agent path) and its existing tests are unchanged.
9. `docs/glossary.md`'s closed definition is updated to note the 14-day
   customer reopen window instead of flatly stating "they start a new
   ticket."

## Out of scope

- Any change to the SLA calculation or `sla_due_at`.
- A reopen-count limit or rate limiting.
- Changing `portal.reply`'s behavior on closed tickets.
- Agent-facing UI for seeing *why* a ticket was reopened beyond the queued
  notification and the new message in the thread (both already covered
  above).
