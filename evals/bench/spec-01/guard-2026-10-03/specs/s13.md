# Spec: customer reopens a closed ticket from the portal

Status: draft, awaiting review (written while the requester was away; not implemented). ACT, no COUNCIL-area conflict.

## Request, restated

Customers want to reopen their own closed ticket from the portal, within 14 days of it being closed, instead of filing a new one. When they do, the agent assigned to that ticket should be notified. Today the only reopen path is agent-only (`tickets.reopenTicket`, `src/tickets.js:38-44`), and it only accepts a `resolved` ticket; the portal's `reply` throws on any closed ticket (`src/portal.js:24`) and tells the customer to open a new one, with no exception for recently-closed ones.

## Touchpoints (file:line)

- `src/tickets.js:4` — `STATUS` enum (`open`, `pending`, `resolved`, `closed`).
- `src/tickets.js:38-44` — `reopenTicket(store, id, agentId)`: agent-only, requires `RESOLVED`, notifies the previous assignee only if different from the reopening agent. Tests pin its exact error messages (`test/tickets.test.js:37,40`): `assert.throws(..., /cannot reopen a open ticket/)`, `/cannot reopen a closed ticket/`. **This function and its messages must not change.**
- `src/portal.js:21-28` — `reply(...)`: throws `'this ticket is closed; please open a new one'` for any closed ticket; no org-scoping check of its own shown here, but `getMyTicket` (`src/portal.js:10-14`) is the established pattern — returns `null` (not an exception) when the ticket doesn't exist or belongs to another org.
- `src/jobs/purge-closed.js:10-20` — `purgeClosed`: 7 days after `closed_at`, deletes the ticket's messages and sets `purged: true`. Line 13, `if (t.purged) continue`, is a **one-way latch**: once `purged` is `true`, this job never looks at that ticket again.
- `src/jobs/close-resolved.js:8-16` — day-math convention used elsewhere in this codebase: `now.getTime() - new Date(t.X).getTime() < N * DAY` (strict less-than).
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`: throws if `agentId` is falsy; queues `{ to, event, queued_at }`. Generic — no changes needed here.
- `src/store.js` — `updateTicket` is a plain `Object.assign` patch (no partial-write transaction semantics to worry about beyond keeping one call).
- `docs/glossary.md:12` — "**closed**: final. A closed ticket is never changed again." This line becomes inaccurate once this ships and needs a matching exception.

## Edge cases

1. **Ticket already purged.** A closed ticket can sit past the 7-day purge window before a customer reopens it within the 14-day reopen window (purge: 7 days, reopen: 14 days — the purge runs first). `store.getMessages` returns `[]` already; reopening must still succeed, the new customer message starts the thread fresh, and `purged` must be reset to `false` (see "non-negotiable" below) so a later close cycle purges it again.
2. **Boundary timing.** A reopen attempt at exactly `closed_at + 14 days` should use the same strict `<` convention as `closeResolved`/`purgeClosed` — treated as expired, not eligible. Picking `<` keeps all three day-math checks in this codebase consistent.
3. **Unassigned ticket.** `assignee_id` can be `null` (new tickets start unassigned, `src/tickets.js:14`). Reopening must not call `notifyAgent` in that case — `notifyAgent` throws on a falsy `agentId` (`src/notify.js:7`), so the call needs a guard, not a try/catch.
4. **Empty or missing message.** The customer action must carry a message (this is what makes it a deliberate "I'm back" action, not a silent status flip). An empty/whitespace-only body is rejected before any store write — no partial update.
5. **Double reopen / race.** Two reopen calls for the same ticket: the first flips status to `open`; the second's status check (`status !== CLOSED`) now fails naturally, so no explicit idempotency token is needed.
6. **Wrong organisation.** A customer passing another org's ticket id must get the same "not found" shape as every other portal function — `null`, not a thrown error, matching `getMyTicket` (`src/portal.js:10-14`) and `reply`'s dependence on it. No leaking whether the ticket exists.

## Assumptions

- **High.** The 14-day window is measured from `closed_at` with the same strict-less-than boundary `closeResolved` and `purgeClosed` already use (`src/jobs/close-resolved.js:11`, `src/jobs/purge-closed.js:14`) — consistency with existing day-math, not a new rule.
- **High.** Target status after reopen is `open` (not `pending`) — matches both the agent path (`reopenTicket` → `open`) and the customer-reply-to-resolved path (`portal.reply` → `open`, `src/portal.js:26`).
- **Medium.** `resolved_at` and `closed_at` are cleared back to `null` on reopen, mirroring how `reopenTicket` clears `resolved_at` (`src/tickets.js:41`) when moving a ticket backward out of a terminal-ish state. Worth a sanity check against reporting: if closed-ticket reports key off `closed_at` being non-null, clearing it removes this ticket from that report's slice going forward, which is the intended effect of "it's reopened now."
- **Medium.** SLA (`sla_due_at`) is **not** recomputed on reopen. Lowest-risk default — it avoids inventing a new SLA rule the request didn't ask for — but it's a support-process call, not a technical one, so flagging it rather than assuming silently.
- **Low.** No cap on how many times a ticket can be reopened this way, and no new "reopen count" field. If this turns out to matter for abuse/reporting reasons, it's a cheap follow-up (a counter alongside the existing fields), not a redesign.

## Clarifying questions, answered inline (recommendation, since sign-off is pending)

1. **Does this replace or sit alongside the agent-only `reopenTicket`?** → Alongside. New function, `reopenTicket` untouched — its tests pin its messages exactly (see touchpoints), and the two have different preconditions (`resolved` vs `closed`) and different actors.
2. **Which statuses can a customer reopen from?** → Only `closed`. `open`/`pending` need no reopen (they're already active); `resolved` already has a customer path (`reply`, which flips it to `open`).
3. **Is the message required?** → Yes, non-empty. It's the deliberate signal that distinguishes this from an automatic status flip, and it gives the agent something to act on.
4. **What happens to `closed_at`/`resolved_at`?** → Both reset to `null`; see Assumptions (medium confidence — flagging in case reporting relies on `closed_at` surviving).
5. **Is the SLA clock reset?** → No. See Assumptions (medium confidence, a process call more than a technical one).
6. **What if the ticket was already purged (messages gone)?** → Reopen still succeeds; the thread continues with just the new message. The ticket row (subject, dates, org) was never deleted, only messages were.
7. **Does `purged` need to be reset?** → **Yes, unconditionally, to `false`.** This is the one item in this spec that isn't a style choice: `purgeClosed`'s `if (t.purged) continue` (`src/jobs/purge-closed.js:13`) is a one-way latch. If a reopened-then-re-closed ticket still has `purged: true`, the next purge cycle skips it forever and its new messages never get removed — a retention-policy miss, not a cosmetic bug.
8. **Who gets notified, and when?** → The current `assignee_id`, only if one is set. No assignee → no notification call (guard, not try/catch, since `notifyAgent` throws on a falsy id).
9. **What event type?** → `ticket_reopened_by_customer`, distinct from the agent path's `ticket_reopened`, so anything consuming the notify queue can tell the two apart.
10. **Does this change `portal.reply`'s behavior on closed tickets?** → No. `reply` keeps throwing for every closed ticket. Reopening is a separate, explicit action — not a side effect of answering.
11. **Any reopen-count limit?** → No, see Assumptions (low confidence — easy follow-up if needed).
12. **Does `docs/glossary.md` need updating?** → Yes — the "closed: final" line needs a one-line exception, or the glossary will contradict the product behavior.

## Design

Two new functions, following the existing split between ticket rules (`src/tickets.js`) and portal org-scoping (`src/portal.js`):

```js
// src/tickets.js
function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed more than 14 days ago; please open a new one');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id });
  return updated;
}
```

```js
// src/portal.js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, message, { now });
}
```

`REOPEN_WINDOW_DAYS = 14` alongside `KEEP_DAYS`/`QUIET_DAYS`'s style in the job files, exported from `src/tickets.js`.

`docs/glossary.md:12` gets one added sentence: "...A closed ticket is never changed again, except that the customer may reopen it within 14 days of closing; after that, they start a new ticket."

## Acceptance criteria

1. `reopenByCustomer` on a `closed` ticket within 14 days of `closed_at` sets status to `open` and clears `resolved_at`/`closed_at`.
2. `reopenByCustomer` throws `cannot reopen a ${status} ticket` for any non-closed status (`open`, `pending`, `resolved`).
3. `reopenByCustomer` throws when `now - closed_at >= 14 days` (boundary itself is expired, matching the `<` convention elsewhere).
4. `reopenByCustomer` throws on an empty/missing message, before any store write.
5. `reopenByCustomer` appends the customer's message via `store.addMessage`.
6. `reopenByCustomer` resets `purged` to `false` unconditionally — including when the ticket had already been purged — so a subsequent close-then-7-days cycle purges its (new) messages again.
7. `reopenByCustomer` calls `notifyAgent` with event type `ticket_reopened_by_customer` only when `assignee_id` is set; no call (not a swallowed error) when unassigned.
8. `portal.reopen` returns `null`, not an exception, for a non-existent ticket id or one belonging to another organisation — matching `getMyTicket`.
9. `tickets.reopenTicket` and `portal.reply` are unchanged; `test/tickets.test.js:34-41`'s exact-message assertions still pass untouched.
10. `docs/glossary.md`'s closed-ticket line reflects the 14-day exception.
