# Spec: customer reopen of a closed ticket

Status: **draft — awaiting review** (written while the requester was away; not implemented)

## Request, restated

Customers keep asking for this. Today `docs/glossary.md:12` says closed is
final: "If the customer comes back, they start a new ticket." The ask is to
relax that from the portal only: let a customer reopen their *own* closed
ticket within 14 days of it being closed, and tell the assigned agent it
happened. Technically this means a new portal-facing action, parallel to the
existing agent-only `reopenTicket` (`src/tickets.js:38-44`), with its own
time window, its own notification event, and its own interaction with the
nightly purge job.

The questions below are the ones I'd normally ask before writing acceptance
criteria. Since you're away until tomorrow, each one carries the answer I'd
recommend, and the rest of this spec is built on those recommendations —
flag any you'd answer differently and I'll adjust before this moves to a
build.

## Open questions, answered by recommendation

**Q1. What exactly counts as "within 14 days"?**
Recommendation: strict `<` on `now - closed_at < 14 days`, matching the
existing style in `purge-closed.js:14` and `close-resolved.js:11` (both use
strict `<` with a day constant). Day 14 at the same time-of-day as closing
is the last reopenable moment; day 15 is not.

**Q2. What does "reopen" set the ticket back to?**
Recommendation: `open`, not `pending` or `resolved`. This matches what the
*agent*-side `reopenTicket` already does (`src/tickets.js:41`) and what a
customer reply to a resolved/pending ticket already does
(`src/portal.js:26`). One mental model for "this ticket is active again."

**Q3. Does reopening require the customer to say anything, or is it a bare status flip?**
Recommendation: require a non-empty message, added to the ticket as a new
customer message (same shape as `reply`, `src/portal.js:25`). A bare reopen
with no content gives the agent nothing to act on; the portal already
collects a message for every other customer action on a ticket.

**Q4. Should `resolved_at`/`closed_at` be cleared, kept, or moved to history?**
Recommendation: clear both to `null`, same as the agent path clears
`resolved_at` (`src/tickets.js:41`). There's no history/audit table in this
codebase today (`src/store.js` has no event log), so "cleared" is consistent
with how every other status transition here already discards the prior
timestamp. **Medium confidence** — if reporting depends on `closed_at`
surviving a reopen, this needs a different answer; flag if so.

**Q5. What event does the agent get, and does it differ from the agent-reopen event?**
Recommendation: a distinct event type, `ticket_reopened_by_customer`, not a
reuse of `ticket_reopened` (`src/tickets.js:42`). An agent reading their
queue needs to tell "a peer reopened this" from "the customer came back,"
and reusing the same event type would blur that. Delivered the same way —
`notify.notifyAgent` (`src/notify.js:6`) — queued, not sent inline, same as
every other notification in this codebase.

**Q6. What happens if the ticket has no assignee?**
Recommendation: skip notification silently. `notifyAgent` throws if
`agentId` is falsy (`src/notify.js:7`), and an unassigned closed ticket is a
real, reachable state (a ticket can be closed before ever being assigned,
since `assignTicket` only blocks on already-closed tickets —
`src/tickets.js:26-28` — not on being unassigned). Reopen must not crash on
this path.

**Q7. Does this interact with the nightly purge job?**
Recommendation: yes, and this is the one non-negotiable part of the design.
`purgeClosed` (`src/jobs/purge-closed.js:13`) treats `purged` as a one-way
latch — `if (t.purged) continue` — and once a closed ticket's messages are
deleted it's never revisited. If a ticket was closed, purged (messages
deleted after 7 days per `KEEP_DAYS`, `purge-closed.js:7`), then reopened by
a customer on day 13, closed again, and left to reach day 7-post-close a
second time, `purgeClosed` would skip it forever and the second
conversation's messages would never be deleted. That's a retention-policy
violation (`purge-closed.js:3-4`: "Legal asked for this: we do not keep
conversation text of finished tickets longer than a week"), not a style
question. **Reopen must unconditionally reset `purged: false`**, regardless
of its current value. This is acceptance criterion #6 below and is not
optional.

**Q8. Does reopening reset the SLA, or cap how many times a ticket can be reopened?**
Recommendation: no to both, for v1. No SLA field tracks "time since reopen"
today (`sla_due_at` is set once, at creation — `src/tickets.js:16`), and
there's no existing reopen-count field to cap against. Adding either is new
schema, which is bigger than this request. If repeat-reopen abuse turns out
to be a real problem, that's a follow-up with its own spec.

**Q9. Should this live in `tickets.js` as a business rule, or directly in `portal.js`?**
Recommendation: split the same way every other portal action already
splits — a business-rule function in `tickets.js` plus a thin,
org-scoped wrapper in `portal.js`, mirroring `openTicket`/`reply`
(`src/portal.js:16-28`). Keeps the org-scoping check (`t.org_id !==
customer.orgId`) in exactly one place, matching `getMyTicket`
(`src/portal.js:11-12`).

## Design

**New constant, `src/tickets.js`:** `const DAY = 24 * HOUR;` — the file
currently defines `HOUR` (`tickets.js:6`) but not `DAY`; both nightly jobs
redefine `DAY` locally (`close-resolved.js:6`, `purge-closed.js:8`). A third
local redefinition isn't worth it; promote it to the one file that's
becoming the shared home for ticket time-math.

**`tickets.js`: `reopenByCustomer(store, id, message, { now = new Date() } = {})`**
- Throws if the ticket isn't `closed` (mirrors `reopenTicket`'s own-status
  check, `tickets.js:40`, message style `cannot reopen a ${t.status} ticket`
  — but note this function is reached only through the portal wrapper below,
  which already enforces org scoping first).
- Throws if `now - closed_at >= 14 * DAY` (window expired).
- Throws if `message` is empty/whitespace-only (no content to give the
  agent).
- On success: `store.updateTicket(id, { status: STATUS.OPEN, resolved_at:
  null, closed_at: null, purged: false })`, then `store.addMessage(id, {
  from: 'customer', body: message, at: now.toISOString() })`.
- Notifies via `notifyAgent(store, t.assignee_id, { type:
  'ticket_reopened_by_customer', ticketId: id })` only if `t.assignee_id` is
  set; skip silently otherwise.
- Returns the updated ticket.

**`portal.js`: `reopen(store, customer, id, message, { now } = {})`**
- Looks up via `getMyTicket`-style org check; returns `null` if the ticket
  doesn't belong to the customer's org (mirrors `getMyTicket`,
  `portal.js:11-12`) — same "not yours, not visible" behavior as every
  other portal lookup, rather than leaking a different error for
  out-of-org tickets.
- Otherwise delegates to `tickets.reopenByCustomer` and returns its result
  (or re-throws its validation errors — closed-only, window, empty
  message — unchanged).

**`tickets.reopenTicket` (agent-side) stays untouched.** It's a different
action (resolved→open only, no window, no message) pinned by exact-message
assertions in `test/tickets.test.js:34-41`. This spec adds a sibling, not a
replacement.

**`docs/glossary.md`** needs its "closed" bullet (`glossary.md:12`) updated
— it currently says flatly "if the customer comes back, they start a new
ticket," which this feature makes only conditionally true (true after 14
days, false within them).

## Edge cases

1. **Reopen right at the 14-day boundary.** `now - closed_at == 14 * DAY`
   exactly → rejected (strict `<`), consistent with Q1's recommendation and
   the codebase's existing boundary style.
2. **Ticket closed, never assigned.** Reopen succeeds, no notification sent
   (Q6). Must not throw — `notifyAgent` would throw on a null agent id if
   called unconditionally.
3. **Ticket already purged before the 14-day window closes.** Purge runs 7
   days after close (`KEEP_DAYS = 7`); the reopen window is 14 days, so a
   ticket can absolutely be purged (messages gone) and still be inside its
   reopen window. Reopen must still succeed — the ticket row and its
   `purged` flag are separate from message history — and must reset
   `purged: false` (Q7) so a second close-and-purge cycle isn't silently
   skipped. The customer's reopen message is the first message in what is,
   from the store's point of view, a fresh conversation.
4. **Empty or whitespace-only reopen message.** Rejected before any state
   change (Q3) — no partial update, no notification queued.
5. **Customer targets a ticket from another organisation.** Returns `null`,
   same as every other cross-org lookup in `portal.js` (Q9) — never reveals
   that the ticket exists.
6. **Ticket is `open`, `pending`, or `resolved` (not `closed`).** Rejected —
   this action is closed-only by design; an already-active ticket has
   `reply` (`portal.js:21-28`) or the agent-side `reopenTicket` for that.
7. **Two reopen calls race on the same ticket** (e.g. double-submit from the
   portal). The in-memory store (`store.js:19-24`) and its production
   Postgres counterpart aren't shown to serialize `updateTicket`, so a
   second call during the window after the first succeeds would see the
   ticket already `open` and correctly fail with "cannot reopen a open
   ticket" — not a correctness bug, just worth noting this isn't
   transactional beyond what the existing codebase already provides for any
   other ticket update.

## Acceptance criteria

1. A customer can reopen their own ticket while `status === 'closed'` and
   `now - closed_at < 14 days`; the ticket becomes `status: 'open'`.
2. Reopening outside the 14-day window throws and leaves the ticket
   unchanged.
3. Reopening without a non-empty message throws and leaves the ticket
   unchanged.
4. A successful reopen adds the message to the ticket's message list
   (`from: 'customer'`).
5. A successful reopen clears `resolved_at` and `closed_at` to `null`.
6. **A successful reopen sets `purged: false`, unconditionally — including
   when the ticket was already purged.** (Non-negotiable; see Q7.)
7. If the ticket has an assignee, a successful reopen queues exactly one
   `ticket_reopened_by_customer` notification to that agent via
   `notify.notifyAgent`.
8. If the ticket has no assignee, a successful reopen queues no
   notification and does not throw.
9. A customer cannot reopen (or discover the existence of) a ticket outside
   their own organisation — same visibility rule as `getMyTicket`.
10. The existing agent-side `reopenTicket` behavior is unchanged (all of
    `test/tickets.test.js:24-41` still passes unmodified).
11. `docs/glossary.md`'s closed-ticket bullet reflects the new conditional
    behavior.

## Classification

- **COUNCIL**, not ACT: this touches data-deletion semantics shared with
  the Legal-driven purge job (`purge-closed.js:3-4`), tenant/org-scoping
  logic (`portal.js`'s org check), and a module contract
  (`tickets.js`/`portal.js` split) across four files — above the project's
  informal three-file ACT threshold (`tickets.js`, `portal.js`,
  `glossary.md`, `test/tickets.test.js`). Per the gate patterns, "unsure →
  COUNCIL," and this isn't even unsure: data deletion and multi-module
  impact are both named COUNCIL triggers on their own.
- Not a hot path in the auth/payments/migration sense, but the
  purge-interaction criterion (#6) should get the same independent-review
  treatment as a hot-path change before this ships, given what's at stake
  (a second cycle of conversation text surviving past the retention
  promise).
