# Reopen ticket from the portal

Status: draft, awaiting review (user away until 2026-10-04). Not implemented.

## Restatement

Customer request: "let a customer reopen a closed ticket from the portal within 14 days of it
being closed, and notify the assigned agent when they do."

Technical reading: today a **closed** ticket is final (`docs/glossary.md:12`) — `portal.reply`
throws on any closed ticket (`src/portal.js:24`), and the only existing reopen path,
`tickets.reopenTicket` (`src/tickets.js:38-44`), is agent-only and only accepts a
**resolved** ticket, not a closed one (`if (t.status !== STATUS.RESOLVED) throw ...`,
`src/tickets.js:40`). So this is new behavior, not a relaxation of something that already
exists: a second, customer-facing reopen path that accepts **closed** tickets, gated by a
14-day window measured from `closed_at`, that leaves the existing agent-only path untouched.

## What already exists (step 0)

- `tickets.reopenTicket(store, id, agentId)` (`src/tickets.js:38-44`) — agent reopens a
  **resolved** ticket back to open, notifies the previous assignee if it's a different agent.
  Pinned by exact-message assertions in `test/tickets.test.js:34-41`. This spec does not touch it.
- `portal.reply(store, customer, id, body, { now })` (`src/portal.js:21-28`) — the customer's
  only existing way to act on a ticket. Throws on closed (`src/portal.js:24`); on
  resolved/pending it flips the ticket back to open as a side effect of answering
  (`src/portal.js:26`). There is no customer-facing reopen today.
- No `DAY` constant in `src/tickets.js` — it only defines `HOUR` (`src/tickets.js:6`). The two
  job files each redefine `DAY` locally (`src/jobs/purge-closed.js:8`,
  `src/jobs/close-resolved.js:6`).

Nothing matching "customer reopen" was found built or attempted elsewhere in `src/` or `test/`.

## Design

Two new functions, kept separate from the agent path:

- **`tickets.reopenByCustomer(store, id, message, { now = new Date() } = {})`** in
  `src/tickets.js`, next to `reopenTicket`. Rules:
  1. Ticket must exist (reuse `mustGet`, `src/tickets.js:46-50`).
  2. Ticket must be **closed**; otherwise throw `` `cannot reopen a ${t.status} ticket` ``
     (same message shape as `reopenTicket`'s existing check, `src/tickets.js:40`).
  3. Must be within 14 days of `closed_at`, strict `<` — i.e. the same exclusive-window style
     `purgeClosed` already uses (`src/jobs/purge-closed.js:14`). On or after day 14, throw
     `'this ticket closed too long ago to reopen'`.
  4. `message` must be non-empty (after trimming); otherwise throw
     `'a message is required to reopen a ticket'`.
  5. On success: add the message as a customer message (`store.addMessage`, same shape as
     `reply`'s, `src/portal.js:25`), then `store.updateTicket(id, { status: STATUS.OPEN,
     resolved_at: null, closed_at: null, purged: false })`.
  6. If `t.assignee_id` is set, call `notifyAgent(store, t.assignee_id, { type:
     'ticket_reopened_by_customer', ticketId: id })`. If there's no assignee, skip the call —
     `notifyAgent` throws when given no agent (`src/notify.js:7`), and an unassigned closed
     ticket has nobody to notify.
  7. Add `const DAY = 24 * HOUR;` next to the existing `HOUR` (`src/tickets.js:6`) rather than
     inlining the literal a third time.

- **`portal.reopen(store, customer, id, message, { now = new Date() } = {})`** in
  `src/portal.js`, next to `reply`. Org-scoping wrapper mirroring `getMyTicket`/`openTicket`:
  look the ticket up with `getMyTicket` (`src/portal.js:10-14`); if it's `null` (wrong org or
  missing), return `null` rather than throwing. Otherwise delegate to
  `tickets.reopenByCustomer` and let its errors (wrong status, window expired, empty message)
  propagate — this matches how `reply` already lets the "closed" throw bubble up
  (`src/portal.js:24`) instead of swallowing it.

`portal.reply` is **not** changed to also reopen closed tickets — reopening is a distinct,
deliberate customer action with its own message and its own event type, not a side effect of
replying.

### Why `closed_at` and `resolved_at` both clear to null

A ticket's null-valued timestamp fields already mean "not currently in that state": `reopenTicket`
clears `resolved_at` when taking a resolved ticket back to open (`src/tickets.js:41`). Clearing
`closed_at` on reopen keeps that same convention, and it also lets the ticket close normally a
second time — `closeResolved` only looks at `resolved_at` (`src/jobs/close-resolved.js:10-11`), so
leaving a stale `closed_at` around would not itself block that, but clearing it keeps the field
meaning "the time it was last closed, or never" rather than "the time it was first closed."

### Why `purged` resets unconditionally — not just when previously `false`

`purgeClosed` treats `purged` as a one-way latch: `if (t.purged) continue` (`src/jobs/purge-closed.js:13`).
If a ticket was closed, purged (messages deleted, `purged: true`), then reopened, replied to, and
closed again, a `purged` left at `true` would make the *second* close-and-purge cycle skip it
forever — the new conversation's messages would never be deleted, breaking the 7-day retention
promise Legal asked for (`src/jobs/purge-closed.js:3-4`). So `reopenByCustomer` resets
`purged: false` every time it reopens a closed ticket, whether or not it had been purged yet.

## Edge cases

1. **Empty or whitespace-only message.** Rejected with `'a message is required to reopen a
   ticket'`; no state change, no notification, no message added. Mirrors the idea that
   `addMessage`/`reply` always carry real content — nothing today sends a blank message.
2. **Wrong organisation.** A customer tries to reopen another org's ticket. Handled by
   `portal.reopen` returning `null` (not found) before `tickets.reopenByCustomer` is ever
   called — same pattern as `getMyTicket` (`src/portal.js:12`) and the existing cross-org test
   (`test/tickets.test.js:46`).
3. **No assignee.** The ticket was closed while unassigned. Reopen still succeeds; the
   notification step is skipped (not attempted and not an error) because `notifyAgent` would
   throw on a null agent (`src/notify.js:7`).
4. **Already purged.** The ticket's messages were already deleted by a prior `purgeClosed` run
   (`purged: true`, `src/jobs/purge-closed.js:16`). Reopen still succeeds: the new message is
   added to what is now an empty message list, and `purged` resets to `false` so a future
   close-and-purge cycle will correctly purge the new conversation too (see design note above).
5. **Boundary at exactly 14 days.** `now - closed_at == 14 * DAY` is treated as expired (the
   window check is strict `<`, matching `purgeClosed`'s own strict `<` at
   `src/jobs/purge-closed.js:14`), so the window is "up to but not including" day 14.
6. **Concurrent reopen attempts.** Two reopen calls racing on the same ticket id. The in-memory
   store's `updateTicket` (`src/store.js:19-24`) is a synchronous last-write-wins merge, same as
   every other mutation in this codebase (`resolveTicket`, `reopenTicket`); no new locking is
   introduced here, consistent with the rest of `tickets.js`.

## Assumptions

- The 14-day window is measured from `closed_at` using a strict `<` (exclusive) comparison,
  matching `purgeClosed`'s existing convention. **Confidence: high** (direct precedent at
  `src/jobs/purge-closed.js:14`).
- `resolved_at` and `closed_at` both clear to `null` on reopen. **Confidence: medium** — flagged
  as open question #1 below; it's a new case (no ticket in this codebase has had `closed_at`
  cleared before), reasoned from the existing "null means not currently in that state"
  convention rather than observed directly.
- `purged` resets to `false` unconditionally, even if the ticket was never purged.
  **Confidence: high** given the one-way-latch mechanics of `purgeClosed`, but still called out
  as open question #2 since it's a deliberate decision, not just a mechanical default.
- The customer must supply a non-empty message to reopen. **Confidence: medium** — flagged as
  open question #3.
- No limit on how many times a ticket can be reopened this way, and no SLA reset.
  **Confidence: medium** — flagged as open question #4.
- New notify event type is `'ticket_reopened_by_customer'`, distinct from the agent path's
  `'ticket_reopened'` (`src/tickets.js:42`), so agents/analytics can tell who reopened it.
  **Confidence: medium**, not asked separately since it follows directly from "notify the
  assigned agent" plus keeping the two reopen paths distinguishable; low cost to rename later.

## Open questions (user away — recommendations applied, mark as assumed until confirmed)

1. **Should reopening clear both `resolved_at` and `closed_at` to `null`, or leave `closed_at`
   set as a historical record?** Recommend: clear both to `null`. It matches the convention
   `reopenTicket` already sets (`src/tickets.js:41`) and keeps the ticket able to close normally
   a second time without a stale `closed_at` lying around.
2. **Should `purged` reset even if the ticket had already been purged?** Recommend: yes,
   unconditionally. `purgeClosed`'s `purged` flag is a one-way latch (`src/jobs/purge-closed.js:13`);
   leaving it `true` after a reopen would silently break the 7-day message-retention policy on
   the next close.
3. **Should the customer be required to include a message when reopening, or can it be a bare
   status change?** Recommend: require a non-empty message. It gives the agent context and
   keeps the action visible in the ticket's own history, at the cost of one validation check.
4. **Should there be a cap on repeat reopens, or an SLA reset on reopen?** Recommend: no cap, no
   SLA reset. Nothing in the current code tracks reopen counts or re-arms the SLA clock for the
   agent path either; add a limit later only if repeat-reopen abuse actually shows up.

## Acceptance criteria

1. `tickets.reopenByCustomer` on a **closed** ticket, within 14 days of `closed_at`, with a
   non-empty message: ticket status becomes `open`, `resolved_at` and `closed_at` become `null`,
   the message is recorded via `store.addMessage`.
2. Reopening sets `purged` to `false`, whether it was `false` or already `true`.
3. Reopening at exactly 14 days (`now - closed_at === 14 * DAY`) throws
   `'this ticket closed too long ago to reopen'`; no state change.
4. Reopening a ticket that is `open`, `pending`, or `resolved` (not `closed`) throws
   `` `cannot reopen a ${status} ticket` ``; no state change.
5. Reopening with an empty or whitespace-only message throws
   `'a message is required to reopen a ticket'`; no state change, no message added.
6. If the ticket has an `assignee_id`, reopening calls `notifyAgent` with event type
   `ticket_reopened_by_customer` and that agent id. If `assignee_id` is `null`, no call to
   `notifyAgent` is made and no error is thrown.
7. `portal.reopen` returns `null` (does not throw) when the ticket does not belong to the
   calling customer's organisation, or does not exist.
8. `tickets.reopenTicket` (the agent-only, resolved-only path) is unchanged; all of
   `test/tickets.test.js:24-41` still pass without modification.
9. `docs/glossary.md`'s "closed: final" bullet (`docs/glossary.md:12`) is updated to note the
   14-day customer-reopen exception, so the glossary stays accurate.

## Out of scope

No SLA reset, no limit on number of reopens, no change to `portal.reply` or to the agent-only
`tickets.reopenTicket`, no change to how `purgeClosed`/`closeResolved` select tickets (they
already operate on current status/timestamps, which this feature updates correctly).
