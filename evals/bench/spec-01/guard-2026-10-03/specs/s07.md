# Spec: customer self-service ticket reopen

Status: **draft — written while the requester was away; not yet reviewed.**

## 1. Restatement

Request, in the customer-support sense: a customer who already has a closed
ticket should be able to reopen it themselves from the portal, instead of
filing a new one, as long as it hasn't been closed too long — and whoever
owns that ticket on the agent side should be told it came back.

Technical reading: add a portal-facing action that takes a **closed**
ticket back to **open** when called within 14 days of `closed_at`
(`docs/glossary.md:12` defines closed as "final... they start a new
ticket" — this spec is the one approved exception to that rule, so the
glossary needs a matching edit), and queue a notification to
`assignee_id` through the existing `notify.notifyAgent` the same way
`tickets.js:42` already does for the agent-initiated reopen.

This is a new customer-facing action, not a change to the existing
agent-only `reopenTicket` (`src/tickets.js:38-44`), which only accepts a
**resolved** ticket and is pinned by exact-message assertions in
`test/tickets.test.js:37` and `:40`. The two reopen paths are kept
separate throughout this spec.

- `src/tickets.js:6` — `HOUR` constant; no `DAY` constant exists yet in this file (each job file redefines `DAY` locally: `src/jobs/close-resolved.js:6`, `src/jobs/purge-closed.js:8`). New code needs one.
- `src/tickets.js:38-44` — `reopenTicket(store, id, agentId)`, the agent-only path. Untouched by this spec.

- `src/portal.js:21-28` — `reply`, the closest existing precedent: loads via `getMyTicket`, throws on `closed`, calls `store.addMessage`, then `store.updateTicket` to flip status and clear `resolved_at`.
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`; throws if `agentId` is falsy, so callers must guard, not rely on it to no-op.
- `src/jobs/purge-closed.js:13` — `if (t.purged) continue`. **The one correctness-critical touchpoint**: this is a one-way latch keyed only on the `purged` flag, not on `closed_at`. See §4, assumption 5.
- `src/store.js:19-24` — `updateTicket`, a plain `Object.assign` patch; no transaction or optimistic-lock support, so the reopen write is a single call like every other mutation in this codebase, not a new mechanism.
- `test/tickets.test.js` — existing ticket lifecycle tests; new tests for this feature belong here.
- `docs/glossary.md:12` — the "closed... final" line that this feature is the exception to.

## 3. Edge cases

1. **Message is empty or whitespace-only.** Rejected before any store write — `reopenByCustomer` throws, same defensive style as the rest of `tickets.js` (e.g. `mustGet`'s not-found throw).
2. **Ticket is not closed** (open/pending/resolved). Rejected with a status error; never silently no-ops, since a customer intentionally decided to reopen it.
3. **Exactly at the 14-day boundary.** `now - closed_at` equal to `14 * DAY` is treated as *expired* (strict `<` to stay eligible), matching the "still within the window" comparison style already used in `close-resolved.js:11` and `purge-closed.js:14`.
4. **Ticket belongs to a different organisation.** Returns `null` from the portal wrapper, mirroring `getMyTicket` (`src/portal.js:12`) — never leaks existence of another org's ticket via an error message.
5. **Ticket's messages were already purged** (closed 7+ days, so `purgeClosed` ran, but still inside the 14-day reopen window). Reopen still succeeds — `purgeClosed` keeps the ticket row for reporting (`src/jobs/purge-closed.js:2-3`), so there's a valid row to reopen; the customer just starts the visible conversation over. This is exactly why the `purged` flag must be reset (assumption 5) — otherwise a second close would never get purged.
6. **Ticket has no assignee** (`assignee_id` is `null`, still in the unassigned queue). Notification is skipped — calling `notifyAgent` with no agent throws (`src/notify.js:7`), so the caller must check first, not rely on a try/catch.
7. **Customer reopens, it gets closed again, then reopens a second time** within 14 days of the *second* close. No count limit (see out-of-scope); each reopen is independent and keyed off the current `closed_at` only.

## 4. Assumptions

1. **Only the ticket's own-org customer can call this**, through the same org-scoping wrapper pattern as every other `portal.js` function. *(high confidence — directly follows the existing module's own stated contract, `src/portal.js:2-3`)*
2. **Target status is `open`**, not `pending`. *(high confidence — matches both existing reopen paths: `tickets.js:41` and `portal.js:26` both land on `OPEN`)*
3. **A non-empty message is required**, stored as a normal customer message (`from: 'customer'`), giving the agent context for why it came back. *(medium confidence — the request doesn't say this explicitly; recommended because `reply()` already requires a body for every other customer action, and "just a button with no context" is a worse support experience. Flagged in §6 for sign-off.)*
4. **Both `resolved_at` and `closed_at` are cleared to `null`** on reopen. *(medium confidence — consistent with `reopenTicket` clearing `resolved_at`, and with the ticket no longer being in either of those states; flagged in §6 since nothing today reads a stale `closed_at` on a non-closed ticket, so this is a hygiene choice, not something a test can currently distinguish.)*
5. **`purged` must be unconditionally reset to `false`** on every reopen, even if it was already `true`. *(high confidence — not a style choice. `purge-closed.js:13` skips any ticket with `purged: true` forever, regardless of a new `closed_at`. Without this reset, a ticket that is reopened-and-reclosed after being purged once would never have its second round of messages purged — a silent miss of the retention policy `purge-closed.js:3-4` says Legal asked for.)*
6. **No SLA reset and no reopen-count limit.** *(high confidence this is out of scope — the request only asks for reopen + notify; see §7.)*
7. **New notification event type**, e.g. `ticket_reopened_by_customer`, distinct from the agent path's `ticket_reopened` (`tickets.js:42`). *(high confidence — the agent will want to tell the two apart, and reusing the same event type with a different `by` field is a smaller distinction than this already-established pattern uses elsewhere.)*
8. **A `DAY` constant is added to `tickets.js`** (`const DAY = 24 * HOUR;`) rather than inlining the literal a third time alongside the two job files. *(high confidence, pure code hygiene.)*

## 6. Open questions (answered by recommendation — user unavailable)

1. **Should reopening require a message from the customer, or is a bare "reopen" action enough?**
   Recommend: **require a non-empty message**, stored like any other customer reply, so the agent has context. *(assumption 3)*
2. **Should `closed_at` be cleared back to `null`, or kept as a record of when it was last closed?**
   Recommend: **clear it to `null`**, matching how `resolved_at` is already cleared on both existing reopen paths; nothing currently reads `closed_at` on a ticket that isn't closed. *(assumption 4)*
3. **What should the reopen window be measured from if the ticket was reopened and closed more than once?**
   Recommend: **always the current `closed_at`** — each close/reopen cycle is independent, no cumulative tracking. *(assumption 7 in the project memory sense; no count limit — see out of scope)*
4. **Should the notification distinguish a customer-initiated reopen from an agent-initiated one?**
   Recommend: **yes, a new event type** (`ticket_reopened_by_customer`) rather than reusing `ticket_reopened`, since the agent will want to tell the two apart. *(assumption 7)*

## 7. Acceptance criteria

1. `tickets.js` exports a new `reopenByCustomer(store, id, message, { now = new Date() })` that:
   a. throws if `message` is empty or whitespace-only;
   b. throws if the ticket's status is not `closed`;
   c. throws if `now.getTime() - new Date(t.closed_at).getTime() >= 14 * DAY` (14-day window, exclusive at the boundary);
   d. otherwise adds a customer message (`from: 'customer'`, the given `message`, `at: now.toISOString()`) via `store.addMessage`;
   e. updates the ticket to `status: STATUS.OPEN`, `resolved_at: null`, `closed_at: null`, `purged: false` (unconditionally — criterion 6 is the one that must never regress);
   f. if `assignee_id` is non-null, calls `notifyAgent(store, assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id })`; if `assignee_id` is `null`, skips notification entirely (no throw);
   g. returns the updated ticket.
2. `portal.js` exports `reopen(store, customer, id, message, { now = new Date() })` that:
   a. returns `null` if the ticket doesn't exist or doesn't belong to `customer.orgId` (same check as `getMyTicket`);
   b. otherwise calls and returns `tickets.reopenByCustomer(store, id, message, { now })`, letting its validation errors (empty message, wrong status, window expired) propagate.
3. `tickets.reopenTicket` (the agent path) is unchanged byte-for-byte; `test/tickets.test.js:37` and `:40`'s existing assertions still pass unmodified.
4. A ticket whose messages were already purged (`purged: true`, still within the 14-day window) can still be reopened, and `purged` becomes `false` afterward.
5. A ticket reopened once, closed again, and reopened a second time has its second-cycle `closed_at`/window computed independently of the first cycle.
6. **Regression test added:** a ticket is closed, purged, reopened, closed again, and purged again — the second `purgeClosed` run must delete its messages a second time (proves the `purged` latch reset in 1.e, not just that reopen "works").
7. `docs/glossary.md`'s **closed** bullet (`docs/glossary.md:12`) is updated to note the 14-day customer reopen exception, so "final" no longer reads as absolute.
8. New tests are added to `test/tickets.test.js` covering: happy-path reopen + notification event type, empty message rejection, non-closed-status rejection, window-boundary rejection (13 days ok, 14 days rejected), cross-org `null`, and the criterion-6 double-purge regression.

## 8. Out of scope

- Any change to `sla_due_at` on reopen (no SLA reset).
- A limit on how many times a ticket may be reopened.
- Any HTTP/API route or UI wiring — this codebase has no web layer yet (`src/portal.js` is a plain module, not a server); this spec covers only the business-logic functions `tickets.reopenByCustomer` and `portal.reopen`.
- Changing `reopenTicket`'s (agent-side) behavior or error wording in any way.
