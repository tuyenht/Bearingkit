# Spec: customer self-service ticket reopen

Status: **draft, awaiting review** (written while the requester was away; not implemented)

## Request, restated

> Let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do.

Technical reading: add a new portal action, separate from the existing agent-only `reopenTicket`, that:
- takes a closed ticket belonging to the calling customer's organisation,
- checks it closed less than 14 days ago,
- requires a reopen message (so there's something for the agent to see, matching how a reply works today),
- moves it back to `open`,
- notifies the assigned agent (if any),
- and undoes anything the nightly purge job would otherwise treat as final.

This doesn't change what "closed" means for an agent's `reopenTicket` (`src/tickets.js:38`) or for `portal.reply` (`src/portal.js:21`) — both keep rejecting closed tickets exactly as today. The new path is a distinct, deliberate action a customer takes, not a side effect of replying.

## Questions I'd ask, answered by recommendation

**Q1: Does reopening require a message from the customer, or can it be a bare status flip?**
Recommend: **require a non-empty message**, stored the same way a reply is (`from: 'customer'`). Rationale: an agent re-reading a reopened ticket needs to know *why* — a reopen with no content is strictly worse than today's "start a new ticket" instruction. This also keeps the ticket's message history self-explanatory for reporting.

**Q2: Window is "within 14 days of it being closed" — closed means `closed_at`, and is it a strict or inclusive boundary?**
Recommend: `now - closed_at < 14 days` (strict `<`, same style as the existing `QUIET_DAYS`/`KEEP_DAYS` checks in `src/jobs/close-resolved.js:11` and `src/jobs/purge-closed.js:14`). A ticket closed exactly 14 days and 0 seconds ago is just outside the window. Pick `closed_at`, not `resolved_at` — a ticket can sit resolved for 3 quiet days before auto-closing, and the reopen window should count from when it actually became final, not from when the agent finished it.

**Q3: What happens to `resolved_at` and `closed_at` on reopen?**
Recommend: **clear both to `null`**, mirroring what `reopenTicket` does to `resolved_at` (`src/tickets.js:41`) and what `reply` does when it pulls a resolved/pending ticket back to open (`src/portal.js:26`). Leaving `closed_at` set would be inert today, but it's one less stale timestamp to explain later, and it matches the existing precedent of clearing timestamps that no longer apply. **Medium confidence — flagging for explicit sign-off since it's not forced by any existing test.**

**Q4: Does the 14-day reopen window reset the SLA clock (`sla_due_at`) or count against any reopen limit?**
Recommend: **no SLA reset, no reopen-count limit** for this first version. Nothing in the request asks for either, `sla_due_at` is only ever set once today (`src/tickets.js:16`), and adding a limit/reset is speculative scope the requester didn't ask for. Can be added later as its own change if agents complain about repeat-reopen abuse.

**Q5: What if the ticket has already been purged (messages deleted by the nightly `purgeClosed` job, `src/jobs/purge-closed.js`) but is still within the 14-day reopen window?**
Recommend: **allow the reopen anyway.** `purgeClosed` only deletes message *text* after 7 days closed; the ticket row survives as a summary. 7 days < 14 days, so a customer reopening late in the window will find an empty message history but can still reopen and add a new message — better than refusing a reopen the request explicitly promised. This is why acceptance criterion #6 below exists: a ticket reopened after being purged must be purge-*eligible again* if it's closed a second time (see Q6).

**Q6 (the one non-negotiable item): if a previously-purged ticket is reopened and later closed again, must it be purged again after 7 more days?**
Recommend: **yes — unconditionally reset `purged: false` on reopen.** `purgeClosed` treats `purged` as a one-way latch (`src/jobs/purge-closed.js:13`, `if (t.purged) continue`). If reopen does not reset it, a ticket that goes closed → purged → reopened → closed again would never have its *second* round of conversation text deleted, silently breaking the 7-day retention promise in the job's own comment ("Legal asked for this: we do not keep conversation text of finished tickets longer than a week"). This is a compliance correctness issue, not a style preference, so it's listed as its own acceptance criterion rather than folded into "reopen clears state."

**Q7: Does the agent get notified for every reopen, or only if a different agent should know (compare to `reopenTicket`'s `t.assignee_id !== agentId` check, which skips notifying an agent who reopened their own ticket)?**
Recommend: **always notify the assignee if one exists**, with no "unless it's the same person" check — unlike the agent-reopen path, the customer is never the assignee, so that suppression doesn't apply here. If there is no assignee (`assignee_id === null`), **skip notification silently** — `notifyAgent` throws on a falsy agent id (`src/notify.js:7`), and an unassigned ticket has nobody to tell yet.

**Q8: What event type should the notification carry?**
Recommend: a new, distinct event type `ticket_reopened_by_customer` (not reusing `ticket_reopened`), so agent-side notification handling/filtering can tell "the agent brought this back" apart from "the customer brought this back" if it ever needs to. Payload shape mirrors the existing one: `{ type: 'ticket_reopened_by_customer', ticketId, by: 'customer:<id>' }`.

## Design

**New function in `src/tickets.js`:**
```js
const DAY = 24 * HOUR; // tickets.js currently only defines HOUR; jobs redefine DAY locally — add it here once, reuse it
const REOPEN_WINDOW_DAYS = 14;

function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed more than 14 days ago; please open a new one');
  }
  if (!message || !message.trim()) throw new Error('a reopen needs a message');
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id, by: `customer:${t.customer_id}` });
  return updated;
}
```
Exported alongside the existing functions. Kept separate from `reopenTicket` (agent-only, resolved→open) — that function is untouched and still pinned by the exact-message assertions in `test/tickets.test.js:37,40`.

**New wrapper in `src/portal.js`:**
```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, message, { now });
}
```
Mirrors the org-scoping pattern already used by `openTicket`/`getMyTicket`/`reply` — returns `null` for a ticket that isn't the customer's rather than leaking existence of another org's ticket.

**`docs/glossary.md` update:** the "closed: final... If the customer comes back, they start a new ticket" bullet needs a qualifier, e.g.: "closed: final, unless the customer reopens it from the portal within 14 days — after that window, or after declining to reopen, they start a new ticket."

## Edge cases

| Case | Handling |
|---|---|
| Ticket is not closed (open/pending/resolved) | `reopenByCustomer` throws `cannot reopen a ${status} ticket`, same style as the existing agent-side check |
| Ticket closed exactly 14 days ago (boundary) | Rejected — window check is strict `<` on elapsed time, consistent with `QUIET_DAYS`/`KEEP_DAYS` elsewhere |
| Empty or whitespace-only message | Rejected with `a reopen needs a message` before any state changes |
| Ticket belongs to another organisation | `portal.reopen` returns `null` via `getMyTicket`'s org check, same as every other portal function |
| Ticket already purged (messages deleted, still in window) | Allowed; customer sees an empty history and starts fresh; `purged` is reset to `false` so a second close cycle purges again after 7 more days (acceptance criterion #6) |
| No assignee on the ticket | Notification is skipped silently; `notifyAgent` is never called with a falsy id (it would throw, `src/notify.js:7`) |
| Reopened ticket closes again later | Goes through the normal `closeResolved`/`purgeClosed` nightly jobs exactly as a fresh ticket would, because `closed_at`, `resolved_at`, and `purged` were all reset |
| Concurrent reopen + nightly purge job | Not a real race in this codebase — both run synchronously against the in-memory/DB store with no shared background timer in tests; same assumption as every existing job/portal interaction. Flagged if the production store is ever made concurrent. |

## Assumptions

1. "Closed" in the request means ticket status `closed` as defined in `docs/glossary.md`, not "resolved." (high)
2. The 14-day window counts from `closed_at`, not `resolved_at`. (high — this is the only timestamp that means "became final")
3. A reopen requires a message. (medium — reasonable default, not stated in the request)
4. `resolved_at` and `closed_at` both clear to `null` on reopen. (medium — flagged above for sign-off)
5. No SLA reset, no reopen-count cap, in this first version. (high — nothing in the request asks for either)
6. `purged` must reset to `false` on reopen. (high — forced by the one-way-latch behavior of `purgeClosed`, not a judgment call)
7. New event type `ticket_reopened_by_customer` rather than reusing `ticket_reopened`. (medium — naming choice, easy to change)

## Acceptance criteria

1. Reopening a closed ticket within 14 days of `closed_at` sets status to `open`.
2. Reopening a ticket closed ≥14 days ago throws and leaves the ticket unchanged.
3. Reopening a ticket that is not closed (open/pending/resolved) throws and leaves the ticket unchanged.
4. Reopening without a message (empty or whitespace-only) throws and leaves the ticket unchanged.
5. A successful reopen adds the given message to the ticket's messages, authored `from: 'customer'`.
6. A successful reopen resets `purged` to `false`, even if the ticket had already been purged — verified by: reopen a purged-and-closed ticket, close it again, run `purgeClosed` after 7 more days, and confirm its (new) messages are deleted.
7. A successful reopen clears `resolved_at` and `closed_at` to `null`.
8. If the ticket has an assignee, reopening queues exactly one notification of type `ticket_reopened_by_customer` to that agent.
9. If the ticket has no assignee, reopening queues no notification and does not throw.
10. `portal.reopen` returns `null` (and does not call into `reopenByCustomer`) for a ticket belonging to a different organisation than the calling customer.
11. The existing agent-only `reopenTicket` (`src/tickets.js:38`) and `portal.reply`'s closed-ticket rejection (`src/portal.js:24`) are unchanged — existing tests in `test/tickets.test.js` keep passing unmodified.
