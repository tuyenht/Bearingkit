# Spec: customer reopen of a closed ticket

Status: **draft, awaiting review** (written while the requester was away; every
open question below is answered with a recommendation and the rest of the
spec is built on that recommendation, per their instruction not to block on
live Q&A).

## Problem

Customers keep asking for a way to reopen a ticket that has already been
closed, instead of opening a brand-new one and losing context. Today
`docs/glossary.md` is explicit that closed is final: *"If the customer comes
back, they start a new ticket."* `portal.reply` (`src/portal.js:21-28`)
enforces that by throwing on any closed ticket. We're relaxing this, but only
within a bounded window and only through a deliberate, explicit action (not
as a side effect of replying).

## Scope

- A portal customer can reopen their own closed ticket within **14 days** of
  its `closed_at`.
- Reopening requires a message from the customer (why they're reopening).
- The ticket's assigned agent, if any, is notified.
- Agent-side reopen (`tickets.reopenTicket`, resolved → open) is untouched.

## Questions and recommended answers

1. **Q: How long is the reopen window, and measured from what?**
   A: 14 days from `closed_at`, using the same strict `<` convention the
   nightly jobs already use (`closeResolved`'s `resolved_at` check,
   `purgeClosed`'s `closed_at` check in `src/jobs/*.js`). So: allowed while
   `now - closed_at < 14 days`; at or past 14 days, reject.

2. **Q: Who gets notified, and what if the ticket has no assignee?**
   A: Notify the assigned agent via the existing `notifyAgent` queue
   (`src/notify.js`). If `assignee_id` is null, skip notification silently —
   there's no one to tell, and that's not an error.

3. **Q: New event type, or reuse the agent-reopen event (`ticket_reopened`)?**
   A: New event type, `ticket_reopened_by_customer`. The existing
   `ticket_reopened` event (from `tickets.reopenTicket`) means something
   narrower — an agent pulling a *resolved* ticket back — and reporting/metrics
   will want to tell "an agent changed their mind" apart from "a customer came
   back after close."

4. **Q: New function, or extend `tickets.reopenTicket`?**
   A: New function, `tickets.reopenByCustomer`. The two have different
   preconditions (resolved-only vs. closed-only), different side effects
   (message required, `purged` reset — see Q7), and different notify rules
   (always-if-different-agent vs. if-any-assignee). `reopenTicket` is also
   pinned by exact-message assertions in `test/tickets.test.js:37,40`
   (`/cannot reopen a open ticket/`, `/cannot reopen a closed ticket/`) —
   changing its behavior risks breaking those. Keeping them separate avoids
   entangling two different business rules in one function.

5. **Q: Is a customer message required to reopen, or optional?**
   A: Required, non-empty. A customer reopening a ticket needs to say why
   (what's still wrong) — the same way the original `createTicket` always
   requires a `body`. This also gives the agent something to act on besides
   a bare status flip.

6. **Q: Does reopening reset the SLA due time?**
   A: No. `sla_due_at` is set once, at creation (`src/tickets.js:16`), and
   nothing else in the codebase ever touches it — not `resolveTicket`, not
   the agent `reopenTicket`. Resetting it here would be new and surprising
   behavior for a feature that isn't asking for SLA changes. If support
   wants SLA re-tracking on customer reopen later, that's a separate,
   explicit request.

7. **Q: What happens to the `purged` flag if the ticket was already purged
   (messages deleted after 7 days) before being reopened within the 14-day
   window?**
   A: Reset `purged` to `false`, unconditionally, on every reopen. This is
   the one non-negotiable part of this spec. `purgeClosed` (`src/jobs/purge-closed.js:13`)
   treats `purged` as a one-way latch: `if (t.purged) continue` — it will
   never purge that ticket again once the flag is set. A closed ticket is
   purged after 7 days; the reopen window is 14 days; so it is entirely
   possible for a customer to reopen a ticket whose messages are already
   gone. If we don't reset `purged`, the *new* conversation added after this
   reopen (and after any subsequent close) will never be purged — the
   nightly job will skip it forever, which is a retention-policy violation
   (Legal's "don't keep conversation text of finished tickets longer than a
   week" comment in `purge-closed.js:3-4`), not just a cosmetic bug.

8. **Q: Do `resolved_at` and `closed_at` get cleared on reopen?**
   A: Yes, both set back to `null`. The ticket is active again and its
   status is `open`, same as what `resolveTicket`/the agent `reopenTicket`
   already do with `resolved_at` when a ticket goes back to open
   (`src/tickets.js:34,41`). Leaving a stale `closed_at` around while
   `status: 'open'` would be inconsistent with every other code path, and
   would make "time since closed" math wrong if anything ever reads it
   while the ticket is open. (Flagging this one as medium-confidence — it's
   a small modeling choice, not a hard requirement from the ask. Easy to
   change if you'd rather keep `closed_at` as "last closed" history.)

9. **Q: Is there a limit on how many times a ticket can be reopened this
   way?**
   A: No limit. Nothing in the request asks for one, and the codebase has no
   precedent for counting reopens. Add one later if abuse shows up.

10. **Q: Does `docs/glossary.md`'s definition of "closed" need to change?**
    A: Yes — its current wording ("closed: final. A closed ticket is never
    changed again. If the customer comes back, they start a new ticket.") is
    now wrong and should say closed tickets can be reopened by the customer
    within 14 days.

## Design

### `tickets.reopenByCustomer(store, id, message, { now = new Date() } = {})`

New function in `src/tickets.js`, alongside the existing `reopenTicket`.

```js
const REOPEN_WINDOW_DAYS = 14;

function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket closed more than 14 days ago and can no longer be reopened');
  }
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id });
  }
  return updated;
}
```

(`DAY` already exists as a local constant pattern in the jobs files; add the
same `60*60*1000*24` constant to `tickets.js`, or import it — either is fine,
jobs files each define their own copy today.)

### `portal.reopen(store, customer, id, message, { now = new Date() } = {})`

New function in `src/portal.js`, mirroring the org-scoping pattern of
`getMyTicket`/`openTicket`/`reply`:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, message, { now });
}
```

Returns `null` for a missing ticket or one belonging to another
organisation (same convention as `getMyTicket`/`reply`), and throws for a
business-rule violation on a ticket the customer *can* see (wrong status,
window expired, empty message) — same split `reply` already uses.

- `src/tickets.js` — add `reopenByCustomer`, export it.
- `src/portal.js` — add `reopen`, export it.
- `docs/glossary.md` — update the "closed" definition (Q10).

## Acceptance criteria

1. A closed ticket can be reopened by its own customer within 14 days of
   `closed_at`, moving it to `status: 'open'`.
2. Reopening appends the customer's message to the ticket's messages.
3. Reopening clears `resolved_at` and `closed_at` to `null`.
4. If the ticket has an assignee, reopening queues a
   `ticket_reopened_by_customer` notification to that agent; if unassigned,
   no notification is queued.
5. Reopening with no message, or a whitespace-only message, throws.
6. Reopening a ticket that is not closed throws (e.g. `cannot reopen a open
   ticket`), same wording pattern as the existing agent `reopenTicket`.
7. Reopening after the 14-day window throws and leaves the ticket closed.
8. **If the ticket's `purged` flag was already `true`, reopening resets it
   to `false`.** A subsequent close-and-7-days-quiet cycle must purge the
   new conversation again — this is the retention-policy-critical case and
   needs its own test.
9. A customer cannot reopen a ticket belonging to another organisation
   (`portal.reopen` returns `null`, same as `getMyTicket`).
10. `docs/glossary.md` reflects the new reopen window instead of "closed is
    final."

## Out of scope (explicitly, so it isn't quietly added later)

- SLA re-tracking on reopen.
- A cap on number of reopens per ticket.
- Any change to the agent-side `reopenTicket` (resolved → open) path.
- Reopening a ticket that was closed but never purged vs. one that was —
  both are handled identically by criterion 8; there's no separate code
  path for "already purged."
