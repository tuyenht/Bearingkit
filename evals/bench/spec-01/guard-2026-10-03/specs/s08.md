# Spec: customer reopens a closed ticket from the portal

**Status:** awaiting review. Written while the requester was away; every
open question below is answered with a recommendation rather than left
for a live Q&A, per their request. Nothing in this spec has been built.

## 1. Request, restated

Customer-facing: a customer should be able to reopen their own ticket
after support has closed it, as long as it hasn't been closed too long,
and the agent who owned it should hear about it.

Technical reading: add a portal-facing action that moves a ticket from
`closed` back to `open` when `now - closed_at` is under a threshold,
distinct from the existing agent-only reopen path
(`tickets.reopenTicket`, `src/tickets.js:38`, which only accepts a
`resolved` ticket and has no time limit), and queue a notification to
the assignee via the existing `notify.notifyAgent` (`src/notify.js:6`).

No gap between the two readings — "reopen" here always means customer
-initiated, from the portal, on a ticket currently `closed`.

## 2. Clarifying questions, answered inline

1. **How is the 14-day window measured, and is day 14 itself allowed?**
   Recommend: measured from `closed_at`, using the same idiom already in
   this codebase (`src/jobs/close-resolved.js:11`,
   `src/jobs/purge-closed.js:14`): allowed while
   `now - closed_at < 14 * DAY`. So a ticket closed exactly 14 days ago
   (to the millisecond) is just past the window — consistent with how
   the nightly jobs treat their own day windows.

2. **Does the customer have to say why?**
   Recommend: yes, require a non-empty message, same validation level as
   any other customer reply. An agent who gets pulled back into a ticket
   with no text to go on is the complaint this feature exists to avoid.

3. **What status does a reopened ticket land in — `open` or `pending`?**
   Recommend: `open`. The customer is the one acting, so the ticket
   should land where it already lands when a customer answers a resolved
   ticket (`src/portal.js:26`): waiting for an agent, not waiting for the
   customer.

4. **Do `resolved_at` and `closed_at` get cleared?**
   Recommend: yes, both reset to `null` — a reopened ticket is active
   again and neither timestamp is still true. **Medium confidence** —
   flagging this one explicitly because nothing else in the code reads
   `resolved_at`/`closed_at` off a ticket that isn't in that corresponding
   status today, so there's no existing behavior to match against. If
   reporting ever wants "was this ticket ever closed before," that's a
   history question this spec doesn't answer and `purged`/the message
   log already lose that detail anyway.

5. **Does this interact with the nightly purge job?** This is the one
   answer that isn't really a judgment call. `purgeClosed`
   (`src/jobs/purge-closed.js:13`) skips any ticket where `purged` is
   already `true` — it's a one-way latch, not a status check. A ticket
   can be closed, sit past the 7-day `KEEP_DAYS` purge window
   (`src/jobs/purge-closed.js:7`), get its messages deleted, and still be
   inside the 14-day reopen window (14 > 7, so this is the normal case,
   not an edge one). If a customer reopens that ticket and it's later
   closed and purged again, `purged` is still `true` from the first
   round, the nightly job's `if (t.purged) continue` skips it forever,
   and the second close's messages — which do need to go — never get
   deleted. That's a silent Legal/retention-policy miss, not a cosmetic
   bug. **Reopen must unconditionally set `purged: false`**, whether or
   not it was already `true`. This is non-negotiable, not a
   recommendation to sign off on.

6. **What event fires, and what if the ticket has no assignee?**
   Recommend: a new event type, `ticket_reopened_by_customer`, queued
   through the existing `notify.notifyAgent(store, agentId, event)`
   (`src/notify.js:6`) — don't invent a second notification path.
   `notifyAgent` throws if `agentId` is falsy (`src/notify.js:7`), and a
   ticket can sit in the unassigned queue with `assignee_id: null`
   (`src/tickets.js:14`), so: if there's no assignee, skip the
   notification silently. There's no "notify the unassigned queue"
   channel in this codebase today, and building one is out of scope for
   a reopen feature.

7. **New function, or extend the existing `reopenTicket`?**
   Recommend: new, separate functions —
   `tickets.reopenByCustomer(store, id, message, { now })` in
   `src/tickets.js`, and a portal wrapper `portal.reopen(store, customer,
   id, message, { now })` in `src/portal.js`. The agent-only
   `reopenTicket` (`src/tickets.js:38`) stays untouched: it's exercised
   by exact-message assertions in `test/tickets.test.js:34-41`
   (`/cannot reopen a open ticket/`, `/cannot reopen a closed ticket/`),
   it has different rules (resolved-only, no time limit, no customer
   message), and folding customer and agent reopen into one function
   with branching rules is a worse read than two small ones.

8. **Is this a variant of `portal.reply`, or its own action?**
   Recommend: its own action. `portal.reply` (`src/portal.js:21`)
   continues to throw on every closed ticket, unchanged — reopening is a
   deliberate, separate customer action, not a side effect of answering.
   A customer reopens, then (optionally, separately) replies.

9. **Org scoping?**
   Recommend: mirror `getMyTicket`/`openTicket`
   (`src/portal.js:10`, `src/portal.js:16`) exactly — `portal.reopen`
   returns `null` if the ticket doesn't belong to the customer's
   `orgId`, rather than throwing, so the portal layer can't be used to
   probe for another organisation's ticket IDs.

10. **SLA reset, or a limit on how many times a ticket can be reopened?**
    Recommend: neither. Nobody asked for an SLA reset and the ticket
    already has no concept of a reopen counter; adding either is scope
    nobody requested (YAGNI).

11. **Does the glossary need updating?**
    Recommend: yes. `docs/glossary.md`'s **closed** entry currently reads
    "final... If the customer comes back, they start a new ticket" —
    that's no longer true once this ships. Proposed replacement text
    (not applied by this spec):

    > **closed**: done, for now. A closed ticket is never changed by an
    > agent again, but the customer who owns it can reopen it from the
    > portal within 14 days of the close. Past that window, they start a
    > new ticket.

## 3. Edge cases

1. **Ticket closed more than 14 days ago.** Rejected —
   `reopenByCustomer` throws (e.g. `this ticket closed too long ago to
   reopen`); `portal.reopen` lets that propagate like `portal.reply`
   does for a closed ticket today.
2. **Ticket not currently closed** (open, pending, or resolved).
   Rejected — this path is for closed tickets only; throws
   `` cannot reopen a ${t.status} ticket `` (mirrors the existing message
   shape in `tickets.js:33`/`tickets.js:40`, but note it is a *different*
   function from the agent-only one, so this isn't the same error path
   the pinned tests in `test/tickets.test.js:34-41` cover).
3. **Empty or missing message.** Rejected before any state changes —
   same "must say something" rule as any other customer-authored text in
   this codebase.
4. **Ticket belongs to a different organisation.** `portal.reopen`
   returns `null`, same as `getMyTicket` on a foreign ticket
   (`src/portal.js:12`) — no error, no existence leak.
5. **Ticket has no assignee.** Reopen succeeds; the notification step is
   skipped (not attempted with a `null` agent, which would throw per
   `src/notify.js:7`).
6. **Ticket was already purged** (closed > 7 days, nightly
   `purgeClosed` already deleted its messages) but is still inside the
   14-day reopen window — this is the normal case, not a rare one, since
   the purge window (7 days) is shorter than the reopen window (14 days).
   Reopen succeeds (the ticket row and its history survive purge, only
   the messages were deleted); `purged` is unconditionally reset to
   `false` so a second close-and-wait cycle purges the ticket again. See
   question 5 above — this is the acceptance criterion that matters most.
7. **Nightly jobs racing a reopen.** Out of scope: this repo's store has
   no locking today (`src/store.js`), and a customer reopen doesn't
   introduce a new race that `resolveTicket`/`closeResolved` don't
   already have.

## 4. Assumptions

- **High** — the 14-day window uses the same `{ now = new Date() }`
  injection pattern as every other time-based function here
  (`tickets.js`, `close-resolved.js`, `purge-closed.js`), for the same
  testability reason.
- **High** — "notify the assigned agent" means the existing
  `notify.notifyAgent` queue, not a new channel (email, webhook, etc. are
  not in this codebase).
- **Medium** — clearing both `resolved_at` and `closed_at` on reopen
  (question 4). Flagged for explicit sign-off since there's no existing
  code path that reads either field off a ticket outside its matching
  status.
- **Medium** — `sla_due_at` is left untouched on reopen (question 10).
  If support actually wants a fresh SLA clock on reopened tickets, that
  changes `tickets.reopenByCustomer`'s shape; flagging so it isn't
  assumed silently.
- **Low** — none. (No unfamiliar library or platform behavior is involved
  here; everything touches code already in this repo.)

## 5. Design

New, in `src/tickets.js`:

```js
function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_DAYS * DAY) {
    throw new Error('this ticket closed too long ago to reopen');
  }
  if (!message || !message.trim()) throw new Error('say what you need before reopening');
  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id, by: `customer:${t.customer_id}` });
  }
  return updated;
}
```

`REOPEN_DAYS = 14`, exported alongside `SLA_HOURS` the way `KEEP_DAYS` and
`QUIET_DAYS` are exported from their job files. `tickets.js` currently
only defines `HOUR` (`src/tickets.js:6`), not `DAY` — add
`const DAY = 24 * HOUR;` alongside it rather than redefining the literal
a third time (it already appears in both job files).

New, in `src/portal.js`:

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, message, { now });
}
```

(`reopenByCustomer` imported from `./tickets` alongside `STATUS` and
`createTicket`.)

Both functions live beside their siblings (`reopenTicket` in
`tickets.js`, `reply`/`openTicket` in `portal.js`) rather than in a new
file — this codebase keeps one file per actor (agent vs. customer), not
per action.

## 6. Acceptance criteria

1. Reopening a `closed` ticket within 14 days of `closed_at` sets status
   to `open`, clears `resolved_at` and `closed_at`, and appends the
   customer's message.
2. Reopening a ticket closed exactly 14 days ago (or longer) throws and
   leaves the ticket unchanged.
3. Reopening a ticket that is `open`, `pending`, or `resolved` throws
   `` cannot reopen a ${status} ticket `` and leaves it unchanged.
4. Reopening with an empty or whitespace-only message throws and leaves
   the ticket unchanged.
5. `portal.reopen` on another organisation's ticket returns `null` and
   makes no change.
6. Reopening an assigned, closed ticket queues exactly one
   `ticket_reopened_by_customer` notification to that assignee.
7. Reopening an unassigned, closed ticket succeeds and queues no
   notification.
8. Reopening a ticket whose `purged` flag is already `true` (it was
   closed, sat past the 7-day purge window, and had its messages
   deleted, but is still inside the 14-day reopen window) resets
   `purged` to `false`. A subsequent close-and-7-day-wait purges it
   again (messages deleted a second time).
9. The existing agent-only `reopenTicket` behavior and its pinned error
   messages (`test/tickets.test.js:34-41`) are unchanged.
10. `portal.reply` still throws on a ticket that is `closed` (unaffected
    by this feature — reopening and replying stay separate actions).

## 7. Classification

**Files touched:** `src/tickets.js`, `src/portal.js`,
`docs/glossary.md`, `test/tickets.test.js` — four files, one over this
project's informal three-file ACT ceiling.

**Gate-pattern check:** no path or content pattern from
`gate-patterns.md` matches directly (no `auth/`, `tenant*/`, `payments/`,
`migrations/`, no `DELETE FROM`/`password`/`token`/etc. in the new
code).

**Judgment call, so classifying COUNCIL:** two things outweigh the clean
gate-pattern check. First, this changes a data-retention mechanism
(`purgeClosed`'s one-way `purged` latch) — getting the reset wrong is a
silent compliance miss, not a bug a user would notice and report, which
is exactly the kind of risk the "unsure → COUNCIL" default exists for.
Second, it crosses the org-scoping boundary (`portal.reopen` on
`customer.orgId`) that every other customer-facing function in this file
also has to get right. Neither is in a path the glob patterns watch, but
both are the kind of change the protocol's hot-path list means by "data
deletion" and "tenant scoping."

**RBA-lite:**

```
Objective: let a customer reopen their own ticket within 14 days of it
  being closed, from the portal, and notify the assignee.
Scope: src/tickets.js (new reopenByCustomer), src/portal.js (new reopen
  wrapper), docs/glossary.md (closed entry), test/tickets.test.js (new
  cases). Out of scope: SLA reset, reopen-count limits, a new
  notification channel, any change to the agent-only reopenTicket.
Rollback: revert the commit(s); no migration, no schema, no flag — the
  new fields used (purged, resolved_at, closed_at) already exist on
  every ticket row.
Edge cases:
  1. Ticket already past its 7-day purge when reopened within the
     14-day window — purged reset to false so the next close-and-wait
     purges it again (see section 3.6).
  2. Reopen attempted outside the 14-day window — rejected, ticket
     unchanged.
  3. Reopen attempted on an unassigned ticket — succeeds, no
     notification sent (notifyAgent would throw on a null agent).
Decision: needs approval — because of the purged-latch interaction and
  the medium-confidence call on clearing resolved_at (section 4), this
  stops here for the requester's sign-off rather than proceeding to
  bk-plan unapproved.
```
