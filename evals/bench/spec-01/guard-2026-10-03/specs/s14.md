# Spec: customer reopen of a closed ticket

Status: **draft, awaiting review** — written while the requester was away; no live Q&A was done. Every open question below carries the recommended answer the rest of this spec is built on, per the requester's instruction to proceed on recommendations rather than wait.

## Request, restated

Let a customer reopen their own ticket from the portal within 14 days of it being closed, and notify the ticket's assigned agent when they do.

Technical reading: add a customer-facing path from `closed` back to `open`, gated on `now - closed_at < 14 days`, that records the customer's reason as a message and fires an agent notification — distinct from the agent-only reopen path that already exists.

## Terms (existing word, new meaning risk)

- **"Reopen" is already a defined operation**, but a different one: `tickets.reopenTicket` (`src/tickets.js:38-44`) lets an **agent** take a `resolved` ticket back to `open`; it throws on anything else, including `closed` (enforced by `test/tickets.test.js:34-41`, which pins the exact error text `cannot reopen a open ticket` / `cannot reopen a closed ticket`). This request is a **different operation**: customer-initiated, `closed` → `open` only, time-boxed. To avoid the two being confused in code or conversation, this spec names the new one **"customer reopen"**, implemented as a separate function (`reopenByCustomer`), with its own notification event name (`ticket_reopened_by_customer`, distinct from the agent path's `ticket_reopened`). The existing `reopenTicket` is not touched.
- **Glossary conflict, said at once:** `docs/glossary.md:12` currently states *"closed: final. A closed ticket is never changed again. If the customer comes back, they start a new ticket."* This request makes that false for the first 14 days. The glossary needs a one-line amendment (see Acceptance Criteria) — the code is being asked to change, not the glossary's intent elsewhere, but the sentence as written becomes incorrect and must be updated in the same change.

## Open questions, answered by recommendation

Per the requester: answered inline below rather than asked live, each marked **assumed, not confirmed**.

1. **On reopen, does `closed_at` get cleared, or kept for history?**
   Recommend: clear both `resolved_at` and `closed_at` to `null`, same as the existing agent `reopenTicket` already does to `resolved_at` (`src/tickets.js:41`). The ticket re-enters the live lifecycle as if freshly reopened; no new "reopened_at"/history field is added (YAGNI — nothing in the request asks for a visible reopen history). *Confidence: medium — reasonable given the codebase's minimal style, but there's no stated audit requirement either way.*
2. **Is a reason/message required from the customer, or optional?**
   Recommend: **required, non-empty.** It's stored as the first message of the reopened conversation via the existing `addMessage`, mirroring how `portal.reply` already requires a `body` (`src/portal.js:21-28`). An agent getting pinged with no context would be the main complaint if this were optional. *Confidence: high.*
3. **Does reopening reset the SLA clock, or cap how many times a ticket can be reopened?**
   Recommend: **no SLA reset, no reopen-count limit** for this version. The agent already has full history; resetting the SLA would only be generous to the customer, not a risk. The 14-day window is itself the abuse limiter. If reopen abuse becomes a real pattern, add a count limit later as a separate, scoped change. *Confidence: medium — this is a product-policy call, flagged for explicit sign-off rather than treated as settled.*
4. **Can a ticket reopen after its messages have already been purged?**
   Yes, and this is load-bearing, not a preference. `purgeClosed` deletes messages **7 days** after close (`KEEP_DAYS = 7`, `src/jobs/purge-closed.js:7`), while this feature's window is **14 days** — so a ticket purged on day 7 is still legally reopenable on day 10. `purgeClosed` uses `purged` as a one-way latch (`if (t.purged) continue`, `src/jobs/purge-closed.js:13`): once true, that ticket is skipped on every future run. **Customer reopen must unconditionally reset `purged: false`**, even if it was already `true`, so that a second close happens later → day-7 purge still deletes the new round of messages. Skipping this reset would permanently exempt the ticket from the 7-day message-retention policy (`src/jobs/purge-closed.js:2-4` cites this as a Legal requirement) — a compliance bug, not a style choice. *Confidence: high — this follows directly from reading the purge job, not a guess.*

## Edge cases

| Case | Handling |
|---|---|
| Ticket is `open`/`pending`/`resolved` (not `closed`) | Reject with `cannot reopen a ${status} ticket` (mirrors `src/tickets.js:40`'s existing message shape for the agent path, so error-handling code only needs one pattern). |
| Exactly 14 days since `closed_at` | Rejected — window is `now - closed_at < 14 days`, strict less-than, matching the existing strict-`<` pattern in `purgeClosed` (`src/jobs/purge-closed.js:14`). |
| Empty or whitespace-only message | Rejected before any store write — `addMessage`/`updateTicket` must not run on an invalid request. |
| Ticket belongs to a different organisation than the requesting customer | `portal.reopen` returns `null`, same as `portal.getMyTicket` does today for cross-org access (`src/portal.js:10-14`) — this is the existing org-scoping/tenant-isolation pattern and needs its own regression test since it's being touched for the first time by this function. |
| Ticket has no assignee (`assignee_id` is `null`) | No notification is sent. `notifyAgent` throws if called with no agent id (`src/notify.js:7`), so the call must be skipped, not attempted-and-caught. |
| Ticket was already purged (`purged: true`) and is still inside the 14-day window | Allowed (see open question 4); `purged` is reset to `false` unconditionally as part of the same update. |
| Concurrent agent action (e.g. agent re-assigns or re-resolves) while customer reopens | Out of scope for this spec — the existing store has no transaction/locking primitive beyond single-row `updateTicket`, and no other code path handles this race either. Not introduced here. |

## Assumptions

- The "14 days" in the request means calendar days from `closed_at`, using the same millisecond-window arithmetic as the rest of the codebase (`HOUR`/`DAY` constants), not business days. **Confidence: high** — every existing time window in this codebase (`SLA_HOURS`, `QUIET_DAYS`, `KEEP_DAYS`) is a flat wall-clock window with no business-day logic.
- "Notify the assigned agent" means the existing `notify.notifyAgent` queue (`src/notify.js:6-9`), not a new channel. **Confidence: high** — it's the only notification mechanism in the codebase and the agent-reopen path already uses it for a near-identical event.
- `src/tickets.js` has no `DAY` constant today (only `HOUR`, `src/tickets.js:6`); each job file currently redefines `DAY` locally. This spec adds `const DAY = 24 * HOUR;` to `tickets.js` itself rather than inlining the literal a third time, since the new function lives there. **Confidence: high**, this is a style call with no real alternative given the existing duplication.

## Acceptance criteria

1. A customer can reopen their own ticket only when its status is `closed`; any other status throws `cannot reopen a ${status} ticket`.
2. Reopen is rejected when `now - closed_at >= 14 days` (strict `<` for "allowed", matching the purge job's own boundary style).
3. Reopen is rejected when the message is empty or whitespace-only.
4. On a successful reopen: `status` → `open`, `resolved_at` → `null`, `closed_at` → `null`, `purged` → `false` (unconditionally — see open question 4), and the customer's message is recorded via `addMessage` with `from: 'customer'`.
5. If `assignee_id` is set, the assignee is notified via `notifyAgent` with a new event type `ticket_reopened_by_customer` (not `ticket_reopened`, which stays the agent path's event name). If `assignee_id` is `null`, no notification call is made.
6. **Non-negotiable:** a ticket that was already purged (`purged: true`) and is reopened within the 14-day window has `purged` reset to `false`, so that a later close-and-7-day-wait purges its messages again. A test must assert this explicitly (close → purge → reopen → close again → purge again → messages gone).
7. `portal.reopen(store, customer, id, message, { now })` returns `null` when the ticket doesn't belong to the customer's organisation, mirroring `getMyTicket`'s existing org check — with its own regression test, since this is the first time `reopen` touches that boundary.
8. The existing agent-only `tickets.reopenTicket` (`src/tickets.js:38-44`) is unchanged, and `test/tickets.test.js:34-41`'s exact-message assertions for it still pass unmodified.
9. `portal.reply` continues to throw on any `closed` ticket (`src/portal.js:24`) — customer reopen is a separate, deliberate action, never a side effect of replying.
10. `docs/glossary.md`'s "closed" bullet is updated to note the 14-day customer-reopen exception, so the glossary stops contradicting the code.

## Out of scope

SLA reset on reopen, a limit on how many times a ticket can be reopened, any new audit/history field for past close-reopen cycles, portal UI/frontend work, and concurrent-edit locking — none of these were asked for and none are needed to satisfy the request as stated.

## Design sketch

- **`src/tickets.js`**: add `const DAY = 24 * HOUR;` near the existing `HOUR` constant (`src/tickets.js:6`). Add:
  ```js
  function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
    const t = mustGet(store, id);
    if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
    if (!message || !message.trim()) throw new Error('a reopen needs a message');
    if (now.getTime() - new Date(t.closed_at).getTime() >= 14 * DAY) {
      throw new Error('this ticket closed more than 14 days ago; please open a new one');
    }
    store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
    const updated = store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null, purged: false });
    if (t.assignee_id) notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id });
    return updated;
  }
  ```
  Exported alongside the existing functions.
- **`src/portal.js`**: add a thin org-scoping wrapper, following the existing `openTicket`/`getMyTicket` shape:
  ```js
  function reopen(store, customer, id, message, { now = new Date() } = {}) {
    const t = getMyTicket(store, customer, id);
    if (!t) return null;
    return reopenByCustomer(store, id, message, { now });
  }
  ```
- **`docs/glossary.md`**: amend the "closed" bullet to read something like *"closed: final, except that the customer may reopen it within 14 days of closing; after that, or once reopened and closed again, a new conversation starts a new ticket."*
- **`test/tickets.test.js`**: add cases for criteria 1–7 above, following the file's existing `at(days)` helper pattern.
