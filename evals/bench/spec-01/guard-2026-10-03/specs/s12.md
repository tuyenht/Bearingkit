# Spec: customer self-service ticket reopen

Status: draft, awaiting review. Not implemented.

## Problem

Customers keep asking to reopen a ticket that closed, instead of starting a
new one and losing context. Today `closed` is final (see `docs/glossary.md`):
nothing in `src/tickets.js` or `src/portal.js` lets a customer or anyone else
move a ticket out of `closed`. `tickets.reopenTicket` exists, but it's
agent-only and only works on `resolved` tickets (`src/tickets.js:38-44`,
pinned by `test/tickets.test.js:34-41`).

## Goal

From the portal, a customer can reopen their own ticket within 14 days of it
closing, by sending a message. The ticket goes back to `open` and the
assigned agent is notified.

## Open questions and recommended answers

I'm answering these myself and building the spec on the answers, rather than
blocking on you until tomorrow. Flag anything you'd answer differently and
I'll adjust before this moves to implementation.

**Q1: Does this replace `reopenTicket`, or is it a separate path?**
Recommendation: separate. `reopenTicket` is agent-initiated and only valid on
`resolved` tickets; this is customer-initiated and only valid on `closed`
tickets. Different actor, different precondition, different notification
semantics (agent reopen only notifies if a *different* agent did it; customer
reopen should always notify the assignee). Keep them as two functions —
`tickets.reopenByCustomer` alongside the existing `tickets.reopenTicket` —
rather than overloading one function with branching behavior. This also
avoids touching `reopenTicket`'s error strings, which the existing test
asserts on verbatim.

**Q2: What's the reopen window, and from what timestamp?**
Recommendation: 14 days from `closed_at`, using the same strict `<` boundary
the nightly jobs already use (`closeResolved`'s `QUIET_DAYS`, `purgeClosed`'s
`KEEP_DAYS`). So: allowed while `now - closed_at < 14 days`; on day 14
exactly it's too late. This matches customer expectation ("within 14 days")
and keeps the convention consistent across the codebase.

**Q3: Does reopening require a message, or can the customer just flip the
status?**
Recommendation: require a non-empty message, same as every other customer
action that touches a ticket (`openTicket`, `reply` both take a body). A bare
status flip with no content gives the agent nothing to act on and invites
accidental reopens. The message is appended as a normal customer message.

**Q4: What status does it land in?**
Recommendation: `open`, not `pending`. The ticket needs an agent to look at
it again, and `open` is what every other "customer needs a response" state
already means in this codebase (see `docs/glossary.md`).

**Q5: Does reopening reset the SLA due time?**
Recommendation: no. `sla_due_at` is documented as "set when the ticket is
created" and nothing else in the codebase ever touches it. Changing that
invariant for this one case is a bigger decision than this feature needs —
leave `sla_due_at` untouched. Agents can judge urgency from the reopen itself.

**Q6: Is there a limit on how many times a ticket can be reopened?**
Recommendation: no limit. Nothing in the current model counts reopens, and
there's no stated abuse problem to justify adding a counter and a cap. Revisit
if it turns out customers are gaming it.

**Q7: What happens if the ticket has no assignee (was closed unassigned)?**
Recommendation: reopen succeeds, no notification is sent. `notifyAgent`
throws if given a falsy agent id (`src/notify.js:7`), so this needs an
explicit guard — same pattern `reopenTicket` already uses
(`if (t.assignee_id && ...)`, `src/tickets.js:42`). An unassigned ticket just
goes back into the open queue.

**Q8: Does `portal.reply` on a closed ticket change — i.e. does replying
implicitly reopen it, the way it already does for `resolved`/`pending`
tickets?**
Recommendation: no. `portal.reply` keeps throwing
`'this ticket is closed; please open a new one'` for closed tickets
unchanged. Reopening is a deliberate, separate action (it has its own 14-day
rule and notification), not a side effect of sending a message. Keeping
`reply`'s behavior untouched also avoids touching code the existing tests
pin.

**Q9: What happens to `closed_at` and `resolved_at` on reopen?**
Recommendation: clear both (`closed_at: null`, `resolved_at: null`), the same
way `reopenTicket` already clears `resolved_at` when it un-resolves a ticket
(`src/tickets.js:41`). The ticket is open again; these timestamps describe a
past state that no longer applies, and a later close cycle will set fresh
values.

**Q10 (the one with real stakes): what happens to the `purged` flag?**
`purgeClosed` is a one-way latch — once `purged` is `true` it skips the
ticket forever (`if (t.purged) continue`, `src/jobs/purge-closed.js:13`). A
ticket can be reopened after its messages were already purged (purge runs at
7 days, reopen window is 14 days, so there's a real window where both have
happened). If we reopen without resetting `purged`, the ticket's *next*
closed-and-purged cycle will be silently skipped forever, leaving that
round's conversation text sitting in the database past the 7-day retention
promise — a Legal/retention problem, not just a data quirk.
Recommendation: `reopenByCustomer` unconditionally sets `purged: false` as
part of the same update. This needs no change to `purge-closed.js` itself —
resetting the flag on reopen is enough for the existing job to pick the
ticket up correctly next time it closes.

## Design

### `tickets.reopenByCustomer(store, id, message, { now = new Date() } = {})`

New function in `src/tickets.js`, alongside the existing `reopenTicket`.

```
function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`only a closed ticket can be reopened, not ${t.status}`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('too late to reopen this ticket; please open a new one');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');

  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    closed_at: null,
    resolved_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id, by: `customer:${t.customer_id}` });
  }
  return updated;
}
```

New constant: `REOPEN_WINDOW_DAYS = 14` (next to `SLA_HOURS`, same `DAY`
constant pattern used in the job files). Export it alongside `reopenTicket`.

### `portal.reopen(store, customer, id, message, { now = new Date() } = {})`

New function in `src/portal.js`, mirroring how `openTicket`/`reply` wrap the
`tickets` functions with org-scoping:

```
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  reopenByCustomer(store, id, message, { now });
  return getMyTicket(store, customer, id);
}
```

Org-scoping happens first (unknown ticket or wrong organisation both return
`null`, same as `getMyTicket`/`reply`); business-rule errors (wrong status,
window expired, empty message) come from `tickets.reopenByCustomer` and
propagate as thrown errors, same as `reply`'s closed-ticket error does today.

### Notification

No changes needed to `src/notify.js` — `notifyAgent` already accepts an
arbitrary `event` payload. The new event type is `ticket_reopened_by_customer`
(distinct from the agent-reopen's `ticket_reopened`, so downstream consumers
— email templates, the mail worker — can tell them apart and word the email
appropriately, e.g. "your customer reopened ticket #123" vs. "ticket #123 was
reopened").

### `docs/glossary.md`

The `closed` line currently reads: "final. A closed ticket is never changed
again. If the customer comes back, they start a new ticket." This becomes
inaccurate and needs updating to something like: "final once 14 days have
passed since closing. Within 14 days of closing, the customer may reopen it
from the portal with a message; after that, they start a new ticket."

## Out of scope

- No change to `tickets.reopenTicket` (agent reopen of a resolved ticket).
- No change to `portal.reply`'s closed-ticket behavior.
- No change to `purge-closed.js` or `close-resolved.js` job logic.
- No SLA reset, no reopen-count limit (Q5, Q6).
- No new ticket fields / schema migration — reuses `status`, `closed_at`,
  `resolved_at`, `purged`, `assignee_id`, all of which already exist.

## Acceptance criteria

1. A customer can reopen their own `closed` ticket within 14 days of
   `closed_at`, by calling `portal.reopen` with a non-empty message; the
   ticket's status becomes `open`.
2. Reopening on day 14 or later (`now - closed_at >= 14 days`) throws and
   leaves the ticket closed.
3. Reopening a ticket that isn't `closed` (e.g. `open`, `pending`,
   `resolved`) throws and makes no change.
4. Reopening with an empty or missing message throws and makes no change.
5. A customer cannot reopen (or even see, per existing `getMyTicket`
   behavior) a ticket belonging to another organisation — `portal.reopen`
   returns `null`.
6. **If the ticket was already assigned, the assignee is notified** with a
   `ticket_reopened_by_customer` event. If unassigned, reopen still succeeds
   with no notification.
7. **The reopened ticket's `purged` flag is reset to `false`**, so that if it
   is closed and left untouched again, `purgeClosed` purges its (new)
   messages after 7 days rather than skipping it forever. This is the one
   non-negotiable correctness requirement in this spec — a regression here is
   a silent retention-policy violation, not just a bug.
8. `tickets.reopenTicket` and `portal.reply`'s existing behavior and error
   messages are unchanged; `test/tickets.test.js:34-41`'s assertions on
   `reopenTicket` still pass unmodified.

## Suggested new tests (`test/tickets.test.js`)

- Happy path: close a ticket, reopen it within the window with a message,
  assert status `open`, assert the assignee got `ticket_reopened_by_customer`.
- Window boundary: reopen at exactly 14 days fails, at 13 days succeeds (mirror
  the existing `at(3)`/`at(4)` boundary-pair style used for `closeResolved`).
  stays throws.
- Wrong status: reopening an `open` ticket throws.
- Empty message: throws, ticket stays closed.
- Cross-org: `portal.reopen` for a different organisation's ticket returns
  `null`.
- Purge-then-reopen-then-purge-again: close, purge (messages gone, `purged:
  true`), reopen within window, close again, purge again at day 7+ from the
  *second* close — assert the second purge actually runs (`purged` was reset)
  and messages from the reopened conversation are deleted.
