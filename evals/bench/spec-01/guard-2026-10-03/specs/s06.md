# Spec: customer self-service ticket reopen

Status: draft, awaiting review (tuyenht away until 2026-10-04). Not implemented.

## Restatement

Customers asked: let us reopen a ticket we closed too soon, instead of starting
a new one and losing context. Technical reading: add a portal-facing action
that moves a ticket from `closed` back to `open` when the customer acts within
14 days of `closed_at`, requires a message (so the agent has something to
react to, and so it isn't indistinguishable from an accidental click), and
notifies whichever agent is currently assigned. This is new customer-facing
behavior on top of the existing agent-only reopen path
(`src/tickets.js:38-44`); it does not change that path.

## Clarifying questions, answered by recommendation

Tuyen is unavailable, so each question below is answered with the
recommended default rather than left open. Anything marked **medium** or
**low** confidence is worth a second look on review; everything else is safe
to build as-is.

1. **What status does a reopened ticket get?**
   Recommendation (**high**): `open`, same target as the existing
   agent-initiated reopen (`src/tickets.js:41`). The customer's message is new
   information an agent needs to triage, same as today's flow.

2. **Are both `resolved_at` and `closed_at` cleared on reopen?**
   Recommendation (**medium**): clear both to `null`, mirroring
   `reopenTicket`'s clearing of `resolved_at` (`src/tickets.js:41`). Nothing in
   the schema reads `closed_at` once a ticket leaves `closed`, so leaving it
   set would be dead, confusing state. Flagged for explicit sign-off since
   there's no audit-trail requirement on record either way.

3. **Does the assignee change, or go back to the unassigned queue?**
   Recommendation (**high**): unchanged. The ticket stays with whoever was
   last assigned (or stays unassigned if it never was). No reassignment logic
   exists for the agent reopen path either; adding triage logic here would be
   new scope.

4. **Is there a limit on how many times a customer can reopen the same
   ticket?**
   Recommendation (**high**): no limit, matching the agent reopen path, which
   also has none. Adding a cap is a product policy nobody asked for (YAGNI).

5. **Does the SLA clock (`sla_due_at`) reset on reopen?**
   Recommendation (**high**): no. `sla_due_at` is set once at creation
   (`src/tickets.js:16`) and the existing agent reopen doesn't touch it. A
   fresh SLA on reopen would be a distinct, separately-requested policy.

6. **Is the 14-day window strict (`<`) or inclusive (`<=`), and measured in
   calendar days or exact 24h periods?**
   Recommendation (**high**): strict `<` over exact 24h periods
   (`14 * DAY` ms), matching the existing day-window checks in
   `closeResolved` (`src/jobs/close-resolved.js:11`, `< QUIET_DAYS * DAY`) and
   `purgeClosed` (`src/jobs/purge-closed.js:14`, `< KEEP_DAYS * DAY`). Day 14
   at the same time-of-day as `closed_at` is where reopen stops being allowed.

7. **What happens when the ticket's messages were already purged (closed
   7–14 days ago)?**
   Recommendation (**high**, and the one non-negotiable item in this spec):
   the customer's reopen message becomes the ticket's first message again
   (the old ones are genuinely gone — purge deletes, it doesn't archive), and
   `purged` must be reset to `false` **unconditionally**, whether or not it
   was already `true`. `purgeClosed` treats `purged` as a one-way latch
   (`if (t.purged) continue`, `src/jobs/purge-closed.js:13`); if reopen didn't
   clear it, a second resolve→close cycle would never get its messages
   purged, silently breaking the 7-day retention policy Legal asked for
   (`src/jobs/purge-closed.js:2-4`). This is acceptance criterion 6 below.

8. **Does the agent get told this reopen was customer-initiated, as opposed
   to the existing agent self-reopen?**
   Recommendation (**high**): yes, a distinct event type
   `ticket_reopened_by_customer` (vs. the existing `ticket_reopened` for the
   agent path, `src/tickets.js:42`), carrying `by: customer:<id>`, mirroring
   the existing `by: agent:<id>` shape.

9. **Does notification fire when the ticket is currently unassigned?**
   Recommendation (**high**): no, skip silently. `notifyAgent` throws when
   called without an agent (`src/notify.js:7`), and there's no "notify the
   unassigned queue" mechanism to substitute.

10. **Does this reuse `reopenTicket` (agent path) or `portal.reply`, or get
    its own function?**
    Recommendation (**high**): a new function, kept fully separate from both.
    `reopenTicket` only accepts a `resolved` source status with no window and
    no message requirement, and its exact error-message text is pinned by
    `test/tickets.test.js:34-41`, which must keep passing unmodified.
    `portal.reply` (`src/portal.js:21-28`) is a reply, not a status-change
    action by itself, and must keep throwing on closed tickets
    (`src/portal.js:24`) — reopening is a distinct, deliberate action, not a
    side effect of answering.

## Edge cases

| Case | Handling |
|---|---|
| Ticket belongs to a different organisation | `portal.reopen` returns `null`, same as `portal.getMyTicket` (`src/portal.js:10-14`) — no error, no leak that the ticket exists |
| Ticket is not `closed` (open/pending/resolved) | throws, e.g. `` cannot reopen a ${status} ticket `` |
| Message is empty or whitespace-only | throws, e.g. `a message is required to reopen a ticket` |
| Now is ≥ 14 days after `closed_at` | throws, e.g. `too late to reopen this ticket` |
| Ticket's messages were already purged (7–14 day window) | allowed; `purged` reset to `false` unconditionally (Q7 above) |
| Ticket has no assignee (`assignee_id === null`) | reopen succeeds; notification is skipped, not attempted |
| Double-submit / second reopen click | second call fails naturally: after the first call the status is `open`, not `closed`, so the "not closed" check (above) rejects it — no extra idempotency logic needed |
| Customer tries `portal.reply` on a closed ticket instead of reopening | unchanged: still throws `this ticket is closed; please open a new one` (`src/portal.js:24`) — reply and reopen stay distinct actions |

## Design

### New code

- `tickets.reopenByCustomer(store, id, message, { now = new Date() })` in
  `src/tickets.js`, next to `reopenTicket`. Business rules only (no org
  scoping — that belongs to the portal layer, matching how `createTicket` vs.
  `openTicket` split today):
  - `mustGet` the ticket (reuse existing helper, `src/tickets.js:46-50`).
  - Require `t.status === STATUS.CLOSED`, else throw.
  - Require `now.getTime() - new Date(t.closed_at).getTime() < 14 * DAY`,
    else throw. `src/tickets.js` currently defines `HOUR` only
    (`src/tickets.js:6`); add `const DAY = 24 * HOUR;` there rather than
    inlining the literal a third time (both job files already redefine it
    locally).
  - Require a non-empty (trimmed) `message`, else throw.
  - `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null,
    closed_at: null, purged: false })` — the `purged: false` is
    unconditional (Q7).
  - `store.addMessage(id, { from: 'customer', body: message, at:
    now.toISOString() })`.
  - If `t.assignee_id`, call `notifyAgent(store, t.assignee_id, { type:
    'ticket_reopened_by_customer', ticketId: id, by: `customer:${?}` })` —
    see portal wrapper for where the customer id comes from.
  - Return the updated ticket.

- `portal.reopen(store, customer, id, message, { now = new Date() })` in
  `src/portal.js`, mirroring the `getMyTicket`/`openTicket` org-scoping
  pattern:
  - Look up via `getMyTicket`-style check; return `null` if the ticket isn't
    the customer's org (don't call into `tickets.reopenByCustomer` at all in
    that case, so an org mismatch never throws).
  - Otherwise call `tickets.reopenByCustomer(store, id, message, { now })`
    with the customer id threaded through for the notification's `by` field,
    and return the result (or re-expose it via `getMyTicket` shape, matching
    how `reply` returns `getMyTicket(store, customer, id)` at
    `src/portal.js:27`).

### Unchanged

- `tickets.reopenTicket` (agent path, `src/tickets.js:38-44`) — untouched,
  tests at `test/tickets.test.js:24-41` keep passing as-is.
- `portal.reply` (`src/portal.js:21-28`) — untouched; still throws on closed.
- `closeResolved`, `purgeClosed` — untouched; purge's `purged` check
  (`src/jobs/purge-closed.js:13`) is exactly why criterion 6 below exists.

### Docs

- `docs/glossary.md:12`'s **closed** bullet currently reads "final. A closed
  ticket is never changed again." Update it to note the 14-day customer
  exception, e.g.: "closed: final 14 days after `closed_at`. Within that
  window the customer may reopen it with a message; after it, they start a
  new ticket."

## Acceptance criteria

1. A customer can reopen their own `closed` ticket when `now - closed_at <
   14 days` and the message is non-empty: resulting status is `open`,
   `resolved_at` and `closed_at` are both `null`, the message is appended.
2. `portal.reopen` returns `null` (no throw) when the ticket belongs to a
   different organisation.
3. Reopening a ticket whose status is not `closed` throws.
4. Reopening a `closed` ticket at or past the 14-day boundary throws.
5. Reopening with an empty or whitespace-only message throws.
6. Reopening a ticket that had already been purged resets `purged` to
   `false`; a subsequent resolve→close→7-day-purge cycle deletes its new
   messages (does not skip it via the `purged` latch).
7. When `assignee_id` is set, `notifyAgent` is called exactly once with
   `{ type: 'ticket_reopened_by_customer', ticketId, by: 'customer:<id>' }`.
   When `assignee_id` is `null`, `notifyAgent` is not called.
8. `tickets.reopenTicket` and its existing tests
   (`test/tickets.test.js:24-41`) are unchanged and still pass.
9. `docs/glossary.md`'s closed-ticket definition reflects the 14-day
   exception.
