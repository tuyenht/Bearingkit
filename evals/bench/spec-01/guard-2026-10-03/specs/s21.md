# Spec: customer reopens a closed ticket

Status: **draft, awaiting user review**. Written while the user was away; every
open question below is answered with a recommendation and the spec is built
on that recommendation rather than left blocked.

## Restatement

> "Let a customer reopen a closed ticket from the portal within 14 days of it
> being closed, and notify the assigned agent when they do."

Technical reading: add a new portal-facing action, available only on a
ticket whose `status` is `closed` and whose `closed_at` is less than 14 days
in the past, that moves the ticket back to `open` and queues a notification
to the ticket's `assignee_id` if one is set. This is **not** the same action
as the existing `reopenTicket` in `src/tickets.js:38` — that one lets an
*agent* take a *resolved* ticket back, and the glossary already documents it
(`docs/glossary.md:11`). The request is for a second, customer-facing path
that starts from `closed`, a status the glossary currently calls "final"
(`docs/glossary.md:12`). See **Terms** below for how this spec keeps the two
apart.

## Terms

- **Reopen (agent)**: the existing action at `src/tickets.js:38-44`. An agent
  moves their own *resolved* ticket back to `open`. Unchanged by this spec.
- **Reopen (customer)**: the new action this spec defines. The *customer*
  moves their own *closed* ticket back to `open`, only within 14 days of
  `closed_at`, and only by supplying a message explaining why.
- **Reopen window**: the 14-day period after `closed_at` during which
  "reopen (customer)" is allowed. Measured the same way the existing nightly
  jobs measure their windows (see Decision 2).

`docs/glossary.md:12` currently reads: *"closed: final. A closed ticket is
never changed again. If the customer comes back, they start a new ticket."*
This is now only true for agents and for the customer once the window has
passed. **Required edit** (see AC9): replace that sentence with something
like *"closed: final for agents — a closed ticket is never changed by an
agent. The customer may reopen it themselves within 14 days of closing,
with a message; after that window, or once it is closed again, they start a
new ticket."*

## Touchpoints

- `src/tickets.js:38-44` — existing agent `reopenTicket`; pattern to follow,
  function to keep untouched (pinned by `test/tickets.test.js:34-41`'s exact
  error-message assertions).
- `src/tickets.js:4` — `STATUS` enum, `src/tickets.js:19` — `purged: false`
  on creation.
- `src/portal.js:10-14` — `getMyTicket`, the org-scoping pattern every
  customer-facing portal function uses; the new action must use it too, to
  return `null` rather than leak another organisation's ticket.
- `src/portal.js:21-28` — `reply`, the closest existing precedent for a
  customer action that adds a message and changes status.
- `src/notify.js:6-9` — `notifyAgent`; throws if `agentId` is falsy, so an
  unassigned ticket must be handled by *not calling it*, not by passing
  `null`.
- `src/jobs/purge-closed.js:10-20` — the nightly purge job. Line 13,
  `if (t.purged) continue`, is a one-way latch: once `purged` is `true` the
  job never looks at that ticket again. **This is the one non-negotiable
  item in this spec** — see AC6.
- `test/tickets.test.js:34-41` — current reopen tests, to extend rather than
  change.
- `docs/glossary.md:12` — needs the wording update above.

## Edge cases

1. **Ticket not closed** (`open`, `pending`, or `resolved`). Rejected with a
   clear error; ticket unchanged. (A `resolved` ticket already has its own
   reopen path — the agent one, or the customer can just reply per
   `src/portal.js:26`.)
2. **Outside the 14-day window.** Rejected with an error telling the
   customer to open a new ticket instead; ticket unchanged.
3. **Exactly at the 14-day boundary.** Resolved by Decision 2 below: the
   same `now - closed_at < N * DAY` convention the nightly jobs already use.
4. **Ticket already purged** (`purged: true`, messages deleted by
   `src/jobs/purge-closed.js`). Still reopenable if inside the window — the
   ticket row and its dates survive purge; only the message history was
   deleted (`src/jobs/purge-closed.js:15`). Reopening must reset
   `purged: false` (AC6) or the row would never be eligible for purge again
   after it closes a second time, which is a retention-policy violation.
5. **No assignee** (`assignee_id: null`, e.g. never picked up, or unassigned
   when closed). No notification is sent; this must not throw, since
   `notifyAgent` requires an agent id (`src/notify.js:7`).
6. **Empty or missing message.** Rejected with an error; a reason is
   required to reopen (see Assumptions, first bullet).
7. **Wrong organisation.** A customer reopening another organisation's
   ticket gets the same `null`-and-stop treatment as
   `src/portal.js:10-14`'s `getMyTicket` — no existence leak, no error that
   reveals the ticket exists.
8. **Concurrent reopen attempts** (double-click, two tabs). The store has no
   locking anywhere else in this codebase (`src/store.js`); this spec keeps
   that existing risk level rather than adding locking here. Worst case: two
   messages get added and one redundant `updateTicket` call runs — no data
   loss, consistent with how `src/portal.js:21-28` already behaves under the
   same conditions.

## Decisions

(Recorded per the three-part test — hard to reverse, surprising without
context, a real trade-off — because all three apply to each one below.)

1. **Reset `purged` to `false` unconditionally on reopen.** The alternative
   (leave it `true` if already purged) silently breaks the 7-day retention
   job forever for that ticket: `purgeClosed`'s `if (t.purged) continue`
   (`src/jobs/purge-closed.js:13`) would skip it on every future run, so a
   second close would keep that conversation's text indefinitely — the
   opposite of what Legal asked for in `src/jobs/purge-closed.js:3-4`.
2. **Reuse the existing window convention**: eligible while
   `now - closed_at < 14 * DAY`, i.e. the same strict-less-than check
   `closeResolved` and `purgeClosed` already use
   (`src/jobs/close-resolved.js:11`, `src/jobs/purge-closed.js:14`). Picking
   a different boundary convention for the same kind of check would be an
   inconsistency a future reader would have to puzzle out.
3. **Keep `reopenTicket` (agent) and the new customer action as two
   separate functions**, not one function branching on caller type. They
   have different source statuses (`resolved` vs `closed`), different
   actors, and `reopenTicket`'s exact error strings are pinned by
   `test/tickets.test.js:34-41`. Merging them risks changing agent-facing
   behavior to accommodate the customer path.
4. **`portal.reply` keeps throwing on a closed ticket** (`src/portal.js:24`)
   rather than being taught to reopen on the customer's behalf. Reopening is
   a deliberate, separate action (with its own required message and its own
   14-day check) — not a side effect of answering.

## Assumptions

- The reopen message is required and non-empty, the same way a reply always
  carries a `body` (`src/portal.js:21`, `src/tickets.js:21`). *Confidence:
  high* — directly follows the existing pattern, not a new judgment call.
- The notification event name is `ticket_reopened_by_customer` (distinct
  from the agent path's `ticket_reopened`, `src/tickets.js:42`), so agents
  and any downstream email templates can tell the two apart. *Confidence:
  high.*
- Reopening does not reset `sla_due_at` — that field is set once at creation
  (`src/tickets.js:16`) and the existing agent reopen doesn't touch it
  either (`src/tickets.js:41`). *Confidence: high.*
- There is no limit on how many times a ticket can be reopened by the
  customer. Nothing in the codebase tracks a reopen count today, and adding
  one is a new piece of product policy nobody asked for (YAGNI).
  *Confidence: medium* — flagged as Open question 3 below in case the
  "customers keep asking for this" framing implies abuse is also a concern.
- `resolved_at` is cleared back to `null` on customer reopen, matching what
  the agent path already does when it reopens (`src/tickets.js:41`), so a
  ticket that is `open` never has a stale `resolved_at`. *Confidence: high.*

## Open questions

(Nobody was available to answer live; each is answered with a
recommendation and the spec is built on it. Marked *assumed, not
confirmed*.)

1. **Should the `purged` flag reset to `false` when reopening a
   purged-and-closed ticket?** **Recommended: yes, unconditionally** (see
   Decision 1) — the alternative is a silent, compounding retention-policy
   violation. This is the one answer in this spec most worth double-checking
   before implementation, since it's easy to miss if the purge job isn't
   read closely.
2. **Where does the 14-day count start if the ticket was closed, then
   reopened by an agent some other way, then closed again?** **Recommended:
   always from the most recent `closed_at`** — `closed_at` is overwritten
   each time `closeResolved` runs (`src/jobs/close-resolved.js:12`), so this
   falls out naturally from reading the current value; no extra "first
   closed" tracking is needed.
3. **Is there a cap on how many times one ticket can be reopened by a
   customer?** **Recommended: no cap for now** — nothing in the current
   product tracks this, and a cap is easy to add later as its own small
   change if abuse shows up in practice. (See Assumptions above.)
4. **Does reopening need its own notification event name, or should it
   reuse `ticket_reopened`?** **Recommended: a new, distinct event,
   `ticket_reopened_by_customer`** — so the agent can tell at a glance
   whether they or the customer brought the ticket back, without parsing
   the `by` field the way the agent path does today (`src/tickets.js:42`).

## Acceptance criteria

1. A customer can reopen their own ticket when, and only when, its status is
   `closed` and `now - closed_at < 14 days`. On success: `status` becomes
   `open`, `closed_at` becomes `null`, `resolved_at` becomes `null`.
2. Calling reopen on a ticket whose status is `open`, `pending`, or
   `resolved` throws a descriptive error and leaves the ticket unchanged.
3. Calling reopen more than 14 days after `closed_at` throws a descriptive
   error (telling the customer to open a new ticket) and leaves the ticket
   unchanged.
4. Calling reopen with an empty or missing message throws a descriptive
   error and leaves the ticket unchanged — no message is added, no status
   change happens.
5. Calling reopen on a ticket belonging to a different organisation than the
   calling customer behaves exactly like `getMyTicket` on a foreign ticket
   (`src/portal.js:10-14`): no error that reveals the ticket's existence.
6. If the ticket's `purged` field was `true` before reopening, it is `false`
   immediately after — regardless of prior value. (Covers edge case 4 /
   Decision 1 / Open question 1.)
7. If the ticket has a non-null `assignee_id`, exactly one notification is
   queued via `notifyAgent` with event type `ticket_reopened_by_customer`
   and the ticket's id. If `assignee_id` is `null`, no notification is
   queued and no error is thrown.
8. The customer's reopen message is recorded as a new message
   (`from: 'customer'`) and is visible via `store.getMessages(id)` after
   reopening.
9. `docs/glossary.md`'s `closed` definition (`docs/glossary.md:12`) is
   updated to reflect that a customer can reopen within 14 days, so the
   glossary and the behavior stay in agreement.
10. The existing agent `reopenTicket` behavior and its exact error messages
    (`test/tickets.test.js:34-41`) are unchanged.

## Out of scope

- Any change to SLA tracking, reopen counts/limits, or the reopen window
  length becoming configurable per organisation — none of this was asked
  for (YAGNI; see Assumptions).
- Any change to the agent-facing `reopenTicket` action or its notification.
- The actual email/template content the mail worker sends when draining the
  notification queue (`src/notify.js:11-13`) — out of scope for this
  feature, unchanged by it.
- Any UI/portal-page work; this spec covers the `src/portal.js` and
  `src/tickets.js` behavior only.
