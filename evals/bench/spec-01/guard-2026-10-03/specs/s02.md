# Spec: customer self-service reopen of a closed ticket

Status: **draft, awaiting review** — not implemented.

## Summary

A customer can reopen their own **closed** ticket from the portal within 14
days of it being closed. Reopening puts the ticket back to `open` and
notifies the assigned agent, if there is one.

## Current behavior (for context)

- `docs/glossary.md` currently says closed is final: *"A closed ticket is
  never changed again. If the customer comes back, they start a new
  ticket."* This spec changes that.
- `src/tickets.js` already has an agent-only `reopenTicket(store, id,
  agentId)`, but it only works on a `resolved` ticket, not a `closed` one.
  It's pinned by exact-message assertions in `test/tickets.test.js:34-41`
  ("cannot reopen a open ticket" / "cannot reopen a closed ticket") — this
  feature must not touch that function or its errors.
- `src/portal.js`'s `reply()` already throws on a closed ticket ("this
  ticket is closed; please open a new one") and auto-reopens a
  `resolved`/`pending` ticket to `open` when the customer answers it. This
  feature is a new, separate action, not a change to `reply`.
- `src/jobs/close-resolved.js` sets `closed_at` when it closes a ticket.
- `src/jobs/purge-closed.js` deletes a closed ticket's messages 7 days
  after `closed_at`, then sets `purged: true` and **never looks at that
  ticket again** (`if (t.purged) continue`, line 13 — a one-way latch).
  Since the reopen window (14 days) is longer than the purge window (7
  days), a ticket can legitimately be reopened *after* its messages are
  already gone.

## Open questions and recommendations

**1. What exactly starts the 14-day clock, and is the boundary inclusive?**
Recommend: anchor on `closed_at` (already on the row, set by
`close-resolved.js`), and use the same strict `<` convention the two
existing nightly jobs use for their own day-windows (`close-resolved.js`,
`purge-closed.js`). So: reopenable while `now - closed_at < 14 days`;
exactly 14 days or more is too late. This matches the existing code's
style rather than introducing a different boundary convention.

**2. Does reopening require the customer to say why?**
Recommend: **yes, require a non-empty message.** Reasoning: the reopen
window (14 days) outlives the purge window (7 days), so a customer who
reopens on day 10 is reopening a ticket whose prior conversation has
already been deleted. Without a required message, the agent would get a
notification pointing at an empty, context-free ticket. This is the one
place this spec adds validation beyond what was asked — flagging it
explicitly in case you'd rather keep the action message-less and let the
customer send a follow-up `reply()` afterward instead (cheap to change
either way if you disagree).

**3. What status does a reopened ticket land in — `open` or `pending`?**
Recommend: `open`. The glossary defines `open` as "waiting for an agent,"
which is exactly the state a just-reopened ticket is in, and it matches
what the existing agent-side `reopenTicket` and `portal.reply`'s
auto-reopen both do.

**4. Do `resolved_at` and `closed_at` get cleared?**
Recommend: clear both to `null`. `resolved_at` already gets cleared by the
existing agent-side `reopenTicket` on the same transition, so this just
matches precedent. `closed_at` is less obvious — flagging as a judgment
call — but leaving it set while `status` is `open` would make the row
self-contradictory for anyone reading `closed_at` as "currently closed."
If it's closed again later, `close-resolved.js` overwrites `closed_at`
with a fresh value anyway, so clearing it now loses no information that
matters operationally (the purge job keys off `status`, not `closed_at`).

**5. Does the reopen reset the one-way `purged` latch?**
**Not really optional — this one's load-bearing, not a style choice.**
`purge-closed.js:13` skips any ticket with `purged: true` forever. If a
ticket was purged, then reopened, then closed and left alone again, a
second `purgeClosed` run would silently never delete its new messages
unless `purged` is reset to `false` on reopen. That would quietly violate
the 7-day retention policy stated in `purge-closed.js`'s own comment
("we do not keep conversation text of finished tickets longer than a
week"). Recommend: unconditionally set `purged: false` on reopen,
regardless of its current value. This is acceptance criterion #6 below
and needs a regression test, not just a code review nod.

**6. Does reopening reset the SLA due time, or cap how many times a
ticket can be reopened?**
Recommend: no to both. `sla_due_at` is documented in the glossary as set
once, at creation, and nothing in the current code — including the
existing agent-side reopen — ever recalculates it. Each close cycle
already refreshes `closed_at`, so the 14-day window naturally restarts on
its own without a separate counter; adding a reopen-count limit isn't
something you asked for and isn't needed for correctness.

**7. What does the agent get notified with?**
Recommend: a distinct event type, `ticket_reopened_by_customer`, rather
than reusing the agent-side `ticket_reopened` type. The two cases mean
different things to an agent (a customer came back vs. a colleague took
the ticket back) and conflating them would make any future
notification-rendering code have to inspect `by` just to tell them apart.
Skip the notification silently if the ticket has no assignee —
`notify.notifyAgent` throws on a missing agent id, and an unassigned
closed ticket is a real (if rare) case.

**8. Where does the logic live?**
Recommend following the existing `createTicket`/`openTicket` split: the
business rule goes in `src/tickets.js` as a new, separate function (not
touching `reopenTicket`), and `src/portal.js` gets a thin org-scoped
wrapper, mirroring how `getMyTicket`/`openTicket` already work.

## Design

**`src/tickets.js`**

Add a `DAY` constant (`24 * HOUR`) — the file currently only defines
`HOUR`; the two job files each redefine a day-length constant locally, so
this follows that existing pattern rather than inlining the literal a
third time. Export `REOPEN_WINDOW_DAYS = 14`, alongside the new function,
the same way `close-resolved.js` exports `QUIET_DAYS` and
`purge-closed.js` exports `KEEP_DAYS`.

```js
const DAY = 24 * HOUR;
const REOPEN_WINDOW_DAYS = 14;

// A customer reopens their own closed ticket, within the window. Separate from the
// agent-only reopenTicket above, which only ever takes a ticket back from resolved.
function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('too late to reopen; it closed more than 14 days ago');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');

  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id, by: `customer:${t.customer_id}` });
  }
  return updated;
}
```

Export `reopenByCustomer` and `REOPEN_WINDOW_DAYS` from `tickets.js`.

**`src/portal.js`**

```js
// The customer reopens their own closed ticket within the 14-day window. Unlike reply(),
// this is a deliberate separate action, not a side effect of answering.
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = getMyTicket(store, customer, id);
  if (!t) return null;
  return reopenByCustomer(store, id, message, { now });
}
```

Export `reopen` from `portal.js`.

**`docs/glossary.md`**

Replace the "closed is final" sentence:

> - **closed**: final, unless the customer reopens it within 14 days of
>   closing. After that, or for a ticket closed longer ago, they start a
>   new ticket.

## Acceptance criteria

1. A customer can reopen a ticket that is `closed` and was closed fewer
   than 14 days ago; the ticket's status becomes `open`.
2. Reopening fails (throws) if the ticket is not `closed`.
3. Reopening fails (throws) once 14 days or more have passed since
   `closed_at`.
4. Reopening fails (throws) if no message, or only whitespace, is given.
5. Reopening fails silently as a no-op (returns `null`, matching
   `getMyTicket`/`openTicket`) if the ticket doesn't exist or belongs to
   a different organisation than the calling customer.
6. **Reopening unconditionally sets `purged` back to `false`**, even if
   the ticket was already purged — verified by a test that purges a
   ticket, reopens it, closes and purges it again, and asserts the
   second purge actually deletes the new messages.
7. If the ticket has an assignee, reopening queues a
   `ticket_reopened_by_customer` notification to that agent. If it has no
   assignee, no notification is queued (and nothing throws).
8. `resolved_at` and `closed_at` are both `null` after a successful
   reopen.
9. `docs/glossary.md`'s description of `closed` is updated to match.

## Non-goals

- No change to `sla_due_at` on reopen.
- No limit on how many times a ticket can be reopened over its lifetime.
- No change to the agent-only `reopenTicket` or to `reply()`'s existing
  behavior on closed tickets.
