# Spec: customer reopens a closed ticket from the portal

Status: **draft — awaiting review**. Written while the ticket owner was away;
every open question below is answered with a recommendation rather than left
blank, per their request. Treat the recommendations as proposals, not
decisions — confirm or override each one before implementation.

## Problem

Today, per `docs/glossary.md`, **closed is final**: `portal.reply` throws on
any closed ticket, and there is no path back to `open` once a ticket is
closed (`src/tickets.js`'s `reopenTicket` only accepts `resolved` tickets,
and only an agent can call it). Customers have repeatedly asked for a way to
reopen a ticket themselves instead of filing a new one that loses the
history.

## Goal

A customer can reopen their own closed ticket from the portal, within 14 days
of it closing, and the assigned agent is notified.

## Open questions and recommendations

**Q1: How long is the reopen window, and measured from what?**
Recommendation: 14 days from `closed_at`, using the same strict `<`
comparison style already used by `closeResolved` and `purgeClosed` (i.e.
allowed while `now - closed_at < 14 * DAY`; at exactly 14 days it's too
late). Keeps the new code consistent with the two existing nightly jobs
rather than introducing an inclusive/exclusive inconsistency.

**Q2: Does the customer have to say anything, or is reopening a bare status
flip?**
Recommendation: require a non-empty message, same validation shape as
`portal.reply`'s body. Store it as a normal customer message
(`store.addMessage`) so the reopened ticket reads naturally to the agent —
"why this is back" shouldn't be a separate side channel.

**Q3: What status does the ticket land in?**
Recommendation: `open`, matching what `reply` already does when a customer
answers a `resolved`/`pending` ticket. There's no agent context at reopen
time to justify `pending`.

**Q4: Do `resolved_at` and `closed_at` get cleared?**
Recommendation: yes, both reset to `null`. `reopenTicket` (the agent path)
already clears `resolved_at` on the same reasoning: a `resolved`/`closed`
timestamp on an `open` ticket is stale data that would otherwise make the
ticket look closed to anything that reads those fields directly. Medium
confidence — flagging for explicit sign-off since nothing today exercises
reading those fields off a reopened ticket.

**Q5: What happens if the ticket's messages were already purged?**
`purgeClosed` deletes messages 7 days after `closed_at` (`KEEP_DAYS = 7`,
`src/jobs/purge-closed.js`), which is *before* the proposed 14-day reopen
window closes. So a ticket closed on day 0 can be purged on day 7 and still
be eligible for reopening through day 13.
Recommendation: allow it. The retention policy ("don't keep conversation
text of finished tickets longer than a week," per the comment in
`purge-closed.js`) is about *closed* tickets, not a promise that reopening
restores history. The customer's reopen message simply starts the
conversation again with no prior messages visible — that's a correct
reflection of the policy, not a bug to work around.

**Q6: `purged` flag on reopen — the one non-negotiable item.**
`purgeClosed` skips any ticket where `t.purged` is already `true`
(`src/jobs/purge-closed.js:13`). It's a one-way latch with no code path that
ever resets it. If a reopened-then-reclosed ticket keeps `purged: true` from
its first close, the *second* close-and-purge cycle will silently skip it
forever, and its new messages will never be deleted — a retention-policy
violation, not a style question.
Recommendation (required, not just a preference): reopening must
unconditionally set `purged: false`, whether or not it was `true` going in.
This is acceptance criterion #6 below and should get its own test.

**Q7: Does reopening reset the SLA due time, or cap how many times a ticket
can be reopened?**
Recommendation: no to both, for v1. Nothing in the current code touches
`sla_due_at` after creation, and there's no existing concept of a reopen
counter. Adding either would be scope beyond "let customers reopen within 14
days" — revisit only if support raises it as a real problem (e.g. abuse).

**Q8: Does the agent-only `reopenTicket` change at all?**
Recommendation: no. It stays exactly as-is (`resolved` → `open` only, agent
sender, `ticket_reopened` event). It's pinned by exact-message assertions in
`test/tickets.test.js:34-41` ("cannot reopen a open ticket" /
"cannot reopen a closed ticket"), and conflating "agent takes back a
resolved ticket" with "customer reopens a closed ticket" would blur two
different business actions behind one function. Add a new, separate
function instead (see Design).

**Q9: What do we tell the assigned agent, and what if there isn't one?**
Recommendation: queue a notification via the existing `notify.notifyAgent`
with a new event type `ticket_reopened_by_customer` (distinct from the
agent-driven `ticket_reopened`, so downstream consumers — email templates,
dashboards — can tell who triggered it). If `assignee_id` is `null`, skip
notifying silently: `notifyAgent` throws when called with no agent
(`src/notify.js:7`), and an unassigned closed ticket is a real, unexceptional
case (the queue may never have gotten to it before it closed).

## Design

**`src/tickets.js`**
- Add `const DAY = 24 * HOUR;` near the existing `HOUR` constant — every job
  file currently redefines `DAY` locally (`close-resolved.js`,
  `purge-closed.js`); this is the third such need, so it belongs on the
  module that owns ticket time math instead of being inlined again.
- Add `REOPEN_WINDOW_DAYS = 14` alongside `SLA_HOURS`.
- New function:
  ```js
  function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
    const t = mustGet(store, id);
    if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
    if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
      throw new Error('this ticket closed too long ago to reopen');
    }
    if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');
    store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
    const updated = store.updateTicket(id, {
      status: STATUS.OPEN,
      resolved_at: null,
      closed_at: null,
      purged: false,
    });
    if (t.assignee_id) notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id });
    return updated;
  }
  ```
- Export `reopenByCustomer` and `REOPEN_WINDOW_DAYS` alongside the existing
  exports.
- `reopenTicket` (agent path) is untouched — see Q8.

**`src/portal.js`**
- New function, mirroring the org-scoping already done by `openTicket` /
  `getMyTicket` / `reply`:
  ```js
  function reopen(store, customer, id, message, { now = new Date() } = {}) {
    const t = getMyTicket(store, customer, id);
    if (!t) return null;
    return reopenTicket.call /* placeholder */;
  }
  ```
  Concretely: scope with the same `getMyTicket` null-check `reply` uses, then
  delegate business rules to `tickets.reopenByCustomer`:
  ```js
  function reopen(store, customer, id, message, { now = new Date() } = {}) {
    const t = getMyTicket(store, customer, id);
    if (!t) return null;
    return reopenByCustomer(store, id, message, { now });
  }
  ```
  Returns `null` for a ticket that isn't in the customer's org, same as
  `getMyTicket`, rather than leaking existence of other orgs' tickets.
- Export `reopen` alongside the existing exports.

**`docs/glossary.md`**
- The **closed** bullet currently reads "final. A closed ticket is never
  changed again. If the customer comes back, they start a new ticket." That
  is no longer accurate. Recommendation: replace with something like
  *"closed: final, unless the customer reopens it from the portal within 14
  days of closing. After that window (or once purged), the customer starts a
  new ticket instead."*

**`test/tickets.test.js`** (or a new `test/reopen-ticket.test.js` — either
is fine; existing file already covers the full lifecycle so extending it
keeps the lifecycle story in one place)
- Customer reopens a closed ticket within the window → status `open`,
  `resolved_at`/`closed_at` cleared, message appended, assignee notified with
  `ticket_reopened_by_customer`.
- Reopen attempt at/after 14 days → throws.
- Reopen attempt on anything other than `closed` → throws (mirrors the
  existing `only a resolved ticket can be reopened` test shape).
- Empty/whitespace message → throws.
- Unassigned ticket (`assignee_id: null`) reopened → no throw, no
  notification queued (`drain()` returns `[]`).
- **Acceptance criterion #6 (required):** a ticket closed, reopened, and
  closed a second time must purge on its *second* cycle — i.e.
  `purged: false` after reopen, verified by running `purgeClosed` again
  after the second close and asserting messages are actually deleted.
- Portal-level: `portal.reopen` returns `null` for another org's ticket,
  same as `portal.getMyTicket`.

## Acceptance criteria

1. A customer can reopen their own `closed` ticket within 14 days of
   `closed_at` via `portal.reopen`.
2. Reopening requires a non-empty message, which is appended to the ticket's
   messages.
3. Reopening more than 14 days after `closed_at` throws and leaves the
   ticket unchanged.
4. Reopening sets status to `open` and clears `resolved_at` and `closed_at`.
5. The assigned agent (if any) is notified via `notifyAgent` with event type
   `ticket_reopened_by_customer`; an unassigned ticket reopens without error
   and without a notification.
6. **A reopened-then-reclosed ticket purges correctly on its second cycle** —
   `purged` is reset to `false` on reopen, regardless of its prior value.
7. A customer cannot reopen, or see, another organisation's ticket.
8. The existing agent-only `reopenTicket` (resolved → open) is unchanged and
   its pinned test assertions still pass.
9. `docs/glossary.md`'s description of "closed" reflects the new behaviour.

## Explicitly out of scope (v1)

- Resetting or extending the SLA due time on reopen.
- Limiting how many times a ticket can be reopened.
- Restoring purged messages — reopening after purge starts a visibly empty
  conversation, not a resurrection of deleted text.
- Any change to who can reopen (agents keep using `reopenTicket`; this spec
  only adds a customer-facing path).
