# Spec: customer-initiated ticket reopen (portal)

Status: **draft, awaiting sign-off** — written while the owner was away; not implemented.

## 1. Request

"Let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do."

## 2. Current behavior (today's code)

- Status is one of `open → pending/resolved → closed`. Per `docs/glossary.md`, **closed is final**: "A closed ticket is never changed again. If the customer comes back, they start a new ticket."
- `tickets.reopenTicket(store, id, agentId)` (`src/tickets.js:38`) lets an **agent** move a `resolved` ticket back to `open`. It explicitly refuses anything else: `if (t.status !== STATUS.RESOLVED) throw ...`. This path is pinned by `test/tickets.test.js:34-41`, which asserts the exact error text for both an `open` and a `closed` ticket.
- `portal.reply(store, customer, id, body)` (`src/portal.js:21`) is the only portal write to an existing ticket. It throws on a closed ticket ("this ticket is closed; please open a new one") and implicitly reopens `resolved`/`pending` tickets back to `open` when the customer answers.
- `src/jobs/close-resolved.js`: closes a `resolved` ticket 3 quiet days after `resolved_at`.
- `src/jobs/purge-closed.js`: 7 days after `closed_at`, deletes the ticket's **messages** and sets `purged: true`. The ticket row (subject, dates, org) is kept for reporting. The job skips any ticket where `t.purged` is already `true` — it never re-checks a purged ticket.
- `src/notify.js`: `notifyAgent` just queues `{to, event}`; a separate mail worker sends it. Today's only reopen event is `{ type: 'ticket_reopened', by: 'agent:<id>' }`, sent only when the reopening agent differs from the assignee.

This is a **contract change**: it breaks the glossary's "closed is final" rule and adds a new way for a non-agent to move a ticket's status. It touches `tickets.js`, `portal.js`, `notify.js`, and `docs/glossary.md`.

## 3. Proposed behavior

A customer who can see a **closed** ticket of their own organisation may reopen it, provided fewer than 14 days have passed since it closed. Reopening:

- moves the ticket to `open` (same target status as an agent reopen),
- requires the customer to submit a message explaining why (reuses the "add a message" mechanic `reply` already has),
- notifies the assigned agent, if any,
- is only available in that 14-day window; after that, the UI/API tells them to open a new ticket (today's existing message).

## 4. Design decisions (questions I'd ask you, answered by recommendation)

**Q1: Does reopening require the customer to write a message, or can they reopen with no comment?**
Recommendation: **require** a non-empty message, same as `portal.reply`. An agent landing on a reopened ticket with zero content and no indication of what changed is a worse outcome than asking the customer for one line. Implementation-wise this also means reopen can reuse the same "append customer message" step `reply` uses.

**Q2: Is the reopen path a new function, or does it live inside the existing `tickets.reopenTicket`?**
Recommendation: a **new** function (e.g. `tickets.reopenByCustomer`), not a branch inside the agent one. `reopenTicket` is agent-only by contract, pinned by `test/tickets.test.js:34-41`'s exact-message assertions, and only ever accepts a `resolved` ticket. Reusing it would mean either loosening that contract (risk to agent-side behavior) or adding an `actor`/`role` parameter that callers must get right. A separate function keeps the agent path untouched and lets the customer path have its own precondition (`status === closed` + 14-day window) without entangling the two.

**Q3: Does `portal.reply` on a closed ticket implicitly reopen it, now that reopening exists?**
Recommendation: **no** — keep `reply` throwing on every closed ticket, exactly as today. Reopening should be a deliberate, named action (so the "why are you reopening this" message is always captured and the event fired is unambiguous), not a side effect of answering. The portal UI shows a distinct "Reopen this ticket" action on closed tickets inside the window, separate from the (disabled) reply box.

**Q4: What event type does the notification use — reuse `ticket_reopened`, or a new type?**
Recommendation: a **new** event type, `ticket_reopened_by_customer`. The existing `ticket_reopened` event's `by` field is agent-shaped (`agent:<id>`) and the mail worker likely has copy tailored to "a colleague reopened this." A customer reopening is a different notification (arguably higher priority, different tone), so giving it its own type lets the mail template differ without a conditional on `by`'s string prefix.

**Q5: Who gets notified if the ticket has no assignee (never assigned, or unassigned before close)?**
Recommendation: **no notification is sent**; the ticket simply goes back into the unassigned `open` queue, same as a brand-new ticket. There's no agent to tell. Don't notify a team/channel instead — out of scope unless you tell me otherwise.

**Q6: The 14-day reopen window overlaps the 7-day purge window — a ticket closed 8–14 days ago has already had its messages deleted by `purge-closed.js`. Should reopening still be allowed?**
Recommendation: **yes, allow it.** Purge only deletes messages and sets `purged: true`; the ticket row always survives (that's the whole point of "keep the row for reporting"). The customer just resumes a ticket with no visible history above their new message, same as if it were a slightly-aged paper trail. Flagging the missing history in the portal copy ("earlier messages on this ticket are no longer available") is a UI nicety, not a blocker.

**Q7 (the gotcha): if a reopened-and-later-purged ticket gets closed a second time, will it purge again?**
This is the one that must not be missed: `purge-closed.js:13` does `if (t.purged) continue` — it is a one-way latch with no reset anywhere today. If reopen does not clear `purged`, the ticket is permanently invisible to the purge job: its second round of messages (from the reopen onward) would never be deleted, which is a direct violation of the 7-day retention policy `purge-closed.js`'s own comment attributes to Legal.
Recommendation: reopening **must** unconditionally set `purged: false` alongside `status: open`, `closed_at: null`, `resolved_at: null`. This is not optional/stylistic — treat it as a required part of the change, and add a test that closes → purges → reopens → closes → purges again and asserts messages are deleted the second time too.

**Q8: Does reopening reset the SLA due time (`sla_due_at`)?**
Recommendation: **no, leave it untouched**, for consistency with the existing agent `reopenTicket`, which also never touches `sla_due_at`. If support wants a fresh SLA clock on reopen (agent- or customer-triggered), that's a separate decision affecting both paths — raise it as its own follow-up rather than making the customer path behave differently from the agent path.

**Q9: Is there a limit on how many times a ticket can be reopened, or how many times a given closed ticket can be reopened by the customer?**
Recommendation: **no limit**, matching today's agent-side `reopenTicket` (which also has none). Add one later only if abuse shows up in practice.

## 5. Proposed API shape

`src/tickets.js` — new function alongside `reopenTicket`, not replacing it:

```
REOPEN_WINDOW_DAYS = 14

reopenByCustomer(store, id, customerId, { now }):
  t = mustGet(store, id)
  if t.status !== CLOSED: throw `cannot reopen a ${t.status} ticket`
  if now - t.closed_at >= REOPEN_WINDOW_DAYS * DAY: throw 'too late to reopen; please open a new ticket'
  updated = store.updateTicket(id, { status: OPEN, resolved_at: null, closed_at: null, purged: false })
  if t.assignee_id: notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id, by: `customer:${customerId}` })
  return updated
```

The `< / >=` boundary mirrors the convention already used by `close-resolved.js` and `purge-closed.js` (elapsed time compared with a plain `<`), so "within 14 days" means the window closes at exactly 14×24h after `closed_at`, same semantics as `KEEP_DAYS`/`QUIET_DAYS`.

`src/portal.js` — new function alongside `reply`:

```
reopenTicket(store, customer, id, body, { now }):
  t = getMyTicket(store, customer, id)
  if !t: return null
  tickets.reopenByCustomer(store, id, customer.id, { now })   // throws per Q2/Q6 rules above
  store.addMessage(id, { from: 'customer', body, at: now })
  return getMyTicket(store, customer, id)
```

Org-scoping stays in `portal.js` (via `getMyTicket`), matching every other portal function — `tickets.js` never sees `customer`, only `customerId`.

## 6. Notification

Reuses the existing `notifyAgent` queue/mail-worker split; no new infrastructure. New event:

```
{ type: 'ticket_reopened_by_customer', ticketId, by: 'customer:<id>' }
```

Sent once, only when `assignee_id` is set (Q5).

## 7. Docs that need to change alongside the code

`docs/glossary.md`'s **closed** entry currently reads "final... never changed again. If the customer comes back, they start a new ticket." That sentence becomes false. Recommended rewrite:

> **closed**: normally final. A closed ticket may be reopened by the customer within 14 days of closing, or by an agent at any time while it is resolved (see **status**); otherwise, if the customer comes back, they start a new ticket.

## 8. Edge cases

1. **Already purged, still in window** — allowed; history is gone, new message starts fresh (Q6).
2. **Reopened then closed again, then purged again** — must purge correctly the second time (Q7); this is the one regression test that matters most.
3. **No assignee** — reopens with no notification, lands back in the unassigned queue (Q5).
4. **Exactly at the 14-day boundary** — not allowed, per the `<` convention matching other jobs (see §5).
5. **Ticket from another organisation** — `getMyTicket` already returns `null` for cross-org access; `portal.reopenTicket` returns `null` the same way `reply`'s org check does, no new exposure.
6. **Empty/whitespace-only reopen message** — rejected before calling into `tickets.js`, same validation style as a normal reply would need (today's `reply` doesn't validate body either — if you want this enforced, it should apply to both functions, not just the new one; flagging as a pre-existing gap, not something this change should fix unilaterally).
7. **Ticket is `open`/`pending`/`resolved`, not `closed`** — rejected with `cannot reopen a <status> ticket`, same message shape as the agent path, so portal error handling can share a pattern.

## 9. Out of scope

- Changing `reply`'s behavior on closed tickets (Q3).
- Resetting `sla_due_at` on any reopen path, agent or customer (Q8).
- A cap on reopen count (Q9).
- Any change to `close-resolved.js` or the 7-day purge window itself — this spec only adds a new entry point into `open`, it doesn't touch why or when tickets close or purge.

## 10. Acceptance criteria

1. A customer can reopen their own org's ticket while `status === closed` and `now - closed_at < 14 days`, moving it to `open`.
2. Reopening outside the 14-day window throws/returns the existing "too late, open a new ticket" style error and leaves the ticket closed.
3. Reopening a ticket in any status other than `closed` is rejected with a status-specific error, mirroring the agent-side message shape.
4. Reopening requires and stores a customer message on the ticket.
5. The assigned agent is notified via a new `ticket_reopened_by_customer` event when one exists; no notification is sent when the ticket is unassigned.
6. Reopening clears `purged` back to `false` unconditionally, and a ticket that is closed → purged → reopened → closed again gets its second round of messages purged on schedule.
7. `agentTicket.reopenTicket` (the existing agent path) and `test/tickets.test.js:34-41` are unchanged and still pass untouched.
8. A customer from a different organisation cannot reopen or see the ticket (existing `getMyTicket` org check covers this; add a test if one doesn't already exist for the new function).
9. `docs/glossary.md`'s **closed** definition is updated to describe the new exception.

## 11. Suggested next step

Once you've reviewed §4's recommendations (especially Q1–Q4, which shape the API) and confirmed or amended them, this is ready to go through `writing-plans` → implementation. The only item I'd treat as non-negotiable rather than a preference is **Q7** (the `purged` reset) — skipping it reopens a compliance gap Legal already asked to close.
