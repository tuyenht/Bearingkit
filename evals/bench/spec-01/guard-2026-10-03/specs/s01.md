# Spec: customer reopens a closed ticket

Status: **Draft — awaiting review**. Written while the requester was away;
every open question below is answered with a recommendation rather than left
blocking, per their instruction. Nothing in this spec is built yet.

## Request, restated

Customers keep asking to reopen a ticket after it's been closed, instead of
filing a new one. Build: a portal customer can put their own org's closed
ticket back to `open` within 14 days of it closing, and the agent who owns
the ticket is notified that it happened.

## This conflicts with a documented rule — read first

`docs/glossary.md` currently says:

> **closed**: final. A closed ticket is never changed again. If the customer
> comes back, they start a new ticket.

This feature reverses that rule for a 14-day window. That's not a reason to
stop — it's the actual ask — but it means:

1. The glossary needs an edit alongside the code, or the docs will lie to the
   next reader. **Recommendation: yes, update it** (edit included below).
2. This is a change to a stated domain invariant, not a routine feature add.
   Combined with its interaction with the legal-mandated purge job (next
   section), **this is classified COUNCIL**, not ACT. It should get the
   requester's explicit sign-off before `bk-plan`/`bk-build`, even though the
   implementation itself is small. See the RBA at the end.

## The purge-job interaction (the part most likely to be missed)

`src/jobs/purge-closed.js:7-8` — *"Legal asked for this: we do not keep
conversation text of finished tickets longer than a week."* `KEEP_DAYS = 7`.
It deletes a closed ticket's messages and sets `purged: true` once, 7 days
after `closed_at`, and skips any ticket where `purged` is already `true`
(`src/jobs/purge-closed.js:13`).

The requested reopen window is **14 days** — twice the purge window. So:

- A ticket closed on day 0 is eligible for reopen through day 14, but its
  messages are already deleted by day 7.
- If reopened and later re-closed, the new conversation must be purgeable
  again. If `purged` is left `true` from the first cycle, `purgeClosed` will
  skip it forever (`t.purged` short-circuits the loop) and the second
  conversation's text would never be deleted — a real compliance bug, not a
  style nit.

**Recommendation:** allow reopening even after purge (the customer is still
inside the promised 14-day window; don't punish them for the back-office
retention schedule), and reset `purged: false` on reopen so the second
close-and-purge cycle works. Surface to the customer/agent that pre-purge
history is gone (see Q5).

**Alternative considered and rejected:** shorten the reopen window to 7 days
to match the purge window, so this case can't happen. Rejected because the
requester asked for 14 days specifically ("customers keep asking for this"),
and narrowing it to dodge a back-office job is optimizing for our
convenience over the stated ask. Flag instead; don't silently shrink scope.

## Decisions (asked and answered, so review is approve/amend rather than
stuck on open questions)

| # | Question | Recommendation | Why |
|---|---|---|---|
| Q1 | Is the 14-day window inclusive of day 14? | **Inclusive**: allowed while `now - closed_at <= 14 days`. | "Within 14 days" reads as inclusive to a customer; an off-by-one that rejects on day 14 would generate support tickets about the reopen feature itself. |
| Q2 | Allow reopening a ticket whose messages were already purged (closed 7–14 days ago)? | **Allow it**, and reset `purged: false` on reopen (see above). | Covered above — the customer's window promise shouldn't depend on an internal retention job's timing. |
| Q3 | Does reopening require a message from the customer, or can it be a bare status flip? | **Require a non-empty message body**, added the same way `portal.reply()` adds one. | Mirrors the existing resolved-ticket reopen-by-reply pattern (`src/portal.js:21-27`); and for a purged ticket there would otherwise be zero conversation content for the agent to act on. |
| Q4 | What status does the ticket enter? | **`open`**, `closed_at` cleared to `null`. | Matches `reopenTicket`'s agent-side behavior (`src/tickets.js:38-44`) and `reply()`'s resolved→open transition — consistently "a reopened ticket is waiting on an agent." |
| Q5 | Should the customer/agent be told when pre-purge history is gone? | **Yes, at the API/data level**: the reopen result still reports whether purge had occurred (callers can show "earlier messages on this ticket were removed after it closed"). No UI exists in this repo to build the actual banner — flagged as a follow-up, not built here. | Silent data loss is worse than a visible note; cheap to expose now, awkward to retrofit later. |
| Q6 | Recompute the SLA due time on reopen? | **No — leave it as originally set.** | Glossary: "SLA due time... is set when the ticket is created," scoped to creation only. Recomputing it is a bigger, separate behavior change nobody asked for. Trade-off: a reopened ticket's SLA will read as already overdue; that's a back-office display concern, out of scope here. |
| Q7 | Keep the same assignee on reopen? | **Yes, unchanged.** | Nothing in the current model unassigns a ticket on close; there's no reason to invent an unassign step just for this. |
| Q8 | Notification event name? | **`ticket_reopened_by_customer`**, distinct from the existing agent-side `ticket_reopened` (`src/tickets.js:42`). | Lets notification templates / agent-facing copy distinguish "an agent pulled this back" from "the customer asked for it back," which is a different tone and possibly a different queue. |
| Q9 | Notify when the ticket has no assignee (was never picked up before closing)? | **Skip notification, no error.** `notifyAgent` currently throws on a falsy `agentId` (`src/notify.js:7`); the new code must check `assignee_id` before calling it, same as nothing-to-notify is a normal case, not a failure. | An unassigned ticket reopening should go back to the unassigned queue, not crash the request. |
| Q10 | Where does the logic live? | **Core transition + validation in `src/tickets.js`** (new function, parallel to `reopenTicket`), **thin org-scoped wrapper in `src/portal.js`** (parallel to `reply()`). | Matches the existing split: `tickets.js` owns status rules, `portal.js` owns "which customer may touch which ticket." |

## Design

### `src/tickets.js` — new function `reopenClosedTicket(store, id, { now })`

- Loads the ticket (`mustGet`); throws `cannot reopen a ${status} ticket` for
  anything other than `closed` — same error shape as the existing
  `reopenTicket` guard (`src/tickets.js:40`), so callers and tests can match
  the pattern they already know.
- Throws `too late to reopen; start a new ticket` if
  `now - closed_at > 14 days`.
- Updates the ticket: `status: OPEN`, `closed_at: null`, `purged: false`.
- Returns `{ ticket, wasPurged }` so the portal layer (Q5) knows whether to
  flag lost history, without re-deriving it from a patch that already
  cleared the flag.
- Notifies the assignee only if `assignee_id` is set, with event
  `ticket_reopened_by_customer` (Q8/Q9). Reuses `notifyAgent` from
  `src/notify.js` as-is — no change needed there.

### `src/portal.js` — new function `reopen(store, customer, id, body, { now })`

- Loads via `getMyTicket` (org-scoped, same as `reply()`); returns `null` if
  missing or cross-org, matching existing behavior (`src/portal.js:10-14`).
- Rejects an empty/missing `body` before touching the store.
- Calls `reopenClosedTicket`; on success, appends the customer's message via
  `store.addMessage` (same as `reply()`), then returns the refreshed ticket
  (via `getMyTicket`) plus the `wasPurged` flag from Q5.
- Lets `reopenClosedTicket`'s errors (wrong status, too late) propagate
  unchanged — the two existing error-throwing patterns in this codebase
  (`tickets.js` guards, `portal.js` lets them bubble, see `reply()`'s
  closed-ticket throw) are reused rather than adding a third error style.

### `docs/glossary.md`

Replace the "closed" entry's last sentence:

> **closed**: final. A closed ticket is never changed again automatically,
> but the customer may reopen it from the portal within 14 days of closing;
> after that, they start a new ticket.

### No changes needed

- `src/jobs/close-resolved.js` — unaffected; it only ever acts on `resolved`
  tickets.
- `src/jobs/purge-closed.js` — unaffected as code; its *behavior* is now
  depended on correctly re-triggering because `reopenClosedTicket` resets
  `purged`. No line there needs to change, but this is the one place a
  future edit to either file should make someone re-read the other.
- `src/notify.js` — `notifyAgent` is already generic over event shape.

## Edge cases

1. **Exactly 14 days since `closed_at`.** Allowed (Q1, inclusive).
2. **15 days since `closed_at`.** Rejected with `too late to reopen; start a
   new ticket`.
3. **Reopened between day 7 and day 14, after the nightly purge already
   ran.** Allowed; `purged` reset to `false`; caller gets `wasPurged: true`
   so it can surface the data-loss note (Q2, Q5).
4. **Ticket has no assignee.** Reopen succeeds; no notification is sent, no
   error is thrown (Q9).
5. **Ticket belongs to a different organisation than the caller.** Treated
   as not found (`null`), same as every other portal lookup — no leak of
   whether the ticket exists.
6. **Ticket is `open`, `pending`, or `resolved` (not `closed`).** Rejected
   with `cannot reopen a ${status} ticket`; customers already have `reply()`
   for those statuses.
7. **Missing or empty `body`.** Rejected before any store write; no
   half-applied reopen with no message.
8. **Ticket id doesn't exist at all.** Same as case 5 — `null`, not found.

## Acceptance criteria

- A customer can reopen their own org's ticket that is `closed` and was
  closed ≤14 days ago, by supplying a non-empty message; the ticket becomes
  `open` with `closed_at` cleared and the message appended.
- The same action on a ticket closed >14 days ago is rejected and the
  ticket is left unchanged.
- The same action on a ticket that is not `closed` is rejected with a status
  error and the ticket is left unchanged.
- The same action on another organisation's ticket, or a nonexistent ticket,
  behaves like the existing `getMyTicket`/`reply` miss case (no data leak).
- On success, if the ticket had an assignee, exactly one
  `ticket_reopened_by_customer` notification is queued to that assignee; if
  it had none, zero notifications are queued and no error is raised.
- Reopening a ticket whose messages were already purged succeeds, clears
  `purged`, and reports that history was lost; a subsequent close-and-wait-7-
  days cycle purges the new messages (regression test should assert the
  second purge actually fires — this is the case memory flags as easy to
  miss).
- `docs/glossary.md`'s "closed" definition matches the implemented rule.

## Out of scope (flagged, not built)

- Any UI/portal front-end rendering of the "history was removed" note — this
  repo has no front-end; only the data needed to build one (`wasPurged`).
- Rate-limiting repeated reopen/close cycles — the nightly close job already
  imposes a ≥3-day floor between a reply and the next closure, which seemed
  sufficient; revisit if abuse shows up.
- Recomputing or extending the SLA due time on reopen (Q6).
- Changing the agent-side `reopenTicket` (resolved-ticket path) — untouched.

## RBA (COUNCIL)

```
Objective: A portal customer can put their own org's closed ticket back to
  open within 14 days of closed_at, with a message, notifying the assignee.
Scope: src/tickets.js (new reopenClosedTicket), src/portal.js (new reopen
  wrapper), docs/glossary.md (closed definition). Out of scope: close-resolved
  job, purge-closed job code, SLA recompute, agent-side reopenTicket, any
  front-end/UI, rate limiting.
Rollback: additive new functions plus one doc edit; no schema/migration, no
  new columns (purged and closed_at already exist). Revert = revert the
  commit/PR; no data backfill either direction.
Edge cases:
  1. Reopen at exactly 14 days — allowed (inclusive boundary, Q1).
  2. Reopen after the ticket was already purged (day 7-14) — allowed, purged
     flag reset to false so the next close cycle purges correctly (Q2).
  3. Ticket has no assignee at reopen time — succeeds, notification skipped,
     no thrown error (Q9).
  4. Wrong status (not closed), wrong org, missing ticket, empty body — all
     rejected before any store write, reusing existing error/miss patterns.
Decision: needs approval, because it reverses a documented domain invariant
  ("closed is final") and its correctness depends on the legal-mandated
  purge job resetting correctly — a compliance-adjacent interaction, not a
  routine ACT change. Recommendation above is to proceed with Q1-Q10 as
  written; awaiting the requester's review (back tomorrow).
```
