# Spec: customer reopen of a closed ticket

Status: **draft, not implemented** — written while the owner was unavailable. Every decision below is a recommendation the owner still needs to confirm or override before this goes to `bk-plan`/`bk-build`. Classified **COUNCIL** (see §4); nothing in this document has been built.

## 1. Restatement

Request, in the owner's words: "let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do."

Technical reading: add a new portal-facing action, distinct from the existing agent-only reopen and from a customer's ordinary reply, that:
- is only available on a ticket whose `status` is `closed` (`docs/glossary.md:12`) and whose `closed_at` is less than 14 days in the past,
- is scoped to the ticket's own organisation, the same way every other portal action is (`src/portal.js:6-14`),
- moves the ticket back to `open` and records what the customer said,
- queues a notification to the ticket's assignee, if it has one, the same way an agent-triggered reopen already does (`src/tickets.js:42`).

**Where the request conflicts with the project's own words:** `docs/glossary.md:12` currently defines closed as *"final. A closed ticket is never changed again. If the customer comes back, they start a new ticket."* This request replaces that promise with a time-boxed exception. See Decision D1 below — the glossary needs to change, not just the code.

## 2. Touchpoints (`file:line`)

- `docs/glossary.md:12` — the "closed is final" definition that this feature carves an exception into.
- `src/tickets.js:37-44` — `reopenTicket`, the existing **agent**-only reopen: only accepts a `resolved` ticket, has no time limit, no org scoping (callers are back-office). Stays untouched (Decision D3).
- `src/portal.js:20-28` — `reply`, the existing customer action closest to this one: org-scoped via `getMyTicket`, throws `'this ticket is closed; please open a new one'` for any closed ticket (`src/portal.js:24`). That error text is the current, soon-to-be-partially-wrong, customer-facing statement of the same "closed is final" rule.
- `src/jobs/purge-closed.js:10-20` — nightly job that deletes a closed ticket's messages 7 days after `closed_at` and sets `purged: true`, then skips any ticket where `purged` is already `true` (`src/jobs/purge-closed.js:13`). The reopen window (14 days) is longer than the purge window (7 days), so a reopenable ticket can already be purged — see Decision D2 and Edge case E2.
- `src/jobs/close-resolved.js:8-16` — sets `closed_at` each time a ticket is closed. A ticket reopened and later closed again gets a new `closed_at`, which restarts the 14-day window (Q7).
- `src/notify.js:6-9` — `notifyAgent`, reused as-is; requires a truthy `agentId`, so "no assignee" must be guarded by the caller, as `reopenTicket` already does (`src/tickets.js:42`).
- `test/tickets.test.js:34-41` — locks in, via regex, that `tickets.reopenTicket` throws `/cannot reopen a (open|closed) ticket/` for anything but `resolved`. This is evidence for Decision D3: the agent path's contract must not change.

## 3. Terms

- **Reopen (agent)** — existing, `src/tickets.js:38`: an agent takes a `resolved` ticket back to `open`. No time limit, no customer involved.
- **Reopen (customer)** — new, this spec: a customer brings a `closed` ticket back to `open`, within 14 days of `closed_at`, by posting a message. Distinct action from the above; sharing the name "reopen" is a coincidence of English, not a shared code path (Decision D3).
- **Reply** — existing, `src/portal.js:21`: a customer answers a ticket that is not closed. Unchanged by this feature — see Decision D4 on why reply and reopen stay separate actions.
- **Purged** — existing, `src/jobs/purge-closed.js:3-4`: the ticket's messages have been deleted; the ticket row (subject, dates, org) is kept for reporting. This spec treats `purged` as describing *the messages of the closed period that just ended*, not a permanent property of the ticket — see Decision D2.

## 4. Classification

**COUNCIL.** Per the gate: this changes a module's existing contract (what "closed" and "reopen" mean), touches more than one module (`tickets.js`, `portal.js`, interacts with `purge-closed.js`), and the glossary's own stated invariant is the thing being changed. None of these are reversed by a revert alone once customers rely on the new behavior.

### RBA-lite

```
Objective: a customer can bring their own closed ticket back to open within 14 days of closing, and the assigned agent is told.
Scope: src/portal.js (new function), docs/glossary.md (closed definition), docs/specs/reopen-ticket.md (this file).
        Out of scope: src/tickets.js (agent reopen untouched), src/jobs/*.js (both jobs untouched, only reasoned about), any UI/HTTP layer (none exists in this repo yet).
Rollback: revert the commit; the new portal function and the glossary wording are additive, nothing is migrated or deleted.
Edge cases:
  1. Ticket closed >= 14 days ago: reopen rejected, ticket unchanged (E1).
  2. Ticket closed < 14 days ago but already purged (closed > 7 days ago): reopen still allowed, purged flag reset (E2).
  3. Ticket belongs to a different organisation: behaves like a missing ticket, no existence leak (E3).
Decision: needs approval — this is a customer-facing change to a documented invariant ("closed is final"), so it is proposed below (§ Council, § Open questions) rather than built.
```

## 5. Council

### Council: should a customer be able to bring a closed ticket back to `open`, and if so, through what contract?

Roles: domain integrity (glossary & data-deletion correctness), support operations (what a customer and an agent actually experience), engineering contract (how this is exposed without breaking the agent path).

#### Options

- **Domain integrity**: add the behavior as a new function, never by loosening `tickets.reopenTicket`'s guard to also accept `closed`. Cost: one more function name to document. Risk avoided: the agent path silently starts accepting a case it was never designed or tested for (`test/tickets.test.js:40` would need to lie).
- **Support operations**: make "reopen" one customer action that both flips the status and records what they said, rather than "reopen" then "reply" as two calls — a customer reopening a ticket always has something to say. Cost: the new action takes a required message body, unlike the agent's `reopenTicket`, which takes none. Risk: a UI that calls this as a bare button click (no text) needs to supply *some* body, even a default one.
- **Engineering contract**: keep `reply()` throwing on every `closed` ticket, with no special case for "closed but still in the 14-day window." Cost: a customer who tries to use the ordinary reply box on a recently-closed ticket still gets the existing error and must use the distinct reopen action. Risk avoided: an ordinary reply silently resurrecting an old ticket when the customer only meant to leave a comment, with no explicit "reopen" intent captured anywhere (notification text, audit trail).

#### Conflicts

No disagreement on the shape of the solution. The only friction is support operations' "always require a message" against the agent path's "no message needed" — that is an intentional asymmetry (Decision below), not a conflict to resolve.

#### Verdict

Add `portal.reopenClosedTicket(store, customer, id, body, { now })`:
- org-scoped the same way `getMyTicket` already is (`src/portal.js:10-14`);
- guarded to `status === 'closed'` and `now - closed_at < 14 days`;
- requires a message body (the reopen *is* the customer's message, not a bare status flip);
- sets `status: 'open'`, `resolved_at: null`, `purged: false`;
- appends the message via `store.addMessage`, same shape `reply()` already uses;
- notifies the assignee, if any, with a new event type `ticket_reopened_by_customer`.

`tickets.reopenTicket` (agent path) is **not** touched — it keeps its existing signature, guard, and test contract.

#### Rejected

- Extending `tickets.reopenTicket` to accept a `closed` ticket when the caller is a customer: rejected because it forces one function to carry two authorization models (agent vs. customer) and two different time windows (none vs. 14 days) behind one guard clause, which is exactly the kind of change `test/tickets.test.js:34-41` is pinning down today.
- Letting an ordinary `reply()` on a closed-but-within-window ticket silently reopen it: rejected (Decision D4) — reopening should be a deliberate, nameable action with its own notification text, not a side effect a customer could trigger without meaning to.

### Decisions on record

**D1 — the glossary's "closed is final" promise gets an explicit exception, not a quiet override.** Hard to reverse: customers will learn and rely on the new behavior once shipped. Surprising: yes — a future reader of `docs/glossary.md` would otherwise believe closed tickets can never change, which becomes false. Real trade-off: keeping "closed is final" absolute (simpler mental model, but customers who come back within days are forced to retell their issue on a new ticket) vs. a time-boxed exception (matches how most helpdesks behave, at the cost of a less absolute glossary term). Chosen: the exception, worded narrowly ("...unless a customer reopens it from the portal within 14 days, see below").

**D2 — reopening a ticket whose messages were already purged must reset `purged` to `false`, unconditionally.** Hard to reverse: getting this wrong is a silent compliance bug — the next time this ticket is closed, `purgeClosed` would see `purged: true` left over from the *previous* closed period and skip it forever (`src/jobs/purge-closed.js:13`), meaning the new round of messages is never deleted. Surprising: yes, nothing in the purge job's code signals this interaction. Real trade-off: resetting unconditionally (simpler, always correct) vs. only resetting if it was actually `true` (saves one field write, same outcome) — chosen unconditional reset, since the conditional buys nothing and is one more branch to get wrong.

**D3 — the agent reopen path (`tickets.reopenTicket`) and the customer reopen path are separate functions with no shared code.** Hard to reverse: once the agent path's tests encode "only a resolved ticket, any time, no message" (`test/tickets.test.js:34-41`), merging in a second, differently-scoped caller later means re-deriving which guard applies to whom. Surprising: moderately — the names are easy to conflate. Real trade-off: one function with a caller-type branch (less code) vs. two functions (more code, each independently testable and each readable in isolation). Chosen: two functions.

**D4 — reopening is a distinct action from replying; `reply()` keeps throwing on every closed ticket, with no window exception.** Hard to reverse: once a UI is built around "type into the reply box," changing a closed ticket to sometimes accept that silently is a behavior change customers would not notice happening. Surprising: yes — the whole point of "closed" showing a clear error today is that the customer knows they need to act differently. Real trade-off: merging reopen into reply (one text box, fewer customer-facing concepts) vs. a separate explicit reopen action (one more button, but an unambiguous, loggable "I am reopening this" moment with its own notification wording). Chosen: separate action.

## 6. Open questions (answered by recommendation — owner unavailable)

1. **Who may reopen — the original customer only, or anyone in the ticket's organisation?** Recommend: anyone in the organisation, same as every other portal read/write today (`src/portal.js:6-14` scopes by `org_id`, never by `customer_id`); the glossary defines the sharing boundary as the organisation (`docs/glossary.md:18`), not the individual customer.
2. **Is the 14-day window inclusive or exclusive of day 14?** Recommend: exclusive — `now.getTime() - closedAt.getTime() < 14 * DAY`, matching the strict-less-than style already used by `QUIET_DAYS` (`src/jobs/close-resolved.js:11`) and `KEEP_DAYS` (`src/jobs/purge-closed.js:14`).
3. **What status does a customer-reopened ticket land in?** Recommend: `open` — the same target every other "something happened, an agent needs to look again" transition uses (`src/tickets.js:41`, `src/portal.js:26`).
4. **Does `sla_due_at` get recomputed on reopen?** Recommend: no, leave it as originally set. The agent reopen path already leaves it untouched (`src/tickets.js:41` touches only `status`/`resolved_at`); the SLA clock is about the *first* response, which already happened.
5. **What happens if the ticket was already purged (messages deleted) but is still inside the 14-day reopen window?** Recommend: allow the reopen — the ticket row survives purging by design (`src/jobs/purge-closed.js:2-4`, confirmed by `test/tickets.test.js:69`); the customer's new message simply starts the (now empty) message list again. See Decision D2 for the required `purged: false` reset.
6. **Does reopening notify the agent when the ticket has no assignee?** Recommend: no notification, no error — mirror the existing guard at `src/tickets.js:42` (`if (t.assignee_id && ...)`), since `notifyAgent` itself throws on a missing agent id (`src/notify.js:7`).
7. **Can a ticket be reopened more than once within the policy (reopen → closed again by the nightly job → reopen again)?** Recommend: yes, with no cap. "Within 14 days of it being closed" reads as relative to the *current* `closed_at`, which the close job overwrites each time (`src/jobs/close-resolved.js:12`); nothing in the request suggests a lifetime limit.
8. **What notification event type does the agent receive, and does it reuse `'ticket_reopened'`?** Recommend: a distinct type, `'ticket_reopened_by_customer'`, with payload `{ type, ticketId, by: 'customer:<id>' }` mirroring the existing `by: 'agent:${agentId}'` shape (`src/tickets.js:42`) — an agent reading their notification feed should be able to tell a customer-initiated reopen from a colleague handing a ticket back.

## 7. Requirements (acceptance criteria)

- **AC1.** `portal.reopenClosedTicket(store, customer, id, body, { now })` on a ticket with `status: 'closed'`, `org_id === customer.orgId`, and `now - closed_at < 14 days`, given a non-empty `body`: sets `status: 'open'`, `resolved_at: null`, `purged: false`; appends `{ from: 'customer', body, at: now.toISOString() }` to the ticket's messages; returns the updated ticket (same shape `getMyTicket` returns, including `messages`).
- **AC2.** Same ticket, but `now - closed_at >= 14 days`: throws, ticket and messages unchanged.
- **AC3.** Ticket with any status other than `closed`: throws with a message distinct from both existing reopen-error strings (`cannot reopen a ${status} ticket` from `tickets.js`, and `this ticket is closed; please open a new one` from `portal.reply`), so callers and tests can tell the three cases apart.
- **AC4.** Ticket belonging to a different organisation than `customer`: behaves exactly like `getMyTicket` on a foreign ticket — returns `null`, does not throw, reveals nothing about the ticket's existence or status.
- **AC5.** Ticket with a non-null `assignee_id`: exactly one `notifyAgent(store, assignee_id, { type: 'ticket_reopened_by_customer', ticketId, by: 'customer:<customer.id>' })` call is queued.
- **AC6.** Ticket with `assignee_id: null`: no call to `notifyAgent` happens (it would throw if called with no agent — `src/notify.js:7`), and no error is raised to the customer.
- **AC7.** Ticket with `purged: true` (messages already deleted) but still inside the 14-day window: reopen succeeds per AC1; after reopening, `purged` is `false`; a subsequent `purgeClosed` run does not purge this ticket again until `KEEP_DAYS` have elapsed from the *new* `closed_at` set by the next close.
- **AC8.** `docs/glossary.md`'s definition of `closed` is updated to state the 14-day customer-reopen exception, so the glossary and the code agree.

### Out of scope

- Any HTTP/UI layer — this repository has none yet (`README.md` lists only the model layer); this spec defines the function contract only, same altitude as the existing `portal.js` functions.
- A configurable reopen window — hard-coded at 14 days as a named constant, same pattern as `QUIET_DAYS`/`KEEP_DAYS`.
- Rate-limiting or abuse protection on repeated reopens.
- Any change to `tickets.reopenTicket`, `close-resolved.js`, or `purge-closed.js` beyond the `purged` reset performed by the new function itself.
- Concurrency control beyond what already exists (none of `resolveTicket`, `assignTicket`, or `reopenTicket` lock a row today; this feature accepts the same last-write-wins behavior rather than introducing a new primitive).

## 8. Edge cases

1. **Closed exactly at or past the 14-day boundary.** Rejected (AC2); boundary is strict `<`, consistent with `QUIET_DAYS`/`KEEP_DAYS`.
2. **Already purged, still inside the window.** Allowed; `purged` reset to `false` (AC7, Decision D2) — the one gotcha most likely to be missed, because nothing elsewhere in the codebase hints at the dependency between "reopen" and "purge."
3. **Different organisation.** Returns `null`, same as any other cross-org lookup (AC4) — no existence leak.
4. **No assignee.** No notification, no error (AC6).
5. **Wrong status (open/pending/resolved).** Rejected with its own distinct error text (AC3) — must not collide with the agent-path or reply-path error strings that tests already assert on.
6. **Reopened, closed again, reopened again.** Allowed every time (Q7) — the 14-day clock restarts from each new `closed_at`.
7. **Concurrent reopen + nightly job run.** Not newly handled — same last-write-wins behavior the rest of the codebase already has; explicitly out of scope (see above) rather than silently assumed away.

## 9. Assumptions

- The reopen window and purge window can legitimately overlap in either direction (14 > 7 today) — **high confidence**, read directly from the two jobs' constants.
- No HTTP/API layer exists to design against yet — **high confidence**, `README.md` and the file listing show only the model layer and an in-memory/Postgres store interface.
- "Notify the assigned agent" means queuing through the existing `notify.js` mechanism, not a new delivery channel — **high confidence**, it's the only notification path in the codebase and the request's wording ("notify the assigned agent") matches what `reopenTicket` already does for agents.
- A customer-reopened ticket should carry a message, because the request describes a customer action ("a customer can reopen...") rather than a silent status change — **medium confidence**; if the owner wants a bare reopen with no required text, AC1 and the function signature change to make `body` optional, and Decision in §5 (support operations' option) would need revisiting.
