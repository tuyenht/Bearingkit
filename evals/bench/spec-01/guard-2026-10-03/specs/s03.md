# Spec: customer reopens a closed ticket from the portal

Status: draft, awaiting review. Written while the requester was unavailable; the "Open questions" section below is answered by recommendation rather than live Q&A, per their instruction.

## 1. Restatement

**Request, in the customer's words:** "Let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do."

**Technical reading:** add a portal-facing function that, given a ticket the signed-in customer owns, is in status `closed`, and was closed less than 14 days ago, moves it to `open` and queues a `notifyAgent` event to its assignee. No existing function does this today:

- `tickets.reopenTicket` (`src/tickets.js:38-44`) is agent-only and only accepts a `resolved` ticket — `if (t.status !== STATUS.RESOLVED) throw ...`. It is not reusable here without weakening its guard, which would also weaken the agent-facing contract.
- `portal.reply` (`src/portal.js:21-28`) explicitly refuses on a closed ticket: `if (t.status === STATUS.CLOSED) throw new Error('this ticket is closed; please open a new one')` (`src/portal.js:24`). That message is the current product position that closed is final; this feature reverses it under conditions, so the message and the glossary both need updating (see Terms below).

**Terms** (`docs/glossary.md:12`): the glossary currently defines closed as *"final. A closed ticket is never changed again. If the customer comes back, they start a new ticket."* This request changes that definition for the 14-day window. The glossary line needs to become conditional (e.g., "closed is final once 14 days have passed; within 14 days the customer may reopen it instead of starting a new ticket"). Flagged as a required doc update, not silently left stale.

## 3. Edge cases

1. **Ticket closed more than 14 days ago.** Rejected with a clear error; customer is told to open a new ticket (same spirit as the existing closed-ticket message in `portal.js:24`).
2. **Ticket already purged** (`purged: true`, messages deleted by `purge-closed.js`). The row still exists with `closed_at` set. Since purge only runs at 7+ days and this window is 14 days, a purged-but-reopenable ticket is a real, common case, not a corner case. Allowed to reopen (the 14-day window doesn't care whether messages survived) — see Decisions for why `purged` must be reset to `false`.
3. **Concurrent reopen + nightly purge job.** If `purgeClosed` runs between the customer's reopen and ticket inspection, a ticket that is no longer `closed` (now `open`) is simply skipped by `purgeClosed`'s `status: STATUS.CLOSED` query filter (`purge-closed.js:12`) — no race condition, the status change itself is the guard. No additional locking needed.
4. **Ticket with no assignee** (`assignee_id: null`, e.g. closed while still in the unassigned queue — possible if an agent resolves and closes happens via the nightly job without reassignment, or an assignee was cleared). `notifyAgent` throws if `agentId` is falsy (`notify.js:7`). The reopen must not crash in this case — skip notification, same pattern as `reopenTicket`'s own `if (t.assignee_id && ...)` guard (`tickets.js:42`).
5. **Empty/missing customer message.** Rejected — see Decisions (reopen requires a reason, same spirit as `reply` requiring a body).
6. **Cross-tenant access.** Customer from org A tries to reopen org B's ticket. Must return the same "not found" behavior as `getMyTicket` (`portal.js:11-12`), not a status-specific error that would leak the ticket's existence.
7. **Ticket not found at all** (bad id). Same not-found behavior as #6.
8. **Boundary at exactly 14 days.** Resolved by picking one comparison operator and testing it explicitly (see Decisions — reuses the codebase's existing `<` convention).

## 4. Assumptions

| # | Assumption | Confidence |
|---|---|---|
| 1 | "14 days of it being closed" means `now - closed_at < 14 days`, mirroring `closeResolved`'s `now - resolved_at < QUIET_DAYS * DAY` (`close-resolved.js:11`) and `purgeClosed`'s identical pattern (`purge-closed.js:14`). | High — established codebase convention, not guessed. |
| 2 | The customer must supply a message when reopening (not a bare status flip), consistent with `reply` requiring a `body` and with giving the agent something to act on. | Medium — see Open Questions #1. |
| 3 | No SLA re-calculation on reopen (ticket keeps its original `sla_due_at`). Nothing in the request asks for a new SLA clock, and `reopenTicket` (agent path) doesn't reset it either. | Medium — see Open Questions #2. |
| 4 | Unlimited reopens per ticket (no cap). Nothing in the request suggests a limit, and adding one would be speculative. | Medium — see Open Questions #3. |
| 5 | This is a new function, `tickets.reopenByCustomer`, not a parameter added to `tickets.reopenTicket`. Reason: the two have different preconditions (resolved vs. closed-within-14-days), different actors, and the agent path's exact error messages are pinned by tests (`test/tickets.test.js:36-40`) — overloading it risks breaking that contract for no shared benefit. | High. |

## 6. Open questions (answered by recommendation — user unavailable)

1. **Should a reopen require a customer message, or can it be a bare "reopen" click?**
   *Recommendation: require a non-empty message.* Why: the assigned agent needs context for why it's being reopened, exactly as `reply` already requires a body; a bare reopen with no message gives the agent nothing to act on. *(Assumption #2.)*

2. **Does reopening reset the SLA due time?**
   *Recommendation: no.* Why: no existing reopen path (`tickets.reopenTicket`) resets SLA either; the simplest consistent behavior is "SLA clock doesn't move on reopen," and introducing an SLA reset changes reporting semantics well beyond what was asked. *(Assumption #3.)*

3. **Is there a cap on how many times a ticket can be reopened this way?**
   *Recommendation: no cap.* Why: nothing in the request implies abuse is a concern yet; add a cap later if support reports it's being misused. Building a limit now would be speculative scope. *(Assumption #4.)*

4. **What should the new ticket status be after a customer reopen — `open`, or should it go back to whatever status it was in before closing (e.g., straight to the assignee without re-entering the open queue)?**
   *Recommendation: `open`* (the unassigned/general queue status), matching exactly what `tickets.reopenTicket` does for the agent path (`tickets.js:41`) and what `portal.reply` does when it un-resolves a ticket (`portal.js:26`). Consistent with the rest of the codebase's one notion of "reopened = open."

## 7. Requirements (acceptance criteria)

1. **New function `tickets.reopenByCustomer(store, customerId, id, message, { now } = {})`** (exact signature decided at build time; mirrors `portal.reply`'s shape). Given a ticket that is `status: 'closed'` and `now - closed_at < 14 days`, and a non-empty `message`: sets `status: 'open'`, resets `purged: false` unconditionally, appends the message as a customer message (same shape as `store.addMessage` in `createTicket`, `tickets.js:21`), and — if the ticket has an `assignee_id` — queues `notifyAgent(store, assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id })`.
   - Test: reopening a closed, unpurged ticket within the window sets it to `open` and queues exactly one notification to the assignee.
   - Test: reopening a closed, *purged* ticket within the window succeeds and clears `purged` back to `false`.
2. **Ownership check.** A customer may only reopen a ticket belonging to their own `orgId`; a ticket belonging to another org, or a nonexistent id, is treated as not-found (same contract as `portal.getMyTicket`, `portal.js:11-12`) — no status-revealing error.
   - Test: a customer from org B gets a not-found result reopening org A's ticket.
3. **Window check.** A ticket closed 14 or more days ago is rejected with a clear, customer-facing error distinct from the not-found case (e.g., "this ticket can no longer be reopened; please open a new one").
   - Test: `now - closed_at` exactly at 14 days and past 14 days both reject; `13` days, `0` days accept (boundary uses the same `<` convention as `closeResolved`/`purgeClosed`).
4. **Status check.** A ticket that is not `closed` (open, pending, resolved) is rejected by this function — it is not a generic "reopen anything" entry point. It coexists with, and does not replace, the agent-only `tickets.reopenTicket` for resolved tickets.
   - Test: calling `reopenByCustomer` on an `open` or `resolved` ticket throws.
5. **Message required.** An empty or missing message is rejected before any state changes.
   - Test: empty-string message throws; no ticket mutation and no notification occurs.
6. **Purge-latch reset is mandatory, not optional.** Because `purgeClosed` (`purge-closed.js:13`) skips any ticket where `t.purged` is already `true`, a reopened ticket that keeps `purged: true` would be permanently invisible to the *next* purge cycle after it closes again — its new round of messages would never be deleted, a retention-policy violation (Legal's stated reason for `purgeClosed` existing at all, `purge-closed.js:2-4`). `reopenByCustomer` must explicitly set `purged: false` on every reopen, purged or not.
   - Test: reopen a purged ticket, resolve, close it again, advance 7+ days, run `purgeClosed` again — confirm it purges on this second cycle (`purged` became `true` again and messages are deleted a second time).
7. **No change to `tickets.reopenTicket` or its error messages.** The existing agent-only reopen path and its tests (`test/tickets.test.js:34-41`) are untouched.
   - Test: existing test suite continues to pass unmodified.
8. **Portal wiring.** Expose the new capability through `src/portal.js` (e.g. `portal.reopenClosedTicket(store, customer, id, message)`) so the customer-facing surface goes through the same org-scoping pattern as every other portal function, rather than calling `tickets.reopenByCustomer` directly from a route/controller.
   - Test: `portal.reopenClosedTicket` enforces org scoping (reuses #2's test through the portal layer).
9. **Glossary update.** `docs/glossary.md:12`'s closed definition is updated to state the 14-day reopen exception.
   - Test: n/a (doc change); reviewed as part of this spec's acceptance.

## 8. Out of scope

- Any change to SLA calculation, reopen limits, or the agent-facing `reopenTicket` function's preconditions (see Open Questions #2, #3).
- A UI/portal route or controller layer — this spec covers `tickets.js`/`portal.js` business logic only; wiring to an actual HTTP endpoint is a separate, follow-on piece of work once this is approved.
- Changing `purge-closed.js`'s own logic beyond relying on it already calling `updateTicket` correctly — no edit to that file is required by this feature; the dependency is one-directional (reopen must set a flag that purge already respects).
- Any retroactive fix for tickets currently closed before this feature ships (no backfill).
