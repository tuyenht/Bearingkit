# Spec: customer self-service ticket reopen

Status: **draft, awaiting sign-off** (written while the owner was unavailable; recommendations below are assumed, not confirmed). Classification: **COUNCIL** (module-contract change + multi-module impact + touches the data-deletion/purge path). Not implemented.

## 1. Restatement

**In the request's words:** let a customer reopen their own closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do.

**Technical reading:** add a new customer-facing action that transitions a ticket from `closed` back to `open`, gated on `now - closed_at < 14 days` and on the ticket belonging to the calling customer's organisation, and that enqueues an agent notification when the ticket has an assignee.

**Where the request conflicts with the project's own documentation:** `docs/glossary.md:12` currently defines closed as *"final. A closed ticket is never changed again. If the customer comes back, they start a new ticket."* This feature deliberately carves a 14-day exception into that rule. The glossary is wrong the moment this ships, so updating it is part of the deliverable (see §7, AC9), not an afterthought.

## 2. Touchpoints (current code, read before writing this spec)

- `src/tickets.js:38-44` — `reopenTicket(store, id, agentId)`: the **existing** reopen path. Agent-only, only accepts a `resolved` ticket, throws otherwise. Covered by regex-matching tests at `test/tickets.test.js:34-41` (`/cannot reopen a open ticket/`, `/cannot reopen a closed ticket/`) — changing its error strings or its accepted-status check would break those tests.
- `src/portal.js:21-27` — `reply(store, customer, id, body, {now})`: throws `/this ticket is closed; please open a new one/` on a closed ticket. This is the thing the new feature is adding an exception to.
- `src/jobs/purge-closed.js:10-20` — nightly job, `KEEP_DAYS = 7`. Deletes messages 7 days after `closed_at` and sets `purged: true`; **skips any ticket where `t.purged` is already `true`** (`purge-closed.js:13`, `if (t.purged) continue`). This is 7 days, shorter than the proposed 14-day reopen window — a ticket's messages can be purged *before* the reopen window closes.
- `src/jobs/close-resolved.js` — nightly, closes a `resolved` ticket after 3 quiet days, setting `closed_at`.
- `src/store.js` — in-memory store standing in for Postgres; `updateTicket` is a plain `Object.assign` patch, `deleteMessages` empties the message array but keeps the ticket row.
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)` queues a message; **throws if `agentId` is falsy**, so callers must guard unassigned tickets themselves (as `tickets.js:42` already does with `if (t.assignee_id && ...)`).
- `docs/glossary.md:7-13` — status definitions; `closed` is the one this feature amends.

No existing "customer reopen" code was found — this is new.

## 3. Terms

- **Closed (amended).** Final, with one exception: within 14 days of `closed_at`, the customer may reopen it themselves from the portal. After 14 days, or after any other status, "final" holds as the glossary says — the customer starts a new ticket.
- Everything else (**Ticket**, **Status**, **Assignee**, **SLA due time**, **Organisation**) keeps the existing glossary meaning; no new overloaded terms are introduced.

## 4. Decisions

- **D1 — separate function, not a shared one.** Add `reopenByCustomer` in `src/tickets.js` rather than extending `reopenTicket`. *Why:* `reopenTicket` only makes sense from `resolved` (an agent taking work back); the customer path only makes sense from `closed` within a window. Merging them would force one function to carry two unrelated preconditions and risks breaking the regex-pinned tests at `test/tickets.test.js:34-41`. Hard to reverse later without a second migration of callers, so worth deciding explicitly now.
- **D2 — target status is `open`, not `pending`.** Matches the existing convention: both `tickets.reopenTicket` (`tickets.js:41`) and `portal.reply` on a resolved/pending ticket (`portal.js:26`) land on `open` with `resolved_at: null`. No reason for this path to be different.
- **D3 — window boundary mirrors the existing jobs' convention.** `closeResolved`/`purgeClosed` both treat the threshold as "act once elapsed >= N days" (`continue` while `<`). By the same convention, reopen is allowed while `now - closed_at < 14 days` and rejected once `>= 14 days`. Stated explicitly because an off-by-one here is the kind of thing nobody notices until a customer complains their ticket "should still be reopenable."
- **D4 — `purged` is unconditionally reset to `false` on reopen.** *Why, and why this is the one decision that must not be missed:* `purge-closed.js:13` skips any ticket where `purged` is already `true`. The purge window (7 days) is shorter than the reopen window (14 days), so a ticket can legitimately be purged, then reopened on day 10, replied to, and closed again. If `purged` is left `true`, the *next* purge cycle silently skips it forever — the new messages added after reopening would never be purged, breaking the legal retention guarantee the purge job exists for (`purge-closed.js:2-4`). This is a correctness requirement, not a style preference.

## 5. Open questions — answered inline (owner unavailable; proceed on these recommendations)

1. **Does reopening require the customer to submit a message, or is it a bare status flip?**
   *Recommendation: bare flip, with an optional `reason` string.* If `reason` is given, store it via `store.addMessage` (`from: 'customer'`) so it shows up in the thread the agent sees, the same way `createTicket` seeds the first message (`tickets.js:21`). If omitted, no message is added — the customer can call `portal.reply` right after, since the ticket is now `open`.
2. **What happens to `sla_due_at` on reopen?**
   *Recommendation: leave it untouched.* The SLA was about the first response, already given; out of scope to redefine SLA semantics for a reopened ticket.
3. **What event type does the agent notification carry?**
   *Recommendation: a new `ticket_reopened_by_customer` type*, distinct from the agent-driven `ticket_reopened` (`tickets.js:42`), so reporting/analytics can tell the two apart. Same `notifyAgent(store, agentId, event)` call, same queue.
4. **What happens when the closed ticket has no assignee (`assignee_id` is `null`)?**
   *Recommendation: skip notification silently, still succeed.* `notifyAgent` throws without an `agentId` (`notify.js:7`), so the new function must guard with `if (t.assignee_id) notifyAgent(...)` exactly like the existing agent path does (`tickets.js:42`).
5. **Is there a cap on how many times a ticket can be reopened this way?**
   *Recommendation: no cap.* The existing agent-side reopen has none either, and a cap isn't needed to satisfy the request — each close/reopen cycle is independently bounded by its own 7-day purge and 14-day reopen window, so this doesn't create an unbounded-retention loophole.
6. **Where does the new customer-facing function live — directly in `portal.js`, or a thin wrapper over a `tickets.js` function?**
   *Recommendation: thin wrapper.* `portal.reopenTicket(store, customer, id, {reason, now})` checks organisation ownership (same pattern as `getMyTicket`, `portal.js:11-12`) and returns `null` for another org's ticket or a missing one, then delegates the state transition to `tickets.reopenByCustomer(store, id, {reason, now})`. Keeps the org-scoping convention consistent with every other portal function.
7. **Does the glossary wording change need the owner's explicit sign-off, or can it ship with the code?**
   *Recommendation: ship together, but call it out explicitly in the PR description* since it's a documented invariant changing, not just an implementation detail — per `[[project-reopen-ticket-spec]]`-style caution, a module-contract change like this should get the owner's eyes before `bk-plan`/`bk-build` starts.
8. **Should this be reachable from the agent/back-office side too, or portal-only?**
   *Recommendation: portal-only for this spec.* The request is specifically about the customer-facing portal; an agent already has `reopenTicket` for the resolved case and can presumably also just... not close tickets they don't want closed. Out of scope here; revisit only if asked.

## 6. Edge cases

1. **Already purged, still in window.** Ticket closed 10 days ago, `purged: true`, messages gone. Reopen must still succeed (the ticket row survives purge; only messages are deleted, `purge-closed.js:15-16`) and must reset `purged: false` (D4) so the next cycle purges post-reopen messages on schedule.
2. **Past the window.** Ticket closed 20 days ago. Reopen throws a clear error (e.g. `cannot reopen a ticket closed more than 14 days ago`); ticket state is unchanged; the customer is pointed at opening a new ticket, matching the existing closed-ticket message in `portal.reply` (`portal.js:24`).
3. **Wrong organisation.** A Globex customer tries to reopen an Acme ticket. Must behave like `getMyTicket` (`portal.js:11-12`) — return `null` (not found), never leak the ticket's existence or state.
4. **Not currently closed.** Reopen called on an `open`/`pending`/`resolved` ticket (e.g., a double-submitted portal click after the first reopen already succeeded). Throws, mirroring the existing `cannot reopen a ${status} ticket` pattern (`tickets.js:40`); ticket unchanged — this also makes the action idempotent-safe against double clicks.
5. **Unassigned closed ticket.** `assignee_id` is `null`. Reopen succeeds, status becomes `open`, no notification is queued, and the call does not throw (guarded per §5.4).
6. **Exactly at the boundary.** `now - closed_at` is exactly 14 days (not a millisecond under). Per D3, this is rejected — the window is `< 14 days`, not `<= 14 days`. Worth a dedicated test since boundary math is the easiest thing to get backwards.
7. **Reopen → close → reopen again.** A ticket reopened on day 10, replied to, resolved, and closed again starts a fresh `closed_at` and thus a fresh 7-day purge clock and 14-day reopen clock. No special handling needed beyond D4 already resetting `purged`; this is just the normal lifecycle repeating.

## 7. Acceptance criteria

- **AC1.** A ticket closed `< 14` days ago: `portal.reopenTicket` returns the ticket with `status: 'open'`, `closed_at: null`, `resolved_at: null`.
- **AC2.** A ticket closed `>= 14` days ago: throws; ticket unchanged (`status` still `closed`, `closed_at` unchanged).
- **AC3.** On success with an assignee set: `notify.drain()` contains exactly one entry, `{ to: 'agent:<assignee_id>', event: { type: 'ticket_reopened_by_customer', ticketId, ... } }`.
- **AC4.** On success with no assignee (`assignee_id: null`): `notify.drain()` is empty; the call does not throw.
- **AC5.** A ticket already purged (`purged: true`) but within the 14-day window: reopen succeeds and the resulting ticket has `purged: false`.
- **AC6.** A customer from a different organisation calling reopen on another org's ticket: returns `null`; the ticket's `status`/`closed_at`/`purged` are all unchanged.
- **AC7.** Reopen called on a ticket that is not `closed` (`open`, `pending`, or `resolved`): throws; ticket unchanged.
- **AC8.** `src/tickets.js:38-44`'s existing `reopenTicket` and `test/tickets.test.js:24-41` are untouched and still pass unmodified — the new path is additive.
- **AC9.** `docs/glossary.md`'s `closed` definition states the 14-day customer-reopen exception.

## 8. Assumptions

- **High confidence:** the in-memory store (`src/store.js`) is representative of the production Postgres interface per its own comment (`store.js:2`), so no schema migration is implied by this feature — it's a new code path over existing columns (`status`, `closed_at`, `resolved_at`, `purged` all already exist on the ticket row, `tickets.js:9-20`).
- **High confidence:** "14 days" means calendar days measured the same way the existing jobs measure their windows (plain millisecond arithmetic against `closed_at`), not business days — nothing in the code or glossary suggests otherwise.
- **Medium confidence:** "notify the assigned agent" means the existing `notify.js` queue (email via a separate mail worker), not a new notification channel — this is the only notification mechanism in the codebase today.
- **Low confidence, not acted on without more evidence:** whether there's a UI/portal frontend beyond `src/portal.js`'s functions is unknown — no frontend code was found in this repo, so this spec assumes `src/portal.js` is the full surface to change and any UI lives elsewhere/out of scope.
