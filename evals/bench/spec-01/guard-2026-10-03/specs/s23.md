# Spec: customer reopens a closed ticket from the portal

Status: **draft, awaiting review** — written while the user was away; every
question below is answered with a recommendation rather than left open, per
their instruction. Do not implement until this is reviewed.

## 1. Restate

**Request, in the user's words:** "Let a customer reopen a closed ticket from
the portal within 14 days of it being closed, and notify the assigned agent
when they do."

**Technical reading:** add a portal-facing action that moves a ticket from
`closed` back to `open` when called by the ticket's own customer, only while
`now - closed_at < 14 days`, and that queues a notification to the ticket's
`assignee_id` (if any) when it succeeds.

**Where this collides with the existing glossary:** `docs/glossary.md:12`
currently defines closed as final — *"A closed ticket is never changed
again. If the customer comes back, they start a new ticket."* This request
is a deliberate, scoped exception to that rule, not a bug in it. The
glossary needs a matching edit (see §6) so it stays true.

**Not the same as the existing `reopenTicket`:** `src/tickets.js:38-44` is
already a "reopen", but it is agent-only and only accepts a *resolved*
ticket (`if (t.status !== STATUS.RESOLVED) throw ...`). It is exercised by
exact-message assertions in `test/tickets.test.js:34-41`
(`/cannot reopen a (open|closed) ticket/`). This spec adds a **second**,
customer-facing path for the *closed* case; it does not change
`reopenTicket`.

## 2. Touchpoints

- `src/tickets.js:38-44` — existing agent-only `reopenTicket`; read for
  pattern, left untouched.
- `src/tickets.js:4-6` — `STATUS` enum and `HOUR`; only `HOUR` exists today,
  no `DAY`, and the two nightly jobs each redefine `DAY` locally
  (`src/jobs/close-resolved.js:6`, `src/jobs/purge-closed.js:8`). A third
  local redefinition in the new code would be the second copy-paste of the
  same literal in `tickets.js`'s own file; add `const DAY = 24 * HOUR;` once
  in `tickets.js` instead.
- `src/portal.js:1-31` — the module this request extends; `getMyTicket`
  (`:10-14`) is the org-scoping pattern to copy, `reply` (`:21-28`) is the
  closest existing "customer acts on their own ticket" example.
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`; throws if
  `agentId` is falsy, so callers must guard, not rely on it to no-op.
- `src/jobs/purge-closed.js:10-20` — nightly job, `if (t.purged) continue`
  at line 13 is a **one-way latch**. See the non-negotiable item below.
- `docs/glossary.md:12` — the "closed is final" line needs a caveat.
- `test/tickets.test.js` — new tests follow the existing style (`at(days)`
  helper at `:12`, `drain()` from `src/notify.js` to assert notifications).

## 3. Edge cases

1. **Ticket not closed** (open/pending/resolved) — reject with an error.
   Mirrors `reopenTicket`'s own status guard (`src/tickets.js:40`).
2. **Window boundary** — exactly 14×24h after `closed_at`. Use strict `<`,
   matching the existing convention in both nightly jobs
   (`purge-closed.js:14`, `close-resolved.js:11`), so the window is "under
   14 days", not "14 days or less".
3. **Wrong organisation** — a customer from another org calls reopen on a
   ticket that isn't theirs. Mirrors `getMyTicket` (`src/portal.js:12`):
   return `null`, don't leak existence of the ticket.
4. **No assignee** (`assignee_id` is `null`) — a ticket can sit unassigned
   (`src/tickets.js:14`). `notifyAgent` throws on a falsy agent id
   (`src/notify.js:7`), so the caller must skip notification, not call it
   and catch.
5. **Already purged** (`purged: true`) — a ticket closed between 7 and 14
   days ago has had `purgeClosed` delete its messages
   (`src/jobs/purge-closed.js:15-16`) but is still inside the 14-day reopen
   window. Reopening must still succeed (empty message history is not a
   reason to refuse); see §4 for what the customer sees.
6. **Empty or missing message** — reject. Nothing in the existing code
   enforces non-empty message bodies (`reply` at `src/portal.js:25` accepts
   whatever `body` it's given), so this would be a new validation rule
   introduced by this feature, not copied from elsewhere — flagged in Q2.
7. **Re-closing after a customer reopen** — the ticket must be able to
   reach `closed` again through the normal `closeResolved` path (resolve →
   3 quiet days → closed) and then purge again on its own schedule. This is
   why the `purged` flag must reset (see non-negotiable item below): the
   second purge cycle has to be able to find and delete the new round of
   messages.

## 4. Non-negotiable: reset `purged` on reopen

`src/jobs/purge-closed.js:13` skips any ticket where `t.purged` is already
`true`. If a customer reopens a purged ticket and it later gets
closed-and-purged again without `purged` being reset to `false` first, the
*second* round of messages will never be deleted — `purgeClosed` will skip
the row forever on `if (t.purged) continue`. Given `purge-closed.js:1-4`'s
own stated reason for existing ("Legal asked for this: we do not keep
conversation text of finished tickets longer than a week"), silently
keeping old messages past the retention window is a compliance bug, not a
style choice.

**Rule:** customer-reopen unconditionally sets `purged: false`, whether or
not it was `true` going in. This is acceptance criterion #6 below and
should get its own test.

## 5. Assumptions

| # | Assumption | Confidence |
|---|---|---|
| 1 | "Closed" means `status === STATUS.CLOSED` and the clock starts at `closed_at`, set by `closeResolved` (`src/jobs/close-resolved.js:12`). No other field marks closure. | High — only writer of `closed_at` in the codebase. |
| 2 | 14 days means calendar days of wall-clock time (`14 * 24 * 60 * 60 * 1000` ms), same units as the two existing nightly-job windows. | High — matches existing `DAY` constant pattern. |
| 3 | This is a portal (customer) action only; nothing here changes what agents can do. | High — stated in the request. |
| 4 | The reopened ticket's target status is `open` (not `pending`), matching what `reply` does when it un-resolves a ticket (`src/portal.js:26`). | High — existing convention. |
| 5 | `resolved_at` and `closed_at` are both cleared to `null` on reopen. | Medium — reasonable given `reopenTicket` already clears `resolved_at` (`src/tickets.js:41`), and leaving a stale `closed_at` on an `open` ticket would be inconsistent with every other row, but this is a product call, flagged as Q1. |
| 6 | No SLA reset and no cap on how many times a ticket can be reopened. | Medium — simplest behavior consistent with "no reopen limit" being unmentioned; flagged as Q6. |

## 6. Questions and recommendations

Answering inline rather than live, per the instruction to work from
recommendations while the user is away.

**Q1. Does reopening clear `closed_at` (and `resolved_at`) back to `null`?**
Recommend **yes, both**. An `open` ticket with a non-null `closed_at` would
be the only row shape like that in the system, and would make the "is this
ticket closed" check implicitly `status === CLOSED` while a stale
`closed_at` sits there unused. Clearing both leaves the ticket
indistinguishable from one that was simply reopened by an agent, other than
history.

**Q2. Does reopening require a message from the customer, or can it be a
bare status change?**
Recommend **require a non-empty message**, and store it the same way
`reply` stores a customer message (`store.addMessage`, `from: 'customer'`),
so the ticket doesn't reopen with zero context for the agent — especially
important for the already-purged case (edge case 5), where otherwise the
agent would see an empty ticket reopen with no explanation at all. Treat
this as a new `reopen` action distinct from `reply`, not a special case of
`reply` (see Q3).

**Q3. Should this live inside `portal.reply`, or be a new function?**
Recommend a **new function**, `portal.reopen`, calling a new
`tickets.reopenByCustomer`. `reply` explicitly throws on a closed ticket
(`src/portal.js:24`, message `"this ticket is closed; please open a new
one"`) and that behavior is relied on by the test at
`test/tickets.test.js:58`. Overloading `reply` to sometimes reopen a closed
ticket would contradict its own error message and turn one function into
two intents. A separate, explicit action is also the better UX: "reopen
this ticket" is a different button from "send a reply."

**Q4. What happens to the ticket's visible history when it's reopened after
its messages were already purged (edge case 5)?**
Recommend inserting one synthetic system message noting the history was
removed under the retention policy (e.g. `from: 'system'`, body like
"Earlier messages were removed after 7 days per retention policy."),
immediately before the customer's reopen message, so the agent isn't
looking at a reopened ticket with no explanation. Medium confidence — a
simpler option (do nothing, let the agent see zero messages plus the new
one) is also defensible if the system-message convention doesn't exist
elsewhere in the codebase; it doesn't currently (`from` is only ever
`'customer'` today), so introducing it is a small new convention. Flagging
for sign-off; falls out cleanly either way without touching other files.

**Q5. New notification event type, or reuse `ticket_reopened`?**
Recommend a **new event type**, `ticket_reopened_by_customer`, distinct from
the agent-reopen path's `ticket_reopened` (`src/tickets.js:42`). Reasons:
agents likely want to filter/triage these differently (a customer coming
back is a different signal than a teammate taking a ticket back), and reusing
the same type would make `test/tickets.test.js:31`'s exact-match assertion
("`ticket_reopened`" for the agent path) ambiguous with the new path if
their payloads ever get compared. Keep them as two distinct event types.

**Q6. Reopen limit or SLA reset?**
Recommend **no limit, no SLA reset**. Nothing in the request asks for
either; the original SLA was about first response time, already met long
ago by the time a ticket reaches closed. Revisit only if abuse is observed
in practice.

## 7. Design

New code, additive only — no existing function's signature or behavior
changes.

**`src/tickets.js`**
- Add `const DAY = 24 * HOUR;` near the existing `HOUR` constant (`:6`).
- Add `REOPEN_WINDOW_DAYS = 14`.
- Add `reopenByCustomer(store, id, message, { now = new Date() } = {})`:
  - `mustGet` the ticket.
  - Throw if `status !== STATUS.CLOSED`.
  - Throw if `now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY`.
  - Throw if `message` is empty/whitespace-only.
  - If `t.purged`, insert the system note message first (Q4).
  - `store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() })`.
  - `store.updateTicket(id, { status: STATUS.OPEN, resolved_at: null, closed_at: null, purged: false })`.
  - If `t.assignee_id`, call `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id })`.
  - Return the updated ticket.

**`src/portal.js`**
- Add `reopen(store, customer, id, message, { now = new Date() } = {})`:
  - `getMyTicket(store, customer, id)`; return `null` if it isn't theirs
    (mirrors `reply`'s own org-scoping, `src/portal.js:22-23`).
  - Delegate to `tickets.reopenByCustomer`, letting its errors (not closed,
    window expired, empty message) propagate the same way `reply`'s
    closed-ticket error does today.
  - Return the refreshed `getMyTicket(...)` result.

**`docs/glossary.md`**
- Amend the `closed` bullet (`:12`) to note the exception, e.g.: *"closed:
  final. A closed ticket is never changed again, except that the customer
  may reopen it from the portal within 14 days of closing; after that, or
  for an agent, it is final and they start a new ticket."*

**`test/tickets.test.js`**
- New tests, following the existing `at(days)` / `drain()` style:
  - reopening within the window succeeds, notifies the assignee, clears
    `resolved_at`/`closed_at`.
  - reopening at/after day 14 throws.
  - reopening a non-closed ticket throws.
  - reopening with an empty message throws.
  - reopening an unassigned-ticket's closed state does not throw and
    queues no notification.
  - reopening a purged ticket resets `purged` to `false`, and a subsequent
    close + 7-day purge cycle deletes messages again (the non-negotiable
    item in §4) — this is the one test that most needs to exist even if
    nothing else does.

## 8. Acceptance criteria

1. A customer can reopen their own `closed` ticket when
   `now - closed_at < 14 days`, with the ticket ending in `status: 'open'`.
2. Reopening a ticket closed 14 or more days ago throws and does not change
   the ticket.
3. Reopening a ticket that is not `closed` throws and does not change the
   ticket.
4. Reopening requires a non-empty message; an empty/whitespace message
   throws and does not change the ticket.
5. A customer cannot reopen a ticket belonging to another organisation
   (`portal.reopen` returns `null`, same as `getMyTicket`).
6. Reopening a ticket whose `purged` flag is `true` sets it back to
   `false`, unconditionally.
7. On success, if the ticket has an `assignee_id`, exactly one
   `ticket_reopened_by_customer` notification is queued for that agent; if
   there is no assignee, no notification is queued and nothing throws.
8. `resolved_at` and `closed_at` are both `null` after a successful reopen.
9. The existing agent-only `reopenTicket` (`src/tickets.js:38-44`) and its
   tests (`test/tickets.test.js:34-41`) are unchanged.
10. `docs/glossary.md`'s definition of "closed" reflects the exception.

**Out of scope:** SLA recalculation, a cap on how many times a ticket may
be reopened, any change to the agent-side `reopenTicket`, any change to
`purgeClosed`'s own logic beyond the `purged` field being reset by this
feature, concurrent-reopen handling beyond what the single-threaded
in-memory store already gives for free.
