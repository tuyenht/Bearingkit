# Reopen a closed ticket from the portal

## Request

Customers keep asking for this: let a customer reopen their own closed ticket from the portal within 14
days of it being closed, and notify the assigned agent when they do.

## Open questions, answered

The questions below would normally be asked live. Since the author is unavailable, each is answered with
the recommended call, and the rest of this spec is built on those answers.

1. **Who can trigger this — customer only, or agents too?**
   Customer only, from the portal. Agents already have `tickets.reopenTicket`, which only works on a
   `resolved` ticket (see `src/tickets.js:38`) and is pinned by `test/tickets.test.js:34-41`. This is a
   new, separate action, not a change to that one.

2. **What statuses are eligible to reopen?**
   `closed` only. That's what was asked for, and it's the only status the customer can't already act on —
   `resolved`/`pending` tickets already reopen for the customer automatically when they reply
   (`src/portal.js:26`).

3. **What status does the ticket move to?**
   `open`. Matches what `reopenTicket` does for agents and what `docs/glossary.md` already says a
   reopened ticket does ("either puts it back to open").

4. **How is the 14-day window measured, and where does it start?**
   From `closed_at`, using the same `now.getTime() - closedAt.getTime() < 14 * DAY` strict-less-than
   convention `closeResolved` and `purgeClosed` already use (`src/jobs/close-resolved.js:11`,
   `src/jobs/purge-closed.js:14`). At exactly 14 days the window has closed.

5. **Does reopening require a message, or can the customer just flip the status?**
   Require a non-empty message. Every other customer action that touches a ticket (`openTicket`, `reply`)
   requires body text; a bare status flip with no explanation gives the agent nothing to act on.

6. **What happens to the ticket's `purged` flag if the ticket was already purged (messages deleted after
   7 days, per `src/jobs/purge-closed.js`)?**
   Reset `purged: false` unconditionally, every time a ticket is reopened. `purgeClosed` uses `purged` as
   a one-way latch (`if (t.purged) continue;` — `src/jobs/purge-closed.js:13`). If a reopened ticket is
   closed again later without resetting that flag, the second close's messages would never get purged —
   a silent retention-policy violation, not just a style nit. This is the one non-negotiable item in this
   spec.

7. **Does reopening reset the SLA due date?**
   No. `sla_due_at` is set once at creation and nothing else in the codebase touches it after. This is a
   continuation of the same ticket, not a new SLA clock.

8. **Is there a limit on how many times a ticket can be reopened?**
   No limit. Nothing in the existing code tracks a reopen count, and the request didn't ask for one.

9. **Who gets notified, and what if the ticket has no assignee?**
   Notify the assignee, using the existing `notifyAgent` queue (`src/notify.js`). If the ticket has no
   assignee (`assignee_id` is `null`), skip notification — `notifyAgent` requires an agent id
   (`src/notify.js:7`) and there's no one to tell. Routing an unassigned reopened ticket back into a queue
   is a separate, pre-existing concern (every unassigned `open` ticket already has that problem) and is
   out of scope here.

10. **Does `portal.reply` change to allow replying on a closed ticket instead?**
    No. `portal.reply` keeps throwing on every closed ticket (`src/portal.js:24`). Reopening is a
    separate, deliberate action the customer takes before they can reply again — not a side effect of
    trying to reply.

## Design

### `tickets.reopenByCustomer(store, id, message, { now = new Date() } = {})`

New function in `src/tickets.js`, next to `reopenTicket`. Holds the business rule, independent of portal
org-scoping (mirrors how `resolveTicket`/`reopenTicket` sit below `createTicket`):

- Look up the ticket (reuse `mustGet`); throw `no ticket ${id}` if missing.
- Throw `cannot reopen a ${t.status} ticket` if `t.status !== STATUS.CLOSED` (same message shape
  `reopenTicket` already uses, so callers and tests can rely on the same pattern).
- Throw `a customer must say why they are reopening this ticket` if `message` is empty/whitespace.
- Throw `this ticket closed too long ago to reopen` if `now.getTime() - new Date(t.closed_at).getTime() >= 14 * DAY`.
- On success: `store.updateTicket(id, { status: STATUS.OPEN, closed_at: null, purged: false })`, then
  `store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() })`.
- If `t.assignee_id` is set, call `notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id })`.
- Return the updated ticket.

New event name `ticket_reopened_by_customer` (distinct from the agent-driven `ticket_reopened` that
`reopenTicket` already emits) so anything consuming the notification queue can tell who reopened the
ticket.

### `portal.reopen(store, customer, id, message, { now = new Date() } = {})`

New function in `src/portal.js`, mirroring the `openTicket`/`getMyTicket` pattern already used there:

- Use `getMyTicket` to load the ticket scoped to `customer.orgId`; return `null` if it doesn't exist or
  belongs to another org (same convention `getMyTicket`/`reply` already follow).
- Delegate to `tickets.reopenByCustomer(store, id, message, { now })` and return its result.

### Files touched

- `src/tickets.js` — add `reopenByCustomer`, export it.
- `src/portal.js` — add `reopen`, export it.
- `docs/glossary.md` — the **closed** entry currently reads "final. A closed ticket is never changed
  again." That stops being true. Recommend changing it to: "final once 14 days have passed since it
  closed. Within that window the customer can reopen it from the portal; an agent cannot reopen a closed
  ticket directly." (`tickets.reopenTicket` stays resolved-only, untouched.)
- `test/tickets.test.js` — add coverage (see below). No changes to the existing agent-reopen tests.

### Out of scope

- Changing `reopenTicket` (agent-only, resolved-only) in any way.
- Any change to `closeResolved` or `purgeClosed` beyond relying on the `purged` reset above.
- Re-queuing an unassigned reopened ticket for pickup — same gap already exists for any unassigned
  `open` ticket today.
- Rate-limiting or counting reopens.
- SLA changes.

## Acceptance criteria

1. A customer can reopen a ticket that belongs to their org and is `closed`, by providing a non-empty
   message, within 14 days of `closed_at` (strict `<`, matching `closeResolved`/`purgeClosed`).
2. Reopening sets `status: 'open'` and clears `closed_at`.
3. Reopening appends the customer's message to the ticket's messages.
4. Attempting to reopen a ticket closed 14 or more days ago throws and makes no change.
5. Attempting to reopen a non-closed ticket, a ticket in another org, or with an empty message throws (or
   returns `null` for "not found/not mine", matching `getMyTicket`'s existing convention) and makes no
   change.
6. **If the ticket's `assignee_id` is set, reopening it unconditionally resets `purged` to `false`**, so
   that a subsequent close-and-wait-7-days cycle purges the new conversation again. This holds whether or
   not the ticket had actually been purged yet. This is the most important criterion in this spec — a
   regression here silently breaks the retention policy, not just a cosmetic bug.
7. If `assignee_id` is set, the assignee is notified via `notifyAgent` with event type
   `ticket_reopened_by_customer` and the ticket id. If `assignee_id` is `null`, no notification is sent
   (and nothing throws).
8. `tickets.reopenTicket` (agent path) and `portal.reply`'s closed-ticket rejection are both unchanged;
   `test/tickets.test.js:34-41`'s existing assertions still pass unmodified.
