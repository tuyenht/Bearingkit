# Spec: customer self-service ticket reopen

Status: **draft, awaiting review** (written while the requester was away;
all open questions below were answered by recommendation rather than live
discussion — see "Embedded questions").

## Request, restated

Let a customer reopen their own **closed** ticket from the portal, but only
within 14 days of it being closed, and notify the ticket's assigned agent
when that happens. This is a new, deliberate customer action — not a side
effect of replying — distinct from the existing agent-only reopen path.

## Touchpoints (current code, verified against this checkout)

- `src/tickets.js:38-44` — `reopenTicket(store, id, agentId)`: the existing
  **agent**-only reopen. Only works on `RESOLVED` tickets, flips to `OPEN`,
  notifies the assignee if different from the acting agent. Stays untouched.
- `src/tickets.js:4` — `STATUS` enum (`open`, `pending`, `resolved`,
  `closed`).
- `src/portal.js:10-14` — `getMyTicket`: the org-scoping pattern every
  customer-facing read/write follows (`t.org_id !== customer.orgId` → `null`).
- `src/portal.js:21-28` — `reply`: throws `'this ticket is closed; please
  open a new one'` on a closed ticket. This must keep throwing — reopening
  is a separate action, not folded into reply.
- `src/notify.js:6-9` — `notifyAgent(store, agentId, event)`: throws if
  `agentId` is falsy, so callers must only call it when an assignee exists.
- `src/jobs/purge-closed.js:10-20` — nightly job. For every closed ticket
  where `!t.purged` and `now - closed_at >= 7 days`, deletes its messages
  and sets `purged: true`. **`purged` is a one-way latch with no code path
  that ever resets it today.**
- `src/jobs/close-resolved.js:8-16` — nightly job, closes a resolved ticket
  quiet for 3+ days, sets `closed_at`. Shows the project's `<` boundary
  convention for day-windows (`now - x < N * DAY` → still within window).
- `test/tickets.test.js:34-41` — pins the agent `reopenTicket`'s exact
  error messages (`cannot reopen a open ticket`, `cannot reopen a closed
  ticket`). Must not change.
- `test/tickets.test.js:52-59` — pins `portal.reply` throwing on a closed
  ticket.
- `docs/glossary.md:12` — "**closed**: final. A closed ticket is never
  changed again." No longer accurate once this ships; needs an update.

## Design

New function, kept separate from the agent path:

```js
// src/tickets.js
function reopenByCustomer(store, id, message, { now = new Date() } = {}) { ... }
```

New portal wrapper, mirroring `openTicket`/`getMyTicket`'s org-scoping:

```js
// src/portal.js
function reopen(store, customer, id, message, { now = new Date() } = {}) { ... }
```

New notification event: `ticket_reopened_by_customer` (distinct from the
agent path's `ticket_reopened`, so anything consuming the notify queue can
tell the two apart).

14-day check: `now.getTime() - new Date(t.closed_at).getTime() < 14 * DAY`,
the same strict-less-than convention `closeResolved`/`purgeClosed` already
use — exactly 14 days out is rejected, not allowed.

## Embedded questions (answered by recommendation, not asked live)

1. **What should the reopened status be — `open` or `pending`?**
   Recommend **`open`**. It mirrors what the agent-reopen path and
   `portal.reply`'s resolved→open transition already do; there's no
   existing "pending-from-reopen" precedent to justify a different target.

2. **Does a reopen need to carry a message, or can it be a bare status
   flip?**
   Recommend **require a non-empty message**. A reopen with no stated
   reason gives the agent nothing to act on; this also matches the
   customer-facing UX of "why are you reopening this."

3. **Should this reuse `portal.reply`, since replying to a resolved ticket
   already flips it back to open?**
   Recommend **no — keep it a separate function**. `reply` on a *closed*
   ticket throws today and is pinned by a test
   (`test/tickets.test.js:52-59`); changing that behavior would silently
   turn every reply into an implicit reopen, which is a bigger and riskier
   behavior change than what was asked for.

4. **Should the ticket's SLA (`sla_due_at`) be recalculated on reopen?**
   Recommend **no change to `sla_due_at`**. Nothing in the current code
   recalculates SLA on any reopen or reply path; inventing a new SLA rule
   here is out of scope for "let customers reopen," and should be its own
   decision if support wants it.

5. **Is there a limit on how many times a ticket can be reopened this
   way?**
   Recommend **no limit for v1**. Nothing today tracks a reopen count;
   adding one is speculative without a stated abuse case.

6. **What happens if the ticket has no assignee?**
   Recommend **skip the notification silently, don't error**.
   `notifyAgent` throws on a falsy `agentId` (`src/notify.js:7`), so the
   caller must guard on `t.assignee_id` first — same pattern the existing
   agent `reopenTicket` already uses (`src/tickets.js:42`).

7. **The purge job already deleted this ticket's messages (it's been more
   than 7 days since close, but less than 14) — what then?**
   This is the one answer that isn't a judgment call, it's a correctness
   requirement: **`reopenByCustomer` must unconditionally set
   `purged: false`**, regardless of its prior value. `purgeClosed` only
   skips tickets where `t.purged` is already `true`
   (`src/jobs/purge-closed.js:13`); if a reopened-then-re-closed ticket
   keeps `purged: true`, its *new* round of messages would never be purged
   on the next cycle — a silent retention-policy violation (Legal asked
   for the 7-day purge; see `src/jobs/purge-closed.js:3-4`). The customer
   still sees an empty message history for the already-purged messages;
   only the new reopen message is visible, which is expected since the
   old ones are gone for good.

8. **Can a customer reopen a ticket belonging to another organisation?**
   Recommend **no, same scoping as every other portal function**: look the
   ticket up the way `getMyTicket` does (`src/portal.js:10-14`) and treat a
   mismatched `org_id` as not-found.

9. **Should the 14-day window run from `closed_at` or from
   `resolved_at`?**
   Recommend **`closed_at`** — the request says "within 14 days of it
   being closed," and `closed_at` is the field that exists for exactly
   this purpose.

10. **Does `docs/glossary.md` need a wording change?**
    Yes. Recommend replacing "closed: final. A closed ticket is never
    changed again. If the customer comes back, they start a new ticket."
    with: "closed: usually final. A customer may reopen a closed ticket
    themselves within 14 days of closing; after that, or past that window,
    they start a new ticket."

## Edge cases

1. **Ticket closed more than 14 days ago** → reject with a clear error
   (e.g. `cannot reopen a ticket closed more than 14 days ago`); no state
   change.
2. **Ticket not closed at all** (`open`/`pending`/`resolved`) → reject
   (e.g. `cannot reopen a <status> ticket` — mirrors the existing agent
   path's message shape at `src/tickets.js:40`); no state change.
3. **Ticket already purged** (closed 7–14 days, messages already deleted
   by the nightly job) → still reopenable; `purged` resets to `false`
   unconditionally (see Q7); old messages stay gone, only the new message
   appears.
4. **Empty or whitespace-only message** → reject before touching any
   state.
5. **Ticket belongs to a different organisation than the caller** →
   treated as not-found, same as `getMyTicket`.
6. **Ticket has no assignee** → reopen succeeds, no notification is sent,
   no error.
7. **Nonexistent ticket id** → reject (reuse the existing `mustGet` /
   "no ticket `<id>`" pattern from `src/tickets.js:46-49`).
8. **Concurrent nightly `purgeClosed` run while a reopen is in flight** —
   out of scope for the in-memory `store.js` test double (operations are
   synchronous), but worth flagging for the real Postgres store: the
   status flip, the `purged: false` reset, and the new message insert
   should commit as one transaction, per the project's "multi-step state
   changes run in one transaction" rule.

## Assumptions

- **High**: "closed" is checked via `t.status === STATUS.CLOSED`, matching
  every other status check in `tickets.js`/`portal.js`.
- **High**: the 14-day window uses the same strict `<` boundary convention
  as `closeResolved`/`purgeClosed` (exactly 14 days = too late).
- **Medium**: no change to `src/jobs/purge-closed.js` itself is needed —
  correctness is fully handled by `reopenByCustomer` resetting `purged`.
  Worth a test that closes/purges/reopens/closes/purges again and asserts
  messages are deleted the second time too.
- **Medium**: the error-message wording for the new rejection cases should
  follow the existing terse style (`cannot reopen a ${t.status} ticket`,
  `no ticket ${id}`) rather than introducing a different tone.
- **Low**: whether SLA should reset on reopen (Q4) is a product policy
  question, not a technical one — flagged for explicit sign-off since it's
  the assumption most likely to be overturned.

## Acceptance criteria

1. `reopenByCustomer(store, id, message, { now })` throws `no ticket <id>`
   for a nonexistent id.
2. Throws `cannot reopen a <status> ticket` when `t.status !== 'closed'`.
3. Throws a clear, distinct error when `now - closed_at >= 14 days`
   (boundary: exactly 14 days is rejected).
4. Throws on an empty or whitespace-only `message`.
5. On success: sets `status: 'open'`, leaves `resolved_at` as `null`,
   appends the customer's message via `store.addMessage`.
6. **On success, unconditionally sets `purged: false`**, even if it was
   already `false` — verified by a test that purges, reopens, closes, and
   purges again, asserting messages are deleted both times.
7. **If `assignee_id` is set**, queues a `ticket_reopened_by_customer`
   notification to that agent via `notifyAgent`; **if unassigned**, no
   notification is queued and no error is thrown.
8. `portal.reopen(store, customer, id, message, { now })` treats a ticket
   from a different `org_id` as not-found (mirrors `getMyTicket`); on
   success, returns the updated ticket with its messages (same shape as
   `getMyTicket`'s return value).
9. `docs/glossary.md`'s "closed" entry is updated per Q10 above.
10. Existing tests at `test/tickets.test.js:34-41` (agent `reopenTicket`
    error messages) and `:52-59` (`portal.reply` on a closed ticket) are
    unchanged and still pass.
