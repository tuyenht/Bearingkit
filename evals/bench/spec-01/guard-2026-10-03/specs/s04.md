# Spec: customer self-service ticket reopen

Status: **draft — awaiting review**. Not implemented. Written while the user was unavailable; every open question below is answered with a recommendation so the spec is self-contained. Do not start implementation until these are confirmed.

## Problem

Customers keep asking for a way to reopen their own closed ticket instead of filing a new one, within some grace period after it was closed. Today `docs/glossary.md` says closed is final — "If the customer comes back, they start a new ticket" — and `src/portal.js`'s `reply()` enforces that by throwing on any closed ticket. We need a deliberate, separate customer action that reopens a closed ticket within a time window and tells the assigned agent it happened.

## Questions and recommended answers

1. **Who can reopen: the customer who filed it, any customer in the org, or an agent too?**
   Recommend: any customer in the same organisation, matching how `portal.getMyTicket`/`listMyTickets` already scope by `org_id` rather than by the individual customer who opened the ticket. Agents already have their own reopen path (`tickets.reopenTicket`, resolved → open only) — out of scope here.

2. **What's the reopen window, and is the boundary measured from `closed_at` or from `created_at`/last activity?**
   Recommend: 14 days from `closed_at`, matching the ask. Use the same strict-`<` boundary convention the nightly jobs already use (`closeResolved`'s 3-day quiet check, `purgeClosed`'s 7-day keep check): `now - closed_at < 14 * DAY` allows the reopen; at or past 14 days it's rejected.

3. **What status does a reopened ticket land in — `open`, or back to whatever it was before closing?**
   Recommend: always `open`. The ticket needs an agent to look at it again regardless of its pre-close state, and `open` is what every other "something needs attention again" transition in this codebase already uses (`resolveTicket`'s reverse, `reply()`'s resolved/pending → open, `reopenTicket`).

4. **Does reopening require a message from the customer, or can they reopen with no comment?**
   Recommend: require a non-empty message, stored the same way `reply()` and `createTicket()` store the customer's first message (`store.addMessage(id, { from: 'customer', body, at })`). A bare status flip with no context is less useful to the agent and inconsistent with how every other customer-authored event in this system carries a message.

5. **Is this a new function, or should it reuse `portal.reply()` / `tickets.reopenTicket()`?**
   Recommend: new functions, not a branch inside either existing one.
   - `tickets.reopenByCustomer(store, id, message, { now = new Date() })` holds the business rule (closed-only, within-window, non-empty message, purge-latch reset, notify).
   - `portal.reopen(store, customer, id, message, { now = new Date() })` is the org-scoping wrapper, mirroring the `getMyTicket`/`openTicket` pattern: look up the ticket scoped to `customer.orgId`, return `null` if it's not theirs, otherwise call `tickets.reopenByCustomer`.
   Reasons to keep it separate: `tickets.reopenTicket` is agent-only (resolved → open) and is pinned by `test/tickets.test.js:34-41`'s exact error-message assertions (`/cannot reopen a open ticket/`, `/cannot reopen a closed ticket/`) — changing its branching to also accept "closed, by a customer, within 14 days" would risk those tests and conflate two different actors' rules in one function. `portal.reply()` is documented as throwing on every closed ticket, and customers reaching for "reply" vs. deliberately reaching for "reopen" are different intents worth keeping distinct in the UI and the API.

6. **Does the agent get notified, and what happens if the ticket has no assignee?**
   Recommend: yes, notify via the existing `notify.notifyAgent(store, agentId, event)` queue (same mechanism `tickets.reopenTicket` already uses), with a new event type `ticket_reopened_by_customer` carrying `{ type: 'ticket_reopened_by_customer', ticketId: id }`. If `assignee_id` is `null` (ticket was closed without ever being picked up), skip the notify call — `notifyAgent` throws if given no agent, and there's no one to tell.

7. **What happens to `resolved_at` and `closed_at` on reopen?**
   Recommend (medium confidence — flag for explicit sign-off): clear both back to `null`, the same way `resolveTicket`'s reverse path and `reply()`'s resolved/pending → open transition already clear `resolved_at`. Leaving `closed_at` populated on an `open` ticket would be a dangling field other code might misread as "this was once closed," and nothing currently depends on it surviving a reopen. If the back office actually wants a historical "last closed" audit trail, that's a different feature (ticket history/audit log) and shouldn't piggyback on this change by accident.

8. **What happens to the purge latch (`purged: true`) if the ticket had already been purged before it's reopened?**
   Recommend, and this is the one non-negotiable item in this spec: unconditionally reset `purged: false` on every customer reopen, regardless of its current value. `src/jobs/purge-closed.js:13` (`if (t.purged) continue`) is a one-way latch — it's nightly, idempotent, and never un-purges anything. If a ticket is reopened after purge, closed again later, and `purged` is still `true` from the first cycle, `purgeClosed` will skip it forever and the second cycle's messages will never be deleted. Given `purge-closed.js`'s own comment ("Legal asked for this: we do not keep conversation text of finished tickets longer than a week"), leaving stale `purged: true` in place is a retention-policy violation, not just a style nit.

9. **Is there a limit on how many times a ticket can be reopened, or an SLA-timer reset on reopen?**
   Recommend: no limit, no SLA reset. Nothing in the ask calls for either, `sla_due_at` is documented as being set once at creation ("It is set when the ticket is created" — `docs/glossary.md`), and adding either would be scope not asked for.

10. **Does this change what `portal.reply()` does on a closed ticket?**
    Recommend: no. `reply()` keeps throwing `'this ticket is closed; please open a new one'` on every closed ticket, unchanged. Reopening is a separate, deliberate action the customer has to choose, not a side effect of trying to reply. (The error message itself is now slightly stale once this ships — see glossary/doc follow-up below — but changing user-facing copy is a product-content decision, so it's called out rather than changed silently.)

## Design

### New function: `tickets.reopenByCustomer`

```js
function reopenByCustomer(store, id, message, { now = new Date() } = {}) {
  const t = mustGet(store, id);
  if (t.status !== STATUS.CLOSED) throw new Error(`cannot reopen a ${t.status} ticket`);
  if (now.getTime() - new Date(t.closed_at).getTime() >= REOPEN_WINDOW_DAYS * DAY) {
    throw new Error('this ticket was closed too long ago to reopen');
  }
  if (!message || !message.trim()) throw new Error('a message is required to reopen a ticket');

  store.addMessage(id, { from: 'customer', body: message, at: now.toISOString() });
  const updated = store.updateTicket(id, {
    status: STATUS.OPEN,
    resolved_at: null,
    closed_at: null,
    purged: false,
  });
  if (t.assignee_id) {
    notifyAgent(store, t.assignee_id, { type: 'ticket_reopened_by_customer', ticketId: id });
  }
  return updated;
}
```

Constant `REOPEN_WINDOW_DAYS = 14`, alongside the existing `SLA_HOURS`/`HOUR` constants, same `DAY` constant pattern used in the jobs files (would need hoisting or duplicating locally — `tickets.js` doesn't currently define `DAY`).

Exported alongside the existing functions: `module.exports = { STATUS, SLA_HOURS, createTicket, assignTicket, resolveTicket, reopenTicket, reopenByCustomer }`.

### New function: `portal.reopen`

```js
function reopen(store, customer, id, message, { now = new Date() } = {}) {
  const t = store.getTicket(id);
  if (!t || t.org_id !== customer.orgId) return null;
  return reopenByCustomer(store, id, message, { now });
}
```

Mirrors `getMyTicket`'s org-scoping check exactly (`!t || t.org_id !== customer.orgId → null`) rather than leaking a "not found" vs. "not yours" distinction, same as the rest of `portal.js`.

Exported alongside the existing functions: `module.exports = { listMyTickets, getMyTicket, openTicket, reply, reopen }`.

### No changes needed to `src/notify.js`

`notifyAgent` already takes an arbitrary `event` object; the new `ticket_reopened_by_customer` type needs no change to the queue/drain mechanism.

### No changes needed to `src/jobs/purge-closed.js` or `src/jobs/close-resolved.js`

The purge latch reset happens in `reopenByCustomer`, not in the job. If the reopened ticket is later closed again, `closeResolved`/`purgeClosed` run against it exactly as they do for any other closed ticket.

### Documentation: `docs/glossary.md`

The **closed** bullet currently reads:

> **closed**: final. A closed ticket is never changed again. If the customer comes back, they start a new ticket.

This becomes inaccurate once this ships. Recommend:

> **closed**: normally final. A closed ticket is never changed by staff. A customer may reopen it themselves within 14 days of closing; after that, or if staff need to change it, a new ticket is the only path.

## Acceptance criteria

1. A customer can reopen their own org's ticket while it is `closed` and within 14 days of `closed_at`; the result status is `open`.
2. Reopening a ticket that is not `closed` (open/pending/resolved) throws `cannot reopen a <status> ticket`, mirroring `reopenTicket`'s error shape.
3. Reopening a ticket closed 14 days ago or more throws and does not change the ticket.
4. Reopening with an empty or whitespace-only message throws and does not change the ticket.
5. A successful reopen appends the customer's message to the ticket's messages, visible via `getMyTicket`.
6. **A successful reopen unconditionally sets `purged: false`**, even if the ticket had already been purged — so a later second close-and-purge cycle still deletes its messages. (Non-negotiable; see Q8.)
7. If the ticket has an assignee, reopening queues a `ticket_reopened_by_customer` notification to that agent via `notify.notifyAgent`; if there is no assignee, no notification is queued and nothing throws.
8. `resolved_at` and `closed_at` are both cleared to `null` on reopen.
9. A customer from a different organisation cannot reopen the ticket — `portal.reopen` returns `null`, same as `getMyTicket` for an out-of-org id.
10. The existing agent-only `tickets.reopenTicket` and its tests (`test/tickets.test.js:34-41`) are untouched and continue to pass unmodified; `portal.reply()`'s closed-ticket behavior is also untouched.

## Out of scope

- Any change to SLA timers, reopen-count limits, or agent-side reopen rules.
- A "last closed" history/audit trail for tickets reopened more than once.
- Changing `portal.reply()`'s error copy (flagged in Q10 but not changed here).
