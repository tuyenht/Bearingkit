## Claude Code

- Install: `/plugin marketplace add tuyenht/Bearingkit`, then `/plugin install bearingkit@bearingkit`. Do not add the marketplace by local path from a development checkout: the install copies the whole directory except `.git` into `~/.claude/plugins/cache`, untracked `_build/` (upstream clones, the eval profile and its login file) and `evals/results/` included, and `uninstall` then leaves that copy behind marked `.orphaned_at`, which the plugins reference says a background sweep removes about 14 days later (measured 2026-09-24 on 2.1.280, `docs/compat/2026-09-24-claude-plugin-install-local-path.md`); add it from the repository URL, which clones pushed files only. The install writes `"bearingkit@bearingkit": false` into the user's `enabledPlugins` and `claude plugin list` shows the kit disabled (same record). Uninstall through the `/plugin` menu (its Installed tab), with `/plugin uninstall bearingkit@bearingkit` (documented on the discover-plugins page, read 2026-09-24; the plugins reference showed no slash form on 2026-09-19), or from a shell with `claude plugin uninstall bearingkit@bearingkit` (`--keep-data` keeps the plugin's data directory).
- Install from a shell, the same two steps (Claude Code plugins reference, "CLI commands reference", read 2026-09-18): `claude plugin marketplace add <URL or local directory>` with `https://github.com/tuyenht/Bearingkit` (or `tuyenht/Bearingkit`; not the checkout's path, see above), then `claude plugin install bearingkit@bearingkit`. `--scope` takes `user` (the default, every project), `project` (shared through `.claude/settings.json`) or `local` (`.claude/settings.local.json`). Run on this machine on 2026-09-24 with `tuyenht/Bearingkit` while the repository is private (the machine's git credentials sufficed): the cache held the 250 tracked files and nothing else.
- **Per project, not everywhere** (D5 question 29): install once for the machine as above, then switch a project on with `bearingkit activate` inside it, which writes `"bearingkit@bearingkit": true` into that project's `.claude/settings.local.json` and nothing else; `bearingkit deactivate` removes it, `bearingkit status` says which of the two hosts this project has on. The mechanism is the host's own (settings-reference, `### enabledPlugins`, read 2026-09-20): `enabledPlugins` maps `plugin@marketplace` to a Boolean in any settings file, a project's file outranks the machine's, and "a plugin with no entry at any scope falls back to its `defaultEnabled` value" — so the manifest will carry `"defaultEnabled": false` and an install switches the kit on nowhere by itself. `claude plugin enable` takes no `--scope` and the reference does not say which file it writes, which is why `activate` writes the entry itself. The install on 2026-09-24 did write an entry, `"bearingkit@bearingkit": false`, into the user's settings; that a project's `true` outranks it is what the settings reference says, not yet measured here.
- **Following the repository automatically**: in `~/.claude/settings.json`, `"extraKnownMarketplaces": { "bearingkit": { "source": { "source": "github", "repo": "tuyenht/Bearingkit" }, "autoUpdate": true } }` — "Set `"autoUpdate": true` alongside `source` to make Claude Code refresh that marketplace and update its installed plugins in the background after startup" (same page). The kit prints this entry and never writes it: `~/.claude` is yours. Written into the owner's settings on 2026-09-24 at the owner's word; its effect shows after a restart and has not been observed yet. **A manifest that pins a version stops it following new commits**: "If you declare `"version": "1.0.0"` in `plugin.json` and push new commits without changing that string, existing users of those sources keep the cached copy, because Claude Code sees the same version. Bump the field on every release, or omit it to fall back to the resolved version" (plugin-marketplaces page, read verbatim 2026-09-24). Until 2026-09-24 `.claude-plugin/plugin.json` and the marketplace entry both carried `"version": "0.1.0"`, which kept an install on the commit it was installed from (`claude plugin update` skipped it too); since then neither carries a version (D5 question 32), so an install resolves to the commit SHA and follows pushed commits. `tests/manifests.test.cjs` guards the absence.
- Development and evals, no install: `claude --plugin-dir <path to the checkout>`. The kit's evals runner passes this by default.
- Bootstrap: `hooks/hooks.json` runs `hooks/session-start.cjs` on startup, clear and compact; it returns the protocol (`skills/bk-protocol/SKILL.md`) as additional context. Skills appear as `bearingkit:bk-<name>`; `bk-protocol` is hidden from the listing.
- **Host drift, 2026-09-13:** after that day's auto-update, the `/skills` panel lists `bk-protocol` as `user-only · ~80 tok · locked by author` instead of hiding it; on 2.1.267 (2026-09-10) it was absent from `/context all`'s User group. The kit's frontmatter is unchanged. The listing still fits §12 (900 tokens for eleven skills). Evidence: `docs/compat/2026-09-13-daily-profile-readings.md`. The acceptance row above is the record of 2026-09-11 and is not rewritten.
- Agents: `agents/bk-*.md` load with the plugin.
- Deny list for secret files, set by you in `~/.claude/settings.json` if wanted; the kit writes no settings. Patterns follow gitignore syntax ("Configure permissions", read 2026-09-24): `//**/x` matches anywhere on the machine, a bare `x` matches at any depth under the session's working directory, and a following `!x` carves an exception out of the bare rules before it in the same file only. A set measured in the owner's profile on 2026-09-24 (the page says a `Read` deny also stops Edit, Write and `cat`/`head`/`tail`/`sed`/`tee`; measured: Read and `cat` denied, `.env.example` readable): `Read(//**/.env)`, `Read(.env.*)`, `Read(!.env.example)`, `Read(!.env.sample)`, `Read(!.env.template)`, `Read(//**/*.pem)`, `Read(//**/*.key)`, `Read(//**/id_rsa*)`, `Read(//**/secrets.yaml)`, `Read(//**/secrets.yml)`, `Read(//**/secret.yaml)`, `Read(//**/secret.yml)`, `Read(//**/*credentials*.json)`. A script that opens files itself, or `grep -r`, is not covered; the host's sandbox is.

## Antigravity 2.0

- **Install and activate (the way since D5 question 29)**: `bearingkit install --host antigravity` writes one store at `~/.bearingkit/antigravity/plugins/bearingkit` — outside every folder Antigravity scans, so it reaches no workspace by itself — and `bearingkit activate` inside a project adds one entry naming that store to the project's `.agents/plugins.json`, which is the host's documented way of declaring a plugin kept outside its discovery roots (embedded `json_configs.md`; a workspace's declared configurations outrank global discovery). `bearingkit update` refreshes the store for every activated project at once, `bearingkit deactivate` switches one project off, `bearingkit status` and `doctor` read both. **Measured on the 2.0 app, 2026-09-20** (`docs/compat/2026-09-19-per-project-activation.md`, probes AG-1 to AG-3 and AG-5, with no copy under `~/.gemini/config/plugins/` for the whole run): a project that declares the store lists the fifteen `bk-*` skills and its hooks run; the same project with the file removed lists none of them. The entry has to be an **absolute** path — `~` does not expand on Windows — and it may name either the plugin folder or a folder of plugins. It may **not** name the checkout: the checkout root is not plugin-shaped, so no kit skill loads, and whatever other customizations the folder happens to hold are loaded instead. The **Antigravity IDE behaves the same way** (AG-4, 2026-09-20): a folder that declares the store lists the kit's skills there too, and the running IDE picked the declaration up when the folder was opened, with no restart.
- Install (older, global): `node bin/bearingkit.cjs antigravity install` from a checkout, or `npx bearingkit antigravity install` where npm is present (`pnpm dlx bearingkit …` with pnpm). The copy is global: Antigravity loads its always-on rule in every workspace, the IDE included (seen 2026-09-19), so it is the way only where per-project activation is not wanted; a measurement no longer needs it. It copies `skills/`, the manifest and the protocol as an always-on rule into `~/.gemini/config/plugins/bearingkit`, a real directory, because the host's plugin scanner does not follow directory junctions (isolated on 2.0, 2026-09-11). Run it again after updating the kit. `--dry-run` prints the plan; `--dest <dir>` targets another plugin root.
- Uninstall: `bearingkit uninstall --host antigravity` (the store) or `bearingkit antigravity uninstall` (the global copy); either removes only a directory the kit created (marker file `.bearingkit-copy`) and neither touches a project — `bearingkit deactivate` does that, in the project.
- Bootstrap: `rules/bearingkit.md` with `trigger: always_on` inside the plugin copy: the protocol body plus an Antigravity host note. The note matters: this host has no skill tool, and without the sentence "invoking a skill means opening `skills/<name>/SKILL.md` with `view_file` as the first action" the model names the skill and explores the project instead (measured 2026-09-10 and again 2026-09-11). A skill is invoked by opening its file inside the plugin (the path the Customizations panel shows) and following it.
- Tokens are read from the Customizations panel; Phase 1 measured the rule at 1,873 and ten descriptions at 1,045.
- Automated runs (the eval driver, the acceptance test) drive the 2.0 app over the Chrome DevTools protocol. The app does not open that port by itself (verified 2026-09-11: a plainly started app listened on no DevTools port); start it as `Antigravity.exe --remote-debugging-port=1405` (the port `scripts/antigravity/cdp.cjs` expects), or through a launcher that adds the flag. The 2.0 app lives at `%LOCALAPPDATA%\Programs\Antigravity\Antigravity.exe` on this workstation (the IDE is a separate install). **An auto-update relaunches it without its flags:** on 2026-09-17 at 22:12 it updated itself from 2.12.2 to 2.14.0 (read from the DevTools user agent before and after) and came back running hidden with no DevTools port, so a run first checks `http://127.0.0.1:1405/json/version`. That evening, at the owner's request, the session stopped the hidden app and started it again with the flag. On 2026-09-19 it had updated itself to 2.15.0 and was running with its window open, still without the port; at the owner's word the session stopped it and started it again with the flag. Closing the window only sends the app to the tray, so stopping it means ending its processes.
- Eval stage (from 2026-09-19 evening): Antigravity runs in its own copy of the fixture, `C:\work\apps\sample-app` (`evals --host antigravity --stage-only`), not in the copy Claude Code uses under `C:\Projects\.bearingkit-evals\`; its project file is `~/.gemini/config/projects/ba3fd5e7-0841-4ef5-84a4-4bceb21aefd1.json` (name `sample-app`), so `--drive ba3fd5e7-0841-4ef5-84a4-4bceb21aefd1`. The older project `bearingkit-eval-sample-app` still points at the shared copy, where the driver no longer injects.

## Gemini CLI

- Install: `gemini extensions install https://github.com/tuyenht/Bearingkit` (a local path works while the repository is private); update with `gemini extensions update bearingkit`. Unverified until the acceptance test runs there.
- Bootstrap: `gemini-extension.json` names `GEMINI.md`, which imports `./skills/bk-protocol/SKILL.md`. Unlike Claude Code's hook and Antigravity's rule, nothing here adds a kit-root line, and since the 2026-09-17 trim (D5 question 24) the protocol no longer says `<kit>` is "known from this file's own path". The first acceptance run here must check that the model resolves `<kit>` (a `detect-stack` call, a `bk-protocol/references/` read); if it does not, `GEMINI.md` is the place for a kit-root line, not the protocol.
- Shares `~/.gemini/GEMINI.md` conventions with Antigravity's `user_global` rule; install both only if you use both.

## Optional: documentation MCP

The kit installs no MCP server. For libraries newer than the model's training, add context7 yourself: Claude Code `claude mcp add context7 -- npx -y @upstash/context7-mcp`; Antigravity and Gemini CLI through their `mcp_config.json` or settings. `bk-research` and the evidence rules tell the agent when to consult it. For page-load traces and heap snapshots, `bk-perf` uses the vendor's Chrome DevTools MCP when it is present: Claude Code `claude mcp add chrome-devtools --scope user npx chrome-devtools-mcp@latest`, or the vendor's plugin, which also brings its `debug-optimize-lcp` and `memory-leak-debugging` skills; Antigravity through its MCP config, attached to the host's own browser on its debugging port; comparing heap snapshots needs the server started with `--memoryDebugging` (vendor docs at `e33ee48`, `docs/compat/2026-09-23-bk-perf-tool-claims.md`). Without it, `bk-perf` says what it could not measure.
