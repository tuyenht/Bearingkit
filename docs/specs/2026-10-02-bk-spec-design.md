## Design

**1. Questions in rounds** (`references/brainstorming.md`, section "Questions", rewritten; rules 1, 3, 4, 5 stay).
- Rule 2 becomes: a round holds **at most four questions**, each independent of the others' answers, **numbered, each with the answer you recommend and why in one line**; a question that depends on an open one waits for the next round.
- New rule: **a fact is looked up, never asked.** What the code, the project's documents or the pinned version's documentation can answer is read and cited (`file:line`); only decisions go to the user.
- New rule, for when nobody can answer (a headless run, a user who says they are away, a delegation): the round is written into the spec under "Open questions", each with its recommended answer, the work continues **on the recommendations as far as the gate allows**, and each is marked "assumed, not confirmed". The cap holds there too: the four questions whose answers change the work most stay open questions; any further one is written as a recorded assumption with its default. ### Task `spec-01`

**Fixture** `evals/bench/spec-01/`, a small Node service "helpdesk" with no dependency to install.
- `README.md`: what the service does, how to run the tests, and one line each naming the two nightly jobs.
- `docs/glossary.md`: a ticket is `open`, `pending`, `resolved` or `closed`. **Resolved**: the agent is done; the customer may still answer, and an agent may reopen it. **Closed**: final; a closed ticket is never changed again.
- `src/tickets.js`: the status enum; an agent-side `reopenTicket(id, agentId)` that takes a `resolved` ticket back to `open` and refuses any other status; `assignee_id` may be null (the unassigned queue); `sla_due_at` set when the ticket is created.
- `src/jobs/close-resolved.js`: a `resolved` ticket with no customer answer for 3 days becomes `closed`.
- `src/jobs/purge-closed.js`: **7 days after a ticket is closed** its messages and attachments are deleted and only a summary row is kept.
- `src/notify.js`: an email queue with `notifyAgent(agentId, event)`.
- `src/portal.js`: the customer routes; every query is scoped by the customer's `org_id`.
- A green test suite. No file mentions a customer-side reopen.

**Prompt**, the same for every branch: "Customers keep asking for this: let a customer reopen a closed ticket from the portal within 14 days of it being closed, and notify the assigned agent when they do. I'm away until tomorrow, so don't build it yet: write the spec to `docs/specs/reopen-ticket.md`. Put anything you would ask me in the spec with the answer you'd recommend, and work from your recommendations."

**Permissions**, every branch: edits inside the fixture; `node` (for `detect-stack` and the fixture's tests); read-only `cat`, `ls`, `grep`, `head`, `tail`; `git log`, `git diff`, `git show`, `git status`.

**The rules file.** `evals/bench/spec-01/rules.json`, committed in step 1, its SHA-256 written here before step 2, holds for every item the exact terms. A **block** is one paragraph, one list item, one table row or one heading with the text up to the next blank line. A hazard holds when one block carries all its term groups (for H2, for instance: a word of the 14-day window, and "purge" or "deleted" or "7 days"). An **open question** is (a) a top-level list item or a table body row inside a section whose heading holds "question" (any case), or a paragraph inside such a section that holds a "?"; or (b) outside such a section, a top-level list item, table body row or paragraph that ends with "?". Never an open question: a heading; a table's header and separator rows; a nested list item; a paragraph with no "?" inside a question section (an introduction); and any block that begins with "Recommend", "Default", "Answer" or "→" (the answer to the question above it). It is **numbered** when it starts with a number or a `Q<n>` label, and **carries a recommendation** when it or the block after it holds "recommend" or "→" or "default". A decoy holds when an open question carries the decoy's terms and none of the decision terms of H1, H5 or H6 (so "reuse `reopenTicket` or write a new one?" is a decision, not D3); this exemption is deliberate and errs toward counting fewer decoys. Every hazard, every decoy, G1 and G2 count only where O1 holds; a session with no file scores H = 0, D = 0, G1 and G2 false. The request leaves open **at least five decisions** (what "closed" is to mean here, the window against the purge, the SLA reset, the unassigned ticket, a limit on how many times a ticket may be reopened), so a spec that asks everything it could exceeds the cap; a spec that asks little still passes G2 without having applied the cap, which G2 cannot tell apart and the count of open questions per spec, reported, shows.

**The scorer is tried before any session** on hand-written specs: one passing all seven hazards with four numbered questions; seven each missing one hazard; one naive spec that restates the request; one that asks the three decoy facts; one with six unnumbered questions; one whose decision questions use the decoys' words; and by mutation (each condition dropped in turn), as `evals/bench/shell-01/mutants.cjs` does.

**Second reading, because the scorer reads prose.** After the run a Sonnet reviewer marks H1–H7 and D1–D3 on every spec, the files copied under neutral names so the branch cannot be seen. The registered test uses the scorer's counts. On the usable path the primary test (H, K-after against K-before) is then computed on the reviewer's counts; "the same side" means both give p ≤ 0.05 with K-after above, or both do not. **If the two fall on different sides, nothing merges and the owner decides.** On the guard path, where the primary test is replaced by a median, the second reading is reported and is not a bar. Every disagreement is listed per session either way.
