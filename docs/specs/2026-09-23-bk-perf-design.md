## What it is for

One person doing what a performance engineer does before and during an optimization: say what is slow as the user feels it, take the measurement that locates it, record a baseline with its method and noise, change one thing, keep only what beats the noise with the tests green, and leave a guard. The scope test of spec §1 holds: each step is one that role owns. Database tuning is a neighbouring role's (`bk-db`); an error is `bk-debug`'s, a firing alert `bk-ops`'s.

## The shape

- **Symptom first**: slow first load, sluggish interaction, layout jumping, memory growing, one endpoint slow, every endpoint slow, slow only under load; each has a first measurement (`references/method.md`, the symptom tree).
- **Tools found before measuring**; the vendor's `debug-optimize-lcp` and `memory-leak-debugging` skills, when installed, are opened and followed for their part (official first, v2 principle 4); with no tool, what cannot be measured is said, and findings from source are "potential impact".
- **Baseline** with its conditions and spread; **locate** by following the measurement to what it names, ranked by measured share; **one change**, measured the same way, kept only past the noise with tests green, a neutral change reverted; a **ledger** of every attempt; a **guard** whose number is the project's.
- **Gates**: no number without its method; lab, field and trace labelled; thresholds from the metric's owner (web.dev for Core Web Vitals) or the project's budget, never from memory; a cache is a safety question first, and caching authenticated responses is COUNCIL; load tests against non-production, production or a shared staging is COUNCIL; raw heap snapshots and traces read through the tools that summarize them.
