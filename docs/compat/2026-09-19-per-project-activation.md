# Per-project activation: what each host documents · 2026-09-19

D5 question 29 (owner, 2026-09-19): install once, globally, and use the kit only in the projects activated for it. This file records what Claude Code and Antigravity document about scoping a plugin to one project, so the design (`docs/specs/2026-09-19-per-project-activation-design.md`) rests on sources rather than recollection. Nothing here was run on a host; every "verified" below is a reading, and the open rows are probes the design lists before anything is built.

Method. Two research agents (Sonnet) read the docs; the session then re-read every load-bearing claim itself: Claude Code from the raw markdown of the reference pages (curl of `https://code.claude.com/docs/en/settings-reference.md`, and a WebFetch of `plugins-reference` and `settings`), Antigravity from the docs embedded in its language server (`%LOCALAPPDATA%\Programs\Antigravity\resources\bin\language_server.exe`, 2.15.0, read as bytes, never executed; offsets below are byte offsets in that file) and from `https://antigravity.google/docs`. The embedded docs are the files of the built-in skill `agy-customizations` (`rules.md`, `hooks.md`, `skills.md`, `plugins.md`, `json_configs.md`); on plugins and precedence they say more than the public site.

### Measured on this machine, 2026-09-20 (probes CC-1 to CC-3)

Isolated profile `_build/profile/claude` (`CLAUDE_CONFIG_DIR`), Claude Code 2.1.274, two scratch projects outside `C:\Projects` and outside any git repository, sessions run as `claude -p --model sonnet --max-turns 1` and read from the init event's skills listing.

| # | Question | What happened |
|---|---|---|
| CC-1 | What does an install at the default scope do when the manifest ships `"defaultEnabled": false` | `claude plugin marketplace add C:\Projects\Bearingkit` then `claude plugin install bearingkit@bearingkit` → "Successfully installed plugin: bearingkit@bearingkit (scope: user). This plugin is disabled by default — enable it with: `claude plugin enable bearingkit@bearingkit`", and the profile's `settings.json` gains `"enabledPlugins": { "bearingkit@bearingkit": false }`. Installed for the machine, switched on nowhere |
| CC-2 | Does a project's own `enabledPlugins` entry switch it on there and nowhere else | after `bearingkit activate --host claude` in one scratch project: that session listed **33 skills, 15 of them the kit's**, and its transcript carries the bootstrap (`<bearingkit-protocol>`), so the SessionStart hook ran; the other scratch project listed **18 skills, 0 of the kit's**; after `bearingkit deactivate` the first listed **18 and 0** again. The project file was honoured in a `-p` run with no trust dialog |
| CC-3 | Does `--plugin-dir`, which every eval run uses, still load the kit | **no**: with the manifest disabled by default, `claude -p --plugin-dir <checkout>` listed **0 kit skills**. Adding `"enabledPlugins": { "bearingkit@inline": true }` to the profile restored **33 skills, 15 of the kit's**. The runner now refuses to start a Claude run whose named profile lacks that entry, instead of measuring an empty kit |

Open, to probe in the isolated profile before building: what `install --scope local` writes for a plugin with `defaultEnabled: false` (an entry `true`, or nothing), and which file `claude plugin enable` writes when run inside a project.

Consequences for the design, stated as readings, not measurements: (1) any plugin under `~/.gemini/config/plugins/` reaches every workspace, the IDE included, which is what the owner saw on 2026-09-19; a rule trigger other than `always_on` would still leave the skill names and descriptions in every conversation (A2, A3). (2) The only documented per-project handle is a workspace `plugins.json` that registers a plugin kept outside the discovered roots (A5, A6).

### Measured on this machine, 2026-09-20 (probes AG-1 to AG-5)

Antigravity 2.15.0, the 2.0 app restarted with `--remote-debugging-port=1405` under the owner's approval of 2026-09-20, model `gemini-3.8-flash-high`. The store was installed by `bearingkit install --host antigravity` at `~/.bearingkit/antigravity/plugins/bearingkit`, and **no copy existed under `~/.gemini/config/plugins/` at any point of the run** (that folder held only the owner's three unrelated plugins), so nothing but the workspace declaration could load the kit. Workspace: the eval stage `C:\work\apps\sample-app`, project `ba3fd5e7-0841-4ef5-84a4-4bceb21aefd1`. Unless a row says otherwise, one fresh conversation was asked "List by name every skill you can use right now, one per line. If there are none, say NONE."; the kit's own are the fifteen `bk-*`, the host's own are `agy-customizations`, `antigravity-guide`, `generative_ui` and `migrate-workflows`.

| # | Question | What happened |
|---|---|---|
| AG-1 | Does `.agents/plugins.json` in one workspace load a plugin kept under `~/.bearingkit/`, and a workspace without it not | **yes, both ways.** With the entry the conversation listed the four host skills **and the fifteen `bk-*`**; with the file removed from the same workspace the next conversation listed **only the four**. Same app session, minutes apart, so the kit is not cached from the earlier conversation and nothing registers it globally once seen |
| AG-2 | Does the entry name the plugin folder or a folder of plugins; does `~` expand on Windows | **both folder forms load**: `…/plugins/bearingkit`, which is what `activate` writes, and its parent `…/plugins` — the folder form was re-run after the negative above, so a cache cannot explain it. **`~` does not expand**: an entry `~/.bearingkit/antigravity/plugins/bearingkit` loaded nothing (four skills). An entry written by hand has to be absolute, which is why `activate` resolves the path before writing it |
| AG-3 | Does a declared plugin's `hooks.json` run | **yes.** With the eval driver armed inside the store, seven conversations took their prompt from the queue through `PreInvocation` and reset the stage before each; the ledger recorded every one |
| AG-4 | Does the IDE honour the workspace file as 2.0 does | **open.** The IDE was not driven this session (the owner chose to type the question there by hand rather than have its window stopped); `C:\work\apps\web-shop` is activated and waiting for that one conversation |
| AG-5 | May the declared path be the checkout itself, so that `git pull` alone updates every activated project | **no.** With `C:/Projects/Bearingkit` declared, not one `bk-*` skill loaded: the checkout root is not plugin-shaped (its manifest is `.antigravity/plugin.json`, and the always-on rule carrying the protocol is composed at install time). Instead the conversation listed **39 unrelated skills**, and every one of the thirty-nine exists as a `SKILL.md` folder under the checkout’s untracked `_build/upstream/` (four vendored repositories; 24 from one of them, 13 from another), four and five levels below the declared path: a declared folder is scanned for whatever customizations it holds, deep. So `bearingkit update` stays the way a new commit reaches activated projects, and nothing but a purpose-built store should ever be declared |

Acceptance in an activated project, same run: the six approved prompts scored **6/6**, no false activation, and no conversation read the eval harness before deciding (`evals/results/2026-09-20-antigravity-perproject.md`, gitignored); the new boundary prompt `bnd-en-02` reached `bk-setup` (1/1, `evals/results/2026-09-20-antigravity-bnden02.md`, from the same armed driver and the same `--score`). The conversation in the project that was not activated is the AG-1 negative above: no kit at all.

One mechanism note for the harness: the stage has to carry its declaration **in its own first commit**, because the driver resets with `git reset --hard` and `git clean -fdx` before every prompt; `evals --host antigravity --stage-only --activate` writes it before that commit. A check after the fourth driven conversation found the file in place and `bearingkit status` still reading `on`; the driver hook fired on all seven, which it could not have done without it.
