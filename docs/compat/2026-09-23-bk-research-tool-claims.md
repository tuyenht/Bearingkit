Seen in the measurement profile, 2026-09-23 (Claude Code 2.1.280, `claude -p`, no web permission rule): **WebSearch is refused, and WebFetch reaches some documentation domains without a grant** (`developer.mozilla.org`, `nodejs.org`, `www.typescriptlang.org` fetched; `npmjs.com`, `registry.npmjs.org`, `github.com`, `tc39.es`, `caniuse.com`, `unpkg.com`, `v8.dev` refused). That matches line 559 of the tools reference, a "built-in set of preapproved documentation domains that fetch without a prompt"; the set itself is not listed there, so the domains above are what this run saw, not a list to rely on. So the behaviour runs of this sprint had partial web access: official documentation on some domains, no search, no package registry or repository host. Full web behaviour is measured on Antigravity, where the tools need no grant. **From 2026-09-23 afternoon** the profile carries `WebSearch` and `WebFetch(domain:…)` rules for sixteen documentation, registry and repository domains (`_build/bk-research-sprint/grant-eval-web.cjs`, the syntax of tools-reference lines 88–89); a fetch outside them (`unpkg.com`, `devblogs.microsoft.com`) was still refused in the run that followed. On Antigravity, a `read_url_content` call in the second run ended the transcript with no result: most likely the app's approval to read a URL, not seen on screen. What the app offers for it, from the same binary: its embedded guide says "Browser Tools: Enable/disable Javascript execution and manage your URL allowlist for web automation" (offset 52,510,881), and its agent-settings schema carries `internetPolicy`, beside `sandboxMode` and `autoExecutionPolicy` (around 52,385,211). Which of the two governs `read_url_content` is not established.
