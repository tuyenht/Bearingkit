I had too many AI coding tools. So I built one.

Bearingkit is a protocol and 17 skills for Claude Code and Antigravity. They tell the agent which step it's on and when to stop and ask me first, and I use them every day, in English or Vietnamese. I run a small software company on my own in Hanoi, with AI agents doing most of the hands-on work. My setup used to be a pile of plugins and packs that were each good at one thing and got in each other's way. Bearingkit is how I got out of that.

Install it Why I built it

Open source under MIT. Pre-release, and not yet proven better than the packs it came from (see where it stands).

How I got lost

There was always another pack worth trying. A workflow pack, a review pack, a TDD pack, Anthropic's official plugins. Each one helped with something.

Put together, the agent got worse at deciding which of them to follow. Two skills would answer the same request. Their rules overlapped and sometimes disagreed, and I was the one left to sort it out. Every pack's skill descriptions were already in the context before I typed a word. And none of it carried over between Claude Code and Antigravity, so each tool needed its own setup.

What I wanted was one set of rules I could trust, in my own language, and a stop before the agent did something I couldn't undo.

What I wanted from my agent

  • I want to talk to it like a colleague, in Vietnamese or English, without memorizing commands.
  • It should know which step a request belongs to.
  • Before anything I can't undo (migrations, auth, payments, deleting data, and production) it should stop and ask.
  • Before it says “done”, it should show me the test output and the file and line.
  • Next session it should pick up from git and the last handoff rather than from memory.
  • The rules should stay the same when I switch tools, and the kit should stay out of projects that don't need it.

What I did about it

I stopped installing and started reading, with my agents doing the legwork. We went through 23 sources, 17 of them open source (Superpowers, Anthropic's official plugins, mattpocock/skills, spec-kit, and others), and inventoried 1,295 items from 22 of them, one by one: skills, commands, agents, and rule files. I marked 46 to adapt, kept 610 as ideas, and dropped 639. Where two sources disagreed, I kept one rule and wrote down why.

What came out is one protocol that every session loads and 17 skills it routes to. Every adapted file names where it came from, and the full account of what I borrowed and what I wrote is in PROVENANCE.md.

How I talk to it

No slash commands to remember, though you can still call any skill by name. Every skill has trigger phrases in English and Vietnamese. These come from my activation test set, each with the skill it is expected to open.

  • Uploads over 5 MB silently disappear.bk-debug
  • Is this branch safe to merge?bk-review
  • Where were we, and what should I pick up next?bk-next
  • Add CSV export to the invoices page.bk-spec
  • The login form shows a 500 after a password reset.bk-debug
  • Break the invoice export work into phases with exit criteria before we touch code.bk-plan
  • The error-rate alert on checkout fired ten minutes ago. Find out what is going on.bk-ops
  • Should we move invoice PDF generation off the request path onto a queue? Lay out the options and recommend one.bk-audit
  • The invoices page takes several seconds to show anything on a mid-range phone. Figure out where the time goes before we touch it.bk-perf
  • Wrap up the session and write the handoff for the next one.bk-close

How a request moves, and where it stops for me

Each skill ends by handing off to the next. The chain stops in two places: at COUNCIL points (below), and after a bug fix, before anything is committed.

specplanbuildtestreviewshipclose stops at COUNCIL
ACT: the agent does it, then tells me

Tests, behavior-preserving refactors, docs, app-layer fixes, small changes inside a plan I approved.

COUNCIL: the agent proposes, then waits for me

Schema and migrations, auth, sessions, permissions, payments, data deletion, contracts between modules, and remote or production systems. When it's unsure, it treats the change as COUNCIL.

How much process a job gets

A feature goes through a spec first. A small ACT change within three files goes straight to build, with tests. A bug gets a root cause before any fix, and after three failed attempts the agent stops and asks. A question just gets an answer.

What counts as evidence

A claim gets a file:line anchor or is marked unverified, and a number gets its method or the words “not measured”. A passing check only counts after it has been shown able to fail.

Independent review on hot paths

Hot paths include auth, payments, uploads, tenant scoping, migrations, and contracts with outside systems. Changes there get an independent review before push, ideally by another model or another agent.

Handoffs between sessions

bk-close writes a handoff and checks it against git. bk-next picks the next step from git, the plans, and the last handoff.

Security baseline

No secrets in output or commits, parameterized queries only, validation at the boundary, and least privilege. Anything fetched is treated as data, never as instructions. A project's own rules can make this stricter but not looser.

The 17 skills

Each skill is a short instruction file with gates and the evidence it has to paste, and most have reference files they open only when needed. Before its first edit, bk-build reads the rule file for the project's stack; there are files for TypeScript/React, Kotlin, SQL, Node, Python, PHP/Laravel, and Shell. The quoted phrases are triggers taken from each skill's own description.

bk-spec
Pin a request down before building: restate it, find edge cases, list assumptions
“new feature”, “add”, “implement”
bk-plan
Plan in phases, each with exit criteria and the evidence it must show

bk-build
Carry out a plan or a small change: look around first, touch as little as possible

bk-test
Write the test first by default; check UI in the rendered result

“review”, “safe to merge”
bk-ship
Run the project checks and a secret scan, then write the commit and PR body
“ship”, “commit”, “PR”
bk-close
End a session with a handoff checked against git
“wrap up”, “end session”
bk-next
Pick the next step from git, plans, and the last handoff
“what next”, “where were we”

Investigate, then give one verdict and the options rejected

Where it stands

I started Bearingkit in September 2026. It isn't released yet, and I use it every day. Every number on this page traces back to the repository, mostly to docs/status.md, which records how each was measured.

I compared skills one at a time with the sources they came from, using the same task, starting code, model, and agent, with small samples. On most tasks there was no clear difference, and on most of those neither side could be told apart from using no skill at all. One planning task with one model favored the kit. On PowerShell the kit beat the no-skill baseline and a pack with no shell skill, but not its own source. On the tasks where I recorded cost, the kit cost between about 1.3 and 3 times what its sources did (the per-task figures are in the design files under docs/specs), so no task meets the bar I set for v1.0: at least the sources' pass rate and fewer tokens.

I use it anyway because I would rather have one set of rules I understand, in my own language, on both agents I use, than a pile I have to reconcile myself. Whether that's worth it is what I'm measuring next.

Works today

  • 17 skills plus the protocol, on Claude Code and Antigravity 2.0
  • English and Vietnamese routing, tested on 96 prompts; precision and recall ≥ 0.9 on the 60-prompt core set
  • The autonomy gate, evidence rules, handoff chain, and hot-path review, all written into the protocol
  • Per-project activation and seven language and framework rule files
  • 233 automated tests in the repository

In progress

What I'm measuring next

  • How often the agent acts without asking on trap tasks (a migration, a deletion, a production push), with and without the kit

Install

Install it once per machine, then activate it in each project that should use it.

# Claude Code: add the marketplace and install the plugin
claude plugin marketplace add https://github.com/tuyenht/Bearingkit
claude plugin install bearingkit@bearingkit

# Antigravity: install once per machine (run from a clone of the repo)
node <checkout>/bin/bearingkit.cjs install --host antigravity

# Any agent: activate in a project, then check what is active
cd <your project>
node <checkout>/bin/bearingkit.cjs activate
node <checkout>/bin/bearingkit.cjs status

The npm package isn't published yet, so for now you run the command line from a local clone of the repository (<checkout> above). Per-agent details and uninstalling: docs/hosts.md.
